# Agent 进化

> 状态：草案，已通过一次用户视角评审并按评审裁决修订。产品命题、核心旅程、合并语义、回退语义、同步态位置与会话内变化提示的按钮组已获用户确认；标注「待讨论」的条目尚未拍板。
>
> 本文档推翻了两处已确认的产品决策，理由分别记在「升级后自动接收官方改进」和「正在使用该团队的对话」两节：一是 [Agent 团队页](../pages/agent-teams.md) 的显式官方更新与保留副本机制，二是[主对话页](../pages/main-conversation.md)「变化提示不提供前后比较」这一层。两个页面的单页增量随后各自单独提交。
>
> 范围：定义 Agent 的 `AGENT.md` 在本地被调教、被记录、被回看、被回退，以及软件新版本携带的官方改进如何自动合并进用户当前内容的完整端到端流程。它跨越 [Agent 团队页](../pages/agent-teams.md)、[主对话页](../pages/main-conversation.md)、[主左侧栏](../pages/main-left-sidebar.md)和[设置](../pages/settings.md)，因此不归任何单页。单页内部的区域、控件与状态由各自页面 PRD 承接。

## 用户目标

用户希望自己对 Agent 的每一次调教都被记住、看得见、退得回；也希望软件作者对内置团队的改进能自动到达自己手里，而不必在「用官方新版」和「保留自己的改动」之间二选一。

这条流程要让 Agent 团队表现得像一位有记忆的同事：你教过它的话它记得，你能问它「这条规矩哪来的」，它也会随软件升级悄悄变得更好，而不需要你去操作任何一次更新。

## 开始条件

流程有两个独立起点，共用同一套记录与回看机制：

- **本地调教**：用户在团队页修改某名成员的 `AGENT.md` 并保存成功，或在 Finder 中直接修改文件后被应用读取到。
- **接收官方改进**：用户安装新版本并重启应用，且本机至少有一支官方来源团队。

用户团队（非官方来源）只走第一个起点：它们有完整的本地调教记录与回退能力，但不参与官方同步。

## 参与者与职责

| 参与者 | 职责 | 明确不负责 |
| --- | --- | --- |
| 用户 | 调教 Agent、事后回看变化、不满意时回退 | 不需要判断是否更新、不需要裁决合并、不需要阅读差异格式 |
| 桌面应用 | 记录每一次修订、比较官方新旧版本与用户当前内容、决定哪些改动可以直接合入、呈现变化与来历、承接回退 | 不做语义合并，不撰写变化说明 |
| 默认 Agent | 为每条修订写一句用日常语言表达的说明；在官方与用户都改过同一份内容时产出合并结果 | 不做最终裁决——它的产出是既成事实但可被用户整体回退 |

「默认 Agent」是设置中的应用级选择，见[设置](../pages/settings.md)。它服务于应用自己发起的后台工作，与任何会话、团队成员或最近一次运行无关。

## 主流程

### 一、本地调教留痕

用户每一次成功保存 `AGENT.md`，应用记录一条修订。一条修订包含当时的完整内容、作者、发生时间，以及一句用日常语言说明这次改了什么的摘要。

- 作者只有三种：**你**、**官方某个版本**、**Agent**（后者服务于将来的自动进化，现阶段不产生）。用户在 Finder 中的外部修改同样记为「你」，与在团队页里改没有区别。
- 摘要由默认 Agent 在保存完成后于后台撰写，不阻塞保存。摘要尚未产出或写不出来时，用中性说明占位（例如说明这次改动涉及哪几处），不留空白，也不编造内容。
- 修订记录保存在应用自己的数据目录，团队文件夹里始终只有当前内容。用户用 Finder 打开团队目录时看到的是一份干净的 `AGENT.md`。
- 修订史暂不设置数量或时间上限。

### 二、看见变化与来历

从侧边栏的同步提示进入团队首页后，刚被同步改动过、用户还没看过的团队在列表里带一个中性标记，用户不必凭记忆逐支点进去找。用户进入该团队详情后标记消失。

用户查看 `AGENT.md` 的位置只有一个：团队页里那个 markdown 编辑器。不存在独立的「变化查看模式」或「历史对比页」，编辑器本身就是阅读视图。

- 编辑器上方常驻一行最近变化的摘要，用户不展开全文也知道最近发生了什么。
- 正文中最近变动过的段落在左侧带标记，标记旁标明来历（「你 · 3 天前」「官方 v1.3」）。来历不常驻抢占注意力，指向该段落时才显形。
- 点击标记就地展开一小块，说明这里原来是什么，不跳转、不打开第二个界面。
- 从最近变化那一行可以展开完整时间线，按次列出每条修订的摘要与作者，并从任意一条回到那一版。

这套呈现同时回答了两个不同的问题：「我刚说的它记住了吗」和「它为什么会有这条怪规矩」。溯源与看变化是同一个视图，因为用户的心智里它们本来就是同一件事。

### 三、升级后自动接收官方改进

> 本节推翻了 [Agent 团队页](../pages/agent-teams.md) 原先「只有用户从团队详情显式执行操作才会应用更新」以及「更新到最新版 / 保留副本并更新」这套显式更新机制。
>
> 旧决策成立于「系统无法安全合并，所以必须让用户在两个版本之间选一个」这个前提，副本是它唯一的保护手段。现在优先级已经定死（用户的意图优先）、合并由默认 Agent 完成、且每一步都留下可整体撤销的修订，这个前提不再成立。继续保留显式按钮的代价是：用户一旦编辑过就永远看不到后续官方改进——这正是本流程要解决的首要问题。副本机制同时废除，因为它会在用户的团队列表里堆积无人认领的僵尸团队，而修订史已经提供了更好的保护。

用户安装新版本并重启后，应用在后台逐支官方来源团队比较三份内容：上次应用的官方版、当前软件携带的官方新版、用户当前内容。比较覆盖整支团队，而不只是 `AGENT.md`。

- **只有官方改动过**：直接合入，记一条作者为该官方版本的修订。
- **只有用户改动过**：不动用户的内容。
- **两边都改动过**：交给默认 Agent 合并，规则是用户的意图优先。Agent 判断某处官方改动无法与用户写法共存时，保留用户的，并在摘要里说明官方这次的哪部分因此没有合入。

合并结果直接成为新的当前内容，不是等待批准的提案。这里不存在传统版本控制意义上的「冲突待裁决」——优先级已经定死，Agent 总能产出确定结果，因此整个过程不需要用户做任何决定。

团队结构层——成员的增加、移除和改名，团队名称与一句话用途，主 Agent，以及成员的运行配置——按同一条「用户的意图优先」处理，不需要默认 Agent 参与，因为这里的比较是结构性的：

- **官方新增成员**：直接加入。与用户自己添加的成员撞名时保留用户的那名，官方这名不加入，并在说明里讲清楚。
- **官方移除成员**：用户从未改动过它的内容与运行配置时随官方移除；用户改动过则保留，并说明官方新版已不再包含这名成员。这条替代了旧机制中「必须先保留副本再移除」的做法——用户的成员留在原地，不被搬进副本。
- **官方为成员改名**：按移除加新增处理，因此用户改动过的旧成员会被保留在团队里。
- **团队名称、一句话用途、主 Agent**：用户改动过就保留用户的，没改动过则跟随官方新版。
- **运行配置**：沿用既有的「跟随推荐 / 用户覆盖」规则，跟随推荐的成员采纳新版推荐值，用户覆盖过的保持原值。变化的只是触发方式——从用户点击更新，变成升级后自动发生。

结构层的每一处改动同样进入这次同步的修订记录，可以被整体撤销。

同步期间，侧边栏底部显示一个临时的进行中状态；指向它时说明正在同步哪几支团队，点击进入 Agent 团队页。它不带红点，也不是常驻通知。

同步全部干净完成时，该状态无声消失。产生了实际改动时，它变成一次性的「团队已更新」提示，点进去查看或手动关掉才消失——因为 Agent 的行为确实变了，用户至少应当被告知一次。「无感享用」指的是不必手动操作，不是不被告知。

### 四、正在使用该团队的对话

自动合并进来的改动与用户自己保存的改动一样，会让正在使用这支团队的已有会话显示变化提示。提示提供三个动作：

- **查看**：打开弹窗，按成员列出这次变化了什么，复用与编辑器一致的段落标记与来历表达。弹窗右下角是取消与应用；取消只关闭弹窗，提示保留。
- **应用**：把这支团队最新、完整、有效的已保存版本作为一个整体应用到该会话。
- **关闭**：本次会话内不再提示这一批变化；之后若产生新的已保存变化，重新出现。

弹窗里的「应用」与提示上的「应用」是同一个动作，含义完全相同：整体应用。弹窗展示了哪些成员、哪几处变化，都不改变这一点——用户不能只应用弹窗里看到的某一项，也不能选择应用到哪个历史版本。这一点必须在界面上讲清楚，因为把变化摊开来看之后，用户很容易以为自己获得了逐项挑选的能力。

> 本节只推翻[主对话页](../pages/main-conversation.md)原先「不提供前后比较」这一层决策，不推翻与它并列的另外两层。
>
> 被推翻的理由：旧决策成立于「用户看不懂差异、看了也没有帮助」这个前提；现在每处变化都带用日常语言写的说明与来历署名，用户看得懂，藏起来反而让他只能盲目点应用。
>
> 继续成立的：「不提供单类别应用」与「不提供版本选择」保持不变，因为它们防的是另一件事——`AGENT.md` 用新版、运行配置用旧版这种混合快照。看得见变化和只应用一部分变化是两件事，本流程只放开前者。

### 五、回退

自动合并会产出确定结果，但可能产出错误结果——这是把裁决权从用户手上拿走所付出的代价，因此回退必须好找，不能藏在时间线深处。

- 一次官方同步作为一个整体被记录，可以整支团队一起退回同步前的状态，用户不必逐个成员寻找。**整体撤销不设期限**，一个月后想起来要退也能退。
- 它有两个并列入口，指向同一份内容：同步完成后出现在团队详情页的同步结果横幅——它不会自动过期，跨重启保留，只有用户主动收起或执行撤销后才消失；以及团队菜单里常驻的“最近的官方同步”。用户主动收起横幅之后，能力仍然找得到。
- 只保留最近一次官方同步的整体撤销。更早的同步不再提供整体撤销，其内容仍逐条留在各成员的变化时间线里，可以逐名回退。
- 撤销后，这次官方改动记为已知悉，下次启动不再重新合入，也不再提示。
- 更早的修订通过时间线逐条回到。单条修订的回退粒度是单名成员的某一版；整支团队一起退回只服务于官方同步批次，因为只有它才是一次跨成员的整体事件。
- 回退本身也是一条修订，可以被再次回退。用户不会因为退错而丢失任何内容。

## 分支与异常

- **默认 Agent 不可用**（未配置、凭据失效或调用失败）：只有官方改动过的成员照常合入，因为这一类不需要语义合并。两边都改动过的成员保留用户的内容，并标明官方新版有改动尚未合入，提供重试。任何情况下都不允许因为无法合并而覆盖用户内容。
- **摘要写不出来**：修订照常成立，摘要位置用中性说明占位。摘要缺失不影响合并、回退或变化提示。
- **同步过程中退出应用或崩溃**：下次启动继续未完成的同步，不留下半合并的成员，也不重复合入已经完成的部分。
- **团队处于需要修复状态**：不参与同步，沿用既有的修复流程；修复完成后按正常比较继续，不静默重建官方文件。
- **用户在同步进行中编辑同一份 `AGENT.md`**：以用户此刻的编辑为准，该成员的合并推迟到本次编辑保存之后重新比较，不丢弃用户正在写的内容。
- **首次登记的新增官方团队**：按既有的首次登记规则创建，不产生同步记录，也不出现变化提示——它不是一次进化，是一支团队的诞生。
- **官方基线不可考**：本能力上线前就已经存在、且用户已经改动过的官方来源团队，没有留下官方上一版的完整内容。缺了这个参照，无法分辨某处差异是用户主动删掉的官方内容，还是官方这次新加的内容；自动合并在这种情况下最可能犯的错，就是把用户明确删掉的东西又塞回去。因此这一次**不自动合并**：保留用户内容原样，记为“官方新版有改动尚未合入”，并在团队详情页提供一个一次性的显式入口，用户点了才做合并。用户不点也没有任何后果。这个入口只在这一次出现，之后官方基线已经建立，永远走自动路径。同时把迁移当时的用户内容补记成一条署名为「你」的修订，作为时间线的起点，让更早的历史虽然不可考，之后的记录仍然有据可查。

## 等待与自动推进

流程中没有必须等待用户的节点。安装后重启即自动开始，合并完成即自动生效。

用户参与的全部时机都是事后的、可选的：查看变化、把新版本应用到某个正在进行的对话、回退。用户从不参与也能得到一支持续变好的团队，这是这条流程成立的核心判据。

## 完成条件

一次官方同步的完成，表现为：侧边栏底部的进行中状态结束；每支受影响团队的每名受影响成员都有一条新修订；受影响成员的 `AGENT.md` 里能看到带官方署名的变化标记；正在使用这些团队的对话出现变化提示。

一次本地调教的完成，表现为：保存成功反馈出现；编辑器上方最近变化那一行更新为这次的摘要；正文对应段落出现署名为「你」的标记。

## 指标与验收

### 产品指标

- **官方改进到达率**：升级后，已被用户自定义过的官方来源团队中实际吸收了新版改进的比例。现有机制下这个比例接近于零——用户一旦编辑就永久脱队；这条流程存在的首要理由就是把它拉起来。
- **撤销率**：官方同步被用户撤销的比例。持续偏高说明默认 Agent 的合并不可信，应先修合并质量而不是加确认步骤。
- **看懂成本**：用户在保存或同步后，不打开完整 `AGENT.md` 就能说出改了什么的比例。

### 验收清单

1. 用户自定义过的官方团队，在升级后能拿到官方新版的改进，且自己的改动没有丢。
2. 官方与用户改过同一名成员时，最终内容保留用户的意图，摘要如实说明官方哪部分没有合入。
3. 默认 Agent 不可用时，没有任何用户内容被覆盖。
4. 用户可以在不阅读完整 `AGENT.md` 的情况下，知道最近一次变化是什么、是谁改的。
5. 用户能对任意一条规矩问出「这是哪来的」并得到答案。
6. 最近一次官方同步可以整体撤销，且不设期限——刚同步完能从横幅撤，收起横幅一个月后仍能从团队菜单撤；撤销后不会在下次启动重新合入。
7. 全程不需要用户做任何更新决定；不做任何操作的用户也能得到已更新的团队。
8. 会话内变化提示的查看、应用、关闭三个动作语义互不混淆，取消只关闭弹窗；弹窗内的应用与提示上的应用产生完全相同的结果。
9. 官方新版移除了一名用户改动过的成员时，这名成员仍留在原团队里，不产生任何副本团队。
10. 团队名称、主 Agent、成员构成和运行配置的官方改动，与 `AGENT.md` 一样自动到达用户，且同样受用户优先与整体撤销保护。

## 待讨论

- **时间线的呈现密度**：连续多次短时间内的修改是否合并成一条，避免噪音。
- **Agent 自动进化**：任务结束后由一个 Agent 分析对话、自动改进 `AGENT.md`。修订记录已为它预留了作者维度，但触发时机、审阅方式与关闭开关尚未讨论。
- **本地调教是否也需要批次概念**：目前只有官方同步有批次与整体撤销。

## 非目标

- 不做在线的团队分发或订阅。首版的「远端」就是安装包携带的官方版本；分发通道换掉不改变本流程的任何判断。
- 不做通用版本控制：没有分支、没有合并请求、没有多人协作、没有远程仓库概念。
