# 任务提醒与回流

> 状态：产品采访已确认，待实现
>
> 关联页面：[主页面会话区](../pages/main-conversation.md)、[主页面侧边栏](../pages/main-left-sidebar.md)、[设置](../pages/settings.md)、[首次启动引导](../pages/onboarding.md)
>
> 范围：定义一段对话进入“已完成”或“正在等待你”两类终局后，Moebius 如何发送 macOS 系统通知、播放通知声音、更新 Dock 角标，并在应用仍运行时让用户点击后直接回到产生终局的对话与记录。点击已经被主进程接收但页面定位前中断时，下次启动续做定位；用户明确退出后不承诺通知冷启动。终局事实由主页面会话区定义；本流程不从 Agent 正文、成员运行状态或队列空闲自行判断完成。

> **2026-08-09 产品决定：**通知不是状态变化广播。运行开始、运行中、成员交棒、某个成员结束、短暂空队列和用户自己的已读操作都不通知；只有一轮进入“已完成”或“正在等待你”时通知一次。即使 Moebius 正聚焦、用户正在看目标对话，也必须进入同一套发送判断。每次真正准备向 macOS 提交通知前都重新检查系统权限：权限通过才发送；权限未通过则用包含本次终局的应用内权限弹窗替代本次系统通知。用户在弹窗中已经看见终局，因此开启权限并重新检测通过后只关闭弹窗，不补发这一次。每条系统通知显示应用内已有的对话名称、绑定产生终局的具体对话；Moebius 仍在运行时，点击后直接进入该对话。通知总开关默认开启。

> **2026-08-10 产品决定：**用户界面统一称为“任务提醒”，说明为“任务完成或需要你处理时提醒你”；“终局”“投递”“通道”“应用总开关”等仅作为内部规格术语。侧边栏和折叠项目只显示一个状态点，Dock 只统计当前可见的红点与蓝点。

## 用户目标

用户把任务交给团队后，可以切换对话、转到其他应用或暂时离开电脑。团队内部如何接力都不会打扰用户；当一轮已经完成，或已经停在必须等待用户的位置时，用户收到一次明确通知。Moebius 仍在运行时，点击即可看到结果或下一步；用户明确退出后不保留通知冷启动承诺。

一句话产品命题：**每轮只在真正结束推进时通知一次；应用仍在运行时，把用户一步带回这个终局发生的对话。**

```text
用户派活
   │
   ▼
运行、交棒、排队、继续运行 ───────── 不通知
   │
   ├─ 主理人收束为有结果／没有新增内容 ── 已完成通知
   │
   └─ 主理人等待用户／异常阻断／未明确收尾 ─ 正在等待你通知
                                                     │
                                                     ▼
                                           点击直达对话与对应记录
```

## 开始条件

- Moebius 桌面应用正在运行，并且存在一段已创建的对话。
- [主页面会话区](../pages/main-conversation.md#侧边栏状态点的触发)已经保存本轮唯一终局，而不是只有内部运行活动或中间异常。
- 通知总开关与 macOS 当前通知权限状态可以在每次发送前重新读取；权限只决定系统通道能否送出，不改变对话终局。
- 应用完全退出后不继续 Agent 工作，也不会产生新的任务提醒。基于当前 Electron 38 的真机边界，用户通过 `Command+Q` 明确退出后，应用已提交的通知会随进程退出从通知中心移除，不再承担冷启动回流入口；关闭窗口、隐藏、失焦或最小化不等于退出，应用仍在运行时通知继续可点击回流。

## 参与者与职责

### 用户

- 决定是否启用任务提醒并授予 macOS 通知权限；
- 从系统通知、Dock 角标或侧边栏状态回到对应对话；
- 阅读结果，或完成“正在等待你”记录中说明的问题、动作与继续方式。

### 主 Agent 与专业成员

- 主 Agent 按主页面会话区规则把一轮明确收束为有新结果、需要用户处理或确认没有新增内容；
- 专业成员的单次回复、交棒和结束不直接触发通知；
- 所有 Agent 都不能通过正文里的“完成”“失败”“等待”等词自行创建通知或决定通知文案。

### 桌面应用

- 把会话页保存的本轮终局映射为“已完成”或“正在等待你”；
- 每段对话的每一轮最多提交一条任务提醒，不因页面刷新、窗口切换或应用重启重复提交；
- 无论目标对话是否正在显示、窗口是否聚焦，每次发送前都读取 macOS 当前通知权限；权限通过才提交任务提醒并请求系统通知声音；
- 权限未通过时维护唯一一份应用内权限弹窗，把触发发送的终局类别和对话名称直接展示给用户，并提供开启系统通知、重新检测、关闭任务提醒三个明确动作；
- 让通知绑定具体对话和终局记录；应用仍在运行时点击后激活应用并准确定位，点击已经被主进程接收并持久记录但页面尚未完成跳转时发生崩溃或重启，则下次启动继续完成定位；
- 按侧边栏当前可见的红点或蓝点维护 Dock 角标，不把通知条数或历史提醒事实数当作角标数字；
- 在权限或系统通道失败时保留对话与侧边栏事实，不声称通知已经送达。

### macOS

- 决定通知横幅、通知中心、锁屏预览、声音、静音与专注模式下的最终表现；
- 决定通知在横幅、通知中心与锁屏中的保留方式；当前 Electron 38 在 Moebius 明确退出时会移除已提交通知，因此产品不承诺退出后的通知冷启动；
- 提供通知权限状态与系统设置入口。Moebius 不绕过系统权限、静音或专注模式。

## 主流程

### 1. 只把本轮终局变成通知

可通知终局只有两类：

| 通知类别 | 来自会话页的终局 |
| --- | --- |
| 已完成 | 主 Agent 收束为“有新结果”或“确认没有新增内容” |
| 正在等待你 | 主 Agent 收束为“需要用户处理”；异常、不可继续状态或“本轮没有明确收尾”已经让这一轮停止推进并等待用户 |

运行中出现一个红点事实、但同一轮仍有团队工作继续推进时，先保留侧边栏红点，不立即通知。只有整轮最终停在等待用户的终局时才发送“正在等待你”。这样一次内部失败被主理人自行恢复时不会先把用户叫回来。

下列情况永远不产生任务提醒：

- 用户发送消息后从无点进入闪烁点；
- Agent 开始运行、流式更新、排队、交棒或恢复；
- 某个专业成员或主 Agent 的单次 run 结束，但整轮尚未收束；
- 活动成员、待发射内容或待接回结果在调度缝隙里短暂归零；
- 同一终局因刷新、轮询、重绘、休眠唤醒或重启再次被读取；
- 用户打开结果、标记已读／未读、主动停下或确认结束继续能力。

用户对“正在等待你”作出回答、重试或继续后会开始新一轮；新一轮以后再次进入终局时，才产生下一条通知。

### 2. 每次发送前检查权限，未通过时由弹窗承接本次终局

权限检查属于每一次终局发送尝试，不是首次启动、版本升级或某次设置保存后的缓存结论。发送顺序固定为：

```text
本轮形成可通知终局
   │
   ├─ 应用总开关关闭 ───────── 不发送、不弹权限窗
   │
   └─ 应用总开关开启
          │
          ▼
      读取 macOS 当前通知权限
          │
          ├─ 已允许 ─────────── 提交本次系统通知与声音请求
          │
          └─ 未通过／无法确认 ─ 将本次终局放入权限弹窗
                                      │
                                      ├─ 开启系统通知
                                      ├─ 重新检测
                                      └─ 关闭任务提醒
```

“权限已通过”表示系统允许 Moebius 提交通知；声音、横幅、通知中心、锁屏和专注模式仍分别服从 macOS 当前设置。仅声音被关闭或专注模式开启不算权限失败，不弹恢复窗，也不阻止提交系统通知。

权限弹窗不是一张泛化的升级提示，也不是测试通知。它只在真实终局已经触发发送、且发送前检查未通过时出现：

```text
┌──────────────────────────────────────────────────────┐
│ 需要允许系统通知                                     │
│                                                      │
│ <对话名称>                            <已完成／正在等待你> │
│                                                      │
│ 任务提醒已开启，但 macOS 还不允许系统通知。          │
│ 关闭任务提醒后，系统通知、声音和 Dock 提醒都会停用。 │
│ <等待 macOS 确认／请重新检测／错误>                  │
│                                                      │
│ [开启系统通知]   [重新检测]       [关闭任务提醒]      │
└──────────────────────────────────────────────────────┘
```

- 弹窗必须显示触发本次发送的应用内对话名称和终局类别。用户看见弹窗即已看见这次终局，因此这次事件不再进入系统通知、声音或稍后补发队列；侧边栏事实与总开关开启时的 Dock 计数仍按原规则保留。
- 「开启系统通知」在系统尚未由用户选择时发起 macOS 原生授权请求：请求期间显示“等待 macOS 确认…”并锁定三个操作，系统返回后显示“请重新检测”，不显示内部权限枚举，也不替用户跳过重新检测。系统已经拒绝或策略受限时打开该应用的 macOS 通知设置，不循环调用不会再次弹出的系统请求；状态为「暂时无法检测」时也只尝试打开 macOS 通知设置，不猜测权限、不开系统请求。打开过程中主操作持续显示“正在打开系统设置…”并锁定三个操作，不能短暂变回“开启系统通知”；打开成功后弹窗显示“已打开 macOS 通知设置，调整后返回并重新检测”，打开失败时保持弹窗并显示“无法打开系统设置”，主操作变为“再次打开系统设置”并可重试，不出现无反馈或动作语义跳变。
- 「重新检测」重新读取系统当前授权状态，不复用弹窗打开时的旧结果。检测仍未通过或读取失败时弹窗保持打开并更新可理解状态；检测通过时关闭弹窗，但不补发弹窗内已经展示的任何终局。之后新形成的终局才走系统通知。
- 「关闭任务提醒」按设置页同一原子保存规则把应用内「任务提醒」总开关持久化为关闭；保存成功后才关闭弹窗，系统通知、声音和 Dock 随即停用，侧边栏状态点不清除。保存中锁定重复操作；保存失败或超时则保持总开关旧值与弹窗，显示可重试错误，不冒充已经关闭。再次开启只能从设置完成。
- 弹窗没有会被误解为普通取消的第四种关闭方式；标题栏关闭、`Escape` 和点击遮罩均不可静默略过三项选择。关闭应用不等于选择「关闭任务提醒」，不得擅自改总开关。
- Moebius 已聚焦时立即显示弹窗；窗口失焦或最小化时只在原窗口排队，不抢焦点、不强制恢复窗口，用户下次激活 Moebius 时首先看见它。
- 多段对话在同一权限弹窗未解决期间陆续形成终局时，不堆叠多个弹窗；同一弹窗按形成顺序列出每段对话的名称和终局类别，每段对话每轮只列一次。重新检测通过或关闭任务提醒都会一次处理这份可见列表，列表中的事件都不补发系统通知。
- 弹窗尚未向用户呈现时应用退出或崩溃，待展示终局列表随终局投递状态持久保留；下次激活应用时恢复同一弹窗。已经通过弹窗呈现的终局也不会在重启后改走系统通知。

这套分支同时覆盖升级前已完成 onboarding 的用户：不因升级或首次打开主动提示；只有真实终局命中发送检查且权限未通过时才出现弹窗。

### 3. 聚焦当前对话也发送系统通知

在总开关开启且第 2 节权限检查通过后，任务提醒不再根据用户位置决定“发不发”，只决定用户同时能看到哪些应用内事实；权限未通过时无论用户位置如何都进入同一权限弹窗分支：

| 终局形成时的位置 | 系统通知 | 应用内同时可见 |
| --- | --- | --- |
| Moebius 聚焦，目标对话正在显示 | 提交一条 macOS 通知并请求系统声音 | 时间线中的终局记录、结果卡片或待处理内容原位更新；“已完成”的新结果真实呈现后立即视为已查看，“正在等待你”仍保留红色提醒 |
| Moebius 聚焦，但用户在另一段对话、设置或其他应用内位置 | 提交一条 macOS 通知并请求系统声音 | 对应侧边栏状态点；不额外叠加右下角任务提示 |
| Moebius 窗口失焦或最小化 | 提交一条 macOS 通知并请求系统声音 | 对应侧边栏状态点与 Dock 角标 |
| 屏幕锁定但系统仍醒着 | 提交一条 macOS 通知；锁屏展示与声音由系统决定 | 解锁后侧边栏与 Dock 保留真实状态 |
| 专注模式开启 | 正常提交一条 macOS 通知；系统决定立即展示、静默收入通知中心或延后提醒 | 侧边栏与 Dock 不受专注模式影响 |

权限通过时，应用内不再为任务终局另造右下角提示，避免当前对话原位结果、应用内提示和系统通知三份重复。权限未通过时，第 2 节的权限弹窗是本次终局的替代交付，不属于右下角任务提示。设置页已有的语言保存等轻量通知继续按设置页规则工作，不属于本流程。

### 4. 系统睡眠与唤醒

系统睡眠与锁屏不是同一状态：

- **睡眠前已经形成终局：**应用在进入睡眠前已经提交的通知继续由 macOS 管理；唤醒后不补发。
- **系统睡眠期间：**Moebius 与本地 Agent 进程不承诺继续获得运行时间，因此不会声称任务在睡眠中推进或即时形成终局。没有被应用保存的终局就没有通知。
- **唤醒之后：**应用和受管运行恢复后，若此时才收到并保存本轮终局，则在保存边界提交一条通知；若只是重新读到睡眠前已经通知过的终局，不重复发送。
- **唤醒后无法恢复：**按主页面会话区形成真实的等待用户终局，再发送“正在等待你”，不伪装成已完成。

### 5. 通知内容

通知的信息层级固定为：

```text
Moebius
<对话名称>
<已完成 / 正在等待你>
```

- 通知显示应用内已有的对话名称；该名称可能按主页面会话区的既有规则来自首条用户消息，并按 macOS 通知预览设置决定是否出现在锁屏；
- 除对话名称外，通知不再摘录 Agent 正文、用户问题、文件名、项目路径、命令、服务商原始错误或任何凭据；
- “正在等待你”的具体原因、问题、动作与继续方式留在目标对话，通知只负责说明终局类型并提供直达入口；
- 系统通知声音使用 macOS 通知声音，不增加自定义音效、循环播放或应用内音量；
- 无障碍名称包含终局类别，不只依赖颜色或声音；

### 6. 点击通知回到对应对话

- 点击通知时 Moebius 正在运行：激活应用；窗口最小化时恢复窗口；随后打开或聚焦产生终局的对话并定位对应终局记录；
- 点击已经被主进程接收并把目标载荷持久记录后，若 renderer、应用进程或系统在完成页面跳转前中断：下次启动完成正常数据恢复后继续打开目标对话并定位原终局；启动过程不重放这条通知；
- 用户通过 `Command+Q` 明确退出 Moebius 后，Electron 38 会移除已提交通知，因此不存在退出后仍可点击的冷启动入口。重新打开 Moebius 时，只有仍保留红点或蓝点的对话可以从侧边栏找回；“确认没有新增内容”等无点结论在明确退出后不保留提醒入口。产品不伪造一条历史通知，也不把普通启动误判为通知点击；
- 目标是普通根对话时选中对应侧边栏行；目标是 sidebar chat 时复用它自己的主内容区／右侧栏打开规则，不跳到来源对话；
- 跳转前正在编辑的草稿、阅读位置和右侧栏标签按各页面既有规则保存，不因通知导航丢失；
- 用户已经位于目标记录时，点击只聚焦，不创建重复标签或重复已读动作。

点击“已完成”通知并成功展示最新结果后，按侧边栏规则清除未读结果。点击“正在等待你”只打开原因，不自动确认红点、回答 Agent、重试或执行恢复动作。

### 7. 多段对话与“一轮一次”

“多段对话分别通知”只表示：如果对话 A 和对话 B 各自进入终局，每段对话各有一条能直达自己的通知。它不表示一段对话的每次状态变化都通知。

- 同一轮不因“运行中 → 红点 → 闪烁 → 已完成”等中间变化发送多条通知；
- 同一段对话本轮最终只发送“已完成”或“正在等待你”之一；
- 两段对话分别结束时不合并成一条无法直接进入具体目标的“有 2 段对话更新”；
- macOS 可以按应用分组显示多条通知，但每条仍保留自己的目标；
- Dock 数字表示当前未归档且唯一可见状态点为红点或蓝点的对话数，不是通知条数；同一对话只计一次。
- 用户手动建立未读时，无点对话转为蓝点并进入 Dock；该对话开始新一轮后只显示闪烁点并立即退出 Dock，不保留或显示第二个蓝点。本轮结束后只有新形成的红点或蓝点才重新计入。
- 当前聚焦对话的“已完成”结果真实呈现后，本次新结果立即视为已查看并且不增加 Dock，但仍提交系统通知和声音。“正在等待你”不能因当前正在观看而自动确认，仍增加 Dock。
- 普通归档对话保留历史事实但归档期间退出 Dock；从搜索恢复后按当时唯一可见状态决定是否重新计入。项目移除造成的批量归档同样退出 Dock并保留历史事实，但当前版本没有查看或恢复已移除项目的入口。

“确认没有新增内容”属于已完成终局，会发送系统通知。它不形成结果未读或待处理事实，因此不增加 Dock 数字、侧边栏仍为无点；应用仍在运行时，系统通知中心中的该条通知承担回流入口，用户明确清除系统通知或明确退出 Moebius 后视为放弃这条提醒。

## 分支与异常

### 通知总开关关闭

- 通知总开关默认开启；用户可以随时在设置中关闭；
- 总开关关闭后不提交系统通知、不请求声音，也不显示 Dock 角标；
- 时间线、结果卡片、系统记录和侧边栏状态点始终保留，关闭任务提醒不能隐藏产品事实；
- 重新开启只影响之后形成的新终局，并按当前未归档对话中可见的红点或蓝点重建 Dock 角标，不补发关闭期间的通知。

### 系统通知权限未决定、被拒绝或无法读取

- 每次终局发送前都重新读取 macOS 当前权限，不因首次引导曾经允许、拒绝或跳过而省略检查；用户可以随时在系统设置中改变权限；
- 检查未通过时不提交该终局的系统通知或声音，而是进入第 2 节的权限弹窗；对话终局、侧边栏状态和总开关开启时的 Dock 角标继续工作；
- 首次引导负责在用户尚未做任务前解释用途并提供授权；发送时权限弹窗负责承接真实终局触发后的恢复。两者读取同一系统事实，但首次引导完成与否不决定发送时是否检查；
- 权限尚未由用户选择时「开启系统通知」调用系统首次授权；权限已拒绝或暂时无法检测时同一动作打开 macOS 设置。用户返回后必须通过「重新检测」确认当前状态，不凭“已经打开过设置”推断成功；系统设置无法打开时留在弹窗显示可重试错误，不改变权限或总开关；
- 重新检测通过后关闭弹窗，弹窗中已经展示的终局不补发；只有之后形成的新终局可以提交系统通知；
- 用户选择「关闭任务提醒」后总开关关闭，后续终局不再检查系统权限或弹恢复窗，直到用户在设置中重新开启。

### 系统通知提交失败

- 对话终局、侧边栏状态和 Dock 角标不回滚；
- 失败通知不在很久以后或重启后补发；
- 设置保留可理解的权限或通道状态，不能声称通知已经成功送达。

### 点击时目标已变化

- 目标只是被用户普通归档时不自动恢复；应用显示原对话名称与“恢复对话”入口，用户恢复后定位原终局，仍未清除的提醒重新进入 Dock；
- 目标所属项目已经被移除时，当前版本没有查看或恢复入口；应用启动或聚焦后保留用户原工作现场，明确说明该项目已经移除且当前无法打开，不提供虚假的搜索恢复或“重新添加同一路径”捷径；
- 项目不可用、团队已删除或目标存在其他不可继续状态时，仍打开原对话并显示当前恢复入口；
- 目标记录不存在或无法访问时，启动／激活 Moebius 后保留用户原工作现场，显示“这条通知对应的对话已不可用”，不猜测同名或最近对话代替。

## 等待与自动推进

- 流程等待主页面会话区保存本轮终局，不轮询 Agent 正文，也不在中间状态预告完成；
- 终局一旦形成，自动进入发送前权限检查；权限通过时直接提交，权限未通过时由权限弹窗承接，不在系统通道上等待用户确认；
- 通知只负责导航，不自动回复 Agent、不自动重试、不自动修复配置；
- 系统专注模式、锁屏或通知中心造成的展示延迟由 macOS 管理，Moebius 不复制补偿通知；
- 用户处理等待事项后开始新一轮；新一轮再次进入终局时才发送下一条通知。

## 完成条件

一次任务提醒流程在以下任一条件成立时完成：

- 系统通知已经按当前权限提交，并在 Moebius 仍运行时绑定激活应用、打开目标对话和定位终局记录的入口；点击已由主进程接收但页面定位前中断时，下次启动续做同一定位；用户明确退出后通知被移除，不构成冷启动入口；或
- 发送前权限检查未通过，本次终局已持久进入权限弹窗列表并在用户激活 Moebius 后实际呈现；弹窗本身承担本次终局的可见交付，用户随后开启系统通知并重新检测通过或选择关闭任务提醒，本次终局均不补发系统通知；或
- 权限通过但系统提交仍失败，应用准确保留终局、侧边栏状态和 Dock 状态，没有伪造送达成功。

流程完成不等于用户已经阅读结果或解决等待事项；这些由目标对话与侧边栏确认生命周期承接。

- [主页面侧边栏](../pages/main-left-sidebar.md)：显示当前未读与待处理状态，负责确认、手动未读和打开目标对话。

## 现有方案调研（PRD 阶段）

- **Apple `UNUserNotificationCenter`：采用为权限事实语义。**Apple 要求在安排通知前通过 `getNotificationSettings` 读取当前授权，并说明用户可随时在系统设置中改变 alert、sound 等能力；`requestAuthorization` 首次会弹系统请求，后续调用不会再次弹出。它与“每次发送前检查、拒绝后打开设置、返回后重新检测”的产品流程一致。[Asking permission to use notifications](https://developer.apple.com/documentation/UserNotifications/asking-permission-to-use-notifications) · [getNotificationSettings](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/getnotificationsettings%28completionhandler%3A%29) · [requestAuthorization](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/requestauthorization%28options%3Acompletionhandler%3A%29/)
- **Electron 主进程 `Notification`：采用为通知提交与点击回流入口。**Electron 官方支持主进程提交系统通知，并要求 macOS 正式应用完成代码签名；提交失败仍需作为独立通道错误处理。它不替代 Apple 授权状态事实。[Electron Notifications](https://www.electronjs.org/docs/latest/tutorial/notifications)
- **Renderer Web Notifications API 或 Electron 文档提到的 `macos-notification-state`：保留为 OpenSpec spike 候选，不在 PRD 阶段直接选定。**前者需要验证能否在当前主进程架构中稳定读取完整 macOS 授权和分项状态；后者公开能力还包含前台、锁屏与专注模式判断，不能未经验证就当作 Apple 授权状态的唯一事实源。
- **基线候选——直接调用 `show()` 再等失败：不采用。**它无法在发送前给出三操作恢复弹窗，也无法区分尚未决定、已拒绝和通道故障。
- **结论：**产品语义采用 Apple 的“发送前重新读设置”模式；具体通过原生桥、Renderer API 还是经验证的模块实现，由后续 OpenSpec design 的签名打包应用 spike 决定。最小验证必须覆盖尚未决定、允许、拒绝、从系统设置改回允许、声音单独关闭和 Electron `failed` 事件，不能只在未签名开发壳中验证。

## 指标与验收

### 产品指标

- **终局覆盖率：**总开关开启且系统通道可用时，每一轮已完成或正在等待你都恰好提交一条通知的轮次数 / 终局轮次数，目标为 100%。
- **中间状态误报：**运行、交棒、排队、短暂空闲或单个成员结束产生通知的次数，目标为 0。
- **重复通知率：**同一对话同一轮提交两条及以上通知的轮次数 / 已通知轮次数，目标为 0。
- **回流正确率：**Moebius 运行期间接收到的通知点击一次到达正确对话和对应终局记录的次数 / 运行期间收到的通知点击总数，目标为 100%。已接收并持久记录、但因中断延后到下次启动完成的定位同样计入；显式退出后被 Electron 移除的通知不进入分母。
- **终局类型准确率：**实际仍可自动推进却通知“正在等待你”，或实际等待用户却通知“已完成”的次数，目标为 0。
- **隐私泄露：**除应用内已有的对话名称外，Agent 或用户正文摘录、文件名、路径、命令、原始服务商错误或凭据进入系统通知的次数，目标为 0。
- **权限检查覆盖率：**总开关开启时，具有实时权限检查结果的终局发送尝试数 / 全部终局发送尝试数，目标为 100%。
- **权限弹窗替代准确率：**权限未通过时，终局进入单一权限弹窗且没有同时或事后补发系统通知的次数 / 权限未通过的终局发送尝试数，目标为 100%。

### 端到端验收

除条目明确构造权限或总开关分支外，1–15 均以总开关开启且发送前权限检查通过为前置。

1. 在真实桌面应用中让一轮经历运行、专业成员结束、交棒、短暂空队列和继续运行；全过程不产生通知。主 Agent 最终收束为有新结果时，只提交一条“已完成”通知。
2. 分别在目标对话聚焦、Moebius 其他位置、窗口失焦和最小化时形成“已完成”；每种位置都提交一条 macOS 通知并请求系统声音。目标对话聚焦且结果记录真实呈现时，本次新结果立即视为已查看，不残留蓝点或新增 Dock 计数，也不叠加右下角任务提示。
3. 主 Agent 收束为需要用户处理，或异常／不可继续事实让整轮最终停止等待用户时，只提交一条“正在等待你”通知；点击后定位到包含原因、动作和继续方式的记录，不自动处理该事项。
4. 运行中出现异常红点但主理人随后自行恢复并把本轮收束为有结果时，不提前发送等待通知，最终只发送一条“已完成”。
5. 主 Agent 确认没有新增内容时发送一条“已完成”通知；侧边栏保持无点、Dock 不增加。Moebius 仍在运行时，通知横幅消失后仍可从 macOS 通知中心点击并进入该收束记录；用户明确退出后该通知随 Electron 进程退出而移除，不再提供历史回流。
6. 对话 A 与对话 B 各自进入终局时，各提交一条绑定自身目标的通知；A 的中间状态变化不增加通知。点击任一通知只进入对应对话，不先落到聚合列表。
7. 用户发送、打开结果、标记已读／未读、主动停下或确认结束继续能力时不通知；手动未读只让当前无点对话转为蓝点并进入 Dock。该对话开始新一轮后只显示闪烁点并退出 Dock；收束后再根据新结果显示红点、蓝点或无点。以多段对话压力数据验收时，每段对话与折叠项目始终只显示一个点，用户仅凭当前红点和蓝点即可逐一指出 Dock 数字中的全部对话，不显示“计入 Dock”等评审答案标签。
8. 锁屏但系统保持唤醒时形成终局，应用只提交一次通知并服从锁屏预览与声音设置；专注模式下同样只提交一次，由系统决定何时展示，不在解除专注后补发。
9. 终局在系统睡眠前已经通知时，唤醒后不重复；睡眠期间不声称本地任务继续推进或即时通知；唤醒后才保存的新终局只通知一次，恢复失败则通知“正在等待你”。
10. Moebius 运行期间点击通知：应用激活、恢复窗口并进入原对话与终局记录，不重放通知。点击目标已经由主进程持久记录、但页面定位前发生 renderer 崩溃、应用崩溃或系统中断时，重新启动后继续完成同一定位；目标后来被普通归档时提供明确恢复入口，恢复后再定位；目标所属项目已经移除时说明当前无法打开且不伪造恢复入口。另以 `Command+Q` 明确退出验收平台边界：已提交通知被移除，普通重开只展示持久化侧边栏事实，不冒充通知冷启动。
11. 点击“已完成”通知并成功显示最新结果后，对应蓝点按侧边栏规则清除并退出 Dock。点击“正在等待你”只打开原因，不自动清除红点或执行恢复。
12. 总开关关闭时不读取系统权限、不弹权限窗、不伪造系统通知成功；系统通知、声音和 Dock 均停用，对话和侧边栏事实继续正确。用户在设置重新开启后只处理之后形成的新终局，不补发关闭期间的通知。
13. 刷新、重新渲染、休眠唤醒和重启只恢复既有终局，不重复提交通知；一轮结束后用户发起新一轮，新一轮再次结束时允许产生下一条。
14. 通知显示应用内已有的对话名称与终局类别；除对话名称外，不包含正文摘录、文件名、路径、命令、原始服务商错误或凭据，并服从 macOS 的通知预览、静音和专注模式设置。
15. 分别普通归档带蓝色与红色提醒的静止对话：归档后立即退出 Dock，提醒事实不改写；从搜索恢复后未清提醒与 Dock 计数重新出现。移除包含提醒对话的项目时同样立即退出 Dock并保留事实，但当前版本不执行恢复后的页面步骤，重新添加相同路径也不能冒充恢复。
16. 使用升级前已完成 onboarding、总开关开启且系统权限尚未决定的真实用户状态：启动或升级本身不显示提示；第一段对话形成终局时，发送前检查不提交系统通知或声音，而是在 Moebius 内显示包含该对话名称与终局类别的权限弹窗。用户看见弹窗后即能辨认发生了什么。
17. 在权限弹窗中分别验收三个操作：弹窗标题为“需要允许系统通知”，并在操作前明确说明“任务提醒已开启”和“关闭任务提醒后，系统通知、声音和 Dock 提醒都会停用”。系统权限尚未由用户选择时「开启系统通知」触发一次 macOS 原生请求，请求期间显示“等待 macOS 确认…”并锁定操作，系统返回后显示“请重新检测”，不展示内部权限枚举；已拒绝时打开该应用的系统通知设置，打开期间主操作持续显示“正在打开系统设置…”且不得跳回“开启系统通知”，成功后显示返回并重新检测的说明。「重新检测」每次读取当前真实状态，未通过时保持弹窗、通过时关闭；「关闭任务提醒」按设置页保存生命周期持久化关闭应用总开关，成功后关闭弹窗并停用系统通知、声音与 Dock，保存失败或超时则保持旧值、弹窗与重试入口。另以权限读取失败形成“暂时无法检测”：点击「开启系统通知」只打开 macOS 通知设置，打开失败时显示明确错误，主操作变为“再次打开系统设置”并允许重试，均不得推断权限已通过。标题栏关闭、`Escape` 与遮罩点击不得形成第四种静默退出。
18. 权限弹窗展示任务 A 的“已完成／正在等待你”后，用户开启系统通知并点击「重新检测」得到通过：弹窗关闭，A 不产生系统通知、声音或稍后补发；之后新一轮任务 B 结束时才提交一条系统通知。侧边栏与 Dock 在 A、B 两次过程中始终按各自事实和总开关规则工作。
19. 权限弹窗未解决时让对话 A、B 分别形成终局：页面只存在一个弹窗，按形成顺序分别显示 A、B 的对话名称和终局类别，每段对话每轮只出现一次。重新检测通过或关闭任务提醒后两项都不补发系统通知。
20. 在 Moebius 失焦和最小化时触发权限未通过分支：应用不抢焦点、不强制恢复窗口；再次激活时首先看见待处理权限弹窗。弹窗展示前后分别退出或使应用崩溃，重启后恢复同一待展示列表，不把其中事件改走系统通知，也不把关闭应用误作「关闭任务提醒」。
21. 在系统设置外部依次撤销和恢复 Moebius 通知权限：每个新终局发送前都读取最新状态，撤销后的下一次终局进入权限弹窗；用户恢复并重新检测通过后只关闭弹窗，后续新终局恢复系统通知。仅关闭声音、开启专注模式或改变横幅样式时仍提交通知，不误弹权限恢复窗；系统最终展示服从当前分项设置。

## 非目标

- 不通知运行开始、运行中、排队、交棒、成员单次结束或其他中间状态。
- 不提供移动端、邮件、短信、Webhook 或远程推送。
- 不允许 Agent 自定义通知标题、正文、声音或发送时机。
