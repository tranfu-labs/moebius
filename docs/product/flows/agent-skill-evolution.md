# Agent 技能进化

> 状态：草案，已逐步骤通过评审。技能格式、注入机制与加载策略三处在评审后被推翻重定，理由记在「技能的形态与加载」一节。标注「待讨论」的条目尚未拍板。
>
> 范围：定义应用自己发起的后台工作所使用的**技能**如何被存放、被加载、从用户的隐式更正中学会变好，以及每一次自动改动如何被看见、被追溯、被退回。本次只框定一个场景——**自动命名会话**。它跨越[设置](../pages/settings.md)与[主页面侧边栏](../pages/main-left-sidebar.md)，因此不归任何单页。
>
> 本文承接 [Agent 进化](./agent-evolution.md)「待讨论」中的「Agent 自动进化」条目。两条流程共用同一套修订机制（完整内容 + 作者 + 时间 + 一句人话摘要 + 批次整体撤销），但进化对象不同：那条进化的是团队成员的 `AGENT.md`，这条进化的是应用自己的技能。

本文按用户可观察层级使用术语：

- **技能**：应用自己发起的某一类后台工作所依据的规则，例如「怎么给一段新对话起标题」。它不属于任何团队、任何成员、任何一次会话。
- **条目**：技能里的一条规则。技能的可进化部分是一份条目清单，不是一段散文。
- **配对记录**：一次「Agent 生成了什么、用户改成了什么」的事实记录。它是这条流程唯一的信号来源。

## 用户目标

用户希望软件替他做的这些小事越做越合他的意，而不需要他去设置任何东西；也希望在任何时候都能问出「它自己改了什么、凭什么改的」，并且不满意时能退回去。

这条流程要让应用表现得像一个会看眼色的助手：你改过它起的标题，它记住了，下次起得更接近你的习惯；但它每一次自我调整都留下账，你随时查得到、退得回。

## 开始条件

流程只有一个起点：**用户修改了一个由应用自动命名过的会话标题**。

自动命名当前在新会话首条消息落库后触发，走应用级默认 Agent 的一次性调用；用户随后从[主页面侧边栏](../pages/main-left-sidebar.md#重命名对话)重命名。这个动作本来就会发生，不为进化新增任何界面。

**用户改名是否决信号，用户不改名不是认可信号。** 大多数人懒得改标题，将就着用。因此这条流程只有负信号，能做的事只有「少被否决」，做不到「更让人满意」。所有下游设计都接受这个上限，不从「没被改过的标题」里提取正面经验——那是噪音。

## 参与者与职责

| 参与者 | 职责 | 明确不负责 |
| --- | --- | --- |
| 用户 | 照常改标题；事后可查看、可编辑技能、可退回 | 不需要打开审计页、不需要评价好坏、不需要为训练做任何额外动作 |
| 桌面应用 | 记录每一次配对事实、按版本取用技能、判断是否到达学习门槛、留痕与承接回退 | 不判断哪次改名算否决，不撰写技能内容 |
| 默认 Agent | 读一批配对记录产出诊断、提出条目级修改、撰写每条修订的一句人话说明 | 不做最终裁决——它的产出是既成事实但可被用户整体回退；不能修改技能的身份部分 |

「默认 Agent」是设置中的应用级选择，见[设置](../pages/settings.md)。它此前服务两件事（撰写 `AGENT.md` 变化说明、完成上游合并），本流程是第三件，该页说明需相应补充。

## 主流程

一次完整循环分四棒，**第一棒与后三棒彻底解耦**。

### 一、记事实

用户改名后立即记一条配对记录：当时的第一条消息、Agent 生成的标题、用户改成的标题、当时的技能版本、生成与改名各自的时间、两者之间隔了多少条消息。

- **记录环节只记客观事实，不打标签、不做过滤。** 判断哪次算否决放到反思时做。过滤逻辑一旦改动，被过滤掉的历史就再也回不来。
- 这一棒无条件、立即、不调用任何 Agent，不拖慢重命名本身。
- **到这一棒为止，审计已经可用。** 学不学是另一回事——本流程可以只上线第一棒先跑，先看几周真实数据再定后面所有阈值。

### 二、攒够再想

三个条件同时成立才触发一次反思：该技能尚未提炼过的配对记录达到阈值、距上次进化有最小间隔、当前有可用的默认 Agent。不达标就不动。用得少的用户几个月才进化一次是正常的。

- 单次反思喂入的记录数有上限，取最近的一批。样本堆太多会让反思把边缘情况都编码进规则，反而过拟合。
- 已提炼过的记录标记为已提炼，不再参与下一次反思，但**永久保留在审计里**。这是配对记录唯一需要的分层——不是压缩，是不重复喂。
- 反思由默认 Agent 完成，**不为省成本降级到小模型**：从执行轨迹里提炼规律要求对推理进行推理，小模型做不了这件事。
- Agent 必须在结论里写清它采信了哪几条、放弃了哪几条及理由。**Agent 的判断本身也进审计**，用户看到的是「依据 4 条，另有 2 条被判定为话题变更未采信」，不是一个黑箱结论。

### 三、改技能，先回放再生效

反思产出的是**条目级增量**：加一条、改一条、删一条、把语义重叠的几条合并成一条。**永不整篇重写**——整篇重写会让细节被越抹越少，几轮之后技能比原始版本还差。

写回前后各有一道闸门：

- **事前 · 回放**：拿改完的技能重新给历史样本里的第一条消息起标题，看是否比旧技能更接近用户当初改成的那个。不通过就放弃这次修改，记一条「试过，没通过」。
- **事后 · 观察窗**：生效后统计接下来一段时间的否决率。不降反升时**不自动退回**——样本太小，自动回退会来回抖——而是在审计页显眼标出并把退回入口放在旁边。

回放只能当否决闸门用，不能当认可依据：用户当初改成的标题只是一个样本点，不是唯一正确答案。回放通过不证明更好，回放不通过很说明有问题。这与「只有负信号」是同一条逻辑。

### 四、生效

下一次自动命名按名取技能的当前生效版本执行，并把版本号一并记入这次执行产生的配对记录。

## 技能的形态与加载

### 形态：开放标准，身份冻结，正文可进化

技能按 **Agent Skills 开放标准**落盘——一个目录，里面一个 `SKILL.md`，文件头是 YAML（`name` 与 `description` 必需），下面是 markdown 正文。该标准 2025 年底发布，治理权在 Linux Foundation 的 Agentic AI Foundation，Claude Code、Codex CLI、Gemini CLI、Cursor 等三十余种工具支持。

采用标准而不自创格式，换来三件事：用户能用任何编辑器或其他 Agent 工具打开自己调教出来的技能；将来能装社区技能、也能把自己的导出去；我们不必发明一套没人验证过的格式。

标准的天然分界正好就是我们需要的那条：

| 标准里的位置 | 用途 |
| --- | --- |
| 文件头整体 | **Agent 改不了的身份部分**。它可以学会标题该怎么起得更好，不能学会「我不起标题了」 |
| 文件头的 `description` | 技能详情页那块只读的身份说明 |
| markdown 正文 | **条目部分**，可进化 |
| `metadata` | 记当前版本号，与修订链交叉验证 |
| `allowed-tools` | 显式声明为空——后台一次性调用不需要任何工具 |

技能命名遵守标准约束：只用小写字母、数字与连字符，不含保留词。

正文有硬长度上限。上限的作用是逼着 Agent 在加新条目时先合并或删除旧的，而不是无限堆积——规则清单膨胀会直接拖垮效果。

### 住址：三层

| 层 | 在哪 | 谁能改 | 作用 |
| --- | --- | --- | --- |
| 内置版 | 随软件发行 | 只有发版能改 | 保底基线；软件升级时三方比较的那一份 |
| 当前生效版 | 应用数据目录 | 用户、Agent | 实际被执行的那一份 |
| 修订链 | 应用状态存储 | 只增不改 | 时间线、来历、回退 |

这三层与 [Agent 进化](./agent-evolution.md#三自动接收上游改进)已定稿的三方比较完全对应：**软件升级带来新版内置技能时，走同一套自动合并、用户意图优先、整次可撤销**，不为技能另发明一套升级语义。

### 加载：一级跳过，二级直接给，三级保留

渐进披露分三级——元数据（只加载名字与描述，让模型知道有什么可用）、正文（触发后进上下文）、资源（引用文件与脚本按需读）。本流程对三级分别处理：

- **一级跳过。** 应用发起后台工作时百分之百知道要用哪个技能，让模型去发现是空转，还引入一个「模型判断不用它」的失败点。审计要回答「这次用的哪一版」，容不下这个不确定性。这不是违背标准：Claude API 用 `container.skills` 传 `skill_id` 就是绕过发现的程序化指定，Codex CLI 的 `$skill` 与 `allow_implicit_invocation: false` 同理。
- **二级直接给。** 正文百分之百要用，让模型多跑一趟工具调用去读一个必读文件没有收益。
- **三级保留。** 技能目录整个放进执行时的隔离工作目录，引用文件与脚本留在那里按需读，不用就零成本。正文超过标准建议的长度线、或技能带了引用文件，就往三级拆，而不是继续往提示词里堆。

**不往用户的任何全局配置目录写字节。** 放进去的是每次执行新建的隔离目录，用完即弃。

### 这一节被推翻过三次

记下来是为了让后来者不必再走一遍：

1. **格式**：最初打算自创一段提示词模板。推翻理由——丢掉可移植性，且要发明一套没人验证过的格式。改用开放标准。
2. **注入**：曾设想把技能写进用户的 `~/.claude/skills/` 并在启动时检查恢复。推翻理由——该目录不支持嵌套命名空间（官方命名空间机制是插件），会污染用户自己的工作环境，「删了就恢复」等于跟用户抢文件所有权，且只解决一家：Codex 目录不同、Pi 根本没有技能加载这个概念。改为不注入。
3. **加载**：曾打算把正文全量拼进提示词。推翻理由——那等于宣告技能永远不会有引用文件和脚本，把三级的路堵死。改为三级分治。

最直觉的那条路（自创模板、写进用户目录、全量拼接）每一步都是错的，而且错得不明显。

## 分支与异常

- **技能文件缺失或读不出来**：**检查在用技能之前进行，不在应用启动时**——启动时检查会让用户在 Finder 里改过之后、下次启动之前的所有执行都用着旧内容。先从修订链恢复到用户最后调教的那一版；修订链也读不出来才回落内置版。两种情况都留痕并在技能详情页的异常带告知。
- **默认 Agent 不可用**（未配置、凭据失效或调用失败）：不触发反思，配对记录照常记录，审计照常可查。异常带说明「学」停了、「记」没停。
- **反思跑出「这批没有共同模式」**：这是完全合法且应当常见的结论。必须允许 Agent 输出不改动，并同样记一条记录。不给这条出路，Agent 会为了交差硬编一条规则出来——小样本场景下这比学到坏规则更常发生。
- **回放不通过**：放弃这次修改，记一条留痕，涉及的配对记录仍标记为已提炼，不反复重试同一批。
- **观察窗显示否决率上升**：不自动退回，在异常带与该条进化记录上同时标出，退回入口就在旁边。异常带的警示可点击并直接展开对应那条记录——出问题的进化未必是最新一条，沉在列表里等于没告知。
- **用户关闭了该技能的自动学习**：不再触发反思与写回；**配对记录继续记，审计继续可查**。关掉的是「学」，不是「记」。
- **软件升级带来新版内置技能且用户改过当前版**：走 [Agent 进化](./agent-evolution.md#三自动接收上游改进)的三方比较，用户意图优先，结果记入可整体撤销的修订。
- **技能被改到解析不出条目**：按「读不出来」处理，回落并告知，不静默丢弃用户内容。

## 等待与自动推进

流程中没有必须等待用户的节点。改名即记录，攒够即反思，回放通过即生效。

用户参与的全部时机都是事后的、可选的：查看进化记录、直接编辑技能条目、退回。**从不参与的用户也能得到一个逐渐更合用的技能**，这是这条流程成立的核心判据。

## 完成条件

- 一次记录的完成：用户改名后存在一条配对记录，含当时的技能版本，且重命名本身的响应速度未受影响。
- 一次进化的完成：技能当前生效版本更新；修订链新增一条作者为 Agent 的修订，带一句人话说明与本次依据的那批记录；技能详情页最近变化行更新；后续自动命名使用新版本。
- 一次放弃的完成：技能内容不变；存在一条「试过，没通过」的记录；这批配对记录标记为已提炼。

技能详情页的模块顺序为：身份说明 → 异常带（有事才出现）→ 最近变化 → 条目编辑器 → 进化记录。顺序对应用户的提问顺序——替我做什么、现在正不正常、最近变成什么样、它现在怎么想的、它凭什么变成这样。异常带排在第二位，因为「正在用保底版本」这种事放在页面底部等于没告知。

进化记录区提供两个互斥视图：进化记录（默认）与全部改名记录。**大多数用户大多数时候技能一次都没进化过**，空状态是常态而非边缘情况，需要说清现在什么状态、接下来会发生什么、用户还握着什么，并把全部改名记录的入口摆在眼前。

单页的区域、控件、状态与文案由[设置](../pages/settings.md)承接，本流程不展开。

## 指标与验收

### 产品指标

- **否决率**：自动命名后被用户修改的比例。这是本流程唯一的效果指标，也是观察窗的判据。
- **进化采纳率**：反思产出的修改中通过回放并生效的比例。持续偏低说明反思质量不够；持续偏高需警惕回放闸门形同虚设。
- **退回率**：自动进化被用户退回的比例。持续偏高说明该先修反思质量，而不是加确认步骤。
- **可查率**：用户能否在不读完整技能内容的情况下说出最近一次自动改动是什么。

### 验收清单

1. 用户改名后存在配对记录，且重命名的响应速度不受影响；关闭自动学习后记录仍然产生。
2. 技能文件被删除或改坏后，下一次使用前自动恢复到用户最后调教的那一版；修订链也不可用时才回落内置版，两种情况都留痕并告知。
3. 应用不向用户的任何全局配置目录写入内容。
4. 每一次自动进化都能查到依据了哪几条改名记录，包括被判定为未采信的那几条。
5. 反思得出「没有共同模式」时不产生任何技能改动，且这次判断本身可查。
6. 回放不通过的修改不会生效。
7. 观察窗显示否决率上升时，警示与退回入口同时出现，且点击警示能直接定位到对应那条进化记录。
8. 任意一次自动进化可以退回；退回本身也是一条修订，可以再退回。
9. 用户直接编辑技能条目后立即生效，与 Agent 的改动共用同一套留痕、来历与回退。
10. 技能一次都没进化过时，页面说清当前状态与接下来会发生什么，并能查到全部改名记录。
11. 四种执行通道（codex / claude / kimi / pi）使用完全相同的技能加载路径，不为任何一家保留特殊分支。
12. 默认 Agent 不可用时没有任何技能内容被改动。

## 待讨论

- **阈值全部待定**：触发反思的记录数、单次喂入上限、最小间隔、观察窗长度、正文长度上限。**这些数字应当由第一棒上线后的真实数据决定，现在拍的都是猜的。**
- ~~**分类与技能的命名**~~：已定为「Moebius 的技能」与「给对话起标题」，落在[设置](../pages/settings.md)。两个名字都只是文案，改动成本低；用户如有偏好可直接推翻。
- **第二个技能**：`AGENT.md` 修订摘要的撰写规则同样是硬编码的，可以装进同一个容器，但不在本次范围。
- **会话内技能**：会话里的团队成员将来能否携带技能。那需要真正把文件放到执行通道能看见的地方，涉及各家机制差异，与本流程不是一件事。

## 非目标

- 不做评测集、候选提示词池与搜索式优化。那套方法的前提是有标注数据和可以充分试错的预算，桌面产品两样都没有。
- 不做实时学习。单条否决里个人口味与噪音占绝大多数。
- 不从「没被改过的标题」提取正面经验。
- 不在对话里让用户直接教（例如「以后标题短一点」）。那是另一个信号源，需要新增一层意图识别；用户要调教，直接编辑技能条目即可。
- 不压缩或删除原始配对记录。它是审计的地基，压缩证据等于拆掉地基。需要合并的是技能条目，被合并掉的原条目原文完整保留、可展开、可退回。
- 不合并进化记录。每条对应一次可回退的动作，合并了就退不回去。
- 不做技能的跨用户共享、上传或分发。进化结果不出本机。
- 不静默改进。每一次自动改动都必须可见、可查依据、可退回；宁可少学，不可无痕地学。
- 不改变重命名本身的行为。学习永远在事后发生，用户动作零感知。
- 不向用户展示逐行对比、内容指纹或版本号之类的技术细节，理由同 [Agent 进化](./agent-evolution.md)的非目标：技能条目同样是自然语言写的规则而不是代码。
