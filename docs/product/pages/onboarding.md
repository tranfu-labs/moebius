## 页面目标

首启引导不是欢迎，是一次让新用户「信这支团队会替我接力」的最短演示——从环境就绪、看见团队、看它怎么协作，到确认准备开工。

走完引导，用户带走的不是「配置完成」的绿勾，而是**「这支团队会替我接力，我不必当中转站」**的认知。

引导每台电脑只出现一次；走完最后一步落进[主页面会话区](./main-conversation.md)的新建对话形态，此后再打开应用不再重复。

## 用户场景

- 用户下载 moebius 并首次打开，此前用过 Codex 或 Kimi，还没试过多 Agent 团队协作。
- 用户在同一台电脑上曾完整走完引导，重开应用应直接进主页面，不重复。
- Codex、Kimi 任一未装或不可用时，用户在第一步就得到对应的独立安装或登录指引；只要其中一个可用就能继续，不必为了另一套 CLI 阻断首次体验。
- 用户走完引导后自然落入新建对话页，此时项目仍为空——加项目由那页承接，不是引导的职责。

## 入口与去向

### 入口

- 应用首次启动，数据根中没有包含有效 ISO 完成时间的 `.onboarding-completed` marker 时自动进入。
- 已完成引导的用户可从主页面侧边栏底部的“重新查看引导”主动进入回看模式。
- 引导期间侧边栏不出现，主内容区就是引导本身。
- 中途关闭应用后重开，重新从第 1 步开始；引导完成后才写完成 marker。

### 去向

- 首次启动走完第 4 步点「开始使用」，落进[主页面会话区](./main-conversation.md)的新建对话形态。
- 落到新建对话页时项目仍为空，由该页承接添加项目。
- 落到新建对话页时**引导中所选定的团队应等同于「上一次成功创建会话时使用的团队」**（见 [agent-teams.md:361](./agent-teams.md)），作为该对话的默认预选团队。
- 回看模式可随时退出；点击标题栏「退出」或第 4 步「开始使用」都返回进入前的主页面状态，不把回看中选中的团队交给新建对话。

## 页面结构

引导为一屏一步的全屏页，共四步；应用启动即引导，本身不占屏而是一次跳转。

### 每步共用的应用标题栏

```text
┌────────────────────────────────────────────────────────────┐
│ [Moebius 品牌图标] Moebius   [◌ 2 项正在安装]   首次启动   │
└────────────────────────────────────────────────────────────┘
```

四步共用同一应用标题栏。标题栏图标使用[总 PRD](../prd.md#品牌与发行平台)规定的品牌母版派生图像，不使用图标库中的通用无限符号；图标、品牌名和“首次启动”只负责稳定标识应用，不参与步骤进度或状态表达。安装聚合状态只在有后台安装时出现，位于品牌区与右侧身份区之间，不替换“首次启动”、回看身份或退出操作。回看模式把右侧“首次启动”替换为“回看引导”，并在同一区域提供“退出”按钮。下列步骤结构图从标题栏下方开始。

│                                                       │

### 应用启动 → 直接进第 1 步

不是屏。应用启动检测到本机从未完成引导时，主窗口直接渲染第 1 步而不是新建对话页。原「首启即落新建对话页」路径被引导替代。

两行先分别执行 `codex --version` 与 `kimi --version`，再由引导自己的 readiness service 调用执行能力探针，确认该 CLI 已完成登录 / provider 配置并能返回至少一个真实可用模型。只有版本检查与执行能力探针都成功，才显示绿色「可用」；只通过版本检查只能说明“已安装”，不得承诺 Agent 可以启动。准备检查不得发送真实对话、产生模型调用费用、修改项目文件或打开交互式登录流程；Agent 团队管理页不复用或触发这项检查。

正式 Electron 页面在可用行显示**该 CLI 最近一次成功版本检查得到的真实版本文本**；页面生命周期内每次完整准备检查——包括首次检查、某一套 CLI 安装完成后的自动复检和手动「重新检查」——都以当次结果整体替换该行旧值，不得使用硬编码版本、占位版本或缓存中的旧版本。两行可以并行检查，同一行内部按“版本 → 执行能力”顺序收敛；较早发起的旧结果不得覆盖同一行较晚发起的结果。

若评审表面没有连接真实检测（包括本 PRD 字符图、独立 HTML 原型和 Storybook），只显示不含具体版本号的通用状态，不得用示例数字冒充检测结果。「重新检查」是两行共用的手动复检入口，在任一状态下都保留；任一 CLI 可用后「继续」立即可点，另一行仍保留独立的安装或修复指引。

缺失行展示当前官方的一行安装命令：

- Codex：`npm install -g @openai/codex`
- Kimi：`curl -LsSf https://code.kimi.com/install.sh | bash`

命令旁的播放按钮具有对应的可访问名称「安装 Codex CLI」或「安装 Kimi CLI」。点击后直接开始执行该行对应的受信任安装动作，不再弹出第二次确认；按钮立即变为不可重复触发的进行中反馈，行内持续显示「正在安装」和阶段性活动提示，不能让用户面对静止界面猜测是否生效。安装成功后该行自动执行完整准备检查：尚未登录时进入“已安装，需登录”，登录就绪时才进入可用；安装失败或超时后保留该 CLI 的独立失败说明和重试按钮，不展示原始 stderr、本地路径、令牌或安装脚本内部细节。

安装动作只能来自应用内随版本发布的受信任 registry，禁止接受页面文本、团队文件或外部输入提供的任意命令。上面两条命令是当前 macOS arm64 发行基线；每次正式发版前必须对照 Codex 与 Kimi 官方安装文档校准包名、URL 和参数，若官方入口变化则与应用一起更新，不在运行时远程下发替换命令。

每套 CLI 只有在操作系统明确报告可执行文件不存在（`ENOENT` / `ENOTDIR`）时才进入缺失态。版本命令非零退出、存在但不可执行（如 `EACCES`）、其他启动异常，以及退出码为 0 但没有返回非空版本文本，都进入该 CLI 已安装但不可运行态。版本正常、执行能力探针确认没有登录 / provider 配置时进入“已安装，需登录”；能力协议超时、异常或没有真实可用模型时进入“暂时无法验证”。这三类都只给出对应登录 / 排障指引和重新检查，不显示安装命令或播放按钮；底层结果不得把原始 stderr、异常文本、本地路径、provider 密钥或令牌交给 renderer。

第 1 步是**“至少一个可用”的硬门**：Codex 与 Kimi 都未达到“版本正常 + 登录就绪 + 有真实可用模型”时不能进第 2 步，「继续」保持 disabled；任一行完整准备检查通过后立即放行，不要求另一套 CLI 也安装、登录或修复。进行中的安装不锁住另一套已经可用时的「继续」，用户离开本步后安装反馈不得伪装为已成功。

│  │                                                    │    │

- 首问固定聚焦长期工作目标：「你希望这支团队长期替你完成什么工作？」并补充“先说目标就好，不需要想好角色和分工。”用户不需要先提供成员名称或组织结构。
- 信息足够时直接给团队方案；只有缺少会改变成员构成的关键信息时，AI 才每轮追问一个问题，不为显得周到而继续采访。
- AI 建队使用进入子流程时已可用的 CLI：只有 Kimi 可用时使用 Kimi，Codex 可用时优先使用 Codex。所选 CLI 在该建队草稿的整个生命周期内保持不变，不因另一套 CLI 后来变为可用而跨 CLI 切换或丢失上下文；若它中途失效，页面保留草稿并给出对应修复与重试入口。
- 方案必须包含团队名称、一句话用途、2–6 名成员、唯一主 Agent、每名成员的稳定 slug 与可生成完整 `AGENT.md` 的结构化职责 / 交接规格，以及一段供第 3 步播放的协作示例。onboarding 方案卡显示 `@slug`，让用户在创建前看见后续可点名的稳定身份；协作示例属于独立的引导编排数据，不属于团队结构、成员职责或真实运行规则。
- AI 团队设计器是第 2 步内的响应式工作区，不沿用普通步骤约 `512px` 的窄栏上限：宽窗口下最大宽度约 `780px`、最大高度约 `720px`，并随可用窗口缩小；窄窗口继续占满可用宽度并由引导主体承担页面级滚动。
- 团队提案卡必须按内容完整占位，展示全部成员、`@slug`、主 Agent 与接力关系；提案卡自身不得在纵向 flex 布局中被压缩裁切，也不设置第二层内部滚动，超出设计器可视高度时只滚动对话区。
- 用户可以点击「继续聊着调整」并用自然语言修改方案。只有点击「创建并选中」才创建正式用户团队；此前的对话和方案不是团队，也不出现在 Agent 团队首页。
- 「返回选团队」只退出第 2 步的建队子流程，不是四步引导的全局回退；再次进入时恢复尚未确认的对话与最后一版有效方案。
- 创建成功后回到第 2 步团队列表，新团队成为当前选中项；随后「继续」进入第 3 步。

## 操作与反馈

### 前进

- 每步主 CTA 前进到下一步；首次启动第 4 步主 CTA 出引导并落到新建对话页，回看第 4 步主 CTA 则恢复进入前的操作台。
- 上一步的成果携带到下一步：第 1 步的通过状态、第 2 步的所选团队都对下一步继续有效。
- 高保真单 HTML 中的四步前进和第 4 步「开始使用」全部在同一文件内切换可见状态。首次启动的最后一步必须直接渲染出新建对话形态并让所选团队肉眼可见；回看的最后一步必须恢复确定性的进入前主页面展示态且不应用临时团队选择。两种模式都不调用正式应用路由，不以提示框或完成文案代替去向。

### 回退

- 第 2–4 步提供「上一步」，第 1 步不显示回退入口。
- 返回时保留已通过的环境状态和已选择的团队，不清空用户已经完成的选择。
- 从第 4 步返回第 3 步时，接力演示从第一棒重新播放，避免停在一个缺少前序上下文的中间画面。
- 第 2 步 AI 建队子流程另有「返回选团队」，只退出同一步的子流程，并保留未确认的建队对话与方案。

### 中途关闭

应用关闭 = 中断引导。因为完成 marker 尚未写入，下次打开重新从第 1 步开始；本版不持久化四步内的临时进度。

若应用关闭时仍有一项或两项 CLI 安装在进行，先提示“CLI 仍在安装”，逐项列出仍在运行的 CLI，并提供「留在应用」与「取消全部安装并退出」。取消只作用于确认时仍在运行的受控安装进程；已在确认期间成功、失败或超时的任务保留其真实终态，不回退成“已取消”。应用等待所有取消请求收敛后再退出，不能留下界面已关闭但安装仍在后台静默运行的孤儿进程；若确认期间已没有运行任务，则直接继续原退出动作。应用崩溃时下次启动按重新检查结果恢复，不把上次进行中状态当成成功。

回看模式不改变完成 marker；中途关闭应用后，下次启动仍按已完成用户直接进入主页面，不会被回看进度拦回引导。

### 重新查看引导

- 回看复用完整四步内容与交互，但只作为当前 renderer 生命周期内的临时展示态。
- 进入回看时保持原操作台挂载；点击「退出」或第 4 步「开始使用」后恢复进入前的项目、对话、草稿、侧边栏和应用页面状态。
- 进入回看、点击「退出」和第 4 步点击「开始使用」都不得删除、覆盖或重写 `.onboarding-completed`，也不得更新“上一次成功创建会话所用团队”或生成 pending team 选择。
- 回看中的团队选择只服务本次第 3 步演示。AI 建队仍是用户显式确认后才发生的独立创建操作；第 4 步点击「开始使用」只结束回看，不创建、修改或选定持久化团队。

### 第 1 步安装与重新检查

- Codex、Kimi 缺失时各自显示一整行固定官方安装命令和独立播放按钮；用户不需要复制到终端，点击即开始对应安装。
- 播放按钮点击后立即进入 loading，行内持续提供活动反馈；同一 CLI 安装未结束前不得重复启动，另一行的检测、安装和修复入口仍独立可用。
- 若另一套 CLI 已经可用，用户可以在可选 CLI 安装期间离开第 1 步。一项安装运行时，标题栏中间安装状态区以 `◌ 正在安装 Kimi…` 这类轻量全局状态持续反馈；两项并发时显示 `◌ 2 项 CLI 正在安装…`。点击后展示同一个安装详情列表，并逐项显示 CLI、实时阶段与取消入口；仍在引导内时可从详情定位回第 1 步，已进入操作台时由全局详情承接，不得启动第二份同 CLI 安装。单项完成后聚合状态降为另一项，全部结束后按各自真实结果给出一次完成或失败反馈再收起。
- 返回第 1 步时恢复当前进程的实时阶段和取消入口，不从初始 loading 重新计时。取消、失败、超时只影响对应 CLI；取消采用明确按钮和确认文案，避免把误触当成安装失败。
- 安装成功后只自动复检对应 CLI；失败或超时时只更新对应行，保留另一行状态与整个页面的可继续判定。成功安装但尚未登录时给出对应登录指引，不显示为绿色可用。
- 手动「重新检查」同时刷新两行。刷新期间保留最后一次明确的可用结果来避免 CTA 抖动，但本次检查结束后必须以新结果整体替换；乱序旧结果不得回写。
- 同一 CLI 的安装、自动复检与手动复检共用单调递增 revision：安装未结束时手动复检可以报告当前磁盘事实，但不能结束或覆盖安装任务；安装结束后的自动复检只在仍为最新任务时提交。所有状态变化通过可读文本和 `aria-live="polite"` 公告，不能只依赖旋转图标或颜色。

### 第 2 步 AI 建队

- 创建建队草稿时按第 1 步最近一次完整准备结果选择执行 CLI：只有 Kimi 可用时选择 Kimi；Codex 可用时选择 Codex，包括两者都可用的情况。草稿保存这次选择，后续调整、重试和恢复都继续使用同一 CLI，不静默跨 CLI 降级。
- 每个建队草稿拥有该 CLI 的唯一独立执行会话：Codex 草稿使用独立 Codex thread，Kimi 草稿使用独立 Kimi session。草稿第一次执行允许创建；取得 external ID 后，submit、adjust、retry、恢复和唯一一次结构修复都必须 resume 同一个 ID。创建成功并结束该草稿后，下一次建队使用新的 draft 和新的 provider session，跨草稿不得 resume。
- 页面展示的对话、最后一版有效方案和状态由应用自身保存；CLI 执行会话只提供模型上下文，不是产品状态唯一事实源。external ID 一旦取得必须随草稿保留；resume 失败、ID 冲突或 provider 会话丢失时只失败这一次 resume，不清空 ID、不用已保存对话重建、不执行第二次 full / `session/new`，页面准确显示「AI 上下文暂时无法继续，已保留对话和最后有效方案。」并保留「重试」。
- 一轮运行中输入框和「创建并选中」不可重复提交；用户可以退出子流程，运行结果返回时只有仍匹配当前草稿和 turn revision 才能提交，过期结果必须丢弃。
- 用户发送每轮消息（目标、追问回答、自然语言调整）后，文字必须立即以右侧用户消息气泡进入对话，不等待所选 CLI 返回结果；AI 处理期间该气泡保持可见并在其后显示「正在输入」指示。服务端返回持久化消息后，本地临时气泡必须无重复地收敛为正式消息，结果返回前该轮不可重复提交。
- 点击「继续聊着调整」后，当前方案卡片转为只读快照：去除高亮描边并收起操作按钮，调整结果返回后方案恢复可确认状态。
- 所选 CLI 超时、进程失败、恢复失败或输出非法时，页面保留已有对话和最后一版有效方案，显示对应 CLI 的可重试错误；不得无限自动重试、静默改用另一套 CLI，也不得把失败推进为已创建。
- 「创建并选中」只接受当前显示且仍匹配 proposal revision 的有效方案。创建期间按钮进入单次进行中状态；失败后回到同一方案并提供重试。
- 创建成功后不得留下未完成团队；失败、取消或应用崩溃恢复时，团队首页不得出现只有部分成员的 AI 团队。

### 第 3 步重播与继续

- 进入第 3 步后演示自动播放一次；「重新播放」会从第一棒重新开始，不改变已选团队。
- 动画播放期间「继续」始终可用。用户继续后立即结束演示并进入第 4 步，不等待剩余动画。
- 动画播完后停在主 Agent 收尾的完成画面，不自动跳到第 4 步，避免用户还没看清就被带走。

## AI 建队技术约束

AI 建队采用**短提示契约 + 结构化输出 + 确定性校验 + 应用状态机**。专业 LLM 可以补全角色内容、职责和协作方式，但不得自行猜测输出协议、权限、状态迁移或提交时机。

### 最小提示契约

固定的高优先级指令只保留模型在生成时必须知道的语义：

```text
你是 moebius 的团队设计器，只负责把用户目标转成团队方案。
缺少会改变成员构成的关键信息时，只追问一个问题；信息足够时直接给方案。
方案必须包含 2–6 名成员、唯一主 Agent、唯一稳定 slug、每名成员的完整职责与交接规格，以及一段可播放的协作示例。
不得读写文件、运行命令或声称团队已经创建。
只返回指定 schema；phase 只能是 clarifying 或 proposal。
```

不会影响生成内容的约束不继续堆进提示词：

- `phase`、字段类型、必填项与数组形状由所选 CLI 可用的结构化输出约束和应用侧解析共同保证。
- 成员数量、slug 唯一性、主 Agent 引用、接力成员引用、结构化成员字段和应用渲染后的 `AGENT.md` frontmatter 由 TypeScript validator 判定。
- `idle → running → clarifying / proposal / failed → committing → selected` 由应用状态机判定。
- 超时、重试、执行会话连续性、过期响应丢弃和 proposal revision 由 service 层判定。
- 团队目录与记录的原子创建由 team store 判定；所选 AI CLI 永远不获得团队写权限。

同一条会影响生成成功率的关键规则，提示词负责告诉模型怎么做，schema 负责限制输出形状，validator 负责判断是否真的做到；不得只依赖 validator 反复拒绝模型猜测，从而把流程拖入无界重试。

### CLI 执行边界

- AI 建队复用所选 CLI 的受控 driver，但使用独立 execution profile，禁止直接复用普通 Agent 的高权限执行参数。
- execution profile 使用所选 CLI 能提供的只读能力边界、隔离且不含项目素材的工作目录、结构化输出约束与有界 idle / max-duration timeout；不加载项目 `AGENTS.md`、用户 MCP 或会改变团队设计器行为的个人指令。
- 固定角色约束使用所选 CLI 的受控指令通道；本轮用户输入只作为用户消息，不与固定约束拼成可互相覆盖的同级文本。
- 所选 CLI 只返回 `clarifying` 或 `proposal` 两类结构化结果。应用在结构解析之外再次做业务校验；校验失败最多执行一次带明确错误列表的修复 turn，仍失败则进入可见、可重试的失败状态。
- 所选 CLI 不直接创建目录、写 `team.json`、写 `AGENT.md`、写 `onboarding-orchestration.json`、登记团队或改变 onboarding 选择。用户确认后，应用把最后一版有效方案的团队核心、成员文件与独立引导编排写入临时团队目录，分别重读校验后再切换为正式用户团队并登记；任一写入或校验失败都不得暴露半成品团队。

## 指标与验收

### 产品指标

- **完成引导 / 打开应用** 的比例（不完成就强关的比例）。
- 从打开 App 到落到新建对话页的中位时长。
- 第 1 步 Codex / Kimi 各自的缺失、不可运行、安装启动、安装成功与安装失败率（决定 App 下载页和行内指引是否需要调整）。
- 第 2 步进入 AI 建队、看到有效方案、确认创建和中途退出的漏斗。
- AI 建队每轮超时率、非法输出率、一次修复成功率与可见重试成功率。
- 引导完成后 24h 内实际发出第一条对话消息的用户比例。

### 验收标准

1. 本机从未完成引导时打开 App，主窗口进入第 1 步而不是新建对话页。
2. 本机曾完成引导时打开 App，直接进新建对话页，不再看到引导。
3. 第 1 步明确显示“Codex 或 Kimi 至少一个可用即可继续”。“可用”必须同时满足版本正常、登录 / provider 已就绪且执行能力探针返回至少一个真实可用模型；只检测到命令不得显示绿色可用。任一行可用后「继续」立即可点，另一行未安装、未登录、修复中或安装中都不得阻止继续；两行均不可用时才灰置。Codex 缺失行显示 `npm install -g @openai/codex`，Kimi 缺失行显示 `curl -LsSf https://code.kimi.com/install.sh | bash`，各自附带可键盘操作且有可访问名称的播放按钮。点击后立即进入不可重复触发的安装中状态并持续反馈；成功后自动执行完整准备检查，失败或超时后显示脱敏说明和独立重试入口。需登录或不可验证态改给对应登录 / 修复指引，不再显示安装按钮。
4. 第 1 步只准备 Codex 与 Kimi，不检查 gh / GitHub、Claude Code、Node 或其他 CLI。每行先执行 `--version`，再复用对应 CLI 的只读执行能力探针确认登录与真实模型能力；探针不得发送真实对话、产生推理费用或修改文件，因此“可用”表示配置已就绪，不承诺随后每次推理都不受临时网络、额度或服务状态影响。版本阶段只有 `ENOENT` / `ENOTDIR` 属于缺失；非零退出、`EACCES`、其他启动异常及成功退出但版本文本为空都属于不可运行。正式 Electron 页面必须显示各 CLI 最近一次成功版本检查返回的真实版本文本；每次重新检查或安装后自动复检都只用对应行的最新完整结果整体替换旧值，乱序旧结果不得覆盖。renderer 不得接收或展示原始 stderr、异常文本、本地路径、provider 密钥或令牌；静态 PRD、原型和 Storybook 不得固定任何具体版本号。
5. 第 2 步默认选中内置开发团队；选中状态由 accent 描边 + sel 底 + 蓝色实心圆点表达。
6. 第 2 步「跟 AI 聊出一支新团队」在同一步内展开，不跳路由；首问聚焦长期工作目标，信息足够时直接给方案，只有缺少会改变成员构成的信息时才追问；用户可退出并恢复未确认草稿。
7. AI 方案包含 2–6 名成员、唯一主 Agent、唯一稳定 slug、每名成员可生成完整 `AGENT.md` 的结构化职责 / 交接规格与独立协作示例；onboarding 方案卡显示各成员的 `@slug`。未确认前不得创建团队，点击「创建并选中」后必须把团队核心、成员文件与独立 `onboarding-orchestration.json` 原子写入并成为当前选中项。
8. 第 3 步是引导的必经步；必须用约 10 秒的连续动画演示第 2 步所选团队从主 Agent 安排、专业成员执行、发现问题、退回修改、再次复核到主 Agent 交付的协作过程；AI 团队使用其已验证方案中的角色与独立协作示例，不得退回开发团队硬编码或静态占位。编排数据缺失或损坏时只显示局部空态并允许继续，不得影响团队列表、团队可用性或真实会话。
9. 首次启动第 4 步只有一个主 CTA「开始使用」，点击落到新建对话页且已带上第 2 步所选团队作为该对话的默认预选团队。
10. 顶部标题区的「第 n 步，共 4 步」与当前步骤同步，并作为唯一进度提示；页面底部不得重复显示步骤圆点、`n / 4` 或第二套进度。
11. 所有屏的应用标题栏和顶部标题区布局一致；步骤区域共用最大约 `780px` 的响应式内容框架。全局步骤操作位于固定占据窗口底部的全宽 footer，footer 有顶部分割线且不随主体滚动，内部沿用约 `780px` 对齐边界，不恢复旧版独立 `640px` 内层；按钮右对齐且间距 `8px`，主按钮右边缘与内容框架右边缘一致。footer 不显示步骤圆点或 `n / 4`。第 1、2、4 步普通内容在框架内保持 `max-w-lg`；第 2 步 AI 团队设计器打开时使用最多约 `780px × 720px` 并隐藏全局 footer；第 3 步接力舞台使用约 `780px` 并使用更多可用高度。
12. 引导期间侧边栏不出现，主内容区就是引导本身；引导完成后恢复主页面三栏布局。
13. 引导中不出现任何 GitHub / gh / PR / issue 相关字样。
14. 所有色值走 [DESIGN.md](../../../packages/console-ui/DESIGN.md) 的令牌（`bg-canvas` `text-ink` `text-pass` 等），无裸 hex。
15. 亮暗双主题下所有屏可读、按钮状态可区分。
16. 第 3 步支持重新播放，播放期间也可继续；减少动态效果模式保留等价信息但不做持续位移。
17. 第 2–4 步提供「上一步」；返回时保留环境和团队状态，从第 4 步返回第 3 步会从第一棒重新播放。
18. 第 3 步的团队成员只作为节点横向位置；连接线只连接相邻两次发言，不得出现代表某个成员贯穿全程的长竖线，且每条消息必须与对应节点逐行对齐。
19. 高保真原型是可离线直接打开的单个 HTML，所有前进和返回操作都在同一文件内切换状态，能够从第 1 步完整走到带有所选团队的新建对话状态，不依赖外部脚本、样式、字体、图片或应用路由；AI 建队在原型中使用确定性 mock，不调用真实 CLI；原型与正式产品代码双向不共享源码。
20. AI 建队在只有 Kimi 可用时使用 Kimi，Codex 可用时优先 Codex；所选 CLI、模型上下文和独立只读 execution profile 固定在草稿生命周期内，普通 Agent 的高权限执行配置不得泄漏到建队调用，也不得在失败时静默跨 CLI 降级。
21. 非法结构、超时、执行会话恢复失败和创建失败都保留用户对话及最后有效方案、有限结束并提供原 CLI 上的重试；resume 失败准确显示「AI 上下文暂时无法继续，已保留对话和最后有效方案。」。取得 external ID 后不得清空、重建或发起第二次 full / `session/new`；不得无限自动重试、静默丢草稿或创建半成品团队。
22. Codex thread id、Kimi session id、原始执行日志、结构约束文件路径、运行目录和内部错误不得出现在 renderer 可见 DTO；页面只接收安全消息、方案、状态和可执行恢复动作。
23. AI 建队消息发送后，用户文字必须在等待所选 CLI 回复期间立即显示为右侧气泡，并在服务端状态返回后无重复地收敛；「正在输入」显示在该用户消息之后。
24. AI 团队设计器在宽窗口下使用约 `780px × 720px` 的响应式上限，窄窗口下不产生页面级横向滚动；2–6 名成员的有效提案不得因 flex 收缩而隐藏成员行，超高内容只滚动对话区。
25. 第 3 步在宽窗口下使用约 `780px` 的响应式主体，完整显示所选团队名称和 2–6 名成员的角色标签；默认 `1180 × 760` 桌面窗口中的标准六棒完成态无需手动滚动即可全部可见。短窗口或更长脚本优先只让时间线内部滚动，必要时由步骤主体独立滚动；卡片标题、重新播放和完成说明保持可达，固定底部操作 footer 始终可见且不得覆盖主体内容。
26. 已完成用户从侧边栏进入回看时，标题栏显示「回看引导」和「退出」，第 4 步仍显示「开始使用」；退出或点击「开始使用」后恢复进入前的操作台状态，完成 marker 的内容和时间保持不变，回看所选团队不成为下一次新建对话的默认预选。
27. 可选 CLI 安装开始后，只要另一套 CLI 已可用，用户可离开第 1 步且安装在应用存活期间继续；单项安装显示 CLI 名称，双安装显示聚合数量，详情逐项提供阶段和取消入口，任务结束时按真实结果降级或收起。关闭应用时必须列出仍在运行的任务，并允许留在应用或取消全部仍在运行的安装后退出；确认期间已结束的任务保留真实终态，取消、超时和崩溃不得留下孤儿进程或伪成功状态。
28. 第 2 步若所选团队包含绑定未就绪 CLI 的成员，团队卡必须显示受影响成员数与 CLI，并指明之后可在 Agent 团队页调整；提示不得静默替换成员 CLI，也不得把第 1 步门槛提高为两套都就绪。
