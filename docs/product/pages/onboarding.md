## 页面目标

首启引导不是欢迎，是一次让新用户「信这支团队会替我接力」的最短演示——从环境就绪、看见团队、看它怎么协作，到知道任务结束后不必一直盯着窗口，再确认准备开工。

走完引导，用户带走的不是「配置完成」的绿勾，而是**「这支团队会替我接力，我不必当中转站」**的认知。

引导每台电脑只出现一次；走完最后一步落进[主页面会话区](./main-conversation.md)的新建对话形态，此后再打开应用不再重复。

## 用户场景

- 用户下载 moebius 并首次打开，此前用过 Codex、Claude Code 或 Kimi，还没试过多 Agent 团队协作。
- 用户只有 DeepSeek 等受支持服务商的 API Key，没有安装任何编码 CLI，也应能完整走完引导、使用 AI 建队并开始第一个团队任务。
- 用户在同一台电脑上曾完整走完引导，重开应用应直接进主页面，不重复。
- Codex、Claude Code、Kimi 任一未装或不可用时，用户在第一步就得到对应的独立安装或登录指引；只要其中一个可用就能继续，不必为了另外两套 CLI 阻断首次体验。
- 用户走完引导后自然落入新建对话页，此时项目仍为空——加项目由那页承接，不是引导的职责。

## 入口与去向

### 入口

- 应用首次启动，数据根中没有包含有效 ISO 完成时间的 `.onboarding-completed` marker 时自动进入。
- 已完成引导的用户可从主页面侧边栏底部的“重新查看引导”主动进入回看模式。
- 引导期间侧边栏不出现，主内容区就是引导本身。
- 中途关闭应用后重开，重新从第 1 步开始；引导完成后才写完成 marker。

### 去向

- 首次启动走完第 5 步点「开始使用」，落进[主页面会话区](./main-conversation.md)的新建对话形态。
- 落到新建对话页时项目仍为空，由该页承接添加项目。
- 落到新建对话页时**引导中所选定的团队应等同于「上一次成功创建会话时使用的团队」**（见 [agent-teams.md:361](./agent-teams.md)），作为该对话的默认预选团队。
- 回看模式可随时退出；点击标题栏「退出」或第 5 步「开始使用」都返回进入前的主页面状态，不把回看中选中的团队交给新建对话。

## 页面结构

引导为一屏一步的全屏页，共五步；应用启动即引导，本身不占屏而是一次跳转。

### 每步共用的应用标题栏

```text
┌────────────────────────────────────────────────────────────┐
│ [Moebius 品牌图标] Moebius   [◌ 2 项正在安装]   首次启动   │
└────────────────────────────────────────────────────────────┘
```

五步共用同一应用标题栏。标题栏图标使用[总 PRD](../prd.md#品牌与发行平台)规定的品牌母版派生图像，不使用图标库中的通用无限符号；图标、品牌名和“首次启动”只负责稳定标识应用，不参与步骤进度或状态表达。安装聚合状态只在有后台安装时出现，位于品牌区与右侧身份区之间，不替换“首次启动”、回看身份或退出操作。回看模式把右侧“首次启动”替换为“回看引导”，并在同一区域提供“退出”按钮。下列步骤结构图从标题栏下方开始。

### 每步共用的内容与操作骨架

```text
┌────────────────────── 可滚动步骤主体 ──────────────────┐
```

全局步骤操作恢复为固定占据窗口底部的全宽 footer，与中间可滚动步骤主体分离且不覆盖内容。footer 内部沿用最大约 `780px` 的响应式对齐边界并整体右对齐；它只承载操作按钮，不承载第二套步骤进度。窄窗口下主体和 footer 内部框架一起缩小到可用宽度。

### 应用启动 → 直接进第 1 步

不是屏。应用启动检测到本机从未完成引导时，主窗口直接渲染第 1 步而不是新建对话页。原「首启即落新建对话页」路径被引导替代。

### 第 1 步 · 环境就绪（至少一个执行引擎已就绪）

```text

│                                                            │

│   准备一套 CLI 或添加 API，就可以启动团队                 │
│                                                            │
│    ┌────────────────────────────────────────────────┐     │
│    │  ✓  Codex CLI       可用 · 已登录 · 真实版本   │     │
│    ├────────────────────────────────────────────────┤     │
│    │  !  Claude Code      已安装 · 需要登录          │     │
│    ├────────────────────────────────────────────────┤     │
│    │  ✕  Kimi CLI        未安装                     │     │
│    │      官方 Kimi 一行安装命令                 [▶]│     │
│    │      安装 Kimi（可选，不影响继续）             │     │
│    └────────────────────────────────────────────────┘     │
│                                                            │
│    ┌────────────────────────────────────────────────┐     │
│    │  ◆  DeepSeek API     已就绪 · deepseek-chat    │     │
│    │      模型回复与工具调用已通过                  │     │
│    ├────────────────────────────────────────────────┤     │
│    │  ＋ 添加 API 服务商                            │     │
│    │      只需选择服务商、填写 Key 和模型           │     │
│    └────────────────────────────────────────────────┘     │
│                                                            │
│                                                            │
│                         [ 重新检查 ] [ 继续 ]              │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

CLI 区三行先分别执行 Codex、Claude Code 与 Kimi 的 `--version`，再由引导自己的 readiness service 调用各 CLI 的只读能力探针。Kimi 的发现必须与真实 runtime 使用同一个 PATH-first + `~/.kimi-code/bin/kimi` 默认位置 resolver；PATH 首个现有候选为权威候选，不可执行时不得改用默认位置。Kimi 的版本检查与 `provider list --json` 必须使用该次解析出的同一绝对路径，不能在能力探针阶段退回 GUI PATH 中的命令名。Codex 与 Kimi 沿用已有登录 / provider 与真实可用模型枚举；Claude Code 执行 `claude auth status --json`，以机器可读退出状态确认登录，不发送推理请求，也不动态枚举模型，Agent 团队页的内置静态 registry 负责提供 Claude 可选模型。Codex CLI 的最低兼容版本是 `0.145.0`；Claude Code 的最低兼容版本是 `2.1.170`，因为完整对等范围中的 AI 建队隔离依赖 `--safe-mode`，且首版静态 registry 中的 Fable 要求该版本，不能只按更早出现的认证命令判定整套能力 ready。低于对应基线时直接显示真实已安装版本和最低版本升级指引，不再启动能力探针。只有版本满足兼容基线且对应能力探针成功，才显示绿色「可用」；只通过版本检查只能说明“已安装”，不得承诺 Agent 可以启动。CLI 准备检查不得发送真实对话、产生模型调用费用、修改项目文件或打开交互式登录流程；Agent 团队管理页不复用或触发这项检查。

正式 Electron 页面在可用行显示**该 CLI 最近一次成功版本检查得到的真实版本文本**；页面生命周期内每次完整准备检查——包括首次检查、某一套 CLI 安装完成后的自动复检和手动「重新检查」——都以当次结果整体替换该行旧值，不得使用硬编码版本、占位版本或缓存中的旧版本。三行可以并行检查，同一行内部按“版本 → 执行能力”顺序收敛；较早发起的旧结果不得覆盖同一行较晚发起的结果。

若评审表面没有连接真实检测（包括本 PRD 字符图、独立 HTML 原型和 Storybook），CLI 只显示不含具体版本号的通用状态，API 档案只显示确定性 mock 的服务商、模型和验证状态，不得冒充真实检测结果。「重新检查」只刷新三套 CLI；API 档案使用自己的验证或修复动作。任一 CLI 可用或任一 Pi Provider 有效状态为“已就绪”后「继续」立即可点，其他行仍保留独立的安装或修复指引。

```text
│    │      官方 Claude Code 安装命令              [▶] │     │
│    ├────────────────────────────────────────────────┤     │
│    │  ◌  Kimi CLI 正在安装…                         │     │
```

缺失行展示当前官方的一行安装命令：

- Codex：`npm install -g @openai/codex`
- Claude Code：`curl -fsSL https://claude.ai/install.sh | bash`
- Kimi：`curl -LsSf https://code.kimi.com/install.sh | bash`

命令旁的播放按钮具有对应的可访问名称「安装 Codex CLI」「安装 Claude Code」或「安装 Kimi CLI」。点击后直接开始执行该行对应的受信任安装动作，不再弹出第二次确认；按钮立即变为不可重复触发的进行中反馈，行内持续显示「正在安装」和阶段性活动提示，不能让用户面对静止界面猜测是否生效。安装成功后该行自动执行完整准备检查：尚未登录时进入“已安装，需登录”，登录就绪时才进入可用；安装失败或超时后保留该 CLI 的独立失败说明和重试按钮，不展示原始 stderr、本地路径、令牌或安装脚本内部细节。

安装动作只能来自应用内随版本发布的受信任 registry，禁止接受页面文本、团队文件或外部输入提供的任意命令。Claude 安装动作必须把固定 URL 的下载与 `bash` 执行作为两个参数化子进程通过 Node 流连接，保持 `shell: false`，不得把页面文案拼接为 shell 命令。上面三条命令是当前 macOS arm64 发行基线；每次正式发版前必须对照 Codex、Claude Code 与 Kimi 官方安装文档校准包名、URL 和参数，若官方入口变化则与应用一起更新，不在运行时远程下发替换命令。

每套 CLI 只有在操作系统明确报告可执行文件不存在（`ENOENT` / `ENOTDIR`）时才进入缺失态。版本命令非零退出、存在但不可执行（如 `EACCES`）、其他启动异常，以及退出码为 0 但没有返回非空版本文本，都进入该 CLI 已安装但不可运行态。Codex 返回可解析但低于 `0.145.0`，或 Claude Code 低于 `2.1.170` 时进入“需要升级”，显示真实版本与最低版本，不误报为缺失或登录问题，也不继续执行能力探针。Claude 需要升级行提供受信任的「更新 Claude Code」动作；renderer 只能提交固定 update 枚举，主进程对刚刚解析出的同一绝对路径执行参数化 `claude update`，保持 `shell:false`，成功后只复检 Claude。版本正常、执行能力探针确认没有登录 / provider 配置时进入“已安装，需登录”；能力协议超时、异常，或 Codex / Kimi 没有真实可用模型时进入“暂时无法验证”。除 Claude 的固定更新动作外，这些状态只给出对应升级 / 登录 / 排障指引和重新检查，不显示安装命令；底层结果不得把原始 stderr、异常文本、本地路径、provider 密钥或令牌交给 renderer。

第 1 步是**“至少一个执行引擎已就绪”的硬门**：Codex、Claude Code、Kimi 与 Pi API 都没有达到各自完整就绪条件时不能进第 2 步，「继续」保持 disabled；任一 CLI 完整准备检查通过，或任一 Provider 真实能力验证成功后立即放行。进行中的 CLI 安装或 API 验证都不锁住其他已经就绪执行引擎对应的「继续」，用户离开本步后进行中状态不得伪装为成功。

### 第 1 步 · 添加或修复 API Provider

点击“添加 API 服务商”后仍留在第 1 步，在普通步骤主体内切换为 Provider 表单；不打开外部网页，也不要求用户先安装 CLI。

```text
┌──────────────────────────────────────────────────────┐
│ ← 返回环境准备            添加 API 服务商            │
│                                                      │
│ 服务商                                               │
│ [ DeepSeek ▾ ]                                       │
│                                                      │
│ 档案名称                                             │
│ [ DeepSeek ]                                         │
│                                                      │
│ API Key                                              │
│ [ 输入 API Key                                    ] [显示] │
│                                                      │
│ 模型                                                 │
│ [ deepseek-chat ▾ ]                                  │
│                                                      │
│ 提交后会发送固定测试内容并产生极少量 API 用量。       │
│ 验证不读取项目；真实任务会把必要项目内容、附件和       │
│ 工具结果发送给所选服务商。                           │
│                                                      │
│                         [取消] [验证并保存]           │
└──────────────────────────────────────────────────────┘
```

- 服务商只能从 Moebius 明确列出的目录选择，至少包含 DeepSeek；表单不显示 Base URL、自定义地址或任意模型 ID。
- 同一服务商可以有多个档案，但档案名称必须唯一。已有档案以服务商、名称、默认模型和“已就绪 / 需要处理 / 已停用”状态显示，完整 Key 永不回显。
- “验证并保存”先在 Moebius 自带的隔离测试空间中发送固定内容并调用无项目副作用的受控工具。验证成功必须分别显示“模型回复已通过”和“工具调用已通过”，随后进入独立的“正在安全保存”状态；只有凭据和档案元数据作为同一份结果保存并重读成功后，才显示“已就绪”并计入环境门槛。
- 验证失败保留当前表单和 Key 输入，区分 Key、模型兼容、额度或限流、服务暂不可用和无法确认等安全类别；不显示原始响应、内部地址或完整 Key。验证已经通过但本地保存失败时，显示“两项验证已通过，但未能保存；尚未创建档案”，不重复产生验证用量，并在当前表单生命周期内提供“重试保存”。保存重试仍失败或用户离开时，不留下凭据、元数据或引用半成品；未保存 Key 立即从内存丢弃，重新进入必须再次输入并重新验证。
- 验证进行中，返回、取消或关闭引导必须先说明服务商可能已经处理并计费。用户确认离开后停止本地等待、丢弃未保存 Key，只保留服务商、档案名称和模型草稿；重新进入需要再次输入 Key。
- Key 失效、Key 无法读取或模型仍在支持目录内但不可用等“可修复”问题复用同一表单。旧有效版本仍存在时，新 Key 或模型的验证与保存是叠加活动，不影响其他 Agent 继续使用旧版本；新版本保存并重读成功后才原子替换。
- 服务商已从支持目录移除时，档案虽然同样显示“需要处理”，但不得进入旧服务商修复表单。页面说明“该服务商已不再支持，请先添加另一服务商；现有成员和会话稍后可在设置中迁移”，提供“添加新的 API 服务商”和“暂时跳过”，不在 onboarding 承担跨服务商迁移。

- 新装用户在这一步看到两支内置团队：开发团队与通用助手。内置开发团队可用时默认选中它；开发团队不可用时选中通用助手；两支都不可用但存在可用的其他团队时，按当前稳定列表顺序选中第一支。只有完全没有可用团队时保持未选择并禁用「继续」（见 [Agent 团队](./agent-teams.md#内置团队与上游)）。
- 搜索框与当前可用团队总数始终显示，不因团队数量少而隐藏；没有搜索词时显示「共 n 支团队」，有搜索词时显示「匹配 m / 共 n 支团队」。这里的总数与匹配数都只计算当前可用于创建对话的团队，不把需要修复、未完成或读取失败的团队伪装成可选项。搜索按团队名称、描述和成员可读名称即时过滤，不匹配内部 slug 等只供机器使用的信息。
- 团队按「内置团队」和「我的团队」分组，内置团队在前；空分组不显示标题。搜索结果仍保留分组归属，不把不同来源的同名团队混成一组。
- **这里的分组标题不跟随 [Agent 团队](./agent-teams.md#跟随上游与只在本地)的「跟随上游 / 只在本地」。** 引导时用户通常只有两支团队、全在同一组，分组标题几乎不起作用，而「上游」这个概念在第一次开机时是纯噪音。两种说法各自成立：这里说的是它们此刻从哪来（软件自带），团队页说的是它们今后怎么变（跟不跟随上游）。
- 团队总数显示为「共 2 支团队」，不因为数字小而隐藏。把计数藏起来就是遮掩，与官网首屏「我们只带两支团队」的立场自相矛盾。
- 第 2 步团队区使用标题、搜索与固定底部新建入口之间的全部剩余高度。只有中间团队列表纵向滚动，页面标题、搜索、团队总数、「跟 AI 聊出一支新团队」和全局步骤 footer 始终可见；不得用固定 `max-height` 把列表压成只够一两张卡的矮容器。
- 搜索词不匹配当前已选团队时，滚动列表顶部额外固定显示「当前选择」及该团队卡，后面才显示匹配分组，保证用户在点击「继续」前始终看得到实际将使用的团队；当前选择本身匹配时不重复显示。完全无匹配时在当前选择之后显示「没有匹配的团队」。过滤条件不得取消或改写用户已经选中的团队。
- 搜索框提供可键盘操作且具有可访问名称的清空按钮；输入框聚焦时按 `Escape` 也会清空，并把焦点保留在输入框。团队卡使用可读的选中状态，选中后辅助技术得到「已选择 <可辨认团队名称>」反馈。AI 建队创建成功返回列表时自动清空搜索、选中新团队并把焦点移到新团队卡，不能让旧搜索词立即隐藏新结果。
- 同名团队直接复用[主页面会话区的团队辨认契约](./main-conversation.md#团队按钮展开)：始终显示完整名称与来源，跟随上游的团队用 `owner/repo`，同名且同为只在本地时用本地创建时间；不得显示 slug、数据库 ID、文件路径或临时序号。
- 团队目录加载时保留第 2 步框架和团队列表占位，搜索、AI 新建团队入口与「继续」暂时禁用；读取失败时在列表区域显示不同于搜索无结果的失败原因和「重试」，并继续禁用上述操作。需要修复、未完成或其他不可用于新建对话的团队不进入选择列表；若存在这类团队，可提示用户完成引导后前往 Agent 团队页处理，但不在 onboarding 复制修复操作。没有任何可用团队时显示应用配置异常和重试，不允许继续或以 AI 建队掩盖目录异常。
- 团队卡根据本次环境准备结果标出不可用执行配置。不可用包括 CLI 未就绪、Pi Provider 需要处理或已停用、服务商已移除和成员模型不可用。卡内显示受影响成员数量、原因和“改用已就绪 API”；用户选择 Provider、有效模型和该模型实际支持的思考程度，查看逐名成员的替换结果并一次确认后，只改这些成员之后的新会话。用户也可以暂不替换并继续，不静默改写团队，也不推翻第 1 步“至少一个执行引擎已就绪”的门槛。
- “改用这个 API”是一次原子批量修改。确认后卡片进入“正在更新 n 名成员”，禁止重复提交和离开本卡的第二次替换；全部成员配置保存并重读成功后才一起显示新档案、模型和“已更新”。任一成员保存或重读失败都回滚本次全部修改，卡片恢复原受影响清单，显示“未更改任何成员”和可重试入口，不得出现半支团队已经改绑的状态。
- 次卡「跟 AI 聊出一支新团队」进入第 2 步内部的建队子流程；标题区仍显示「第 2 步，共 5 步」，不跳到独立页面或 Agent 团队页。
- 次卡下方一行文字出口：「以后还能从 GitHub 装别人做好的团队」。它只告知，不带按钮，也不跳转。
- **引导里不做 GitHub 搜索。** 这一步的目标是让用户相信这支团队会替他接力；在里面塞进搜索、限流防抖、`AGENT.md` 全文预览和安装，会把一次演示变成一次配置。发现与安装留在 [从 GitHub 找团队](./github-team-discovery.md)，从 Agent 团队页进入。
- AI 建队、从空白开始、复制并编辑、从 GitHub 装一支是四条并列的创建路径。前三条产生只在本地的团队，第四条产生跟随上游的团队；只有前三条在引导里可达。AI 建队不取代熟练用户的空白创建，也不取代从已有团队派生变体的复制能力。

- 首问固定聚焦长期工作目标：「你希望这支团队长期替你完成什么工作？」并补充“先说目标就好，不需要想好角色和分工。”用户不需要先提供成员名称或组织结构。
- 信息足够时直接给团队方案；只有缺少会改变成员构成的关键信息时，AI 才每轮追问一个问题，不为显得周到而继续采访。
- AI 建队进入子流程时列出第 1 步全部已就绪执行引擎，包括 ready CLI 和已就绪 Pi Provider。默认保持 `Codex → Kimi → Claude Code → Pi API 档案顺序`选择第一项，但开始首轮前用户可以明确选择；纯 API 用户直接预选其第一份已就绪档案。首轮发出后冻结执行引擎、Provider 和模型，不因其他引擎后来可用而静默切换。
- Key 或额度问题修复后继续使用同一冻结执行会话。冻结模型或服务商被移除时，页面保留 Moebius 建队对话和最后有效方案，要求用户明确选择另一已就绪模型或 Provider；旧外部会话封存，新 Pi 会话从已保存可见上下文重建，并显示“已更换模型或服务商，AI 原生上下文已重新建立”。
- 方案必须包含团队名称、一句话用途、2–6 名成员、唯一主 Agent、每名成员的稳定 slug 与可生成完整 `AGENT.md` 的结构化职责、克制与启用条件、交接规格，以及一段供第 3 步播放的协作示例。成员职责必须互斥且具体，克制与启用条件写明不做什么、昂贵方法（真实运行验证、截图比对、全量回归等）只在什么条件下启用；主 Agent 必须区分用户在场迭代（就地验证、直接回复）与用户收尾交付（完整验收与提交）两种模式。onboarding 方案卡显示 `@slug`，让用户在创建前看见后续可点名的稳定身份；协作示例属于独立的引导编排数据，不属于团队结构、成员职责或真实运行规则。
- 提案卡在“创建并选中”前必须同时显示每名成员将保存的初始运行配置。默认把用于设计团队的执行引擎应用给全部成员：CLI 保存对应 CLI、模型与可用思考程度；Pi 保存 Provider 档案身份、服务商、已验证模型和该模型实际支持的思考程度。若模型没有可控思考档位则不显示选择器并使用目录规定的固定值，不伪造 Codex 档位。用户可以用“更改”把全部成员统一切换到另一项已就绪配置；本引导不提供逐成员混搭，创建后可在 Agent 团队页逐名调整。展开成员清单时，每一行都重复显示最终执行引擎、Provider（如适用）、模型和思考程度，不能只显示一条含糊的团队默认值。
- AI 团队设计器是第 2 步内的响应式工作区，不沿用普通步骤约 `512px` 的窄栏上限：宽窗口下最大宽度约 `780px`、最大高度约 `720px`，并随可用窗口缩小；窄窗口继续占满可用宽度并由引导主体承担页面级滚动。
- 团队提案卡必须按内容完整占位，展示全部成员、`@slug`、主 Agent 与接力关系；提案卡自身不得在纵向 flex 布局中被压缩裁切，也不设置第二层内部滚动，超出设计器可视高度时只滚动对话区。
- 用户可以点击「继续聊着调整」并用自然语言修改方案。只有点击「创建并选中」才创建正式用户团队；此前的对话和方案不是团队，也不出现在 Agent 团队首页。创建必须把提案和当时逐名可见的初始运行配置作为同一份原子结果保存，任一成员配置失败都不登记团队。
- 「返回选团队」只退出第 2 步的建队子流程，不是五步引导的全局回退；再次进入时恢复尚未确认的对话与最后一版有效方案。
- 创建成功后回到第 2 步团队列表，新团队成为当前选中项；随后「继续」进入第 3 步。

```text
┌────────────────────────────────────────────────────────────┐
│                                                            │
│                  第 3 步，共 5 步                          │
```

演示对象**必须是第 2 步所选的团队**，而不是通用的多 Agent 概念动画。默认开发团队演示「开发经理安排工作 → 开发定位并修复 → 测试指出问题并退回修改 → 开发修改 → 测试再次通过 → 开发经理交付结果」这一条约 10 秒的连续协作；AI 创建的团队使用已确认方案中同时生成并通过校验的协作示例，不退回硬编码的开发团队角色。协作示例以团队目录中的独立 `onboarding-orchestration.json` 保存，不写入 `team.json`，不进入团队登记缓存、身份指纹、团队可用性判断或真实会话 prompt；真实运行只依据主 Agent、成员名单及各自 `AGENT.md` 灵活调度。画面左侧借用 Git graph 的节点与连接线语法：团队成员只提供横向位置，每次发言在对应成员位置产生节点，连接线只连接相邻两次发言，不得用贯穿全程的角色竖线暗示某个成员持续持有控制权；右侧消息与左侧节点逐行对齐。已经发生的步骤在同一舞台里留下完成记录，问题、修改和复核结果不能随焦点移动而消失。用户可以重新播放，也可以不等动画结束直接继续。减少动态效果模式下不做持续位移，改为逐步淡入和静态高亮，信息与正常模式等价。

第 3 步是普通窄栏之外的响应式宽版舞台：宽窗口下主体最大宽度约 `780px`，并使用更多可用高度，让团队名、2–6 名成员的角色标签、接力轨迹和标准六棒记录不再争抢约 `512px` 的窄栏。成员轨道保持稳定且等宽；宽窗口完整显示角色标签，窄窗口才降级为短标签。默认 `1180 × 760` 桌面窗口中的标准六棒完成态无需手动滚动即可全部看见；窗口高度不足或协作示例更长时优先只滚动卡片内的时间线，必要时由步骤主体独立滚动，卡片标题、重新播放、完成说明和固定底部步骤 footer 始终保持可达。该规则只改变第 3 步主体，不强制改变桌面窗口默认尺寸。

升级前创建的团队可能没有独立编排文件，升级过渡期创建的团队也可能仍把 `relayBeats` 内嵌在 `team.json`。两者都不能让团队列表、团队可用性或真实会话失败：内嵌数据应被兼容读取并在后续安全写入时迁出，完全缺失或独立文件损坏时第 3 步只在演示卡内显示“暂无可播放的协作示例，不影响这支团队的实际使用”，保留“上一步”和“继续”，不得加载其他团队的脚本或伪造协作记录。

```text
│    │  任务提醒                            已开启      │     │
│    │  macOS 通知                         尚未开启      │     │
│    │  通知可能显示对话名称和“已完成／正在等待你”    │     │
│    └────────────────────────────────────────────────┘     │

└────────────────────────────────────────────────────────────┘
```

这一页只请求 macOS 系统通知权限，不再放一份应用内总开关，但必须同时读取并展示应用内「任务提醒」总开关的当前真实值。新用户总开关默认开启，之后由[设置](./settings.md)「常规」统一控制；回看模式不得把“默认开启”当成当前值。侧边栏状态点始终保留，不受权限和总开关影响。

授权前必须用用户语言说明通知只在每轮进入「已完成」或「正在等待你」时出现，运行、交棒和中间状态不会通知；系统通知可能显示现有应用内对话名称。页面不展示原始任务正文、项目路径、成员过程或错误详情，也不发送测试通知。

- 权限尚未由用户选择时，页面显示「尚未开启」，主操作为「允许系统通知」。点击后只发起一次系统权限请求；系统返回允许或拒绝后先停留在第 4 步，分别显示任务提醒和 macOS 通知的最新真实状态，再由用户点击「继续」进入第 5 步，不因拒绝阻断使用。
- 「暂时不要」不触发系统权限请求，页面继续显示“尚未开启”，直接进入第 5 步，也不修改任务提醒开关。按钮前必须明确说明：“暂时不要不会关闭任务提醒；下次需要提醒时会再次询问。”只有任务提醒关闭时才不会出现发送时询问。任务提醒开启但尚未获得系统权限时，侧边栏和 Dock 仍然可用，系统通知与声音不可用；任务提醒关闭时，系统通知、声音与 Dock 均停用，只有侧边栏状态点保留。
- 权限已允许时显示「已允许」，主操作改为「继续」，不重复请求。任务提醒开启时说明系统通知、声音和 Dock 已按各自系统策略工作；任务提醒关闭时说明“macOS 通知已允许，但任务提醒仍处于关闭状态”，不得声称系统通知、声音或 Dock 当前可用，也不得自动开启任务提醒。
- 权限已拒绝或受系统策略限制时显示「已拒绝」，说明仍可继续使用，并明确写出之后可到「设置 → 常规 → 任务提醒」查看状态和打开 macOS 通知设置；本页不循环弹系统请求。
- 系统不支持通知、权限读取失败或权限请求无法启动时，显示「暂时无法使用系统通知」。总开关开启时说明侧边栏和 Dock 仍可工作；总开关关闭时只说明侧边栏状态点保留，系统通知、声音与 Dock 均停用。提供「重新检查」与「继续」；重新检查只刷新总开关、能力与权限状态，不发送测试通知，用户继续后进入第 5 步。
- 应用在系统权限弹窗显示期间不接受第二次请求，按钮显示「等待 macOS 确认」并锁定冲突操作。等待由用户在 macOS 弹窗中的允许或拒绝结束，不设会替用户作决定的倒计时；只有系统明确返回结果或请求调用失败时才离开等待态，请求失败不冒充拒绝或允许。

总开关关闭时，标题改为「任务提醒已关闭」，副本改为「如需重新接收提醒，请前往设置开启」。权限允许、拒绝或暂不可用都只改变 macOS 通知行，不改变任务提醒开关；用户若要重新启用提醒，页面明确指向「设置 → 常规 → 任务提醒」，不在引导内复制开关。

## 操作与反馈

### 前进

- 每步主 CTA 前进到下一步；首次启动第 5 步主 CTA 出引导并落到新建对话页，回看第 5 步主 CTA 则恢复进入前的操作台。
- 上一步的成果携带到下一步：第 1 步的通过状态、第 2 步的所选团队都对下一步继续有效。
- 高保真单 HTML 中的五步前进和第 5 步「开始使用」全部在同一文件内切换可见状态。首次启动的最后一步必须直接渲染出新建对话形态并让所选团队肉眼可见；回看的最后一步必须恢复确定性的进入前主页面展示态且不应用临时团队选择。两种模式都不调用正式应用路由，不以提示框或完成文案代替去向。

### 回退

- 第 2–5 步提供「上一步」，第 1 步不显示回退入口。
- 返回时保留已通过的环境状态和已选择的团队，不清空用户已经完成的选择。
- 从第 4 步返回第 3 步时，接力演示从第一棒重新播放，避免停在一个缺少前序上下文的中间画面；从第 5 步返回第 4 步时只读取系统当前权限状态，不重放系统请求。
- 第 2 步 AI 建队子流程另有「返回选团队」，只退出同一步的子流程，并保留未确认的建队对话与方案。

### 中途关闭

应用关闭 = 中断引导。因为完成 marker 尚未写入，下次打开重新从第 1 步开始；本版不持久化五步内的临时步骤、团队选择或未保存 Provider 表单。系统通知权限属于 macOS 持久事实，不随引导重开而重置，也不得在已允许或已拒绝时再次弹请求。此前已经验证并保存的 Provider 档案属于全局设置，关闭引导或重新开始时仍然存在并按真实有效状态展示。AI 建队草稿是唯一例外：已发送的对话、最后有效方案、逐名初始运行配置、所选设计执行引擎和 external ID 作为可恢复草稿持久化，避免多轮投入随应用退出丢失。

若应用关闭时仍有一项至三项 CLI 安装在进行，先提示“CLI 仍在安装”，逐项列出仍在运行的 CLI，并提供「留在应用」与「取消全部安装并退出」。取消只作用于确认时仍在运行的受控安装进程；已在确认期间成功、失败或超时的任务保留其真实终态，不回退成“已取消”。应用等待所有取消请求收敛后再退出，不能留下界面已关闭但安装仍在后台静默运行的孤儿进程；若确认期间已没有运行任务，则直接继续原退出动作。应用崩溃时下次启动按重新检查结果恢复，不把上次进行中状态当成成功。

若应用关闭时 API 验证仍在进行，同一退出确认必须说明服务商可能已经处理请求并产生用量。确认退出后停止本地等待并丢弃未保存 Key；远端请求即使已经送达也不得在应用重启后把迟到结果保存成档案或伪装为验证成功。若该操作是在修复已有档案，旧有效版本继续保持原状态。

正常关闭或崩溃后重新打开，用户仍从第 1 步开始；完成环境门槛并回到第 2 步时，“跟 AI 聊出一支新团队”卡显示“继续上次草稿”和最后更新时间。进入后恢复已发送对话、最后有效方案、逐名初始运行配置与原 external ID；未发送的输入框文字不保证恢复。关闭时尚在运行的一轮一律显示“上次处理已中断”，不得把迟到结果当成成功，也不得自动发起新请求；用户点击“重试”后从同一执行会话恢复。若冻结配置已经不可用，则进入已定义的迁移或结束草稿路径，不静默换引擎。用户可以明确“放弃草稿”，二次确认后删除该草稿及其继续能力；已保存 Provider 档案不受影响。

回看模式不改变完成 marker；中途关闭应用后，下次启动仍按已完成用户直接进入主页面，不会被回看进度拦回引导。

### 重新查看引导

- 回看复用完整五步内容与交互，但只作为当前 renderer 生命周期内的临时展示态。
- 进入回看时保持原操作台挂载；点击「退出」或第 5 步「开始使用」后恢复进入前的项目、对话、草稿、侧边栏和应用页面状态。
- 进入回看、点击「退出」和第 5 步点击「开始使用」都不得删除、覆盖或重写 `.onboarding-completed`，也不得更新“上一次成功创建会话所用团队”或生成 pending team 选择。
- 回看中的团队选择只服务本次第 3 步演示。AI 建队仍是用户显式确认后才发生的独立创建操作；第 4 步只读取或申请系统通知权限，不改应用内总开关；第 5 步点击「开始使用」只结束回看，不创建、修改或选定持久化团队。

- 播放按钮点击后立即进入 loading，行内持续提供活动反馈；同一 CLI 安装未结束前不得重复启动，另一行的检测、安装和修复入口仍独立可用。
- 若其他 CLI 已经可用，用户可以在可选 CLI 安装期间离开第 1 步。一项安装运行时，标题栏中间安装状态区以 `◌ 正在安装 Kimi…` 这类轻量全局状态持续反馈；多项并发时显示 `◌ n 项 CLI 正在安装…`。点击后展示同一个安装详情列表，并逐项显示 CLI、实时阶段与取消入口；仍在引导内时可从详情定位回第 1 步，已进入操作台时由全局详情承接，不得启动第二份同 CLI 安装。单项完成后聚合状态按剩余数量更新，全部结束后按各自真实结果给出一次完成或失败反馈再收起。
- 返回第 1 步时恢复当前进程的实时阶段和取消入口，不从初始 loading 重新计时。取消、失败、超时只影响对应 CLI；取消采用明确按钮和确认文案，避免把误触当成安装失败。
- 安装成功后只自动复检对应 CLI；失败或超时时只更新对应行，保留另一行状态与整个页面的可继续判定。成功安装但尚未登录时给出对应登录指引，不显示为绿色可用。
- 手动「重新检查」同时刷新三行。刷新期间保留最后一次明确的可用结果来避免 CTA 抖动，但本次检查结束后必须以新结果整体替换；乱序旧结果不得回写。
- 同一 CLI 的安装、自动复检与手动复检共用单调递增 revision：安装未结束时手动复检可以报告当前磁盘事实，但不能结束或覆盖安装任务；安装结束后的自动复检只在仍为最新任务时提交。所有状态变化通过可读文本和 `aria-live="polite"` 公告，不能只依赖旋转图标或颜色。

### 第 2 步 AI 建队

- 创建建队草稿前列出全部已就绪执行引擎，并按 `Codex → Kimi → Claude Code → Pi API 档案顺序`提供默认项；用户可以在首轮前选择。草稿保存这次选择，后续调整、重试和恢复都继续使用同一执行引擎，不静默跨引擎降级。
- 每个建队草稿拥有该执行引擎的唯一独立执行会话：Codex 草稿使用独立 Codex thread，Claude 草稿使用独立 Claude Code session，Kimi 草稿使用独立 Kimi session，Pi 草稿使用独立 Pi session。草稿第一次执行允许创建；取得 external ID 后，submit、adjust、retry、恢复和唯一一次结构修复都必须 resume 同一个 ID。只有模型或服务商明确下线、且用户选择迁移时，才封存旧 ID并以 Moebius 已保存上下文建立新的 Pi session。创建成功并结束该草稿后，下一次建队使用新的 draft 和新的 provider session，跨草稿不得 resume。
- 页面展示的已发送对话、最后一版有效方案、逐名初始运行配置和状态由应用持久保存；CLI 或 Pi 执行会话只提供模型上下文，不是产品状态唯一事实源。external ID 一旦取得必须随草稿保留；resume 失败、ID 冲突或 provider 会话丢失时只失败这一次 resume，不清空 ID、不用已保存对话重建、不执行第二次 full / `session/new`，页面准确显示「AI 上下文暂时无法继续，已保留对话和最后有效方案。」并保留「重试」。只有模型或服务商下线且用户明确迁移时，才按前述规则从 Moebius 已保存内容建立新 Pi session。
- 一轮运行中输入框和「创建并选中」不可重复提交；用户可以退出子流程，运行结果返回时只有仍匹配当前草稿和 turn revision 才能提交，过期结果必须丢弃。
- 用户发送每轮消息（目标、追问回答、自然语言调整）后，文字必须立即以右侧用户消息气泡进入对话，不等待所选执行引擎返回结果；AI 处理期间该气泡保持可见并在其后显示「正在输入」指示。服务端返回持久化消息后，本地临时气泡必须无重复地收敛为正式消息，结果返回前该轮不可重复提交。
- 点击「继续聊着调整」后，当前方案卡片转为只读快照：去除高亮描边并收起操作按钮，调整结果返回后方案恢复可确认状态。
- 所选执行引擎超时、进程失败、Provider 失败、恢复失败或输出非法时，页面保留已有对话和最后一版有效方案，显示对应引擎的可重试错误；不得无限自动重试、静默改用其他引擎，也不得把失败推进为已创建。
- 「创建并选中」只接受当前显示且仍匹配 proposal revision 的有效方案。创建期间按钮进入单次进行中状态；失败后回到同一方案并提供重试。
- 创建成功后不得留下未完成团队；失败、取消或应用崩溃恢复时，团队首页不得出现只有部分成员的 AI 团队。

### 第 3 步重播与继续

- 进入第 3 步后演示自动播放一次；「重新播放」会从第一棒重新开始，不改变已选团队。
- 动画播放期间「继续」始终可用。用户继续后立即结束演示并进入第 4 步，不等待剩余动画。
- 动画播完后停在主 Agent 收尾的完成画面，不自动跳到第 4 步，避免用户还没看清就被带走。

## AI 建队技术约束

AI 建队采用**短提示契约 + 结构化输出 + 确定性校验 + 应用状态机**。专业 LLM 可以补全角色内容、职责和协作方式，但不得自行猜测输出协议、权限、状态迁移或提交时机。

### 最小提示契约

固定的高优先级指令只保留模型在生成时必须知道的语义：

```text
你是 moebius 的团队设计器，只负责把用户目标转成团队方案。
缺少会改变成员构成的关键信息时，只追问一个问题；信息足够时直接给方案。
方案必须包含 2–6 名成员、唯一主 Agent、唯一稳定 slug、每名成员的完整职责、克制与启用条件、交棒规格，以及一段可播放的接力示例。
成员职责必须互斥且具体：每个成员只拥有一类结果，写清只做什么；执行与验收必须分离，同一件事不得由两个成员各自重做。
constraints 每条写一句克制规则或启用条件：明确不做什么；昂贵方法（真实运行验证、截图比对、全量回归、外部发布等）必须指定唯一负责成员，并写明只在什么条件下启用，不得默认启用；同一份证据只由一个成员产出，其他成员引用。
主 Agent 的职责必须包含按改动量级选择流程：用户在场持续反馈时就地验证并直接回复用户，不触发内部验收链与提交；用户明确收尾时才进入完整交付、验收与提交。
不得读写文件、运行命令或声称团队已经创建。
只返回指定 schema；phase 只能是 clarifying 或 proposal。
```

不会影响生成内容的约束不继续堆进提示词：

- `phase`、字段类型、必填项与数组形状由所选执行引擎可用的结构化输出约束和应用侧解析共同保证。
- 成员数量、slug 唯一性、主 Agent 引用、接力成员引用、结构化成员字段和应用渲染后的 `AGENT.md` frontmatter 由 TypeScript validator 判定。
- `idle → running → clarifying / proposal / failed → committing → selected` 由应用状态机判定。
- 超时、重试、执行会话连续性、过期响应丢弃和 proposal revision 由 service 层判定。
- 团队目录与记录的原子创建由 team store 判定；所选执行引擎永远不获得团队写权限。

同一条会影响生成成功率的关键规则，提示词负责告诉模型怎么做，schema 负责限制输出形状，validator 负责判断是否真的做到；不得只依赖 validator 反复拒绝模型猜测，从而把流程拖入无界重试。

### 执行引擎边界

- AI 建队复用所选执行引擎的受控 driver，但使用独立 execution profile，禁止直接复用普通 Agent 的高权限执行参数。
- execution profile 使用所选执行引擎能提供的只读能力边界、隔离且不含项目素材的工作目录、结构化输出约束与有界 idle / max-duration timeout；不加载项目 `AGENTS.md`、用户 MCP、Skills 或会改变团队设计器行为的个人指令。
- 固定角色约束使用所选执行引擎的受控指令通道；本轮用户输入只作为用户消息，不与固定约束拼成可互相覆盖的同级文本。
- 所选执行引擎只返回 `clarifying` 或 `proposal` 两类结构化结果。应用在结构解析之外再次做业务校验；校验失败最多执行一次带明确错误列表的修复 turn，仍失败则进入可见、可重试的失败状态。
- 所选执行引擎不直接创建目录、写 `team.json`、写 `AGENT.md`、写 `onboarding-orchestration.json`、登记团队或改变 onboarding 选择。用户确认后，应用把最后一版有效方案的团队核心、成员文件与独立引导编排写入临时团队目录，分别重读校验后再切换为正式用户团队并登记；任一写入或校验失败都不得暴露半成品团队。

## 指标与验收

### 产品指标

- **完成引导 / 打开应用** 的比例（不完成就强关的比例）。
- 从打开 App 到落到新建对话页的中位时长。
- 本次不新增团队搜索埋点，因此搜索使用率、无结果率和搜索后选择成功率暂时不可观测；先以多团队 fixture 的任务完成验证交付，后续若要判断搜索是否降低选择成本，再单独补充指标与埋点。
- 第 1 步 Codex / Claude Code / Kimi 各自的缺失、不可运行、安装启动、安装成功与安装失败率（决定 App 下载页和行内指引是否需要调整）。
- 第 1 步进入 API 配置、开始验证、验证成功、验证失败与主动取消的漏斗，按服务商和安全失败类别聚合，不采集 Key、请求正文或项目内容。
- 没有任何 ready CLI、仅靠已就绪 Pi Provider 通过第 1 步和完成引导的用户比例。
- 第 2 步进入 AI 建队、看到有效方案、确认创建和中途退出的漏斗。
- AI 建队首轮使用的执行引擎分布，以及预选后被用户主动切换的比例。
- 应用重启后看到“继续上次草稿”、实际恢复和主动放弃 AI 建队草稿的漏斗。
- AI 建队每轮超时率、非法输出率、一次修复成功率与可见重试成功率。
- 第 4 步看到权限说明后选择允许、暂时不要、系统返回拒绝和请求异常的漏斗；只记录结果类别，不采集对话名称、通知内容或系统设置详情。

### 验收标准

1. 本机从未完成引导时打开 App，主窗口进入第 1 步而不是新建对话页。
2. 本机曾完成引导时打开 App，直接进新建对话页，不再看到引导。
3. 第 1 步明确显示“至少一个执行引擎已就绪即可继续”。CLI 只有在版本正常且账号、模型等实际启动条件均准备好后才能显示绿色“可用”，只检测到命令不得误报；Pi Provider 只有在页面分别显示模型回复和受控工具调用均通过、且本地保存成功后才能显示“已就绪”。任一执行引擎已就绪后“继续”立即可点，其他 CLI 或档案未准备好、修复中、安装中或验证中都不得阻止继续；全部执行引擎均未就绪时才灰置。CLI 缺失行提供对应官方安装动作和可访问的播放按钮，点击后立即进入不可重复触发的持续反馈；失败或超时后显示脱敏说明和独立重试，需登录或不可验证态只显示匹配的修复指引。
4. 第 1 步只准备 Codex、Claude Code 与 Kimi，不出现 gh / GitHub、Node 或其他 CLI。用户必须能从每行明确区分“可用、缺失、需要升级、已安装但需登录、暂时无法验证”，并看到真实当前版本、最低兼容版本和与该状态对应的唯一下一步。重新检查、安装或更新后只刷新相关 CLI 的最新完整结果，不让旧结果反跳；页面不显示原始错误、本地路径、密钥或令牌，静态评审表面也不冒充真实版本。
5. 用户可在第 1 步添加 Pi API 档案：服务商从明确目录选择且至少包含 DeepSeek，随后只填写唯一档案名称、API Key 与目录内模型；页面不得要求或展示 Base URL、自定义地址或任意模型 ID。提交前必须行内说明固定验证会产生极少量用量且不读取项目，并说明真实任务会把必要项目内容、附件和工具结果发送给所选服务商。
6. “验证并保存”必须依次显示模型回复验证、受控工具验证和本地安全保存三个阶段。前两项均通过后仍不得提前显示“已就绪”；只有保存完成才出现档案并计入门槛。验证失败时保留表单与 Key 输入并显示安全失败类别；验证通过但保存失败时明确显示“尚未创建档案”，在当前表单内提供不重复调用服务商的“重试保存”。离开后未保存 Key 必须丢弃，重新进入需要再次输入和验证；页面任何位置都不回显完整 Key，也不出现凭据或元数据半成品。
7. 第 2 步优先默认选中可用的内置开发团队；它不可用时依次回退到通用助手、第一支可用的其他团队，完全没有可用团队时保持未选择并禁用「继续」。选中状态由 accent 描边 + sel 底 + 蓝色实心圆点表达。搜索框始终显示；无搜索词时显示「共 n 支团队」，搜索后显示「匹配 m / 共 n 支团队」。团队按「内置团队」「我的团队」分组，中间列表使用标题、搜索与固定底部新建入口之间的全部剩余高度并独立滚动。「跟 AI 聊出一支新团队」与其下方「以后还能从 GitHub 装别人做好的团队」一行始终贴住团队区底部，不随团队列表滚走；引导里不出现 GitHub 搜索框或安装入口。搜索不匹配当前选择时，当前选择固定显示在列表顶部；搜索无结果不取消既有选择或隐藏新建入口。清空按钮和 `Escape` 都能清空搜索，团队选中状态可由辅助技术读取；AI 建队返回时清空搜索并聚焦新团队。同名团队沿用新对话团队选择器的来源名称或本地创建时间辨认规则。

33. 第 4 步在系统权限尚未由用户选择时，必须先分别展示“任务提醒”和“macOS 通知”的真实状态，再说明只在「已完成」或「正在等待你」时通知、中间状态不通知，并明确系统通知可能显示应用内对话名称；用户界面不得出现“终局”“投递”“通道”“应用总开关”等内部术语，也不得显示原始任务正文、项目路径、成员过程或错误详情或为了演示发送测试通知。
34. 权限尚未决定时，点击「允许系统通知」只发起一次 macOS 权限请求。等待期间页面显示「等待 macOS 确认」并锁定重复请求、上一步和继续，不设自动代用户决定的倒计时；系统返回允许或拒绝后先回到第 4 步显示两项最新真实值，用户点击「继续」后进入第 5 步，拒绝不得阻断完成引导。请求调用失败时结束等待并显示可重试异常，不得冒充允许或拒绝。
35. 点击「暂时不要」前，页面必须明确说明该动作不会关闭任务提醒：提醒保持开启且 macOS 通知仍未开启时，下次任务完成或需要用户处理会再次询问。点击后不得触发系统权限请求或修改任务提醒开关，用户立即进入第 5 步。提醒开启时，页面准确说明系统通知和声音暂不可用、侧边栏与 Dock 仍然可用；提醒关闭时，页面说明不会再次询问，不得声称系统通知、声音或 Dock 可用，只有侧边栏状态点保留。
36. 组合应用总开关开启/关闭与系统权限已允许、已拒绝、受系统策略限制、系统不支持、读取失败五种确定性状态，从真实引导入口或回看入口到达第 4 步：已允许不重复请求；已拒绝或受限统一显示“已拒绝”并指向「设置 → 常规 → 任务提醒」恢复；系统不支持或读取失败显示「暂时无法使用系统通知」、可重新检查且可继续。页面对系统通知、声音、Dock 与侧边栏的可用性必须与组合后的真实状态一致，所有分支都能到第 5 步并完成或退出引导。
37. 用户在系统权限弹窗出现时关闭应用，重开后仍从第 1 步开始，但到达第 4 步时只读取 macOS 已持久化的真实结果，不把上次等待态当成允许，不因 onboarding 状态重置而清除或改写系统权限。
38. 在默认 `1180 × 760` 与最小支持 `520 × 480` 的真实窗口中，第 4 步的用途说明、对话名称隐私说明、任务提醒、macOS 通知状态和所有可用操作均可见可达，固定 footer 不覆盖主体；键盘焦点顺序为状态说明后的上一步、次操作、主操作，系统返回后焦点落在两项已更新状态，用户继续后再落到第 5 步标题。

## 非目标

本引导明确不做：

- Codex / Claude Code / Kimi 之外的任何 CLI 检查（gh / Node 等）。
- 任意 OpenAI-compatible Base URL、自定义服务商或自定义模型 ID；引导只使用 Moebius 明确维护的服务商和模型目录。
- Provider 档案的完整生命周期管理、跨服务商迁移与模型引用处理；引导只负责首次添加、验证和修复入口，完整管理属于[设置](./settings.md)页。
- 持续任务的费用或用量仪表盘；引导只在真实验证前说明会产生极少量用量。
- 让用户在引导里编辑内置团队的成员或 `AGENT.md`（属于 [Agent 团队](./agent-teams.md)页的职责）。
- 在引导里搜索、预览或安装 GitHub 上的团队（属于 [从 GitHub 找团队](./github-team-discovery.md)与[安装前预览](./github-team-preview.md)）。第 2 步只保留一行文字出口。
- 添加第一个项目（属于[主页面会话区](./main-conversation.md)新建对话形态的职责）。
- 除第 4 步明确限定的 macOS 任务提醒权限外，不做通用授权、隐私政策或用户协议弹层；API 表单内的数据去向与验证用量说明仍是必需信息，不属于该非目标。
- 教用户完整用法——那是官网 / 文档的职责，引导只做「让他信这支团队会接力」这一件事。
- 演示通用的「什么是多 Agent」抽象概念——第 3 步演的是用户刚选的**具体这一支团队**，不做概念铺垫。
