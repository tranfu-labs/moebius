> 范围：定义 Agent 需要用户拿主意时，在输入框上方出现的一份问答表单——它由哪些部分组成、一次问几题、用户如何前进回退和改答、答完发出去的是什么、以及用户不想用它时会怎样。表单出现的时机由 Agent 自己判断，不由产品预设；输入框本身、附件草稿、待发射区与时间线由[主页面会话区](./main-conversation.md)定义。

> 产品基线：[moebius 产品需求文档](../prd.md)

## 页面目标

Agent 经常需要用户拿主意——「要 A 还是 B」「这几件事做哪几件」「还有什么要交代的」。没有表单时，Agent 只能把问题写在正文里，用户读完还得把答案重新组织成一段话打进输入框：问题明明已经问清楚了，用户却要再抄一遍；问题一多，还容易漏答其中一条。

表单让用户点几下就能给出准确、无歧义的回答。

与它冲突时让位的是**表单的表达力**：宁可题型少、样子固定，也不要为了能表达更多情况，而让 Agent 有机会构造出用户看不懂的界面。

## 用户场景

- Agent 做完一段工作，需要用户在两三种收尾方式里选一种才能继续。
- Agent 一次要问好几件事，用户希望一件一件回答，而不是面对一大段问题自己数着答。
- 用户答到第三题才想起第一题选错了，想回去改。
- 用户答到一半去看别的对话，回来想接着答，而不是从头再来。
- 用户看到表单但只想先追问一句别的，不想被表单挡住。
- 用户不用鼠标，全程用键盘答完并发送。

## 入口与去向

### 入口

表单只有一个来源：Agent 在自己的回复里发出它。产品不提供任何预置表单、配置文件或让用户手动召唤表单的入口。

### 去向

- 用户答完发送后，表单变成一条普通用户消息进入时间线，Agent 拿到的是正常上下文。
- 用户不理它，直接在输入框打字发送，表单原地留着。
- Agent 发来新表单时，旧表单被替换。

## 页面结构

表单是主会话底部的一块区域，不是独立页面，也不是弹窗。它固定在输入框上方：

```text
│  … 时间线 …                                        │
├─────────────────────────────────────────────────────┤
│  ┌───────────────────────────────────────────────┐  │
│  │                 表单卡片                       │  │
│  └───────────────────────────────────────────────┘  │
│  [附件草稿 / 文本胶囊 / 待发射区（既有，在表单下方）]│
│  ┌───────────────────────────────────────────────┐  │
│  │  正常输入框                        ＋      ↑  │  │
│  └───────────────────────────────────────────────┘  │
```

越靠近输入框的越是用户自己的东西。表单是外来的，排在最上面，不把用户已经准备好的附件和草稿挤开。

### 表单卡片 · 中间某一题

```text
┌─────────────────────────────────────────────────┐
│  成员          进度                             │
│  ▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁   │
├─────────────────────────────────────────────────┤
│  当前问题标题                                   │
│                                                 │
│  作答区                                         │
│                                                 │
├─────────────────────────────────────────────────┤
│  [上一步]                              [下一步] │
└─────────────────────────────────────────────────┘
```

### 表单卡片 · 最后一题

```text
┌─────────────────────────────────────────────────┐
│  成员          进度                             │
│  ▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁   │
├─────────────────────────────────────────────────┤
│  当前问题标题                                   │
│                                                 │
│  作答区                                         │
│                                                 │
├─────────────────────────────────────────────────┤
│  [上一步]                                [发送] │
└─────────────────────────────────────────────────┘
```

### 三种作答区

每题各自是其中一种，题与题互不相干：

```text
单选              多选              自由输入
( ) title         [ ] title         ┌──────────┐
    description       description   │          │
( ) title         [ ] title         └──────────┘
    description       description
```

### 只有一题时

进度整体不显示，直接是问题加发送——不给用户一个只有一格的进度条看。

```text
┌─────────────────────────────────────────────────┐
│  成员                                           │
├─────────────────────────────────────────────────┤
│  当前问题标题                                   │
│  作答区                                         │
├─────────────────────────────────────────────────┤
│                                          [发送] │
└─────────────────────────────────────────────────┘
```

## 区域与信息

| 区域 | 放什么 | 为什么需要它 |
| --- | --- | --- |
| 卡片外框与进度 | 卡片边界、是哪位成员在问、当前第几题共几题、一条细进度线，每格区分已答与未答 | 知道谁在问、总共几题、现在到哪；跳回去时一眼看见哪几题还空着 |
| 当前问题 | 一题的标题，加上这题的作答区 | 一次只看一题，读题和作答都不用在多组之间跳来跳去 |
| 导航行 | 上一步与下一步；最后一题换成发送 | 能往前走也能回头改；「下一步」和「发送」不同名，用户不会误以为点一下就发出去了 |

问题标题、每个选项的 title 和 description 全部由 Agent 在运行时写，不是产品文案。产品只定下面这些说明位：

| 位置 | 文案 |
| --- | --- |
| 进度 | `1/4`——纯数字，不写成「第 1 题，共 4 题」占地方 |
| 中间各题的前进 | `下一步` |
| 回退 | `上一步` |
| 最后一题 | `发送` |
| 自由输入题的占位 | `写在这里，不写也行` |
| 发送禁用原因 | `至少答一题再发送` |

不给独立的「跳过」按钮。没答时「下一步」照样能点，这本身就说明了不答也行；多一个按钮反而让人以为跳过是件要专门声明的事。

**可访问名称**：卡片区域说明是来自哪位成员的表单；进度整体说明第几题共几题，单个进度格说明第几题以及答没答；每个选项包含它的 title 和 description；三个动作分别是「下一步」「上一步」「发送你的回答」。

## 操作与反馈

### 作答

- 单选、多选都点整行切换，不要求精确点中那个小圆点或方框。
- **选中后不自动跳下一题。** 自动前进会让人来不及看清自己选了什么，也和「可跳过、可回改」的自由度对不上。前进由用户自己点。
- 每题都能不答。

### 前进与回退

- 「下一步」始终可点，不因为当前题还没答就禁用。
- 第一题不显示「上一步」，不放一个点不动的按钮在那儿。
- 最后一题的「下一步」换成「发送」。
- 进度上每一格都可点，点了直接跳到那题，不用逐次点「上一步」。
- 回到已答的题，原答案原样带回；改完继续往前走时，后面已经答过的题不清空。
- 键盘：Enter 前进；自由输入题上 Enter 是换行，用 Cmd + Enter 前进。

### 发送

- 一题都没答时发送禁用，原因常驻显示在按钮旁，不藏进悬停提示。
- 发出去的消息按题目顺序逐行组装，每行是问题标题加这题的答案：单选取选中那项的 title；多选取选中各项的 title，按表单里的原顺序排列；自由输入取用户写的原文。跳过的题不出现在消息里。
- 只用 title，不带 description。description 是帮用户当场判断的，Agent 自己写的东西不用再念给它听。
- 发送后卡片消失，一条普通用户消息进入时间线。**不给卡片留一个「已回答」的壳子**——用户自己那条消息就是最强的确认，再显示一遍是重复。

### 用户绕开表单

用户直接在正常输入框打字发送时，表单原地保留、停在原来那题、已答内容都在，仍然可以继续答。他可能只是想先追问一句再回来。不清除、不禁用、不弹确认。

### 一个位置，一个表单

输入框上方是一个固定位置，同时只放得下一个表单。Agent 发来新表单时旧表单被替换，旧表单里没发送的答案直接丢弃。Agent 已经往下说了新的话，旧问题的上下文已经过期，留着一个还能答的旧表单比清掉更危险。

### 留存

已答的答案**和当前停在第几题**一起按会话草稿处理：切到别的对话再回来、关掉应用再打开，回到原来那一题、原来那些答案。用户常常一边等一边去看别的对话，回来发现答了三题全没了，就再也不敢用表单。

## 页面状态

| 状态 | 表现 |
| --- | --- |
| 多题、答题中 | 卡片显示成员与进度，当前题高亮，已答格实心、未答格空心；导航行是上一步与下一步 |
| 多题、最后一题 | 同上，导航行右侧换成发送 |
| 只有一题 | 不显示进度，导航行只有发送 |
| 一题都没答 | 发送禁用，原因常驻显示在按钮旁 |
| 第一题 | 不显示「上一步」 |
| 已发送 | 卡片消失，时间线出现对应用户消息 |
| 被新表单替换 | 旧卡片连同未发送的答案一起消失，新表单从第一题开始 |
| Agent 只发了表单、没写别的正文 | 时间线不产生一条空消息，卡片就是这一轮的表达；Agent 另有正文时，那些话照常作为正常正文显示 |
| Agent 表单写法不合规 | 输入框上方不出现卡片，那段内容当普通文字留在正文里 |

写法不合规时不跟用户解释「Agent 刚才写错了格式」。那对他没有任何用处——他看到 Agent 把问题列在正文里，自己打字回答就行。表单是当场生成的，写错是常态，降级必须是安全的。

## 弹层与危险操作

不适用。表单不是弹窗、不夺焦点、不阻断用户做别的事；它本身也不执行任何操作，只是把用户的回答变成一条普通消息。答案送出后真正做事的是 Agent，那属于 Agent 自己的执行与确认规则。

## 响应式与窗口行为

- 表单卡片宽度跟随输入框区域，不独立设定宽度。
- 窄窗口下，选项的 title 与 description 竖向排列，不因为挤压而截断 description——用户正是靠它判断选哪个。
- 卡片纵向超出可用高度时，卡片内部滚动，进度与导航行保持可见，不把发送按钮推出视野。
- 表单出现不改变时间线的滚动位置，也不把已有的附件草稿和待发射区顶掉。

## 关联流程

暂无专属流程文档。表单是主会话内的一次局部问答，起止都在同一段对话里，不跨页面。它未来最可能服务的端到端目标是「一段对话做完之后如何收尾」，那需要单独的流程 PRD，本页不预定义。

## 指标与验收

判断这个能力成立的标准：

1. 多题表单出现时，卡片显示是哪位成员在问、当前第几题共几题；Agent 没写别的正文时，时间线不出现空消息。
2. 只有一题的表单不显示进度，导航行直接是发送。
3. 第一题看不到「上一步」；最后一题看不到「下一步」而看到「发送」。
4. 当前题一项没选时「下一步」仍可点，该题在进度上保持未答的样子。
5. 从第三题点进度第一格能跳回去，原答案原样在；改掉它再往前走，后面已答的题没被清空。
6. 一题都没答时发送禁用，禁用原因常驻可见，不是悬停才出现。
7. 单选、多选、自由输入混合作答并跳过一题后发送，消息按题序逐行呈现问题与答案，多选按原顺序排列，跳过的题不出现，全程不含 description。
8. 发送后卡片消失，时间线出现对应用户消息，没有多余的「已回答」标记。
9. 答到第二题切换到别的会话再回来、或退出应用重开，都停在第二题且前面的答案还在。
10. 表单没发送时用户直接在输入框打字发送，表单保留、停在原题、已答内容都在。
11. 旧表单答到一半时 Agent 发来新表单，旧卡片被替换，新表单从第一题开始。
12. Agent 写出不合规的表单写法时，输入框上方没有卡片，那段内容作为普通文字显示在正文里。
13. 全程只用键盘可以完成一次完整作答并发送。
14. 表单出现时，已有的附件草稿和文本胶囊仍在表单与输入框之间，没有被顶掉。

## 非目标

- **Agent 收工场景的按钮化。** 「这段对话做完了，要不要合并、要不要清理独立工作空间」是这个能力最先要服务的用例，但它需要自己的一份流程定义，本页只做表单能力本身。
- **表单的层级化配置。** 不做内置、团队、项目三层的收尾动作清单，也不做任何形式的表单配置文件。表单只能由 Agent 当场产出。
- **题目之间的条件跳转。** 不做「答了 A 才出现第三题」。
- **必填校验与默认值。** 每题都能跳过，唯一的限制是整份表单全空时不能发送。
- **发送前的汇总确认屏。** 答完最后一题不额外多一屏让用户复核全部答案。想回看点进度跳回去就行，为此多加一屏不值。
- **把用户手打的回答沉淀成下次的按钮。**
- 表单在右侧栏分析会话中的呈现。

## 待讨论

- **次要目标用户是否服务。** 本页按「用户可能不是开发者」写文案要求。如果确定只服务开发者，选项文案可以直接用技术话，Agent 的写作要求随之放宽。
- **表单能否被忽略。** 本页规定用户可以绕开表单直接打字，这是从输入框上方其他内容（附件草稿、文本胶囊都不阻断发送）的既有语义推断的，未经采访确认。若改为「必须答完才能继续」，让路规则和发送禁用条件都要重写。
- **Agent 表达表单的具体写法，以及「写坏」的判定边界。** 这是实现层面的事，不属于产品事实，但它直接决定 Agent 能不能稳定写对表单——写不对，这个能力就等于不存在。建议实现前先定。
