## 页面目标

Agent 团队页让用户看见自己当前拥有的团队，理解每支团队负责什么、由谁主理会话、包含哪些专业成员，并在同一团队上下文中完成创建、复制、修改、修复和文件维护。

团队是本页的基本管理单位。每支团队严格包含自己的一组 Agent，并指定其中一名为主 Agent。Agent 不作为脱离团队的全局对象单独管理；相同角色出现在不同团队时，也视为彼此独立的成员配置。

软件自带团队是允许本地编辑的“官方来源团队”，不是只读样板。用户可以直接把官方团队改成适合自己的工作方式；软件升级只带来新的官方版本，不在后台覆盖用户当前内容。页面通过“上次应用的官方基线、用户当前内容、当前软件携带的最新版”三方比较，分别表达“已自定义”和“有更新”，必要时先保留用户副本再更新官方团队。

每名 Agent 除角色内容外，还拥有独立的运行配置：CLI、model 和 effort。运行配置属于“这支团队中的这名 Agent”，不按 slug 跨团队共享；Codex、Claude Code 与 Kimi 是地位对等、不可静默互相降级的 CLI 选项。本页只负责读取、编辑和保存这份可移植配置，不自动检查本机安装、登录或模型能力；动态可执行性由会话真正启动所选 CLI 时裁决。

本页不把团队呈现为组织架构或固定工作流。团队成员扁平并列，主 Agent 是新会话的默认接单者，也是每轮协作的控制权归属者和可见收尾者；这项责任不代表上下级、固定执行顺序或 DAG 关系。

主 Agent 的 `AGENT.md` 是团队接收新任务和最终收尾时的协作入口；其他成员各自的 `AGENT.md` 定义专业职责和自然语言交棒规则。产品只固定显式交棒与控制权最终回归主 Agent，不尝试从“验收”“通过”“不通过”等自然语言理解或证明专业结论一定正确。

团队进入会话后，成员能够知道当前团队包含哪些 Agent 及其稳定标识，从而按各自 `AGENT.md` 的自然语言规则向同团队成员交棒。该成员清单不等同于固定执行顺序。

## 用户场景

- 用户从 Sidebar 进入 Agent 团队页，查看软件自带团队和自己创建的团队。
- 用户进入软件自带的「通用助手」，确认它只是由一名泛用主 Agent 组成的普通团队，并按需要修改职责、成员或运行配置。
- 用户进入某支团队，确认团队用途、主 Agent 和成员构成。
- 用户直接修改一支官方来源团队的团队信息、主 Agent、成员和 `AGENT.md`。
- 用户为同一团队中的不同 Agent 分别选择 Codex、Claude Code 或 Kimi，并设置对应的 model 与 effort。
- 用户看到官方团队“已自定义”或“有更新”，在需要保护本地成果时一键保留用户副本并更新。
- 用户复制任意完整团队，得到内容与当时已保存运行配置都独立演化的用户团队。
- 用户创建一支新团队，逐步添加 Agent，并让第一名成员自动成为主 Agent。
- 用户只描述长期工作目标，由 AI 提议一支完整团队，调整满意后一次确认创建。
- 用户在同一团队详情内切换成员，编辑各自的 `AGENT.md`。
- 用户保存团队或成员设置后，立即确认修改已经落盘、无需重启，以及哪些会话会使用它。
- 用户需要维护 `AGENT.md` 引用的其他文件时，在 Finder 中打开团队或成员位置。
- 用户修复被外部移动、重命名、删除或变得不可读的团队文件。
- 用户将不再使用的用户团队移到系统废纸篓或回收站。

## 入口与去向

### 入口

- 从[主页面侧边栏](./main-left-sidebar.md)顶部的“Agent 团队”进入。
- Sidebar 入口只要发现至少一支团队处于“需要修复”，就在右侧显示一个红点；多支异常团队不叠加数量。
- 红点的悬停提示和辅助名称为“有 Agent 团队需要修复”，不能只依赖颜色传达含义。
- 未完成草稿、“已自定义”和“有更新”都是普通管理状态，不触发 Sidebar 红点。

### 去向

- 点击团队首页的一整条团队横行，进入该团队详情。
- 团队详情中的成员行同时是成员选择器；点击后在当前页面下方切换对应的 `AGENT.md`，不进入独立 Agent 页面。
- “在 Finder 中打开”打开团队或当前成员对应的位置，供用户维护本页不负责编辑的相关文件。
- 返回团队首页时，保留此前的滚动位置；返回主页面时，恢复离开前的项目、对话和 Sidebar 状态。

## 页面结构

### 软件自带的官方来源团队

软件随安装包提供三支官方来源团队：

- `development`：开发团队，由开发经理主理，负责软件方案、实现、测试、复核和收尾。
- `content-production`：内容生产团队，由内容生产总控主理，负责选题调研、内容创作、视觉制作、发布包装和总控交付。
- `general-assistant`：通用助手，由唯一成员 `@assistant` 主理，用于没有预设专业分工的一般对话与任务。

三支团队使用相同的团队磁盘结构、编辑能力、运行配置、文件修复和官方更新规则。用户可以直接修改团队名称、描述、主 Agent、成员构成、`AGENT.md` 和现有规则允许维护的相关成员文件，也可以调整每名成员的 CLI、model 和 effort；官方来源身份保持稳定，团队不可删除。

官方来源表示 Moebius 能识别这支团队对应的官方基线与新版，不表示用户内容只读。软件升级不得静默替换用户当前版本；用户团队不参与官方更新比较。内容生产团队的五名成员分别承担总控、证据调研、创作编辑、视觉制作和发布包装；首次引导中的协作示例只用于说明成员如何接力，不定义真实会话的固定执行顺序。

### 「通用助手」官方基线

「通用助手」不是新的会话模式、分析模式或绕开团队系统的裸模型入口。它是一支正常可见、可选择、可复制、可编辑但不可删除的官方来源团队，并完整参与首页陈列、团队详情、三方更新、自定义标记、文件异常和 Sidebar 修复红点。

官方初始版本固定为：

- 团队稳定标识：`general-assistant`；显示名称：「通用助手」。
- 唯一成员稳定 slug：`assistant`；显示名称：「通用助手」；该成员同时是唯一主 Agent。
- 初始 `AGENT.md` 只包含有效身份 frontmatter：`display_name: 通用助手`、`description: 处理一般对话与任务`，正文不附加专业职责、固定流程、团队交棒或分析权限。它仍完整受 Moebius 的系统提示、团队、主 Agent、会话和工具权限规则约束，不是裸模型入口。
- 该成员的官方推荐运行配置为 `Codex / gpt-5.6-sol / high`。这是本团队自己的推荐配置，不继承来源会话、最近一次运行、其他团队或被分析 run 的 CLI、model 与 effort。

单成员只表示初始结构，不是永久限制。用户可以编辑成员内容和运行配置、添加成员，并在存在另一名有效成员后切换主 Agent 或移除原 `@assistant`；这些修改按普通官方来源团队显示“已自定义”。用户也可以主动复制出不再参与官方更新的用户团队。

「通用助手」的更新完整复用官方三方比较：官方新版不会在启动、升级或创建 sidebar chat 时后台覆盖用户当前内容；用户显式更新时，内容分叉或成员配置存在丢失风险就先保留用户副本。官方推荐配置只有在用户应用更新且该成员仍“跟随推荐”时改变，用户覆盖保持原值。

「通用助手」的修复也不设特殊后门：

- 团队位置不可用时标记“需要修复”，通过“重新定位团队”指向同一团队；官方来源记录与稳定身份不可移除。
- `@assistant` 的 `AGENT.md` 缺失或不可读时，整支团队不可用于新会话。用户可以从 Finder 恢复文件，或先添加另一名有效成员、将其设为主 Agent，再移除失效成员。
- 修复完成前不能应用官方更新，也不能用于首次发送；应用不会静默重建官方文件、改用来源团队或换成其他模型。
- [会话分析流程](../flows/session-analysis.md)中的草稿仍保留「通用助手」选择和用户内容，明确提示修复；用户也可以在发送前主动改选另一支可用团队。

### 既有安装首次登记「通用助手」

从只携带 `development` 与 `content-production` 的旧版本升级时，`general-assistant` 作为一支**新增官方来源团队**首次登记，不套用“已有官方团队 A → C 更新”的用户确认流程，也不修改原有两支团队。

- 本地不存在 `general-assistant` 官方记录，且预定位置没有身份冲突时，应用从当前安装包携带的官方版本原子创建团队文件、登记官方来源身份与当前基线，并写入 `@assistant` 的推荐运行配置。全部成功后它才出现在团队首页和选择器。
- 同名显示名称不是冲突。用户已有一支也叫「通用助手」的用户团队时，两支团队同时保留，通过“官方来源”标识区分；用户团队不被重命名、合并或覆盖。
- 稳定团队标识 `general-assistant` 已被非官方记录占用时，团队页用用户语言说明「现有用户团队与系统的通用助手身份冲突」，不显示或要求用户编辑内部标识，并提供两个入口：
  - 「查看现有团队」进入冲突用户团队的详情或既有修复页；
  - 「保留现有团队并添加官方团队」保留其名称、内容、成员、运行配置、文件和已有会话关系，把它继续作为独立用户团队管理，同时登记新的官方「通用助手」。成功后两支团队都可见，并靠“官方来源”区分。
- 冲突用户团队当前不可读时，不能执行“保留并添加”；用户先在既有修复页重新定位或移除失效的用户团队记录，再回到冲突提示点击「重试添加」。用户不需要也没有入口直接修改稳定标识。
- 预定文件位置已有无法识别为该官方团队的内容时，页面单独说明「通用助手的预定位置已有其他文件」，提供 Finder 入口和「保留现有文件并在新位置添加」。后一个操作不移动、改名、删除或覆盖现有文件，由应用选择新的受管位置完成官方团队登记。
- 两类冲突同时存在且冲突用户团队可读时，页面分别列出原因，并用「保留现有团队与文件并添加官方团队」执行同一原子结果；用户团队不可读时该组合操作不可用，必须先走其既有修复或移除失效记录。任一保留、登记或写入失败都回到冲突页，现有团队、文件和官方缺失状态保持原样；修复或重试成功后恰好新增一支官方「通用助手」，不留下中间身份或重复记录。
- 首次登记的文件、官方记录、基线和推荐配置是一个用户可观察的原子结果。任一步失败都不显示半支团队或重复团队，保留可理解原因和重试入口；重新进入团队页或下次启动可以重试。
- 本地已经有有效 `general-assistant` 官方记录时，不重复首次登记；内容或官方版本差异继续走正常三方比较与显式更新。已有官方记录但文件不可用时进入“需要修复”，不能用首次登记静默重建或覆盖用户内容。

### 运行配置静态校验

运行配置使用产品内置的 CLI → model → effort 联动列表，不从本机 CLI 动态枚举。切换 CLI 时进入该 CLI 的兼容默认组合；切换 model 时保留仍受支持的 effort，否则采用该 model 的默认 effort。没有已保存配置或官方推荐的成员直接使用 `Codex / gpt-5.6-sol / high`，用户无需先打开或保存设置。

Codex 首版列表为 `gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna`、`gpt-5.5`、`gpt-5.4`、`gpt-5.4-mini`；每个 model 只显示其各自支持的 effort。首版不展示会启用自动任务委派的 `ultra`，也不展示 Pro-only research preview `gpt-5.3-codex-spark`。Kimi 首版保存 ACP 精确匹配所需的完整 CLI alias：`kimi-code/k3`、`kimi-code/k3-256k`、`kimi-code/kimi-for-coding`、`kimi-code/kimi-for-coding-highspeed`；受会员等级限制的 model 在选项中标注权限要求。

Claude Code 首版使用 CLI 官方稳定、且能够满足现有 model + effort 精确冻结契约的
alias `fable`、`sonnet` 与 `opus`。`fable` 提供官方支持的
`low / medium / high / xhigh / max`；`sonnet` 与 `opus` 只提供跨当前官方 provider
解析结果共同支持的 `low / medium / high / max`。后两者在部分 provider 解析到不支持
`xhigh` 的模型并会静默回落，因此首版不提供其 `xhigh`。模型实际可用性仍取决于用户的
Claude 账号、组织策略与 provider。首版不提供会动态切换模型的 `default`、`best`、
`opusplan`，不提供随版本变化的完整模型 ID、1M context alias 或没有 effort 选择的
`haiku`；这些值若来自历史配置，继续按旧版自定义配置保留。用户把 CLI 切换到
Claude Code 时使用 `sonnet / high` 作为兼容默认组合。

页面始终保留历史上已经保存但不在当前内置列表中的 model/effort 原值，并将它们显示为“旧版自定义配置（当前列表不支持）”；打开页面、切换成员或保存其他成员都不得静默覆盖。用户为该成员选择当前列表中的 model 后，才用受支持组合替换旧值。页面仍不读取本机 CLI，也不因为当前机器的安装、登录或会员权限状态而改值或阻止团队管理。

## 区域与信息

### 页面标题与新建入口

- 页面标题固定为“Agent 团队”。
- “新建团队”是首页唯一常驻的创建操作；展开后提供「跟 AI 聊出一支新团队」和「从空白开始」。
- 复制团队仍只出现在已有团队详情的“更多”菜单中，不塞进“新建团队”菜单，因为它必须先有明确复制来源。
- 页面不提供独立的全局 Agent 库入口。

### 团队横行

每条团队横行包含：

- 团队名称。
- 一句话用途描述。
- “官方来源”“已自定义”“有更新”“未完成”或“需要修复”等必要状态。
- 成员数量和主 Agent 名称。
- 主 Agent 排在第一位的扁平成员示意。
- 每个可读成员在名称左侧显示统一的中性圆形首字头像。
- 进入详情的整体点击区域。

成员显示名称和一句话描述来自各自 `AGENT.md` 中的对应信息；团队横行和详情不再维护一份独立、可能漂移的成员摘要。

这条规则没有例外：团队位置不可用时读不到成员 `AGENT.md`，横行的成员区显示占位说明，**不回落到任何缓存的成员名称或数量**。团队名称和一句话描述仍来自应用记录，用户据此识别这是哪一支团队；成员构成属于必须实时读盘的事实，宁可显示不出来，也不显示一份可能与磁盘不符的旧名单。

团队横行不常驻修改、复制或删除按钮。首页负责陈列、识别和进入，具体管理操作进入详情后完成。

### 扁平成员表达

- 不绘制连接线、箭头、环形轨道、中心节点、树形缩进或上下层级。
- 所有成员使用相同尺寸和视觉权重。
- 团队首页成员项、详情成员选择器和当前成员标题使用同一套中性圆形首字头像，不使用身份色表达层级或状态。
- 主 Agent 只通过排在第一位和“主 Agent”标签表达。
- 切换主 Agent 后，新主 Agent 自动移动到第一位。
- 其他成员不表达执行顺序，也不提供手动排序。
- 首页空间不足时显示前几名成员和 `＋N`；详情页保持单行并允许横向滚动。

### 团队身份

所有完整团队的“修改信息”只负责团队名称和一句话描述，不展开成员 `AGENT.md`。官方来源团队允许修改这些内容，但来源身份不可改变；更新产生的用户副本不再具有官方来源身份，之后不再出现官方更新提示。

本产品不存在可由用户设置的应用级“默认团队”。普通主会话只记住上一次成功创建会话时使用的团队，供下一次新建对话预选。「通用助手」是 sidebar chat 的上下文专属初始预选，不会因此成为所有新会话的全局默认，也不会在用户尚未发送时改写“上一次使用”记录。

### 主 Agent

- 每支可用团队必须且只能有一名主 Agent。
- 主 Agent 必须是当前团队成员。
- 主 Agent 是所选团队进入新会话后的默认接单者，也是每轮协作最终接回控制权并向用户可见收尾的主理人；它不是其他成员的父节点或管理层级。
- 完整团队详情顶部常驻主 Agent 选择器，不把切换能力藏入“修改信息”或“更多”。
- 第一个成员自动成为主 Agent。
- 删除当前主 Agent 前，必须先指定另一名有效成员。

### Agent 身份与说明

- 每个 Agent 在创建时取得一个团队内唯一的稳定 slug，用于团队内识别和协作引用；创建后不因修改显示名称而变化。
- Agent 的显示名称和一句话描述属于 `AGENT.md` 内容，可以与正文一起在编辑器中修改；新格式 MUST 写在文件开头的 YAML frontmatter，字段固定为 snake_case 的 `display_name` 与 `description`，正文标题与段落只表达 persona，不再兼任机器元数据。
- 成员目录名是稳定 slug 的唯一事实源，frontmatter MUST NOT 再复制 `name` 或 slug 字段。
- 为兼容既有用户团队，只有在 frontmatter 完全没有 `display_name` 与 `description` 时，产品才从正文首个一级标题与其后首段回退读取旧格式身份；一旦出现任一新身份字段，两项都必须是非空单行字符串，缺项或非法值必须显示为需要修复，不得静默混用新旧来源。
- 团队首页、成员行和当前 Agent 标题都读取 `AGENT.md` 中的显示名称和一句话描述。
- 本页不提供修改稳定 slug 的入口，也不把显示名称变化视为另一个 Agent。
- 团队详情中的成员信息持续显示并允许复制 `@<slug>`；显示名称负责帮助人理解，slug 负责稳定引用。
- 成员头像不新增独立元数据：首字优先从 `display_name` 推导；显示名称暂不可用时从稳定 slug 的首字符降级，拉丁字母统一大写。
- 首字头像只用于快速识别；可读名称、稳定 slug、主 Agent 与可用状态仍由现有文字和语义表达，不能只依赖头像字符。

### Agent 运行配置

运行配置属于“某支团队中的某名 Agent”，与该成员的角色内容并列，但不写入 `AGENT.md`。相同 slug 出现在不同团队时，运行配置彼此独立。

每名 Agent 的运行配置包含：

- CLI：支持 Codex、Claude Code 与 Kimi，三者地位对等；绑定后不自动降级或替换成另一套 CLI。
- Model：从产品内置、按 CLI 区分的兼容列表中选择；列表保存执行端要求的精确 model 标识。
- 思考程度（effort）：从当前 model 自己支持的列表中选择，不把不同 model 的能力合并成一份通用列表。
- 配置来源：官方来源团队中的官方成员为“跟随推荐”或“用户覆盖”；用户自行添加的成员、普通用户团队成员使用显式配置。

没有已保存配置或官方推荐时，默认组合为 `Codex / gpt-5.6-sol / high`，无需用户先设置。Codex 内置列表排除会改变 Moebius 交棒架构的 `ultra` 与 Pro-only preview `gpt-5.3-codex-spark`；Claude Code 使用稳定的 `fable` / `sonnet` / `opus` alias 与各自可精确冻结的 effort 列表，切换到 Claude Code 时默认 `sonnet / high`，不把动态默认、混合模式、长上下文变体或完整版本 ID 作为首版选择；Kimi 使用带 `kimi-code/` 前缀的 CLI alias，并在受限选项上标注会员权限。列表更新随 Moebius 版本发布，不读取本机 CLI 生成选项。

用户修改 CLI、model、effort 中任一字段并保存后，该官方成员进入“用户覆盖”。官方新版可以更新同一稳定 slug 的推荐运行配置，但只有“跟随推荐”的成员会在用户确认团队更新后采用新版推荐；“用户覆盖”始终保留原值。点击“恢复推荐配置”会清除该成员的用户覆盖，恢复到**当前已应用官方版本**为该 slug 提供的推荐组合；尚未应用的官方新版不能提前改变这个结果。

用户自行添加且没有官方 slug 推荐来源的成员不显示“恢复推荐配置”，也不伪造官方推荐。复制团队时，每名成员当时已保存的 CLI、model、effort 都复制到新团队，并固化为新团队自己的显式配置，之后与来源团队独立演化。

运行配置不自动保存。修改后，当前成员显示独立于 `AGENT.md` 的运行配置草稿标记；切换成员时草稿继续保留，多名成员可以同时拥有运行配置草稿。“保存运行配置”只保存当前成员；成功后清除该配置草稿，并按下文统一生效反馈确认已经保存。保存失败时保留原草稿、显示原因和重试入口，不能让用户误以为新配置已经生效。离开团队详情时，运行配置草稿与 `AGENT.md` 草稿一起进入现有“继续编辑 / 放弃全部 / 保存全部并离开”保护流程；“保存全部”需要逐项报告失败成员，已经成功保存的项目不回滚。

只修改运行配置不会让团队出现“已自定义”内容标记。团队页只允许新选择当前内置 registry 中属于对应 CLI/model 的组合，不调用 Codex、Claude Code 或 Kimi，不判断某台机器当前是否安装、登录或拥有相应会员权限，也不产生运行配置健康状态。历史已保存的未知组合继续可读、可复制、可参与官方更新保护并进入新会话快照，但 UI 明确标为旧版自定义配置，且只在用户主动选择受支持组合后替换。

### Agent 提及与选择

- 在软件内编辑 `AGENT.md` 时，输入 `@` 和 Agent slug 可以匹配当前团队成员；匹配结果同时显示成员的可读名称和 `@<slug>`。
- 用户选中成员后，编辑器显示以可读名称为主的提及组件，不让 slug 成为正文里的主要视觉噪声。
- 提及组件底层仍保存 `@<slug>`；使用 Finder 或其他编辑器打开原始 `AGENT.md` 时，看到的是稳定的 `@<slug>` 文本。
- 提及组件悬停或获得键盘焦点时，可以查看并复制底层 `@<slug>`。
- 显示名称改变后，既有提及组件自动显示新名称，但底层 slug 和引用关系不变。
- 自动补全只帮助选择当前团队成员，不允许从团队外引入共享 Agent，也不验证整段自然语言交棒是否合理。

### 成员选择器与 Agent 编辑区

- 成员选择器和 Agent 编辑区都属于团队详情，不新增独立 Agent 页面。
- 点击成员只切换下方当前编辑对象。
- 软件内只编辑成员的 `AGENT.md`；它引用的其他文件不在软件内展示文件树或提供编辑器。
- 当前成员菜单承接“在 Finder 中打开”“复制 Agent”和“删除 Agent”。官方来源团队中的成员也可修改、复制或删除；删除或复制不能改变团队稳定的官方来源身份。
- 团队之间不移动 Agent。需要复用时复制团队或复制当前团队中的 Agent，复制后独立演化。
- 删除成员前必须提示：其他成员的自然语言交棒规则可能仍引用该成员，产品不会自动理解或改写这些规则。用户确认后仍可删除；只要剩余结构继续满足可用条件，团队不因此自动进入“需要修复”。

### Finder

- 团队“更多”菜单中的“在 Finder 中打开”打开整支团队对应的位置。
- 当前成员菜单中的同名操作打开当前成员对应的位置。
- Finder 是辅助文件维护入口，不作为页面主操作常驻展示。
- 当前正式产品只面向 Apple Silicon Mac，本页只承诺 Finder 行为，不定义 Windows 或 Linux 文件管理器。
- 官方来源团队允许通过 Finder 维护相关文件。外部修改与软件内修改使用相同的“已自定义”、冲突和保存语义，不会让团队失去官方来源身份，也不会被软件升级静默覆盖。

## 操作与反馈

### 保存后的生效反馈

团队名称与用途、主 Agent、成员构成、成员 `AGENT.md` 或运行配置每次成功保存后，都在当前操作附近显示轻量反馈：

> 已保存，无需重启。新建对话选择这支团队时会使用修改；正在使用这支团队的对话会显示变化提示，点击任一「应用」会载入整支团队最新保存的完整版本。

反馈应保留到用户能够读完，但不形成需要处理的状态。它只确认已经落盘及会话生效边界，不声称对应 CLI 已在当前机器成功启动，也不把保存时间、内容指纹或文件路径暴露给用户。

一次操作只成功保存部分项目时，不显示整体「已保存」：成功列表逐项标明「已保存，无需重启」，并沿用上述会话生效边界；失败列表逐项说明「未保存，仍使用上一次保存的版本」，保留草稿与重试入口。后续新建、明确切换或在旧对话中点击「应用」时，完整团队快照只包含成功落盘的项目和失败项上一次保存的版本，不会把失败草稿混入快照。

「保存全部并离开」全部成功时，导航到团队首页后立即在团队列表上方显示同一条完整生效反馈，并明确已保存的团队与项目数量；反馈不会因离开详情而丢失。部分失败时仍留在团队详情，按上一段逐项显示成功与失败结果，不提前导航。

软件内没有未保存草稿、并成功载入一份有效外部修改时，使用「已载入外部修改，无需重启」作为同类反馈，并沿用相同会话生效边界。存在冲突、文件无效、检查失败或团队需要修复时不得显示这条成功反馈。

### 从空白开始与添加成员

- 从空白开始先创建可恢复的草稿，不要求用户在一个长向导里一次写完整支团队。
- 草稿会保留在团队首页，直到用户继续完成或主动删除。
- “添加 Agent”在当前团队详情内切换到新成员编辑状态，至少包含创建后不再改变的稳定 slug，以及写有可编辑显示名称和一句话描述的初始 `AGENT.md`。
- 第一个成功添加的 Agent 自动成为主 Agent。
- 团队恰好有一名主 Agent、每名成员都有团队内唯一的稳定 slug，且所有成员的 `AGENT.md` 都可读时，就满足结构上的可用条件，可以供新对话选择。
- 单成员团队也可以使用，但只代表结构有效，不代表已经具备多 Agent 专业分工。
- 产品不分析 `AGENT.md` 的自然语言内容来验证交棒是否正确；协作质量由用户实际定义的 Agent 内容和后续会话结果体现。

### AI 建队

- AI 建队对话可以追问或给出完整方案，但没有直接团队写权限。
- 用户可以继续对话调整成员、主 Agent 和职责；每次新方案替换待确认 proposal revision，旧版本不能再被确认。
- AI 建队要求 2–6 名成员，以兑现多 Agent 分工和接力承诺；从空白开始仍允许单成员团队。
- 确认创建只消费当前最后一版有效方案。完整团队核心、成员文件与供首次引导使用的独立 `onboarding-orchestration.json` 写入并登记成功后才进入详情；任一失败都保留方案和重试入口，不显示半成品团队。
- 独立引导编排不是团队结构、成员职责或真实运行规则，不进入 `team.json`、团队登记缓存、身份指纹或可用性判断。真实会话中的调度仍由主 Agent 依据当前任务与各成员 `AGENT.md` 灵活决定；普通手工团队可以没有引导编排文件。
- 从 Agent 团队页创建成功不改变“上一次成功创建会话时使用的团队”；该记录仍只在真正创建会话后更新。

### 修改团队信息

- 用户团队和官方来源团队都可以修改名称和一句话描述。
- 保存成功后使用统一生效反馈；修改不会自动改变已有会话当前载入的团队版本，用户可在会话变化提示中显式应用完整最新版本。

### 切换主 Agent

- 用户从团队详情顶部的主 Agent 选择器中选择现有有效成员。
- 切换成功后立即保存并给出统一生效反馈；不再要求进入额外编辑模式。
- 新主 Agent 移动到成员行第一位。
- 切换不会自动改变正在使用该团队的会话；新建对话并选择这支团队、已有会话明确切换到这支团队，或在该团队变化提示中点击「应用」时，载入包含最新主 Agent 的完整团队版本。

### 编辑与保存 `AGENT.md`

- `AGENT.md` 不自动保存。
- 修改后，当前成员显示未保存标记。
- 切换到其他成员时不弹窗，当前草稿继续保留；多名成员可以同时保留未保存草稿。
- “保存”只保存当前成员；支持标准的 `Command/Ctrl + S`。
- 保存成功后清除对应成员的未保存标记，并显示统一生效反馈。
- 保存失败时保留编辑内容，在当前编辑区显示原因和重试。
- 离开团队详情时如果仍有未保存内容，统一提供“继续编辑”“放弃全部”和“保存全部并离开”。
- “保存全部并离开”全部成功时返回团队首页，在团队列表上方显示统一生效反馈与已保存项目数量。
- “保存全部并离开”逐个保存已修改的 `AGENT.md`。部分保存失败时，成功项保持已保存并逐项显示成功生效反馈，失败项继续保留草稿并明确仍使用上一次保存的版本；用户停留在当前团队详情并看到失败成员列表。产品不伪装成整体成功，也不回滚已经成功保存的文件。

### 外部修改冲突

- 本节适用于用户团队和官方来源团队。官方来源团队的外部修改会参与当前内容与官方基线的比较，但不会移除其官方来源身份。
- 软件内没有未保存内容时，返回应用后重新载入外部更新的 `AGENT.md`，并给出统一的外部修改生效反馈。
- 软件内已有未保存草稿时，不自动覆盖，保留草稿并提示文件已在外部修改。
- 用户只能选择“载入外部版本”或“用当前内容覆盖”。本页不提供逐行 diff 或自动合并。
- 其他引用文件的外部修改不触发本页刷新或冲突提示。
- 外部修改检查失败必须在对应成员上显示可见错误，不得静默忽略。

存在未解决的外部冲突时，返回团队列表会被明确阻止。界面弹出说明并列出所有待处理成员；关闭说明后仍停留在团队详情，成员的冲突状态保持不变。这里不提供“直接离开”：未保存草稿可以放弃，外部冲突必须先在“载入外部版本”和“用当前内容覆盖”之间完成裁决。

```text
┌────────────────────────────────────────────┐
│ 无法返回团队列表                           │
│                                            │
│ 以下 Agent 的文件在应用外被修改，          │
│ 需要先选择保留哪一份：                     │
│                                            │
│   · 开发经理 AGENT.md                      │
│   · 测试 AGENT.md                          │
│                                            │
│                              [ 知道了 ]    │
└────────────────────────────────────────────┘
```

### 官方版本与三方比较

官方来源团队同时保留三份可解释事实：

```text
A = 上次应用到本机的官方基线
    ├─ 官方版本
    ├─ 官方内容指纹
    └─ 各稳定 slug 的推荐运行配置

B = 用户当前可编辑的官方来源团队内容

C = 当前软件携带的最新官方版本
    ├─ 最新官方内容指纹
    └─ 各稳定 slug 的最新推荐运行配置
```

进入 Agent 团队页、打开官方来源团队详情或从 Finder 返回应用时，页面重新读取当前内容并完成三方比较；比较只更新页面状态，不自动应用 C。

官方内容指纹覆盖团队名称与描述、主 Agent、成员结构、各成员 `AGENT.md` 以及现有规则允许维护的相关成员文件。CLI、model、effort、缓存和应用内部元数据不进入内容指纹。独立的 `onboarding-orchestration.json` 只服务首次引导，不属于团队结构、身份或真实运行规则，因此不进入官方内容指纹、自定义判断、团队身份或可用性判断。

版本号用于向用户解释更新，规范化内容指纹用于判定，页面不显示原始 hash：

- `B ≠ A.content`：用户修改过团队内容，显示“已自定义”。
- `C ≠ A`：官方版本、官方内容或官方推荐运行配置发生变化，显示“有更新”。
- 用户运行配置覆盖不参与 `B/A` 内容比较。
- “有更新”与“已自定义”是普通管理状态，不触发“团队需要修复”红点，也不等同于文件损坏。

| 三方结果 | 页面状态 | 主操作 |
| --- | --- | --- |
| `B = A.content`，`C = A` | 官方来源 | 无更新操作 |
| `B ≠ A.content`，`C = A` | 官方来源 · 已自定义 | 继续编辑 |
| `B = A.content`，`C ≠ A`，且没有配置丢失风险 | 官方来源 · 有更新 | 更新到最新版 |
| `B = A.content`，`C ≠ A`，但新版删除或改名了存在用户覆盖的成员 | 官方来源 · 有更新 | 保留副本并更新 |
| C 新增的 slug 与 B 中用户自行添加的成员同名 | 官方来源 · 已自定义 · 有更新 | 保留副本并更新 |
| `B ≠ A.content`，`C ≠ A`，且 `B = C.content`，并且不存在成员配置丢失风险或 slug 来源冲突 | 内容已是最新版 | 完成更新登记，不创建副本 |
| `B ≠ A.content`，`C ≠ A`，且 `B ≠ C.content` | 官方来源 · 已自定义 · 有更新 | 保留副本并更新 |
| 比较所需内容不可读 | 无法检查更新 | 保持原状，进入既有修复或重试入口 |

仅推荐配置发生变化时，可能出现 `A.content = B = C.content` 但 `C ≠ A`。页面仍显示“有更新”；应用更新后，“跟随推荐”的成员采用新版推荐，用户覆盖保持原值，不创建副本。

成员配置保护与 slug 来源保护优先于 `B = C.content` 的快捷登记：只有新版不会删除或改名存在用户覆盖的成员，且 C 新增的 slug 不与 B 中用户自行添加的成员同名时，才可以不创建副本。只要任一保护条件命中，即使 B 的内容指纹已经等于 C，也仍须执行“保留副本并更新”。

### 官方成员与运行配置迁移

官方团队从 A 更新到 C 时，以稳定 slug 判断成员是否为同一人，不根据显示名称或职责文本猜测对应关系：

| A → C 的成员关系 | 官方团队更新结果 | 若本次需要保留用户副本 |
| --- | --- | --- |
| slug 保持，存在用户覆盖 | 原 CLI、model、effort 完整保留 | 固化更新前的已保存配置 |
| slug 保持，仍跟随推荐 | 采用 C 为该 slug 提供的推荐值 | 固化更新前的已保存配置 |
| C 新增 slug | 采用 C 的推荐值 | 更新前没有该成员 |
| C 新增 slug，但 B 已有用户自行添加的同名成员 | 采用 C 的官方成员与推荐值，不继承用户成员配置 | 保留用户自建成员及其已保存配置 |
| C 删除 slug，且没有用户覆盖 | 成员及其推荐配置从官方团队移除 | 仅内容分叉时随完整副本保留 |
| C 删除 slug，且存在用户覆盖 | 必须先保留副本，再从官方团队移除 | 保留旧成员及其已保存配置，包括当前失效的原值 |
| slug 改名 | 按删除旧 slug 与新增新 slug 处理 | 旧 slug 存在用户覆盖时，必须先保留旧成员及配置 |

不存在把已删除成员的配置猜测附着到新成员或新 slug 的行为。即使团队内容从未修改，只要官方新版会删除或改名一个存在用户覆盖的成员，页面也必须使用“保留副本并更新”，不能通过直接更新丢弃用户已保存配置。官方新增 slug 与用户自行添加的成员撞名时，也不能仅凭 slug 把两者当作同一成员；用户成员只留在副本，官方团队采用 C 的成员内容与推荐配置。

### 更新官方来源团队

软件升级只登记当前安装包携带的官方最新版，不在启动或后台检查时覆盖用户团队。页面可在读取团队时发现新版，但只有用户从团队详情显式执行操作才会应用更新。

执行更新前，详情页必须显示当前与最新官方版本，并列出这次更新可由三方比较确定的影响：新增、删除或改名的成员，跟随推荐而将改变的 CLI/model/effort，以及会被保留在用户副本中的成员与用户覆盖。页面不要求提供逐行 diff，但不能只给一个无法判断后果的通用按钮。

```text
官方更新                         v1.2 → v1.3

成员变化      ＋ release    － qa（有用户覆盖）
推荐配置      dev：Codex / gpt-… / 高 → Kimi / kimi-… / 高
保留方式      当前团队将保存为“开发团队（更新前副本）”
              qa 及其已保存配置只保留在副本

                                      [保留副本并更新]
```

当前内容未修改且没有配置丢失风险时：

```text
B = A.content，C ≠ A
  → 点击“更新到最新版”
  → 官方团队内容更新为 C
  → 官方基线登记为 C
  → 同 slug 的用户覆盖保持
  → 同 slug 的跟随推荐采用 C 的推荐值
  → 新增成员采用 C 的推荐值
```

用户内容与官方新版分叉，或新版会删除、改名存在用户覆盖的成员时：

```text
点击“保留副本并更新”
  → 当前 B 成为独立用户团队
  → 副本保留更新前的成员、文件与全部已保存运行配置
  → 副本脱离官方来源身份
  → 官方来源团队更新为 C
  → 同 slug 的用户覆盖保持
  → 同 slug 的跟随推荐采用 C 的推荐值
  → 显示副本名称与进入入口
```

当 `B = C.content`，且不存在成员配置丢失风险或 slug 来源冲突时，不创建冗余副本，只登记最新官方基线并按上述成员规则迁移推荐配置；若任一保护条件命中，仍执行“保留副本并更新”。更新的用户可见结果只能是以下三种之一：

- 操作失败，原团队、运行配置和更新提示保持可见；
- 无需保护时，官方来源团队直接完整更新或完成最新版登记，不创建副本；
- 需要保护时用户副本可见，官方来源团队完整显示为最新版。

更新成功反馈必须显示已应用的官方版本、实际新增/删除/改名的成员，以及跟随推荐配置的变化；创建了副本时，还要显示稳定可辨认的副本名称、被保护的成员和直接进入副本的入口。副本具体命名格式与重名后缀可以在后续交互设计中确定，但不能只显示“已完成”而不告诉用户成果保存在何处。

页面内异常遵循以下规则：

- 存在未保存的 `AGENT.md` 或运行配置草稿时，必须先保存或放弃，再执行更新。
- 存在外部修改冲突时，必须先在现有冲突流程中选择版本，更新不能绕过冲突。
- 无法读取三方比较所需内容时，显示“无法检查更新”，不执行更新。
- 副本创建或更新失败时，保持操作前页面状态和更新入口，允许重试；失败尝试不在团队首页留下无法辨认的半成品副本，也不因重试生成重复副本。
- 团队已经处于既有“需要修复”状态时，沿用现有修复入口；本页不新增损坏内容自动保副本规则。

具体的事务、暂存、文件交换和崩溃恢复机制由后续 OpenSpec 设计，不在本页规定技术实现。

### 复制

- 复制团队会创建一支独立的用户团队，复制团队对应的完整目录，包括团队信息、全部成员目录、各成员 `AGENT.md` 及其他相关文件，并进入新团队详情。
- 复制不会改变新建对话的“上一次使用”记录。
- 用户团队也可以从“更多”菜单复制。
- 官方来源团队也可以从“更多”菜单主动复制；此外，官方更新需要保护用户成果时会自动把当前版本复制为独立用户团队。
- 团队副本不保留官方来源身份，不参与后续官方版本比较；每名成员当时已保存的 CLI、model、effort 都固化为副本自己的显式配置，不根据当前机器环境改写。
- 用户团队中的单个 Agent 可以在成员菜单中复制；复制会包含该 Agent 的整个目录和全部相关文件，复制品仍属于当前团队。
- 在同一团队内复制 Agent 时，复制品取得新的团队内稳定 slug，避免与原成员的协作引用冲突；显示名称和其他文件内容可以从原成员开始再修改。
- 团队或成员存在未保存的 `AGENT.md` 草稿时，复制前必须让用户保存或放弃这些草稿；复制始终基于已经完整落盘的文件，不把内存草稿悄悄混入副本。

### 删除用户团队

- 官方来源团队不可删除。
- 用户团队和未完成草稿可以从详情页“更多”菜单移到系统废纸篓或回收站。
- 删除前说明团队包含的 Agent 和相关文件，并要求确认。
- 有未保存 `AGENT.md` 草稿时必须先处理草稿，不能直接删除。
- 删除成功后返回团队首页，并从新建对话团队选择器中移除。
- 被删除的团队如果是“上一次使用的团队”，下一次普通新建对话按固定官方顺序回退到第一支可用团队。
- 已有会话及其创建时载入的团队版本不因删除而被移除。
- 本产品不建设独立的已删除团队页面，恢复文件使用系统废纸篓或回收站。
- 从系统废纸篓或回收站恢复文件后，团队如何重新回到产品暂不在本页面承诺；文件层可恢复不等于自动恢复应用内记录。
- 已有会话在团队被主动删除后能否继续发送新消息，归会话交互 PRD 裁决；本页面只保证历史和已载入版本不会随删除一起消失。

### 新建对话中的团队预选

本页只定义跨页面约束，具体控件由[新建对话窗口](./new-conversation.md)负责：

```text
新建对话
  → 自动预选上一次成功创建会话时使用的团队
  → 用户可以在创建前改选
  → 进入会话
  → 由所选团队的主 Agent 默认接收消息
```

- 普通主会话首次使用且没有历史选择时，按固定顺序选择第一支可用官方团队：`development` → `content-production` → `general-assistant`。
- 上一次使用的团队已经删除或处于“需要修复”时，按同一固定顺序回退到第一支可用官方团队。
- 打开、编辑或浏览团队不更新“上一次使用”记录；只有成功创建会话后更新。

sidebar chat 使用独立的上下文预选规则：

- 从右侧栏内容选择打开普通「新会话」，或从「分析当前对话」进入时，初始团队固定预选当前本地的 `general-assistant`。
- 这只是发送前可改的初值；用户可以选择任意其他可用团队，首次消息由发送瞬间最终所选团队的主 Agent 接收。
- `general-assistant` 已被用户自定义时，载入用户当前已保存的团队内容和运行配置，不为这次会话临时恢复官方基线。
- `general-assistant` 需要修复时，不静默回退到普通主会话的上次团队、来源团队或其他官方团队；草稿保持，用户修复或主动改选后才能发送。
- sidebar chat 首次消息成功创建后，最终所选团队才按普通规则成为“上一次成功使用”的团队。

### 团队位置不可用

团队整体位置被移动、重命名或变得不可访问时，团队继续显示在首页并标记“需要修复”。详情提供“重新定位团队”；用户团队另提供“移除记录”，官方来源团队的稳定记录不可移除。已有会话历史不消失。

```text
┌────────────────────────────────┬───────────────────────────────┐
│ 我的开发团队          需要修复 │ 成员信息暂时无法读取          │
│ 团队文件夹已移动或不可访问     │ 暂时无法用于新对话            │
└────────────────────────────────┴───────────────────────────────┘
```

成员区显示占位说明而不是成员名称：此时 `AGENT.md` 读不到，任何成员名单都只能来自缓存，而缓存正是本页面拒绝维护的那份“可能漂移的成员摘要”。用户需要的识别信息由团队名称和不可用原因承担，成员构成等修复后自然恢复。

“重新定位团队”只能绑定能够识别为同一支有效团队的位置，不能用任意文件夹替换。

- 重新定位失败时保留原记录并说明选择的位置为何不被接受，不把团队错误绑定到新位置。
- 用户团队的“移除记录”只移除应用中已经失效的团队记录，不删除、移动或修改用户磁盘上的任何文件；执行前必须明确说明这一差异。官方来源团队不显示该操作，只能重新定位或修复其文件。

### 成员 `AGENT.md` 不可用

- 任一成员的 `AGENT.md` 缺失或无法读取，整支团队标记“需要修复”，暂时不能用于新建对话。
- 任一成员缺少稳定 slug，或同一团队内出现重复 slug，也属于“需要修复”。
- 用户可以在 Finder 中恢复文件，或将失效成员从用户团队、官方来源团队删除。
- 失效成员是主 Agent 时，可以先指定另一名有效成员为主 Agent，再删除失效成员。
- 文件恢复后重新检查，并在所有成员恢复有效后解除“需要修复”。
- 软件不检查 `AGENT.md` 引用的其他文件是否完整。

### 跨页面异常反馈

- 只要至少一支团队“需要修复”，Sidebar 顶部“Agent 团队”入口显示一个红点；多支异常仍只显示一个。
- 红点的悬停提示和辅助名称为“有 Agent 团队需要修复”。
- 点击入口后，团队首页对应横行必须以“需要修复”状态明确标出具体异常团队。
- 未完成草稿、“已自定义”和“有更新”都不触发该红点。
- 如果已有会话当前选择的团队变为“需要修复”，会话历史仍可查看，但不能发送新消息；会话内团队按钮显示红色异常标识。
- 会话按钮、发送禁用、切换团队和修复后的恢复细节留给会话交互 PRD 定义。

这里区分两个事实：已有会话继续保留创建时载入的 Agent 内容版本；团队当前是否“需要修复”则实时决定该会话能否继续发送。

## 弹层与危险操作

- “从空白开始”和“修改信息”只承载短字段，不把完整成员编辑塞进弹窗；AI 建队使用页面主体，不把多轮对话塞进弹窗。
- 删除用户团队使用明确确认，说明团队文件和已有会话分别受到什么影响。
- 删除通过系统废纸篓或回收站保持文件层可恢复，不提供软件内永久删除；恢复回产品的方式暂不承诺。
- 官方来源团队不显示删除能力，但团队内容和运行配置使用与用户团队一致的编辑保护。
- 存在未保存草稿时，离开、删除或其他会丢失内容的操作必须先让用户选择保存或放弃。
- 外部修改冲突不得静默选择任何一方覆盖。

## 响应式与窗口行为

- 宽窗口下，团队横行左侧显示身份信息，右侧显示扁平成员行。
- 窄窗口仍保持“一支团队一条横行”，不改成多列卡片网格；成员行移动到描述下方。
- 首页空间不足时用 `＋N` 收敛成员数量。
- 团队详情中的成员选择器保持单行并允许横向滚动，不换行堆成多层。
- `AGENT.md` 编辑器始终占满成员行下方的可用宽度。
- 窗口缩放、成员切换和横向滚动不得丢失各成员尚未保存的草稿。

## 关联流程

- 新建对话时预选上一次使用的团队，并允许用户改选。
- sidebar chat 与会话分析入口初始预选「通用助手」，允许发送前改选；分析只是普通会话的静态文本与提示词切入，不给该团队增加特殊权限。
- 所选团队的主 Agent 接收新会话第一条消息。
- 官方来源团队允许直接修改；有官方新版时根据三方比较直接更新，或先保留独立用户副本再更新。
- 每名 Agent 在团队页配置独立的 CLI、model 和 effort；它们按[主对话页](./main-conversation.md)规则进入会话与 run 快照并硬绑定执行引擎。
- 从 onboarding 或 Agent 团队页进入同一套 AI 建队能力；前者创建后选中并继续演示，后者创建后进入团队详情。
- 团队文件异常后，从 Sidebar 红点或会话异常入口进入修复。
- 已有会话所选团队“需要修复”时，阻止继续发送，修复或切换团队后恢复。

这些流程尚未建立独立的 `flows/` 文档。会话内团队按钮、发送状态、切换团队以及运行中异常的具体行为以[主对话页](./main-conversation.md)为准。

## 指标与验收

1. 用户能从 Sidebar 顶部进入 Agent 团队首页，并用一条横行识别每支团队的名称、用途、主 Agent、成员和必要状态；团队首页、成员选择器和当前成员标题中的同一成员使用一致的中性首字头像。
2. 团队成员始终扁平展示；页面不存在暗示组织层级、执行顺序或 DAG 的连接线和节点结构。
3. 官方来源团队可以修改团队信息、主 Agent、成员、`AGENT.md` 和相关成员文件，但来源身份稳定且团队不可删除；软件内与 Finder 外部修改使用相同的自定义与冲突语义。
4. “新建团队”同时提供 AI 建队与从空白开始；复制仍从明确的已有团队详情发起，三条路径最终产生同一种用户团队。
5. 用户能创建长期保留的空白团队草稿；第一名成员自动成为主 Agent，缺少有效主 Agent 时团队不可用于新建对话。
6. AI 建队未确认时不产生团队列表项；确认后一次创建含 2–6 名成员、唯一主 Agent 和全部有效 `AGENT.md` 的普通用户团队，失败不得留下半成品。
7. 用户在团队详情内即可切换成员并编辑多个 `AGENT.md`，不需要进入独立 Agent 页面；显示名称和一句话描述来自 `AGENT.md`，未保存草稿不会因成员切换丢失。
8. 用户能用 `@<slug>` 匹配当前团队成员，选择后看到可读名称组件；显示名称变化不破坏底层稳定引用，缺失或重复 slug 会让团队进入“需要修复”。
9. 软件内不提供相关文件编辑器；团队和成员均有不抢占主视觉的 Finder 入口，本文不形成 Windows 或 Linux 文件管理器承诺。
10. 普通新建对话预选上一次成功使用的可用团队；没有历史选择或上次团队不可用时，按 `development` → `content-production` → `general-assistant` 回退到第一支可用官方团队。
11. 团队或成员文件不可用时，团队显示“需要修复”、不能用于新建对话，Sidebar 顶部“Agent 团队”入口出现红点。
12. 已有会话选择了“需要修复”的团队时，历史仍可查看，但发送被阻止；详细恢复交互由会话 PRD 承接。
13. 用户团队删除进入系统废纸篓或回收站，官方来源团队无法删除，已有会话载入的团队版本不被清除。
14. 每名 Agent 可以独立选择 Codex、Claude Code 或 Kimi，并从对应 model 及其 effort 联动列表中保存组合；切换到 Claude Code 时默认 `sonnet / high`；不同团队中的同 slug 配置互不影响，绑定不会静默降级到另一 CLI。
15. 未配置成员直接采用 `Codex / gpt-5.6-sol / high`；打开、切换成员和保存运行配置都不会启动 Codex、Claude Code 或 Kimi，也不等待本机能力检查，当前机器暂时不可运行不改变已保存配置。
16. 官方内容未更新而用户内容已修改时只显示“已自定义”；官方有更新而用户内容未修改且没有配置丢失风险时，可以直接更新且不创建副本。
17. 官方内容与用户内容均有变化且不相同时，一个主操作会先保留独立用户副本再更新；用户当前内容已经等于最新版、且不存在成员配置丢失风险或 slug 来源冲突时，不创建冗余副本，否则仍须保留副本再更新。
18. 仅官方推荐运行配置变化也会显示“有更新”；更新后，同 slug 的用户覆盖保持不变，仍跟随推荐的成员采用当前已应用最新版推荐值。
19. 官方新增成员采用最新版推荐配置；删除无用户覆盖的成员可以直接更新，且其配置不会附着到其他成员。
20. 官方删除或改名一个存在用户覆盖的成员时，即使团队内容未修改，也必须“保留副本并更新”；副本保留旧成员及其已保存配置，官方团队按删除旧 slug、增加新 slug 处理。
21. “恢复推荐配置”恢复当前已应用官方版本为该 slug 提供的推荐组合；应用官方更新后才会指向新版推荐。
22. 更新产生或主动复制的用户副本保留当时团队内容与每名成员的已保存运行配置；副本脱离官方来源身份，不再显示官方更新提示。
23. 未保存草稿或外部冲突存在时，更新必须先处理现有状态；副本创建或更新失败后，原团队、运行配置和更新提示保持可见，且不留下半成品或因重试产生重复副本。
24. “有更新”是普通管理状态，不触发“团队需要修复”Sidebar 红点；本页不产生运行配置健康状态。
25. 运行配置草稿独立于 `AGENT.md` 草稿：切换成员不会丢失，离开页面时统一要求保存或放弃；保存成功清除草稿并显示统一生效反馈，保存失败保留草稿并明确仍在使用最近一次已保存配置。
26. 历史未知 model/effort 原值显示为当前列表不支持并保持有效，不能在打开页面或切换成员时被覆盖；只有用户主动选择当前列表中的组合后才替换。
26. 更新前可以看见当前与最新官方版本、成员变化、跟随推荐配置变化和副本保护范围；更新后可以核对实际变化，并从结果提示直接进入稳定命名的用户副本。
27. 官方新增 slug 与用户自行添加的成员同名时，必须保留副本再更新；用户成员及显式配置只留在副本，官方团队使用 C 的成员与推荐配置。
28. 软件正常安装后，团队首页显示官方来源 `general-assistant`「通用助手」；其官方初始结构只有主 Agent `@assistant`，`AGENT.md` 除身份 frontmatter 外没有专业职责、固定流程、交棒或分析权限正文。
29. 「通用助手」初始推荐运行配置为 `Codex / gpt-5.6-sol / high`，且不继承来源会话、被分析 run、最近运行或其他团队配置；用户保存覆盖后，sidebar chat 使用当前用户版本。
30. 「通用助手」与其他官方团队一样可修改信息、成员、主 Agent、`AGENT.md` 和运行配置，也可复制但不可删除；添加成员或改变初始内容后显示“已自定义”，不产生另一套团队生命周期。
31. 「通用助手」完整复用官方三方更新与成员配置保护：升级不静默覆盖，显式更新时按现有规则直接更新或先保留副本，用户运行配置覆盖不丢失。
32. 「通用助手」位置或成员文件不可用时显示“需要修复”且不能用于首次发送；应用不静默重建、换团队或换模型。重新定位、外部恢复，或添加有效成员并切换主 Agent 后移除失效成员，可以解除异常。
33. 普通主会话继续按上次成功团队及固定官方回退顺序预选；右侧栏普通新会话和「分析当前对话」则始终初始预选当前本地 `general-assistant`，发送前可改。首次发送成功前不更新上次使用记录，团队不可用时保留草稿并等待修复或用户主动改选。
34. 从只有两支官方团队的既有安装升级时，缺失的 `general-assistant` 以原子结果首次登记；成功后恰好出现一支官方「通用助手」，不修改原有团队。登记失败不出现半支或重复团队，并提供可重试说明。
35. 用户团队仅与「通用助手」显示名称相同不构成冲突，两支团队直接并存。稳定身份冲突时可以进入现有团队，或执行「保留现有团队并添加官方团队」后看到保留的用户团队与新增官方团队；用户不需要编辑内部标识。文件位置冲突时可从 Finder 核对，并执行「保留现有文件并在新位置添加」；失败不改变现有团队或文件，重试成功后恰好新增一支官方团队。
36. 从右侧栏内容选择手动创建普通 sidebar chat，即使保留初始「通用助手」，也只按[主页面会话区](./main-conversation.md#指标与验收)的普通新会话与已有会话规则运行，不自动获得方案确认或写入闸门。「分析当前对话」入口形成的草稿则始终按[会话分析流程验收 13–15](../flows/session-analysis.md#指标与验收)执行确认与写入边界，即使用户发送前把团队从「通用助手」改成其他团队也不能绕过；闸门归入口流程，不归任何团队身份。
37. 已有有效 `general-assistant` 官方记录时不重复首次登记，而是走三方更新；已有记录但文件异常时进入修复，不得借升级静默重建。
38. 成功保存团队名称与用途、主 Agent、成员构成、`AGENT.md` 或运行配置后，当前操作附近明确显示「已保存，无需重启」，并说明新建对话选择该团队时载入修改、正在使用该团队的会话会出现分类变化提示，点击任一「应用」会载入整支团队最新保存的完整版本。「保存全部并离开」全部成功时，返回团队首页并在团队列表上方显示完整反馈、团队与保存项目数量；部分成功时不离开详情，逐项区分已保存项目与仍使用上一次版本的失败项目，不得显示整体成功，任何会话快照都不能混入失败草稿。无草稿时成功载入的有效外部修改使用同一生效边界；冲突、无效、读取失败或需要修复时不显示成功反馈。

## 非目标

本页面明确不提供：

- 可视化工作流、流程节点、成员连线、组织架构或 DAG 编辑器。
- 脱离团队存在的全局 Agent 库。
- Agent 在团队之间移动、链接或共享同一份可变配置。
- 普通成员手动排序；只有主 Agent 固定排在第一位。
- `AGENT.md` 之外的软件内文件编辑器、文件树、逐行 diff 或官方内容与用户内容自动合并。
- 对自然语言职责和交棒关系做语义正确性验证，或在删除成员后自动改写其他 Agent 的规则。
- 团队发现、在线市场、远程安装、发布或跨来源迁移协议。
- 可由用户设置的应用级默认团队。
- 会话内团队切换和异常恢复的完整交互。
- Codex、Claude Code、Kimi 的独立运行环境诊断、安装、登录和模型能力检查。
- Agent 运行配置如何进入会话快照，以及 Codex、Claude Code、Kimi 的启动、恢复、中止、过程展示和老会话兼容；这些由主对话页定义。
- onboarding 如何展示三套 CLI 环境准备。
- 官方团队的新增、下线、来源迁移，以及文件层事务、崩溃恢复等更新实现细节。
- 软件内永久删除或独立的已删除团队管理页。
