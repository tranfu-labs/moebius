## 页面目标

Agent 团队页让用户看见自己当前拥有的团队，理解每支团队负责什么、由谁主理会话、包含哪些专业成员，并在同一团队上下文中完成创建、复制、修改、修复和文件维护。

团队是本页的基本管理单位。每支团队严格包含自己的一组 Agent，并指定其中一名为主 Agent。Agent 不作为脱离团队的全局对象单独管理；相同角色出现在不同团队时，也视为彼此独立的成员配置。

团队分成两类：**持续接收更新**的团队会继续接收作者更新；**独立维护**的团队不会再接收作者更新，之后由用户自己维护。两类使用完全相同的团队内容、编辑能力、运行配置、文件修复规则和删除能力，区别只是是否继续接收作者更新。

持续接收更新的团队允许本地编辑，不是只读样板。用户可以直接把它改成适合自己的工作方式。作者有新内容时自动合并进来，但用户的意图始终优先：页面通过“上次应用的作者版本、用户当前内容、作者最新内容”三方比较决定怎么合，冲突处保留用户的写法，合并结果记入可整体撤销的修订。用户不需要在“接收作者新版”和“保留自己的改动”之间做选择。

软件随安装包携带的两支团队在 GitHub 上各有上游仓库，走的是同一条更新路径。这样用户不必等 Moebius 发版才能拿到起步团队的改进——`development` 改一版提示词，当天就能到用户手上，和第三方团队一样快。

每名 Agent 除角色内容外，还拥有独立的运行配置：执行引擎、Provider 档案（仅 Pi API）、模型和思考程度。运行配置属于“这支团队中的这名 Agent”，不按 slug 跨团队共享；Codex、Claude Code、Kimi 与 Pi API 地位对等，不可静默互相降级。本页不主动运行 CLI 或调用服务商：CLI 的动态可执行性由会话启动时裁决，Pi 只读取应用已经保存的 Provider 有效状态和已验证模型目录。

本页不把团队呈现为组织架构或固定工作流。团队成员扁平并列，主 Agent 是新会话的默认接单者，也是每轮协作的控制权归属者和可见收尾者；这项责任不代表上下级、固定执行顺序或 DAG 关系。

主 Agent 的 `AGENT.md` 是团队接收新任务和最终收尾时的协作入口；其他成员各自的 `AGENT.md` 定义专业职责和自然语言交棒规则。产品只固定显式交棒与控制权最终回归主 Agent，不尝试从“验收”“通过”“不通过”等自然语言理解或证明专业结论一定正确。

团队进入会话后，成员能够知道当前团队包含哪些 Agent 及其稳定标识，从而按各自 `AGENT.md` 的自然语言规则向同团队成员交棒。该成员清单不等同于固定执行顺序。

## 用户场景

- 用户从 Sidebar 进入 Agent 团队页，查看持续接收更新的团队和独立维护的团队。
- 用户进入软件自带的「通用助手」，确认它只是由一名泛用主 Agent 组成的普通团队，并按需要修改职责、成员或运行配置。
- 用户进入某支团队，确认团队用途、主 Agent 和成员构成。
- 用户看到某支团队来自哪个 GitHub 仓库，点开去看作者为什么这么改，或者给作者提问题。
- 用户手上的任务超出现有团队的能力，直接点击「找现成团队」，去 GitHub 找一支已经配置好的团队。
- 用户直接修改一支持续接收更新团队的团队信息、主 Agent、成员和 `AGENT.md`。
- 用户为同一团队中的不同 Agent 分别选择 Codex、Claude Code、Kimi 或 Pi API，并设置对应模型与思考程度。
- 用户选择 Pi API 后复用一份已就绪 Provider 档案，不为每名成员重复输入 Key；不同成员可以选择同档案的不同已验证模型。
- 用户看到成员保存的 Provider 或模型需要处理、已停用或被下架，选择新的可用配置，或前往设置修复和迁移所有引用。
- 用户回到本页，看到作者新内容已经自动合并进自己的团队，并核对这次改了什么；不满意时整体撤销。
- 用户发现某支团队的来源仓库不见了（被删除、转私有或改名），确认团队还能照常用，并决定是重新检查还是停止接收更新。
- 用户想知道某条 Agent 规则是谁写的、什么时候写的，在 `AGENT.md` 里直接看到来历，必要时回到之前某一版。
- 用户复制任意完整团队，得到内容与当时已保存运行配置都独立演化的独立维护团队。
- 用户创建一支新团队，逐步添加 Agent，并让第一名成员自动成为主 Agent。
- 用户只描述长期工作目标，由 AI 提议一支完整团队，调整满意后一次确认创建。
- 用户在同一团队详情内切换成员，编辑各自的 `AGENT.md`。
- 用户保存团队或成员设置后，立即确认修改已经落盘、无需重启，以及哪些会话会使用它。
- 用户需要维护 `AGENT.md` 引用的其他文件时，在 Finder 中打开团队或成员位置。
- 用户修复被外部移动、重命名、删除或变得不可读的团队文件。
- 用户将不再使用的团队移到系统废纸篓或回收站，需要时再从 GitHub 装回来。

## 入口与去向

### 入口

- 从[主页面侧边栏](./main-left-sidebar.md)顶部的“Agent 团队”进入。
- Sidebar 入口只要发现至少一支团队处于“需要修复”，就在右侧显示一个红点；多支异常团队不叠加数量。
- 红点的悬停提示和辅助名称为“有 Agent 团队需要修复”，不能只依赖颜色传达含义。
- 未完成草稿、“已自定义”、刚完成的上游同步和上游失联都是普通管理状态，不触发 Sidebar 红点。同步进行中与同步完成的临时提示位于侧边栏底部，是另一套表达，不使用红点，见[主左侧栏](./main-left-sidebar.md)。

### 去向

- 点击团队首页的一整条团队横行，进入该团队详情。
- 首页的「找现成团队」进入[找现成团队](./github-team-discovery.md)；安装成功后回到本页，新团队出现在「持续接收更新」分组里。
- 团队横行与团队详情中的来源仓库名在浏览器中打开该 GitHub 仓库。变化时间线中的作者修订可以打开对应的 commit 页面。
- 团队详情中的成员行同时是成员选择器；点击后在当前页面下方切换对应的 `AGENT.md`，不进入独立 Agent 页面。
- “在 Finder 中打开”打开团队或当前成员对应的位置，供用户维护本页不负责编辑的相关文件。
- 返回团队首页时，保留此前的滚动位置；返回主页面时，恢复离开前的项目、对话和 Sidebar 状态。

## 页面结构

### 内置团队与上游

软件随安装包携带两支团队：

- `development`：开发团队，由开发经理主理，负责软件方案、实现、测试、复核和收尾。
- `general-assistant`：通用助手，由唯一成员 `@assistant` 主理，用于没有预设专业分工的一般对话与任务。

**安装包携带的只是离线首启可用的副本，不是更新来源。** 两支团队在 GitHub 上各有自己的公开上游仓库，安装后按与任何第三方团队完全相同的规则持续接收更新。这样起步团队的改进不必等 Moebius 发版。

上游仓库归属 `tranfu-labs`，一仓库一团队一语言：`moebius-team-general-assistant`、`moebius-team-development` 是英文版，加 `-zh` 后缀的是中文版。首启携带哪个语言版本按安装时的界面语言决定。

### 持续接收更新与独立维护

团队只有两类，没有第三类：

| 类别 | 含义 | 更新方式 |
| --- | --- | --- |
| 持续接收更新 | 团队会继续接收作者更新 | 作者有新内容时自动三方合并 |
| 独立维护 | 团队不会再接收作者更新 | 只有用户自己改才会变 |

两类使用完全相同的磁盘结构、编辑能力、运行配置、文件修复规则、复制能力和删除能力。**任何团队都可以删除**，包括安装包携带的两支——它们能从 GitHub 装回来，禁止删除只剩下强迫用户留着不用的东西。

“持续接收更新”表示 Moebius 知道去哪里取新内容，不表示用户内容只读。自动合并绝不静默替换用户改过的部分——冲突处保留用户的写法，整次同步可以整体撤销；独立维护的团队不参与任何比较。

用户主动复制出的团队不继承上游记录，复制品是独立维护的团队。用户也可以主动把一支持续接收更新的团队停止接收更新，见「上游失联」。

### 「通用助手」的初始内容

「通用助手」不是新的会话模式、分析模式或绕开团队系统的裸模型入口。它是一支正常可见、可选择、可复制、可编辑、可删除的普通团队，并完整参与首页陈列、团队详情、三方更新、自定义标记、文件异常和 Sidebar 修复红点。

上游初始版本固定为：

- 团队稳定标识：`general-assistant`；显示名称：「通用助手」。
- 唯一成员稳定 slug：`assistant`；显示名称：「通用助手」；该成员同时是唯一主 Agent。
- 初始 `AGENT.md` 只包含有效身份 frontmatter：`display_name: 通用助手`、`description: 处理一般对话与任务`，正文不附加专业职责、固定流程、团队交棒或分析权限。它仍完整受 Moebius 的系统提示、团队、主 Agent、会话和工具权限规则约束，不是裸模型入口。
- 该成员的上游推荐运行配置为 `Codex / gpt-5.6-sol / high`。这是本团队自己的推荐配置，不继承来源会话、最近一次运行、其他团队或被分析 run 的执行引擎、Provider、模型与思考程度。

单成员只表示初始结构，不是永久限制。用户可以编辑成员内容和运行配置、添加成员，并在存在另一名有效成员后切换主 Agent 或移除原 `@assistant`；这些修改按普通持续接收更新团队显示“已自定义”。用户也可以主动复制出不再持续接收更新的本地团队。

「通用助手」的更新完整复用三方比较与自动合并：上游有新内容时自动合并进来，冲突处保留用户的写法，结果记入可整体撤销的修订；创建 sidebar chat 不触发任何合并。上游推荐配置只对仍“跟随推荐”的成员生效，用户覆盖保持原值。

「通用助手」的修复也不设特殊后门：

- 团队位置不可用时标记“需要修复”，通过“重新定位团队”指向同一团队；上游记录与稳定身份在修复过程中保持不变。
- `@assistant` 的 `AGENT.md` 缺失或不可读时，整支团队不可用于新会话。用户可以从 Finder 恢复文件，或先添加另一名有效成员、将其设为主 Agent，再移除失效成员。
- 修复完成前不参与上游同步，也不能用于首次发送；应用不会静默重建团队文件、改用别的团队或换成其他模型。
- [会话分析流程](../flows/session-analysis.md)中的草稿仍保留「通用助手」选择和用户内容，明确提示修复；用户也可以在发送前主动改选另一支可用团队。

### 存量安装的迁移

从携带九支官方团队的旧版本升级时，本地已有的团队一支都不删、不改名、不覆盖，也不要求用户做任何确认。改变的只是它们今后从哪里取更新：

- `general-assistant` 与 `development` 登记对应的 GitHub 上游仓库，此后按持续接收更新的规则更新。登记只写上游记录，不改动团队内容、成员构成、运行配置或已有会话关系。
- 其余七支（`content-production`、`dev-delivery`、`feedback-driven-engineering`、`marketing-promotion`、`product-development`、`product-governance`、`ui-delivery`）不再有上游，转为**独立维护**的团队。它们照常可用、可编辑、可复制、可删除，只是不会再自己变。
- 用户主动复制出的团队原本就没有上游记录，迁移后仍是独立维护的团队，行为不变。
- 迁移不询问、不弹窗、不生成待办。用户下一次进入团队首页时，看到的差别只有分组标题从「内置团队 / 我的团队」变成「持续接收更新 / 独立维护」，以及持续接收更新的团队多了一个仓库名。
- 上游登记失败（例如首启时没有网络）不阻塞任何事：团队照常可用，下次进入本页或下次启动重试。在登记成功之前，这支团队显示为独立维护，不显示错误。

这条迁移不承诺让七支被移除的团队继续收到改进——它们的目录已不在安装包里，产品也不为它们建立上游。用户想继续演进其中某一支，可以自己把它推成一个仓库并按[团队仓库约定](./github-team-discovery.md#团队仓库约定)打上 topic。

### 上游失联

上游是别人的仓库，消失是必然会发生的事：作者可能删库、转私有或改名。检查更新时取不到上游仓库，团队详情的横幅位置显示失联状态。

```text
← Agent 团队

开发团队      tranfu-labs/moebius-team-development     已自定义

┌ 这支团队照常能用，只是不再接收作者更新 ──────────────────┐
│ 找不到 tranfu-labs/moebius-team-development 了。          │
│ 仓库可能被删除、转成私有或改了名。                        │
│                          [重新检查] [停止接收更新]        │
└───────────────────────────────────────────────────────────┘
```

- **先说“还能用”，再说发生了什么。** 用户看到这条时的默认猜测是团队坏了，标题的职责是消除这个误会，不是报告技术事实；仓库名和可能的原因放进说明里。
- 失联是普通管理状态：团队照常用于新建对话和已有会话，不触发 Sidebar 修复红点，不阻塞编辑或保存。
- 「重新检查」重新访问上游一次。仓库回来了就恢复正常并照常合并；仍然取不到就留在失联状态，不累计错误次数，也不退避到更长的重试间隔而不告诉用户。
- 「停止接收更新」只解除这支团队后续接收作者更新的关系，把它移进「独立维护」分组。团队内容、成员、运行配置、变化时间线和已有会话关系全部保留，用户仍可继续使用和维护。这个动作不可自动撤销——用户之后想重新接收作者更新，需要从 GitHub 重新装一份。因此确认时说明这一点。
- 只是暂时连不上 GitHub（无网络、DNS 失败、GitHub 不可用）不算失联，不显示这条横幅。产品只在能确认“仓库不存在或当前账号看不到”时才判定失联；分不清是哪一种时，按暂时连不上处理，静默等下一次检查。这条偏保守是有意的：把临时断网说成“仓库没了”，会让用户白白断开一个还活着的上游。
- 私有仓库因为本地 gh 登录态变化而看不到时，同样归为失联，说明文字里的三种可能已经覆盖“转成私有”。用户重新登录 gh 后点「重新检查」即可恢复。

### 运行配置静态校验

运行配置先选择执行引擎。Codex、Claude Code 与 Kimi 使用产品内置的 CLI → model → effort 联动列表，不从本机 CLI 动态枚举；切换 CLI 时进入该 CLI 的兼容默认组合，切换 model 时保留仍受支持的 effort，否则采用该 model 的默认 effort。没有已保存配置或上游推荐的成员仍直接使用 `Codex / gpt-5.6-sol / high`，用户无需先打开或保存设置。

Codex 首版列表为 `gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna`、`gpt-5.5`、`gpt-5.4`、`gpt-5.4-mini`；每个 model 只显示其各自支持的 effort。首版不展示会启用自动任务委派的 `ultra`，也不展示 Pro-only research preview `gpt-5.3-codex-spark`。Kimi 首版保存 ACP 精确匹配所需的完整 CLI alias：`kimi-code/k3`、`kimi-code/k3-256k`、`kimi-code/kimi-for-coding`、`kimi-code/kimi-for-coding-highspeed`；受会员等级限制的 model 在选项中标注权限要求。

Claude Code 首版使用 CLI 官方稳定、且能够满足现有 model + effort 精确冻结契约的
alias `fable`、`sonnet` 与 `opus`。`fable` 提供官方支持的
`low / medium / high / xhigh / max`；`sonnet` 与 `opus` 只提供跨当前官方 provider
解析结果共同支持的 `low / medium / high / max`。后两者在部分 provider 解析到不支持
`xhigh` 的模型并会静默回落，因此首版不提供其 `xhigh`。模型实际可用性仍取决于用户的
Claude 账号、组织策略与 provider。首版不提供会动态切换模型的 `default`、`best`、
`opusplan`，不提供随版本变化的完整模型 ID、1M context alias 或没有 effort 选择的
`haiku`；这些值若来自历史配置，继续按旧版自定义配置保留。用户把 CLI 切换到
Claude Code 时使用 `sonnet / high` 作为兼容默认组合。

Pi API 不使用 CLI 静态模型列表，而读取应用级 Provider 档案的已保存状态：

- 切换到 Pi API 后，只把有效状态为“已就绪”的档案列为新选择；“正在验证”期间仍以验证前的有效状态为准。没有已就绪档案时显示空态和“前往设置添加服务商”，保存禁用。
- 只有一份已就绪档案时可以可见地预选；存在多份时必须由用户明确选择，不根据列表顺序或最近运行静默决定。选择档案后，只有默认模型仍可用时才以它预选，并允许改选同档案其他可用已验证模型。档案为“已就绪 · 需设置默认模型”时仍允许选择，但模型字段保持空白并提示“默认模型已下架，请明确选择”；用户必须亲自选择另一可用已验证模型后才能保存，页面不得静默代选。
- Provider 默认模型后来变化不回写成员草稿或已保存模型。成员保存的是稳定 Provider 档案身份、该档案不可变的服务商、明确模型和思考程度；完整 Key 不进入团队文件、运行配置表单或可复制内容。
- 思考程度从所选服务商与模型实际声明的选项中选择。无法可靠控制时不显示选择器，改为说明“该模型使用固定思考程度”，并保存目录规定的固定值；不伪造与 Codex 相同的档位。
- 选择和保存 Pi 配置不会调用服务商，也不产生 API 用量；页面只读取最近已保存的验证状态。保存瞬间若档案、模型或目录状态已经变化，保存失败并刷新真实状态，旧配置继续生效。

页面始终保留历史上已经保存但不在当前内置列表中的 CLI model/effort 原值，并将它们显示为“旧版自定义配置（当前列表不支持）”；打开页面、切换成员或保存其他成员都不得静默覆盖。用户为该成员选择当前列表中的 model 后，才用受支持组合替换旧值。页面仍不读取本机 CLI，也不因为当前机器的安装、登录或会员权限状态而改值或阻止团队管理。

已保存的 Pi 配置若后来进入“需要处理”“已停用”、服务商已移除或模型不可用，表单继续显示原档案名称、服务商、模型和思考程度，并标出准确原因；不把它从字段中抹掉，也不自动切到另一档案。该历史值不是未保存草稿，用户可以只查看；一旦开始修改，只允许保存新的已就绪组合，不能把异常值原样重新提交。用户可以“前往设置修复或迁移全部引用”，也可以只为当前成员选择另一项已就绪配置。后者只改变这名成员之后创建的新会话，不回写既有会话。理论上已被引用的档案不能删除；若导入或损坏数据仍产生缺失档案引用，按“历史 Provider 不可用”保留原标识并要求用户明确重选。

```text
运行配置                                      用户覆盖
┌──────────────────────────────────────────────────────────────┐
│ 执行引擎        [ Kimi                                   ▾] │
│ 模型            [ future-model（旧版自定义配置）          ▾] │
│ 思考程度        [ future-effort（当前列表不支持）         ▾] │
│                                                              │
│ 旧版自定义配置会保留；选择当前支持的模型后才会替换。        │
└──────────────────────────────────────────────────────────────┘
```

### 变化时间线

点击 `AGENT.md` 标题行右侧的“全部”，就地在编辑器上方展开这名成员的完整变化时间线，不跳转、不打开第二个界面。时间线按次列出修订，每条只有一句说明和作者，不显示逐行对比、内容指纹或保存时刻的技术细节。

```text
AGENT.md          最近变化 · 上游 a3450d6 更新了 2 处       全部 ▴

┌ 开发经理的变化 ──────────────────────────────────────────────┐
│ 来自上游 a3450d6   2026-08-06                    [在 GitHub 上看] │
│ 收紧了交付汇总的证据要求，保留了你写的返工轮次上限           │
│                                          [回到这一版]        │
│                                                              │
│ 你               2026-08-03                                  │
│ 把自动返工上限从三轮改成两轮                                 │
│                                          [回到这一版]        │
│                                                              │
│ 来自上游 82d0fdd   2026-07-28   装上这支团队时的版本         │
└──────────────────────────────────────────────────────────────┘
```

上游修订的署名是 commit，不是版本号。用户翻时间线是想知道“这句话是谁改的、为什么”，署名指向 commit 才能真正回答——「在 GitHub 上看」打开该 commit 页面，那里有作者、完整 diff 和 commit message；版本号只是个编号，回答不了任何问题。用户自己的修订署名为“你”，不带外部链接。

独立维护的团队，时间线里只有“你”的修订，结构和入口完全一样。

成员级时间线只做单成员的回退，不承载整支团队的撤销。整支团队的撤销由同步结果横幅和团队“更多”菜单中的“最近的上游同步”承担，见下文。规则见[Agent 进化流程](../flows/agent-evolution.md)。

### 最近的上游同步

整支团队的撤销必须一直找得到，因此它有两个并列入口，指向同一份内容：

- 同步完成后，团队详情页标题下方的同步结果横幅。它**不会自动消失、也不会自动过期**，跨重启保留，只有用户点“×”或执行撤销后才收起。
- 横幅收起后，团队“更多”菜单中的“最近的上游同步”。它常驻可用，不设期限，打开后是同一份内容与同一个撤销按钮。

```text
主 Agent  [开发经理 ▾]             [修改信息] [更多 ▾]
                                              ├─ 最近的上游同步
                                              ├─ 复制团队
                                              ├─ 在 Finder 中打开
                                              └─ 移到废纸篓

┌ 已同步到上游 a3450d6 · 2026-08-06 ──────────────────────┐
│ 新增 release，移除 qa，dev 的职责有更新                   │
│                        [看看改了什么] [撤销这次同步]      │
└───────────────────────────────────────────────────────────┘
```

- 这个入口只保留最近一次上游同步。下一次同步发生时，它被新的一次替换；被替换掉的那次不再提供整体撤销，其内容仍逐条留在各成员的变化时间线里，可以逐名回退。
- 团队从未经历过上游同步、或最近一次同步已经被撤销时，菜单项不显示，不显示为禁用项。
- 独立维护的团队没有这个菜单项。


- 未确认的 AI 对话和方案是建队草稿，不属于正式团队，不显示在团队首页，也不参与新建对话选择。
- 用户确认前，方案必须按 [onboarding 的共享规则](./onboarding.md#第-2-步--ai-建队子流程)逐名显示初始执行引擎、Provider、模型和实际支持的思考程度；纯 API 用户创建的成员不得回落到 Codex 默认值。
- 用户确认后，团队内容、成员与逐名运行配置作为同一原子结果创建为一支独立维护的团队并进入团队详情；从此与空白创建或复制创建的独立维护的团队具有完全相同的编辑、修复、复制和删除能力。
- AI 建队、从空白开始、复制团队是并列路径：AI 从工作意图生成新团队，空白创建提供完全手工控制，复制从已有团队派生变体。
- AI 建队的提示契约、所选 CLI 或 Pi 执行会话、结构化输出、校验、失败恢复与原子创建边界以 [onboarding.md「AI 建队技术约束」](./onboarding.md#ai-建队技术约束)为共享事实，不在本页复制第二套规则。

### 保存结果反馈

详情页的单项成功和部分失败反馈紧邻本次保存操作；“保存全部并离开”全部成功后，反馈随导航进入团队首页并固定在团队列表上方：

```text
┌ 已保存，无需重启 · 开发团队 · 3 个项目 ─────────┐
│ 新建对话会使用修改；旧对话会显示变化提示。       │
└──────────────────────────────────────────────────┘

部分成功：
已保存：开发经理 AGENT.md、测试运行配置
未保存：开发 AGENT.md（仍使用上一次保存的版本） [重试]
```

失败草稿不进入会话 candidate/effective snapshot；冲突、无效或读取失败不显示成功反馈。

## 区域与信息

### 页面标题与任务入口

- 页面标题固定为“Agent 团队”。
- 首页常驻显示两个平级任务入口：「找现成团队」和「新建团队」。用户可以直接选择寻找或创建，不需要先理解菜单层级。
- 「新建团队」展开后只提供：「跟 AI 聊出一支新团队」和「从空白开始」。寻找现成团队不属于新建路径。
- 复制团队仍只出现在已有团队详情的“更多”菜单中，不塞进“新建团队”菜单，因为它必须先有明确复制来源。加上寻找、创建和复制，用户共有四条路径。
- 页面不提供独立的全局 Agent 库入口。

### 团队横行

每条团队横行包含：

- 团队名称。
- 持续接收更新的团队显示来源仓库名 `owner/repo`，可点击打开 GitHub；无障碍名称为「来源仓库 {owner/repo}」。独立维护的团队这个位置为空，不显示“独立维护”字样——分组标题已经说过了。
- 一句话用途描述。
- “已自定义”“未完成”或“需要修复”等必要状态。不存在“有更新”状态，原来的“官方来源”徽标也已取消——团队的行为来自谁写的提示词，仓库名说得比“官方”准确，「官方」两个字反而掩盖了这个信息。
- 刚被上游同步改动过、用户还没进过详情页的团队额外显示“作者有新更新”。它表示**已经发生**的事，不是待办：用户不点也没有任何后果，进入该团队详情后标记消失，不跨用户重新出现。它是用户从侧边栏同步提示进入首页后，用来定位是哪几支团队被改过的唯一依据，因此不能省略。
- 来源暂时不可用的团队不在横行上标注。来源问题不影响使用，把它铺到首页只会制造一排看不懂的警告；用户进入详情后才看到状态提示。
- 若存在 Pi Provider 需要处理、已停用、服务商已移除或模型不可用，以中性状态显示“n 名成员的运行配置需要处理”；这不是团队文件异常，不使用修复红点，也不隐藏成员。
- 成员数量和主 Agent 名称。
- 主 Agent 排在第一位的扁平成员示意。
- 每个可读成员在名称左侧显示统一尺寸的圆形画像。
- 进入详情的整体点击区域。

成员显示名称和一句话描述来自各自 `AGENT.md` 中的对应信息；团队横行和详情不再维护一份独立、可能漂移的成员摘要。

### 默认 Story 与验收入口

- 默认首页直接显示并启用「找现成团队」，不需要先展开「新建团队」菜单。
- 点击「找现成团队」进入[找现成团队](./github-team-discovery.md)，页面标题与入口名称保持一致。
- 默认 Story 不得落在无原因的禁用状态；若特定 Story 确实不可用，显示该 Story 的实际原因。

这条规则没有例外：团队位置不可用时读不到成员 `AGENT.md`，横行的成员区显示占位说明，**不回落到任何缓存的成员名称或数量**。团队名称和一句话描述仍来自应用记录，用户据此识别这是哪一支团队；成员构成属于必须实时读盘的事实，宁可显示不出来，也不显示一份可能与磁盘不符的旧名单。

团队横行不常驻修改、复制或删除按钮。首页负责陈列、识别和进入，具体管理操作进入详情后完成。

### 扁平成员表达

- 不绘制连接线、箭头、环形轨道、中心节点、树形缩进或上下层级。
- 所有成员使用相同尺寸和视觉权重。
- 团队首页成员项、详情成员选择器和当前成员标题对同一名成员显示同一张圆形画像；画像与其底色只用于识别「这是谁」，不表达层级、执行顺序或状态。
- 主 Agent 只通过排在第一位和“主 Agent”标签表达。
- **成员顺序可由用户直接拖拽调整，第一位即主 Agent。** 拖到第一位就是任命，不需要再去别处切换；键盘等价操作见「切换主 Agent」。
- 第一位之外的先后**不表达执行顺序、优先级或层级**，只是用户自己的排列。产品不得在任何地方据此推断调度顺序，也不得用它渲染序号、编号或连接关系。
- 首页空间不足时显示前几名成员和 `＋N`；详情页保持单行并允许横向滚动。

### 团队身份

所有完整团队的“修改信息”只负责团队名称和一句话描述，不展开成员 `AGENT.md`。持续接收更新的团队允许修改这些内容；上游记录本身不在“修改信息”里编辑，用户只能通过「停止接收更新」整体解除它。用户主动复制出的团队不继承上游记录，之后不参与上游同步。

本产品不存在可由用户设置的应用级“默认团队”。普通主会话只记住上一次成功创建会话时使用的团队，供下一次新建对话预选。「通用助手」是 sidebar chat 的上下文专属初始预选，不会因此成为所有新会话的全局默认，也不会在用户尚未发送时改写“上一次使用”记录。

### 主 Agent

- 每支可用团队必须且只能有一名主 Agent。
- 主 Agent 必须是当前团队成员。
- 主 Agent 是所选团队进入新会话后的默认接单者，也是每轮协作最终接回控制权并向用户可见收尾的主理人；它不是其他成员的父节点或管理层级。
- 任命主 Agent 的能力长在成员条自己身上——把成员拖到第一位即可，键盘等价操作见「切换主 Agent」。不再另设主 Agent 下拉：同一件事有两个入口只会让两者有机会不一致，也让「位置即任命」这个模型失去说服力。切换能力同样不得藏入“修改信息”或“更多”。
- 第一个成员自动成为主 Agent。
- 删除当前主 Agent 前，必须先指定另一名有效成员。

### Agent 身份与说明

- 每个 Agent 在创建时取得一个团队内唯一的稳定 slug，用于团队内识别和协作引用；创建后不因修改显示名称而变化。
- Agent 的显示名称和一句话描述以 `AGENT.md` 为唯一事实源，MUST 写在文件开头的 YAML frontmatter，字段固定为 snake_case 的 `display_name` 与 `description`；正文标题与段落只表达 persona，不再兼任机器元数据。
- **但它们在界面上是两个普通表单字段，不是让用户手写 YAML。** 当前成员区顶部直接就是可编辑的名称与一句话描述（画像在其左侧），保存时由产品合成回 frontmatter。`AGENT.md` 的编辑态只呈现正文，frontmatter 不出现在文本框里。理由有二：一级字段用纯文本编辑既难用、又让用户有机会把结构改坏而使团队进入「需要修复」；而添加成员本就使用固定初始身份，若不给表单，用户改名的唯一途径就是编辑 YAML。
- 当前成员区不再另设只读的名称标题——名称与描述只出现一次，就是那两个字段本身。
- 成员目录名是稳定 slug 的唯一事实源，frontmatter MUST NOT 再复制 `name` 或 slug 字段。
- 为兼容既有团队，只有在 frontmatter 完全没有 `display_name` 与 `description` 时，产品才从正文首个一级标题与其后首段回退读取旧格式身份；一旦出现任一新身份字段，两项都必须是非空单行字符串，缺项或非法值必须显示为需要修复，不得静默混用新旧来源。
- 团队首页、成员行和当前 Agent 标题都读取 `AGENT.md` 中的显示名称和一句话描述。
- 本页不提供修改稳定 slug 的入口，也不把显示名称变化视为另一个 Agent。
- slug 仍是稳定引用的事实源，但**团队详情不为它设常驻展示或复制入口**：正文里输入 `@` 就有成员自动补全，手抄 slug 是个不存在的需求，常驻只是占地方。需要看 slug 时走 Finder 或提及组件自身的披露。
- 画像只用于快速识别；可读名称、稳定 slug、主 Agent 与可用状态仍由现有文字和语义表达，不能只依赖画像。

### Agent 画像

- 每名 Agent 有一张画像，作为在团队首页、成员选择器、当前成员标题和会话时间线中快速认出「这是谁」的锚点。画像取自产品内置的固定素材池，不表达职业、层级、状态或品质：任何角色都可能取到池中任何一张脸。
- 画像属于「某支团队中的某名 Agent」，与运行配置存在同一份应用记录中，不写入 `AGENT.md`。相同 slug 出现在不同团队时，画像彼此独立。
- 用户没有设置过时，按稳定 slug 从池中取一张作为默认，用户无需先设置就能看到一张稳定且团队内尽量不重复的脸。
- 用户可更换的只有画像本身。**底色不是可选项**：它沿用该成员现有的身份色，不随画像更换而改变；选择器中的所有候选画像都以该底色渲染，让用户在真实呈现下比较，而不是在中性背景上挑完再被底色改变观感。
- 更换入口是当前成员的画像本身，不新增独立按钮，也不进入设置页。打开后顶部居中常驻一个大尺寸预览，显示这名成员当前的样子；下方平铺整池候选，当前生效项有明确选中态。
- 选中不关闭选择面：预览原地换成新选的那张，用户才能连着比较几个候选。点选即关会让人只能在做完选择之后才看清一张。
- 不提供「恢复默认」入口：默认那张脸本身就在候选里，点它即可；而「显式选过」与「跟随默认」的区别用户看不见，不该为它造一个按钮。未保存前反悔走既有的「放弃修改」。
- 选择面里不解释画像的设计意图。用户打开它只为挑一张脸，产品自己的取舍写在设计文档里，不写进界面。
- 素材池随 Moebius 版本发布。用户不能上传自定义图片，也不能引用本机或网络图片——整池风格统一是这套画像可读的前提，一张风格不同的图片会同时破坏它自己和它周围所有成员的识别效率。
- 画像不自动保存：与 `AGENT.md`、运行配置一样进入当前成员草稿，跟随同一套「保存」以及离开团队详情时的「继续编辑 / 放弃全部 / 保存全部并离开」保护流程。草稿期间团队详情内立即预览新画像，未保存前不改变其他页面与已有会话的呈现。
- 持续接收更新的团队成员同样可以更换画像，规则与运行配置一致：只更换画像不产生「已自定义」内容标记，也不参与上游更新的三方比较，作者新内容不会覆盖用户已设置的画像。
- 画像是识别锚点而不是运行事实：各处始终显示该成员当前画像，不随会话冻结，历史消息的 run 事实浮层也不记录画像。
- 团队横行的圆角方画像代表这支团队的主 Agent，跟随该成员当前画像变化，不单独设置；换主 Agent 时它跟着换人。

### Agent 运行配置

下拉选择器由产品自绘，不使用系统渲染的原生列表：原生列表的样式无法参与产品的面与配色，在深色界面里会弹出一块与四周无关的系统面板。展开动效只做纵向——列表宽度就等于触发器宽度，横向没有可生长的余地；贴边翻转到上方时改为向上展开。

运行配置属于“某支团队中的某名 Agent”，与该成员的角色内容并列，但不写入 `AGENT.md`。相同 slug 出现在不同团队时，运行配置彼此独立。

每名 Agent 的运行配置包含：

- 执行引擎：支持 Codex、Claude Code、Kimi 与 Pi API，四者地位对等；绑定后不自动降级或替换成另一执行引擎。
- Provider 档案：只在 Pi API 下出现，引用一份应用级稳定档案；显示服务商和档案名称，不显示或复制 API Key。
- 模型：CLI 从产品内置兼容列表选择；Pi 从所选档案的可用已验证模型选择。保存执行端要求的精确模型标识。
- 思考程度（effort）：从当前执行引擎、服务商与模型实际支持的列表中选择；Pi 无可控档位时隐藏选择器并保存固定值，不把不同模型能力合并成通用列表。
- 配置来源：持续接收更新的团队中的上游成员为“跟随推荐”或“用户覆盖”；用户自行添加的成员、独立维护团队的成员使用显式配置。

没有已保存配置或上游推荐时，默认组合为 `Codex / gpt-5.6-sol / high`，无需用户先设置。Codex 内置列表排除会改变 Moebius 交棒架构的 `ultra` 与 Pro-only preview `gpt-5.3-codex-spark`；Claude Code 使用稳定的 `fable` / `sonnet` / `opus` alias 与各自可精确冻结的 effort 列表，切换到 Claude Code 时默认 `sonnet / high`，不把动态默认、混合模式、长上下文变体或完整版本 ID 作为首版选择；Kimi 使用带 `kimi-code/` 前缀的 CLI alias，并在受限选项上标注会员权限。列表更新随 Moebius 版本发布，不读取本机 CLI 生成选项。

用户修改执行引擎、Provider、模型或思考程度中任一字段并保存后，该上游成员进入“用户覆盖”。作者新内容可以更新同一稳定 slug 的推荐运行配置，但只有“跟随推荐”的成员会在用户确认团队更新后采用新版推荐；“用户覆盖”始终保留原值。上游内容不能引用用户本机的 Provider 档案，因此上游推荐只使用可移植的 CLI 组合；成员改用 Pi API 必然是用户覆盖。点击“恢复推荐配置”会清除该成员的用户覆盖，恢复到**当前已应用上游 commit**为该 slug 提供的推荐 CLI 组合；尚未应用的作者新内容不能提前改变这个结果。

用户自行添加且没有上游 slug 推荐来源的成员不显示“恢复推荐配置”，也不伪造上游推荐。复制团队时，每名成员当时已保存的执行引擎、Provider 档案引用、模型和思考程度都复制到新团队，并固化为新团队自己的显式配置，之后与来源团队独立演化。复制 Pi 成员继续复用同一应用级档案，不复制 Key，也不新建档案。

运行配置不自动保存，也**不设自己的保存按钮**：它和名称、描述、`AGENT.md` 正文一起归入当前成员那唯一的「保存」（见「当前成员的保存」）。修改后当前成员显示未保存标记；切换成员时草稿继续保留，多名成员可以同时拥有未保存的运行配置。保存成功后清除该草稿并按下文统一生效反馈确认；失败时保留原草稿、显示原因和重试入口，不能让用户误以为新配置已经生效。

页面**不重复陈述「此配置独立属于某团队的某名成员」**。这是系统规则而非当下事实，常态下每次都念一遍只是噪音；来源已由「跟随推荐 / 用户覆盖 / 已显式配置」标签表达。只有当同一 slug 确实还存在于其他团队、用户可能被这次修改的影响范围意外时，才在该处说明。离开团队详情时，运行配置草稿与 `AGENT.md` 草稿一起进入现有“继续编辑 / 放弃全部 / 保存全部并离开”保护流程；“保存全部”需要逐项报告失败成员，已经成功保存的项目不回滚。Pi 草稿保存前重新读取档案和模型状态；已不再就绪时只让该成员保存失败，其他成员的成功项不回滚，原已保存配置继续生效。

当前成员成功保存时，运行配置与 Provider 团队成员引用作为同一个可见结果更新：从 Pi 切到 CLI 或另一档案后，旧档案不再把该成员计为引用；切到 Pi 后，新档案立即显示这名成员。任一步失败都保持原配置和原引用计数，不出现成员显示新配置、设置页仍引用旧档案的分裂状态。既有会话对旧档案的冻结引用不因团队成员改配而解除。

只修改运行配置不会让团队出现“已自定义”内容标记。CLI 选项仍只使用内置 registry，不启动 CLI，也不判断当前机器是否安装、登录或拥有相应会员权限；Pi 选项读取 Provider 已保存状态，但不调用服务商。历史已保存的未知 CLI 组合继续可读、可复制、在上游同步中作为用户覆盖受保护并进入新会话快照，且只在用户主动选择受支持组合后替换。

Pi Provider 或模型异常形成独立的“运行配置需要处理”，不等同于团队文件“需要修复”，也不触发 Sidebar 的团队修复红点。团队首页和成员行显示受影响人数或原因，团队仍可被选择；真正启动受影响成员时由会话页阻止并提供修复或改配入口。页面不得因为异常静默改用 CLI、档案默认模型或另一 Provider。设置页的批量迁移会刷新这里的已保存配置；用户在本页单独改配只影响当前成员之后创建的新会话，既有会话继续使用其冻结快照。

### Provider 引用与团队生命周期

设置页的团队成员引用必须与团队页可见结构保持一致。以下操作把团队或成员结果与 Provider 引用增减作为同一个用户可见提交；任一步失败都保留操作前的团队结构、运行配置和设置引用清单，不允许先出现团队、稍后再补引用：

| 团队页操作 | Provider 团队成员引用结果 |
| --- | --- |
| AI 建队确认创建 | 为最终方案中每名 Pi 成员新增一条引用；团队、全部成员配置与引用一起成功 |
| 空白团队中保存 Pi 成员 | 该成员正式保存时新增引用；未保存草稿不计引用 |
| 复制单个 Agent | 复制品成功出现时，为其 Pi 档案新增引用；失败不产生复制品或引用 |
| 主动复制团队 | 为副本中的每名 Pi 成员新增独立引用；来源团队引用保持 |
| 上游同步自动合并 | 跟随推荐的 CLI 成员不产生 Provider 引用；任何保留的 Pi 用户覆盖继续保持原引用；因用户改动过而留在团队里的成员保持其原有引用 |
| 撤销一次上游同步 | 引用回到同步前的状态；同步中被移除的成员恢复引用，同步中新增的成员解除引用 |
| 删除成员 | 成员从团队消失时解除该成员的团队引用；失败时成员和引用都保留 |
| 删除独立维护的团队或未完成草稿 | 团队从产品记录和选择器消失时解除其全部团队成员引用；失败时团队和引用都保留 |

引用清单使用团队与稳定成员 slug 区分每一项，复制后即使显示名称相同也能分别列出。解除团队成员引用只表示团队默认配置不再使用该档案；既有 AI 建队草稿、任务和可恢复会话的引用不受影响，尤其不能因删除成员或团队而解除既有会话冻结引用。设置页只有在所有类别引用都清零后才允许删除档案。

### Agent 提及与选择

- 在软件内编辑 `AGENT.md` 时，输入 `@` 和 Agent slug 可以匹配当前团队成员；匹配结果同时显示成员的可读名称和 `@<slug>`。
- 用户选中成员后，编辑器显示以可读名称为主的提及组件，不让 slug 成为正文里的主要视觉噪声。
- 提及组件底层仍保存 `@<slug>`；使用 Finder 或其他编辑器打开原始 `AGENT.md` 时，看到的是稳定的 `@<slug>` 文本。
- 提及组件悬停或获得键盘焦点时，可以查看并复制底层 `@<slug>`。
- 显示名称改变后，既有提及组件自动显示新名称，但底层 slug 和引用关系不变。
- 自动补全只帮助选择当前团队成员，不允许从团队外引入共享 Agent，也不验证整段自然语言交棒是否合理。

### 成员选择器与 Agent 编辑区

- 成员选择器和 Agent 编辑区都属于团队详情，不新增独立 Agent 页面。
- 点击成员只切换下方当前编辑对象。
- 软件内只编辑成员的 `AGENT.md`；它引用的其他文件不在软件内展示文件树或提供编辑器。
- 当前成员菜单承接“在 Finder 中打开”“复制 Agent”和“删除 Agent”。持续接收更新的团队中的成员也可修改、复制或删除；删除或复制不能改变团队稳定的上游记录。
- 团队之间不移动 Agent。需要复用时复制团队或复制当前团队中的 Agent，复制后独立演化。
- 删除成员前必须提示：其他成员的自然语言交棒规则可能仍引用该成员，产品不会自动理解或改写这些规则。用户确认后仍可删除；删除成功同时解除该成员的 Provider 团队引用，失败时成员与引用都保留。只要剩余结构继续满足可用条件，团队不因此自动进入“需要修复”。

### Finder

- 团队“更多”菜单中的“在 Finder 中打开”打开整支团队对应的位置。
- 持续接收更新的团队经历过上游同步、且最近一次同步尚未被撤销时，团队“更多”菜单还提供“最近的上游同步”，见[最近的上游同步](#最近的上游同步)。
- 当前成员菜单中的同名操作打开当前成员对应的位置。
- Finder 是辅助文件维护入口，不作为页面主操作常驻展示。
- 当前正式产品只面向 Apple Silicon Mac，本页只承诺 Finder 行为，不定义 Windows 或 Linux 文件管理器。
- 持续接收更新的团队允许通过 Finder 维护相关文件。外部修改与软件内修改使用相同的“已自定义”、冲突和保存语义，不会让团队失去上游记录，也不会被软件升级静默覆盖。

## 操作与反馈

### 保存后的生效反馈

团队名称与用途、主 Agent、成员构成、成员 `AGENT.md`、运行配置、成员顺序或画像每次成功保存后，都在当前操作附近显示轻量反馈：

> 已保存，无需重启。新建对话选择这支团队时会使用修改；正在使用这支团队的对话会显示变化提示，点击任一「应用」会载入整支团队最新保存的完整版本。

反馈应保留到用户能够读完，但不形成需要处理的状态。它只确认已经落盘及会话生效边界，不声称对应 CLI 已在当前机器成功启动，也不把保存时间、内容指纹或文件路径暴露给用户。

一次操作只成功保存部分项目时，不显示整体「已保存」：成功列表逐项标明「已保存，无需重启」，并沿用上述会话生效边界；失败列表逐项说明「未保存，仍使用上一次保存的版本」，保留草稿与重试入口。后续新建、明确切换或在旧对话中点击「应用」时，完整团队快照只包含成功落盘的项目和失败项上一次保存的版本，不会把失败草稿混入快照。

「保存全部并离开」全部成功时，导航到团队首页后立即在团队列表上方显示同一条完整生效反馈，并明确已保存的团队与项目数量；反馈不会因离开详情而丢失。部分失败时仍留在团队详情，按上一段逐项显示成功与失败结果，不提前导航。

软件内没有未保存草稿、并成功载入一份有效外部修改时，使用「已载入外部修改，无需重启」作为同类反馈，并沿用相同会话生效边界。存在冲突、文件无效、检查失败或团队需要修复时不得显示这条成功反馈。

### 从空白开始与添加成员

- 从空白开始先创建可恢复的草稿，不要求用户在一个长向导里一次写完整支团队。
- 草稿会保留在团队首页，直到用户继续完成或主动删除。
- “添加 Agent”在当前团队详情内切换到新成员编辑状态，至少包含创建后不再改变的稳定 slug，以及写有可编辑显示名称和一句话描述的初始 `AGENT.md`。
- 第一个成功添加的 Agent 自动成为主 Agent。
- 团队恰好有一名主 Agent、每名成员都有团队内唯一的稳定 slug，且所有成员的 `AGENT.md` 都可读时，就满足结构上的可用条件，可以供新对话选择。
- 单成员团队也可以使用，但只代表结构有效，不代表已经具备多 Agent 专业分工。
- 产品不分析 `AGENT.md` 的自然语言内容来验证交棒是否正确；协作质量由用户实际定义的 Agent 内容和后续会话结果体现。

### AI 建队

- AI 建队对话可以追问或给出完整方案，但没有直接团队写权限。
- 用户可以继续对话调整成员、主 Agent 和职责；每次新方案替换待确认 proposal revision，旧版本不能再被确认。
- AI 建队要求 2–6 名成员，以兑现多 Agent 分工和接力承诺；从空白开始仍允许单成员团队。
- 确认创建只消费当前最后一版有效方案。完整团队核心、成员文件、逐名运行配置、Pi 成员 Provider 引用与供首次引导使用的独立 `onboarding-orchestration.json` 全部提交成功后才进入详情；任一失败都保留方案和重试入口，不显示半成品团队或孤立引用。
- 独立引导编排不是团队结构、成员职责或真实运行规则，不进入 `team.json`、团队登记缓存、身份指纹或可用性判断。真实会话中的调度仍由主 Agent 依据当前任务与各成员 `AGENT.md` 灵活决定；普通手工团队可以没有引导编排文件。
- 从 Agent 团队页创建成功不改变“上一次成功创建会话时使用的团队”；该记录仍只在真正创建会话后更新。

### 修改团队信息

- 独立维护的团队和持续接收更新的团队都可以修改名称和一句话描述，**在团队详情顶部就地编辑**，与成员的名称和描述用同一种编辑方式；弹窗只留给「新建团队」——那时还没有可点的对象。同一页上同一类数据出现两种编辑方式，是把实现差异暴露成了用户负担。
- 吸顶页头里只放**返回、团队名称、来源标记和保存控件**——这些是滚到任何位置都要够得着的东西，放进去的每一行都是这一页再也拿不回来的视口。**一句话描述不在页头里**，它是正文，跟着页面滚走。
- 页头吸住时必须**盖住它上方的整条页面留白**（正文容器为让开窗口顶栏留出的那一段），并在自己下缘显示一条发丝线。留白不盖住的话，正文会从页头上方继续飘过去，页头看起来就是一块浮在半空的板子而不是页面的头部。发丝线只在真的有内容压在下面时出现——没东西可分隔时画线，是在页面上凭空添一条横线。
- 保存成功的确认是页头的「已保存」与未保存计数归零，不为一次预期之内的成功另立横幅；横幅留给复制成员、删除成员这类一次性文件操作，它们的结果才是用户需要被告知的消息。修改不会自动改变已有会话当前载入的团队版本，用户可在会话变化提示中显式应用完整最新版本。

### 切换主 Agent

- 用户把某名有效成员拖到成员行第一位；键盘用户通过成员条自身的键盘排序完成同一件事（Space 拿起、方向键移动、Space 放下），两条路径结果相同。
- 拖拽必须有完整的键盘等价操作，不能只靠指针；拖拽中要有明确的落点提示，`prefers-reduced-motion` 下不做位移动画。
- 切换进入草稿：拖拽只改这一页的草稿顺序，草稿期间详情页按新顺序预览、「· 主 Agent」标记跟随第一位；点「保存」后一并生效并给出统一生效反馈。
- 新主 Agent 移动到成员行第一位。不可用成员不能被任命，拖入第一位的动作对它不生效并说明原因。
- 顺序本身也是要保存的团队事实：`memberOrder` 的第一项与 `primaryAgentSlug` 由产品保持一致，界面上不存在让两者不一致的路径。
- 切换不会自动改变正在使用该团队的会话；新建对话并选择这支团队、已有会话明确切换到这支团队，或在该团队变化提示中点击「应用」时，载入包含最新主 Agent 的完整团队版本。

### 阅读与编辑 `AGENT.md`

- `AGENT.md` 默认是**渲染后的可读正文**，不是原始文本框。点「编辑」后同一位置换成原始 Markdown 文本框，退出编辑回到渲染态。
- **界面不显示文件名。** 用户在这块关心的是「这个 Agent 负责什么、怎么工作」；`AGENT.md` 是实现细节，正文自带小标题，再加一个文件名标题只是复读。
- 编辑入口不占独立一行：它绝对定位覆盖在正文右上，默认不可见，整块 hover 或获得键盘焦点时才出现，与「历史消息轻操作」同一套轻操作模式。
- 编辑态只呈现正文。名称与一句话描述由上方表单负责，frontmatter 不出现在文本框里，也不需要用户维护 `---` 分隔符。
- 渲染态与编辑态显示的是同一份当前草稿：未保存的修改在渲染态同样可见，不会让用户以为改动丢了。
- `AGENT.md` 不自动保存。
- 修改后，当前成员显示未保存标记。
- 切换到其他成员时不弹窗，当前草稿继续保留；多名成员可以同时保留未保存草稿。

### 这一页的保存

- **整页只有一个「保存」**，一次提交这一页所有未保存内容：团队名称与描述、当前成员的名称、一句话描述、职责说明正文、运行配置、成员顺序和画像。不为其中任何一项单设保存按钮——草稿在实现上分开是保存失败时的隔离规则，属于结果反馈，不该在按钮上就分成两个让用户去认领。
- 界线是：**整页统一走草稿，没有例外。** 拖拽排序和换画像同样只改草稿，点「保存」才落盘。单次拖拽虽然是原子动作，但「把队伍排成什么样」有中间态——你可能拖三四次才满意，中间那几次就是草稿；同理，在 36 张脸里挑到一半想回到原来那张，也需要「放弃修改」能撤。更重要的是，换主 Agent 决定以后新会话由谁主事，这个分量配得上一次明确的保存确认，而不是一松手就定死。
- 保存控件常驻在吸顶的页头，不随正文长短上下浮动；旁边显示未保存项数。「放弃修改」只在确有可放弃内容时出现，一次撤掉这一页的全部草稿。
- 外部修改未解决时不提供保存与放弃：此时只有「载入外部版本」和「用当前内容覆盖」两条路。
- “保存”一次提交这一页的全部未保存内容（与第 1 条同口径）；支持标准的 `Command/Ctrl + S`，等价于点击「保存」。
- 保存结果仍逐项判定：任一项失败时，已成功的项保持已保存、不回滚，失败项保留草稿并说明仍在使用上一次保存的值（例如 Pi 档案在保存前失效，只让该项失败）。
- 保存成功后清除对应成员的未保存标记，并显示统一生效反馈。
- 保存失败时保留编辑内容，在当前编辑区显示原因和重试。
- 离开团队详情时如果仍有未保存内容，统一提供“继续编辑”“放弃全部”和“保存全部并离开”。
- “保存全部并离开”全部成功时返回团队首页，在团队列表上方显示统一生效反馈与已保存项目数量。
- “保存全部并离开”逐个保存已修改的 `AGENT.md`。部分保存失败时，成功项保持已保存并逐项显示成功生效反馈，失败项继续保留草稿并明确仍使用上一次保存的版本；用户停留在当前团队详情并看到失败成员列表。产品不伪装成整体成功，也不回滚已经成功保存的文件。
- 每次保存成功都留下一条修订。编辑器标题行右侧常驻最近一次变化的一句话说明，正文里最近变动过的段落在左侧带标记，指向该段落时显示是谁改的、什么时候改的；点击标记就地展开原来的写法，不跳转、不打开第二个界面。独立维护的团队与持续接收更新的团队同样适用。
- 说明由设置中的默认 Agent 在保存完成后于后台撰写，不阻塞保存。尚未产出时用中性文字占位，不留空白，也不编造内容。
- 编辑器只呈现完整的 markdown 正文，不提供逐行增删对比视图，也不显示内容指纹或版本号之类的技术细节。留痕、来历与回退的完整规则见[Agent 进化流程](../flows/agent-evolution.md)。

### 外部修改冲突

- 本节适用于两类团队。持续接收更新的团队在软件外被修改后，改动会参与当前内容与上游基线的比较，但不会移除其上游记录。
- 软件内没有未保存内容时，返回应用后重新载入外部更新的 `AGENT.md`，并给出统一的外部修改生效反馈。
- 软件内已有未保存草稿时，不自动覆盖，保留草稿并提示文件已在外部修改。
- 用户只能选择“载入外部版本”或“用当前内容覆盖”。本页不提供逐行 diff 或自动合并。
- 其他引用文件的外部修改不触发本页刷新或冲突提示。
- 外部修改检查失败必须在对应成员上显示可见错误，不得静默忽略。

存在未解决的外部冲突时，返回团队列表会被明确阻止。界面弹出说明并列出所有待处理成员；关闭说明后仍停留在团队详情，成员的冲突状态保持不变。这里不提供“直接离开”：未保存草稿可以放弃，外部冲突必须先在“载入外部版本”和“用当前内容覆盖”之间完成裁决。

```text
┌────────────────────────────────────────────┐
│ 无法返回团队列表                           │
│                                            │
│ 以下 Agent 的文件在应用外被修改，          │
│ 需要先选择保留哪一份：                     │
│                                            │
│   · 开发经理 AGENT.md                      │
│   · 测试 AGENT.md                          │
│                                            │
│                              [ 知道了 ]    │
└────────────────────────────────────────────┘
```

### 上游版本与三方比较

持续接收更新的团队同时保留三份可解释事实：

```text
A = 上次应用到本机的上游基线
    ├─ 上游 commit
    ├─ 该 commit 的完整内容
    └─ 各稳定 slug 的推荐运行配置

B = 用户当前可编辑的团队内容

C = 上游仓库默认分支的最新内容
    ├─ 最新 commit 与完整内容
    └─ 各稳定 slug 的最新推荐运行配置
```

A 保存的是那一版的完整内容，不只是一个用于判等的指纹。自动合并必须知道上游上一版究竟写了什么，才能分辨某一处差异是用户改出来的还是作者改出来的；只有指纹时无法回答这个问题，也就只能让用户在两个版本之间二选一。

**这套三方比较与 2026-08-07 确认的规则完全一致，只换了 C 的来源。** 原来 C 是“当前软件携带的最新官方版本”，现在是“上游仓库默认分支的最新内容”；触发时机从“安装新版本后首次启动”换成“检查上游更新时”。合并怎么做、冲突怎么处理、结果怎么撤销都不变，理由见[Agent 进化流程](../flows/agent-evolution.md)。

检查上游更新的时机、频率与失败处理由[Agent 进化流程](../flows/agent-evolution.md)定义。取到 C 之后，应用**直接执行合并**，不把结果停留为一个等待用户点击的更新提示。进入 Agent 团队页、打开团队详情或从 Finder 返回应用时，页面同样重新读取当前内容，用于判断“已自定义”和呈现变化标记；重新读取本地内容不等于去访问上游。

内容指纹覆盖团队名称与描述、主 Agent、成员结构、各成员 `AGENT.md` 以及现有规则允许维护的相关成员文件。执行引擎、Provider 档案引用、模型、思考程度、缓存和应用内部元数据不进入内容指纹。独立的 `onboarding-orchestration.json` 只服务首次引导，不属于团队结构、身份或真实运行规则，因此不进入内容指纹、自定义判断、团队身份或可用性判断。

commit 用于向用户解释这次变化，规范化内容比较用于判定，页面不显示原始指纹：

- `B ≠ A` 的内容：用户修改过团队内容，显示“已自定义”。
- 用户运行配置覆盖不参与 `B/A` 内容比较。
- “已自定义”是普通管理状态，不触发“团队需要修复”红点，也不等同于文件损坏。
- **不存在“有更新”状态**。`C ≠ A` 在检查到之后自动收敛，页面呈现的是已经完成的同步结果，而不是一件待办。
- 上游取不到时不产生任何比较结果：既不显示“已自定义”变化，也不显示同步结果。判定为失联时按「上游失联」呈现，判定为暂时连不上时静默等下一次。

| 三方结果 | 自动合并结果 | 页面呈现 |
| --- | --- | --- |
| `B = A` 的内容，`C = A` | 无事发生 | 来源仓库名 |
| `B ≠ A` 的内容，`C = A` | 无事发生 | 来源仓库名 · 已自定义 |
| `B = A` 的内容，`C ≠ A` | 直接采用 C | 同步结果横幅 |
| `B ≠ A` 的内容，`C ≠ A`，且 B 与 C 内容一致 | 只登记新基线，内容不动 | 来源仓库名 · 已自定义 |
| `B ≠ A` 的内容，`C ≠ A`，且两者分叉 | 交默认 Agent 合并，用户的意图优先 | 来源仓库名 · 已自定义，附同步结果横幅 |
| 默认 Agent 不可用，且需要合并 | 保留用户内容，标明作者有改动尚未合入，可重试 | 来源仓库名 · 已自定义 |
| A 不可考（本能力上线前已被用户改动过） | 不自动合并，保留用户内容；提供一次性的显式合并入口 | 来源仓库名 · 已自定义 |
| 上游仓库取不到（失联） | 不执行合并，保持原状 | 上游失联横幅 |
| 比较所需本地内容不可读 | 不执行合并，保持原状 | 沿用既有修复或重试入口 |

仅推荐配置发生变化时，可能出现 A、B、C 内容一致但 `C ≠ A`。此时同样自动完成：“跟随推荐”的成员采用新版推荐值，用户覆盖保持原值。

无论哪一行，都不创建“更新前副本”。用户内容的保护由完整的修订记录和可整体撤销的同步批次承担，不靠复制出一支脱离上游的团队。理由与被推翻的旧决策记在[Agent 进化流程](../flows/agent-evolution.md)。

### 上游成员与运行配置迁移

团队从 A 更新到 C 时，以稳定 slug 判断成员是否为同一人，不根据显示名称或职责文本猜测对应关系：

| A → C 的成员关系 | 自动合并结果 |
| --- | --- |
| slug 保持，存在用户覆盖 | 原执行引擎、Provider、模型和思考程度完整保留 |
| slug 保持，仍跟随推荐 | 采用 C 为该 slug 提供的推荐值 |
| C 新增 slug | 按 C 的内容与推荐值加入团队 |
| C 新增 slug，但 B 已有用户自行添加的同名成员 | 保留用户自建的那名成员及其配置，上游这名成员不加入，并在同步说明里讲清原因 |
| C 删除 slug，用户从未改动过它的内容与运行配置 | 成员及其推荐配置从团队移除 |
| C 删除 slug，用户改动过它的内容或运行配置 | 成员留在原团队里，说明上游已不再包含它；不搬到别处，也不降级为不可用 |
| slug 改名 | 按删除旧 slug 与新增新 slug 处理，因此用户改动过的旧成员会继续留在团队里 |

不存在把已删除成员的配置猜测附着到新成员或新 slug 的行为，也不能仅凭 slug 相同就把上游新成员与用户自建成员当作同一个人。

“用户改动过的东西留在原地”是这张表的唯一取舍原则。它替代了旧的副本机制：过去上游要移除一名存在用户覆盖的成员时，必须先把整支团队复制一份再移除；现在这名成员直接留在团队中，用户不需要去另一支团队里找回自己的成果。代价是团队可能长期保留作者已经放弃的成员，这是可接受的——那正是用户亲手改过、明确表达过在意的部分。

### 从上游更新团队

应用在后台对每支持续接收更新的团队自动完成三方比较与合并，不需要用户从本页执行任何操作。本页不提供“更新到最新版”“保留副本并更新”按钮，也不提供更新前的影响预览——预览存在的理由是让用户判断要不要点那个按钮；按钮没有了，它的位置由事后的同步结果横幅和编辑器内的变化标记接管。

本页也**不提供“立即检查更新”按钮**。检查时机由[Agent 进化流程](../flows/agent-evolution.md)统一裁决；给用户一个手动检查按钮，等于把“我这份是不是最新的”这个焦虑还给用户，而自动合并的全部意义就是他不必再想这件事。上游失联时的「重新检查」是例外——那是在处理一个已经出现的异常，不是常规轮询入口。

同步进行中的可见状态在[主左侧栏](./main-left-sidebar.md)底部，点击进入本页。

合并完成后，受影响团队的详情页在标题下方显示同步结果横幅：

```text
┌ 已同步到上游 a3450d6 · 3 名成员有变化 ───────────────────┐
│ 新增 release，移除 qa，dev 的职责有更新                   │
│                        [看看改了什么] [撤销这次同步] [×] │
└───────────────────────────────────────────────────────────┘
```

- “看看改了什么”定位到第一名有变化的成员，并展开它的变化时间线。
- “撤销这次同步”把整支团队退回同步前的状态，包括成员内容、成员构成，以及因跟随推荐而改变的运行配置；撤销后这次上游改动记为已知悉，之后的检查不再重新合入。
- “×”只收起横幅，不代表用户接受或放弃了什么。横幅不会自动过期，跨重启保留；收起之后，同一份内容与同一个撤销按钮继续在团队“更多”菜单的“最近的上游同步”里，不设期限。

横幅只说明已经发生了什么，不要求用户做任何决定。用户从不打开本页也不影响合并已经生效。

页面内异常遵循以下规则：

- 存在未保存的 `AGENT.md` 或运行配置草稿时，该成员本次不参与合并；用户保存或放弃草稿后，在下一次读取时重新比较。不丢弃用户正在写的内容，也不要求用户先处理草稿才能升级。
- 存在外部修改冲突时，先走既有冲突流程，合并推迟到用户选定版本之后。
- 无法读取比较所需的本地内容时，不执行合并，沿用既有的修复或重试入口。
- 上游仓库取不到时不执行合并：判定为失联的按「上游失联」呈现，判定为暂时连不上的静默等下一次检查，两种都不修改本地内容。
- 默认 Agent 不可用时，只有上游单方改动的部分照常合入；需要语义合并的部分保留用户内容，标明上游有改动尚未合入并提供重试。任何情况下都不允许因为无法合并而覆盖用户内容。
- 本能力上线前就已被用户改动过的团队没有留下上一版的完整内容，缺少这个参照时不自动合并，理由与降级方式见[Agent 进化流程](../flows/agent-evolution.md)。此时详情页提供一次性的显式合并入口，用户不点也没有任何后果；它只在这一次出现，此后走自动路径。
- 团队已经处于既有“需要修复”状态时不参与同步，沿用现有修复入口；修复完成后按正常比较继续，不静默重建团队文件。
- 合并结果、修订记录与 Provider 团队成员引用作为同一个用户可观察的结果提交。失败时团队内容、运行配置和全部引用保持操作前状态，不留下半合并的成员，也不产生重复记录。

具体的事务、暂存、文件交换和崩溃恢复机制由后续 OpenSpec 设计，不在本页规定技术实现。

### 复制

- 复制团队会创建一支独立的**独立维护**团队，复制团队对应的完整目录，包括团队信息、全部成员目录、各成员 `AGENT.md` 及其他相关文件，并进入新团队详情。
- 复制不会改变新建对话的“上一次使用”记录。
- 独立维护的团队也可以从“更多”菜单复制。
- 持续接收更新的团队也可以从“更多”菜单主动复制。复制只由用户主动发起；上游同步不产生任何自动副本。
- 团队副本不继承上游记录，不参与后续上游比较；每名成员当时已保存的执行引擎、Provider 档案引用、模型和思考程度都固化为副本自己的显式配置，不根据当前机器环境改写，也不复制 Key。
- 团队或 Agent 复制成功时，设置页同时出现副本中每名 Pi 成员的独立团队引用；失败时不出现副本或新增引用。来源团队和来源成员的引用始终保持。
- 独立维护的团队中的单个 Agent 可以在成员菜单中复制；复制会包含该 Agent 的整个目录和全部相关文件，复制品仍属于当前团队。
- 在同一团队内复制 Agent 时，复制品取得新的团队内稳定 slug，避免与原成员的协作引用冲突；显示名称和其他文件内容可以从原成员开始再修改。
- 团队或成员存在未保存的 `AGENT.md` 草稿时，复制前必须让用户保存或放弃这些草稿；复制始终基于已经完整落盘的文件，不把内存草稿悄悄混入副本。

### 删除团队

- **任何团队都可以删除**，持续接收更新的、独立维护的、软件自带的两支，规则完全一样。原来「官方来源团队不可删除」的前提是删了就找不回来；现在任何持续接收更新的团队都能从 GitHub 重装，禁止删除只剩下强迫用户留着不用的东西。
- 团队和未完成草稿从详情页“更多”菜单移到系统废纸篓或回收站。
- 删除前说明团队包含的 Agent 和相关文件，并要求确认。
- 持续接收更新的团队在确认里额外说清两件事：重装需要联网，以及拿回来的是上游的版本——用户在本地改过的内容不会一起回来。删除是不可逆动作，宁可确认文案长一点，也不能让用户以为“反正能装回来”而丢掉自己写过的东西。离线状态下删掉安装包自带的两支团队，在重新联网之前就是没有了，这个后果同样落在这句话里。
- 有未保存 `AGENT.md` 草稿时必须先处理草稿，不能直接删除。
- 删除成功后返回团队首页，从新建对话团队选择器中移除，并同时解除这支团队全部 Provider 团队成员引用；删除失败时团队、选择器和引用清单都保持原状。
- 被删除的团队如果是“上一次使用的团队”，下一次普通新建对话按固定回退顺序取第一支可用团队。
- 已有会话及其创建时载入的团队版本不因删除而被移除。
- 本产品不建设独立的已删除团队页面，恢复文件使用系统废纸篓或回收站。
- 从系统废纸篓或回收站恢复文件后，团队如何重新回到产品暂不在本页面承诺；文件层可恢复不等于自动恢复应用内记录。
- 已有会话在团队被主动删除后能否继续发送新消息，归会话交互 PRD 裁决；本页面只保证历史和已载入版本不会随删除一起消失。

### 新建对话中的团队预选

本页只定义跨页面约束，具体控件由[主页面会话区](./main-conversation.md)的新建对话形态负责：

```text
新建对话
  → 自动预选上一次成功创建会话时使用的团队
  → 用户可以在创建前改选
  → 进入会话
  → 由所选团队的主 Agent 默认接收消息
```

- 普通主会话首次使用且没有历史选择时，按固定顺序选择第一支可用团队：`development` → `general-assistant` → 用户自己的团队按显示顺序。回退顺序不再区分团队来源，只看哪一支当前可用。
- 上一次使用的团队已经删除或处于“需要修复”时，按同一固定顺序回退到第一支可用团队。
- 打开、编辑或浏览团队不更新“上一次使用”记录；只有成功创建会话后更新。

sidebar chat 使用独立的上下文预选规则：

- 从右侧栏内容选择打开普通「新会话」，或从「分析当前对话」进入时，初始团队固定预选当前本地的 `general-assistant`。
- 这只是发送前可改的初值；用户可以选择任意其他可用团队，首次消息由发送瞬间最终所选团队的主 Agent 接收。
- `general-assistant` 已被用户自定义时，载入用户当前已保存的团队内容和运行配置，不为这次会话临时恢复上游基线。
- `general-assistant` 需要修复或已被用户删除时，不静默回退到普通主会话的上次团队或任何其他团队；草稿保持，用户修复、重新安装或主动改选后才能发送。
- sidebar chat 首次消息成功创建后，最终所选团队才按普通规则成为“上一次成功使用”的团队。

| 运行配置已修改 | 当前成员显示独立草稿标记，切换成员不丢失 | 仍使用最近一次已保存配置 |
| 运行配置输入不合法 | 对应字段显示静态校验原因，保存禁用 | 仍使用最近一次已保存配置 |
| 运行配置保存失败 | 保留草稿，显示失败原因和重试入口 | 仍使用最近一次已保存配置 |
| Pi API · 尚无已就绪 Provider | Provider 与模型字段显示空态，提供“前往设置添加服务商” | 保存禁用；团队仍使用旧配置 |
| Pi API · 已就绪 | 显示服务商、档案名称、已验证模型和实际思考程度，不显示 Key | 是 |
| Pi API · 已就绪但默认模型已下架 | Provider 可选择，模型字段保持空白并提示必须明确选择另一可用模型；不静默代选 | 选择模型前保存禁用 |
| Pi API · Provider 正在验证 | 读取验证前的有效状态；旧版本已就绪则继续显示可用，否则不可新选 | 取决于旧有效状态 |
| Pi API · Provider 需要处理或已停用 | 保留原档案、模型和思考程度，显示准确原因与“设置中修复 / 为当前成员更换” | 团队可选；受影响成员不能新运行 |
| Pi API · 服务商或模型已移除 | 保留原配置并显示迁移原因，不静默选择档案默认模型或其他 Provider | 团队可选；受影响成员不能新运行 |
| Pi API · 历史 Provider 不可用 | 显示保存的历史标识和“当前应用找不到此档案” | 团队可选；受影响成员不能新运行 |
| Pi API · 保存前状态变化 | 保留草稿并刷新 Provider / 模型真实状态，说明旧配置仍在使用 | 重选已就绪配置后重试 |
| 团队运行配置需要处理 | 团队横行显示受影响成员数；不触发文件修复红点 | 是；会话启动受影响成员时阻止 |
| 正常团队 | 正常显示团队信息、主 Agent、成员和编辑区 | 是 |
| 未完成草稿 | 标记“未完成”，保留继续添加成员入口 | 否 |
| AI 建队草稿 | 只在 AI 建队主体中恢复对话、方案和错误，不出现在团队列表 | 否 |
| 需要修复 | 红色异常标识，显示具体不可用范围和修复入口 | 否 |
| `AGENT.md` 已修改 | 当前成员显示未保存标记，草稿留在内存 | 仍使用最近一次已保存版本 |
| 正在保存 | 当前编辑区显示进度并防止重复保存 | 仍使用最近一次已保存版本 |
| 保存成功反馈 | 当前操作附近说明已保存、无需重启，并解释新建后选择或已有会话点击变化提示时载入；不声称 CLI 已成功运行 | 使用刚成功落盘的项目；部分失败项目仍使用上一次保存版本 |
| 保存失败 | 保留草稿，显示原因和重试 | 仍使用最近一次已保存版本 |
| 外部修改冲突 | 保留软件内草稿，等待版本选择 | 仍使用冲突前最近一次有效版本 |
| 页面加载中 | 使用保持团队横行结构的加载占位 | 等待加载结果 |
| 页面加载失败 | 保留页面框架，显示错误和重试 | 不把失败误判为没有团队 |

安装包携带两支团队，因此新装用户不会遇到“完全没有团队”的空态。但**空态必须存在**：任何团队都可以删除，用户完全可以把两支都删掉。此时显示空态并给出三条路径（找现成团队、跟 AI 聊、从空白开始），不把它当成异常。

两支自带团队都无法加载（而不是被删除）时，显示应用配置异常和重试，不引导用户把损坏状态当作正常空白重新创建。这两种情况必须区分开：删空了是用户的选择，读不出来是产品的故障。

### 团队位置不可用

团队整体位置被移动、重命名或变得不可访问时，团队继续显示在首页并标记“需要修复”。详情提供“重新定位团队”和“移除记录”，两类团队都有。已有会话历史不消失。

```text
┌────────────────────────────────┬───────────────────────────────┐
│ 我的开发团队          需要修复 │ 成员信息暂时无法读取          │
│ 团队文件夹已移动或不可访问     │ 暂时无法用于新对话            │
└────────────────────────────────┴───────────────────────────────┘
```

成员区显示占位说明而不是成员名称：此时 `AGENT.md` 读不到，任何成员名单都只能来自缓存，而缓存正是本页面拒绝维护的那份“可能漂移的成员摘要”。用户需要的识别信息由团队名称和不可用原因承担，成员构成等修复后自然恢复。

“重新定位团队”只能绑定能够识别为同一支有效团队的位置，不能用任意文件夹替换。

- 重新定位失败时保留原记录并说明选择的位置为何不被接受，不把团队错误绑定到新位置。
- “移除记录”只移除应用中已经失效的团队记录，不删除、移动或修改用户磁盘上的任何文件；执行前必须明确说明这一差异。持续接收更新的团队同样可以移除记录——它能从 GitHub 重新装回来，把用户困在一条修不好的失效记录上没有意义；移除时一并说明重装的代价，与删除确认口径一致。

### 成员 `AGENT.md` 不可用

- 任一成员的 `AGENT.md` 缺失或无法读取，整支团队标记“需要修复”，暂时不能用于新建对话。
- 任一成员缺少稳定 slug，或同一团队内出现重复 slug，也属于“需要修复”。
- 用户可以在 Finder 中恢复文件，或将失效成员从独立维护的团队、持续接收更新的团队删除。
- 失效成员是主 Agent 时，可以先指定另一名有效成员为主 Agent，再删除失效成员。
- 文件恢复后重新检查，并在所有成员恢复有效后解除“需要修复”。
- 软件不检查 `AGENT.md` 引用的其他文件是否完整。

### 跨页面异常反馈

- 只要至少一支团队“需要修复”，Sidebar 顶部“Agent 团队”入口显示一个红点；多支异常仍只显示一个。
- 红点的悬停提示和辅助名称为“有 Agent 团队需要修复”。
- 点击入口后，团队首页对应横行必须以“需要修复”状态明确标出具体异常团队。
- 未完成草稿、“已自定义”和刚完成的上游同步都不触发该红点。
- 如果已有会话当前选择的团队变为“需要修复”，会话历史仍可查看，但不能发送新消息；会话内团队按钮显示红色异常标识。
- 会话按钮、发送禁用、切换团队和修复后的恢复细节留给会话交互 PRD 定义。

这里区分两个事实：已有会话继续保留创建时载入的 Agent 内容版本；团队当前是否“需要修复”则实时决定该会话能否继续发送。

## 弹层与危险操作

- “从空白开始”和“修改信息”只承载短字段，不把完整成员编辑塞进弹窗；AI 建队使用页面主体，不把多轮对话塞进弹窗。
- 删除团队使用明确确认，说明团队文件和已有会话分别受到什么影响；持续接收更新的团队额外说明重装需要联网、且拿回来的是上游版本。
- 删除通过系统废纸篓或回收站保持文件层可恢复，不提供软件内永久删除；恢复回产品的方式暂不承诺。
- 「停止接收更新」使用明确确认，说明团队内容全部保留、停止后不再接收作者更新，并说明想重新接收作者更新需要从 GitHub 重装一份。它不改变磁盘上的任何团队文件，因此不使用删除级别的警告语气。
- 存在未保存草稿时，离开、删除或其他会丢失内容的操作必须先让用户选择保存或放弃。
- 外部修改冲突不得静默选择任何一方覆盖。
- “撤销这次同步”会改变整支团队的当前内容、成员构成和跟随推荐的运行配置，因此必须说明将退回到哪一版、影响哪几名成员，再让用户确认。它不是不可逆操作——撤销本身也是一条修订，可以再退回来，因此不使用删除级别的警告语气。
- 从变化时间线“回到这一版”只影响当前这一名成员，同样先说明影响范围；它不改变其他成员，也不改变团队结构。

## 响应式与窗口行为

- 宽窗口下，团队横行左侧显示身份信息，右侧显示扁平成员行。
- 窄窗口仍保持“一支团队一条横行”，不改成多列卡片网格；成员行移动到描述下方。
- 首页空间不足时用 `＋N` 收敛成员数量。
- 团队详情中的成员选择器保持单行并允许横向滚动，不换行堆成多层。
- 职责说明占据成员区右栏并随内容自然延展；左栏（身份、运行配置、保存）在滚动时固定，读长正文时主线仍在视野内。
- 窗口缩放、成员切换和横向滚动不得丢失各成员尚未保存的草稿。
- Pi API 的执行引擎、Provider、模型和思考程度在窄窗口中纵向排列；长档案名或模型名可以换行或省略显示并提供完整可访问名称，但状态、修复入口和保存按钮不得被挤出或产生页面级横向滚动。

## 关联流程

- 新建对话时预选上一次使用的团队，并允许用户改选。
- sidebar chat 与会话分析入口初始预选「通用助手」，允许发送前改选；分析只是普通会话的静态文本与提示词切入，不给该团队增加特殊权限。
- 所选团队的主 Agent 接收新会话第一条消息。
- 持续接收更新的团队允许直接修改；作者有新内容时按[Agent 进化流程](../flows/agent-evolution.md)自动合并进来，用户的意图优先，结果可整体撤销。本页承载同步结果横幅、编辑器内的变化标记与变化时间线。
- 从首页「找现成团队」进入[找现成团队](./github-team-discovery.md)，经[安装前预览](./github-team-preview.md)确认后安装；安装成功回到本页，新团队进入“持续接收更新”分组并立即可用于新建对话。
- 每名 Agent 在团队页配置独立的执行引擎、Provider 档案（仅 Pi）、模型和思考程度；它们按[主对话页](./main-conversation.md)规则进入会话与 run 快照并冻结，Provider 默认模型或其他成员配置变化不回写。
- 从 onboarding 或 Agent 团队页进入同一套 AI 建队能力；前者创建后选中并继续演示，后者创建后进入团队详情。
- 团队文件异常后，从 Sidebar 红点或会话异常入口进入修复。这类入口已经知道是哪一支团队，应当**直接落在那支团队的详情上**，不是落在团队首页再让用户自己点一次。承载它的是团队页的「打开某支团队」入参，与「当前载入了哪支团队的数据」是两件事——后者在没有别的选择时会回落到第一支团队，若拿它当意图，团队首页就再也回不去了。<!-- 尚未接线：目前只有 Storybook 用到这个入参。 -->
- 已有会话所选团队“需要修复”时，阻止继续发送，修复或切换团队后恢复。

这些流程尚未建立独立的 `flows/` 文档。会话内团队按钮、发送状态、切换团队以及运行中异常的具体行为以[主对话页](./main-conversation.md)为准。

## 指标与验收

1. 用户能从 Sidebar 顶部进入 Agent 团队首页，并用一条横行识别每支团队的名称、用途、主 Agent、成员和必要状态；团队首页、成员选择器和当前成员标题中的同一成员使用一致的圆形画像。
2. 团队成员始终扁平展示；页面不存在暗示组织层级、执行顺序或 DAG 的连接线和节点结构。
3. 持续接收更新的团队可以修改团队信息、主 Agent、成员、`AGENT.md` 和相关成员文件，也可以复制和删除；后续作者更新关系只能通过「停止接收更新」整体解除，不能被逐字段编辑。软件内与 Finder 外部修改使用相同的自定义与冲突语义。
4. 首页直接提供「找现成团队」和「新建团队」两个平级入口；「新建团队」展开后只提供 AI 建队和从空白开始，复制仍从明确的已有团队详情发起。创建或复制产生独立维护团队，找现成团队产生持续接收更新团队。
5. 用户能创建长期保留的空白团队草稿；第一名成员自动成为主 Agent，缺少有效主 Agent 时团队不可用于新建对话。
6. AI 建队未确认时不产生团队列表项；确认前逐名显示初始执行引擎、Provider、模型和实际思考程度，确认后这些配置与 2–6 名成员、唯一主 Agent 和完整成员内容作为同一结果创建。纯 API 用户的成员不会回落到 Codex，失败不得留下半成品。
7. 用户在团队详情内即可切换成员并编辑多个成员的职责说明，不需要进入独立 Agent 页面；未保存草稿不会因成员切换丢失。职责说明默认呈现为可读的渲染正文，编辑是显式的次级动作，入口以轻操作形式覆盖在正文上而不占独立一行，界面不显示文件名；名称与一句话描述是当前成员区的表单字段而非文本里的 YAML，编辑态的文本框只含正文，产品保存时合成回 frontmatter。
8. 用户能用 `@<slug>` 匹配当前团队成员，选择后看到可读名称组件；显示名称变化不破坏底层稳定引用，缺失或重复 slug 会让团队进入“需要修复”。
9. 软件内不提供相关文件编辑器；团队和成员均有不抢占主视觉的 Finder 入口，本文不形成 Windows 或 Linux 文件管理器承诺。
10. 普通新建对话预选上一次成功使用的可用团队；没有历史选择或上次团队不可用时，按 `development` → `general-assistant` → 用户自己的团队按显示顺序，回退到第一支可用团队。回退顺序不区分团队来源。
11. 团队或成员文件不可用时，团队显示“需要修复”、不能用于新建对话，Sidebar 顶部“Agent 团队”入口出现红点。
12. 已有会话选择了“需要修复”的团队时，历史仍可查看，但发送被阻止；详细恢复交互由会话 PRD 承接。
13. 任何团队都能删除，包括软件自带的两支；删除进入系统废纸篓或回收站，已有会话载入的团队版本不被清除。持续接收更新的团队在确认里说明重装需要联网、且拿回来的是上游版本，用户本地改过的内容不会一起回来。
14. 每名 Agent 可以独立选择 Codex、Claude Code、Kimi 或 Pi API。CLI 使用对应 model / effort 联动列表；Pi API 依次选择已就绪 Provider、该档案可用已验证模型和实际支持的思考程度。不同团队中的同 slug 配置互不影响，绑定不会静默降级到另一执行引擎。
15. 未配置成员直接采用 `Codex / gpt-5.6-sol / high`；打开、切换成员和保存运行配置都不会启动 CLI 或调用 API。CLI 当前不可运行不改变已保存配置；Pi 只读取 Provider 最近保存的有效状态，选择与保存本身不产生 API 用量。
16. 上游内容未变化而用户内容已修改时只显示“已自定义”；上游有新内容而用户内容未修改时自动采用新版，不需要用户操作。
17. 上游内容与用户内容均有变化且不相同时，由默认 Agent 自动合并且用户的意图优先，不创建任何副本；用户当前内容已经等于最新版时只登记新基线，内容不动。
18. 仅上游推荐运行配置变化时也自动完成；同 slug 的用户覆盖保持不变，仍跟随推荐的成员采用当前已应用最新版推荐值。
19. 上游新增成员采用最新版推荐配置；删除无用户覆盖的成员可以直接更新，且其配置不会附着到其他成员。
20. 上游删除或改名一个用户改动过的成员时，这名成员连同其已保存配置留在原团队里，不产生副本、不搬到别处；用户从未改动过的成员才随上游移除。
21. “恢复推荐配置”恢复当前已应用的上游 commit 为该 slug 提供的推荐 CLI 组合；上游内容不引用用户本机 Provider，上游同步应用新版之后才会指向新版推荐。
22. 用户主动复制出的团队保留当时团队内容与每名成员的已保存运行配置；Pi 成员继续引用同一应用级档案但不复制 Key。复制品脱离上游记录，不再参与上游同步。
23. 存在未保存草稿或外部冲突的成员本次不参与合并，用户处理后在下次读取时重新比较，草稿不被丢弃；合并失败后团队内容、运行配置和引用保持操作前状态，不留下半合并的成员。
24. 刚完成的上游同步是普通管理状态，不触发“团队需要修复”Sidebar 红点。Pi Provider 或模型异常显示独立的“运行配置需要处理”和受影响成员数，同样不触发文件修复红点。
25. 整页只有一个「保存」，一次提交团队名称与描述、当前成员的名称、描述、职责说明正文与运行配置；「放弃修改」只在确有草稿时出现，外部修改未解决时两者都不提供；各项草稿切换成员不会丢失，离开页面时统一要求保存或放弃。保存逐项判定：成功项不回滚，失败项保留草稿并明确仍在使用最近一次已保存的值。Pi 档案或模型在保存前失效时只让对应成员失败并刷新原因，不回滚其他已保存成员。
26. 历史未知 CLI model/effort 原值，以及需要处理、停用、下架或缺失的 Pi Provider / 模型原值都保持可见，不能在打开页面或切换成员时被覆盖；只有用户主动选择当前支持且已就绪的组合后才替换。
27. 同步完成后可以看见已应用的上游 commit、实际的成员变化和跟随推荐配置变化，并从横幅直接进入第一名有变化的成员核对内容。整体撤销有两个指向同一份内容的入口：不会自动过期、跨重启保留的同步结果横幅，以及横幅收起后“更多”菜单中常驻的“最近的上游同步”；两者都不设期限。
28. 上游新增 slug 与用户自行添加的成员同名时，保留用户自建的成员及其显式配置，上游这名成员不加入，并在同步说明中讲清原因。
29. 软件正常安装后，团队首页在“持续接收更新”分组显示 `general-assistant`「通用助手」与 `development`「开发团队」，各自带来源仓库名；「通用助手」的初始结构只有主 Agent `@assistant`，`AGENT.md` 除身份 frontmatter 外没有专业职责、固定流程、交棒或分析权限正文。
30. 「通用助手」初始推荐运行配置为 `Codex / gpt-5.6-sol / high`，且不继承来源会话、被分析 run、最近运行或其他团队配置；用户保存覆盖后，sidebar chat 使用当前用户版本。
31. 「通用助手」与其他持续接收更新的团队一样可修改信息、成员、主 Agent、`AGENT.md` 和运行配置，也可复制和删除；添加成员或改变初始内容后显示“已自定义”，不产生另一套团队生命周期。
32. 「通用助手」完整复用三方比较与自动合并：上游有新内容时自动合并且用户的意图优先，用户运行配置覆盖不丢失，结果可整体撤销。
33. 「通用助手」位置或成员文件不可用时显示“需要修复”且不能用于首次发送；应用不静默重建、换团队或换模型。重新定位、外部恢复，或添加有效成员并切换主 Agent 后移除失效成员，可以解除异常。
34. 普通主会话继续按上次成功团队及固定回退顺序预选；右侧栏普通新会话和「分析当前对话」则始终初始预选当前本地 `general-assistant`，发送前可改。首次发送成功前不更新上次使用记录，团队不可用时保留草稿并等待修复或用户主动改选。
35. 从携带九支官方团队的既有安装升级时，本地团队一支不删、不改名、不覆盖：`general-assistant` 与 `development` 登记上游仓库，其余七支转为独立维护。迁移不询问、不弹窗、不生成待办；上游登记失败时团队照常可用并显示为独立维护，下次重试。
36. 来源仓库被删除、转私有或改名时，团队详情显示「这支团队照常能用，只是不再接收作者更新」，团队仍可用于新建对话且不触发修复红点；用户能重新检查，或停止接收更新并保留全部内容。暂时连不上 GitHub 不判定为来源失效，静默等下一次检查。
37. 从右侧栏内容选择手动创建普通 sidebar chat，即使保留初始「通用助手」，也只按[主页面会话区](./main-conversation.md#指标与验收)的普通新会话与已有会话规则运行，不自动获得方案确认或写入闸门。「分析当前对话」入口形成的草稿则始终按[会话分析流程验收 13–15](../flows/session-analysis.md#指标与验收)执行确认与写入边界，即使用户发送前把团队从「通用助手」改成其他团队也不能绕过；闸门归入口流程，不归任何团队身份。
38. 已有上游记录的团队不重复登记，而是走三方比较；已有记录但文件异常时进入修复，不得借迁移静默重建。
39. 切换到 Pi API 后，只有一份已就绪档案时可见预选，存在多份时必须明确选择；没有已就绪档案时保存禁用并提供“前往设置添加服务商”。选择档案后只列出该档案可用的已验证模型；默认模型可用时只作预选，默认模型已下架时模型字段必须为空并要求用户明确选择，不能静默代选。
40. Pi 思考程度只显示所选服务商和模型实际支持的选项；无法可靠控制时隐藏选择器、显示固定说明并保存固定值。团队页不显示完整 Key、Base URL 或可复制凭据，也不要求不同成员重复输入同一档案 Key。
41. 成员保存 Pi 配置后，Provider 默认模型变化不回写该成员；Provider 需要处理、已停用、服务商或模型下架时保留原档案、服务商、模型和思考程度，并显示准确修复或改配入口，不静默代选。
42. 用户可以只为当前成员选择另一项已就绪配置，也可以前往设置迁移全部引用。单成员改配只影响之后创建的新会话，既有会话继续使用冻结快照；设置完成批量迁移后，本页刷新对应成员的已保存配置。
43. 复制包含 Pi 成员的团队或单个 Agent 会继续引用同一应用级 Provider，不新建档案或复制 Key；复制品与设置页新增引用一起出现，失败时两者都不出现。上游推荐配置不得携带用户本机 Provider，Pi 用户覆盖在上游同步与撤销时都不会丢失。
44. 当前成员保存执行引擎或 Provider 变更后，团队页配置与设置页的团队成员引用一起更新；删除成员后两边一起解除该成员。任一步失败时成员结构、配置和引用都保持原状态。
45. AI 创建团队、上游同步与其撤销、删除独立维护的团队和删除未完成草稿，都必须让最终团队结构与设置页逐名 Provider 引用同成同败；设置引用清单能分别识别复制后同名团队或成员，不会遗漏仍存在的 Pi 成员，也不会被已删除团队永久占用。
46. 团队成员不再引用旧档案后，既有 AI 建队草稿、任务和可恢复会话的冻结引用仍保留；复制、更新、删除成员或团队都不能绕过设置页对其他引用类别的删除保护。
47. 每名 Agent 未设置画像时按稳定 slug 取得默认画像，无需先设置；用户从当前成员的画像本身打开选择面，顶部大预览显示这名成员当前的样子，下方候选一律以该成员现有底色渲染且底色不可选。选中后面不关闭、预览原地更新，可以连着比较多个候选。页面不提供上传或引用外部图片，也不提供独立的「恢复默认」入口。
48. 画像更换进入当前成员草稿并跟随现有保存与离开保护流程：切换成员不丢失，未保存不改变其他页面与已有会话的呈现，保存失败时明确仍在使用上一张。持续接收更新的团队成员同样可换画像，且只换画像不产生「已自定义」标记、不参与上游更新比较、不被作者新内容覆盖。
49. 成员行支持直接拖拽排序，拖到第一位即任命主 Agent；页面不另设主 Agent 下拉，键盘用户通过成员条自身的键盘排序完成同一件事。拖拽有明确落点提示，不可用成员不能被任命。第一位之外的先后不表达执行顺序或层级，产品不据此推断调度，也不渲染序号或连接关系。
50. 顺序是要保存的团队事实：`memberOrder` 首项与 `primaryAgentSlug` 始终一致，界面上不存在使两者分歧的路径；顺序与画像随「保存」一并提交，成功后给出统一生效反馈。
51. 每次 `AGENT.md` 保存成功都留下一条修订；编辑器标题行显示最近一次变化的一句话说明，正文里变动过的段落带标记，指向时能看到是谁改的、什么时候改的。独立维护的团队与持续接收更新的团队表现一致。
52. 点击段落标记就地展开原来的写法，不跳转、不打开第二个界面；页面任何位置都不出现逐行增删对比、内容指纹或版本号之类的技术细节。
53. 展开变化时间线能看到这名成员的全部修订，每条只有一句说明与作者，并能回到其中任意一版。
54. 默认 Agent 不可用时，上游单方改动的部分照常合入，需要语义合并的部分保留用户内容并标明尚未合入且可重试；任何情况下都没有用户内容被覆盖。
55. 变化说明尚未产出时用中性文字占位，保存、合并、撤销与时间线都不因此不可用。
56. 从侧边栏同步提示进入团队首页后，被改动过的团队在列表里带“作者有新更新”，用户不需要凭记忆逐支点进详情去找；进入该团队详情后标记消失。
57. 收起同步结果横幅后，“更多”菜单仍提供“最近的上游同步”，打开是同一份内容与同一个撤销按钮；下一次同步发生时它被替换，更早的同步只能在各成员时间线里逐名回退。
58. 团队首页按“持续接收更新 / 独立维护”分组，持续接收更新的团队在横行上显示 `owner/repo` 且可点击打开 GitHub；分组不按作者是谁划分，`tranfu-labs` 的团队与第三方团队在同一组内。某一组为空时该组标题不显示。
59. 用户把全部团队删空后看到空态与三条创建路径，而不是错误提示；两支自带团队读不出来时显示应用配置异常，与“删空了”明确区分。
60. 变化时间线中的上游修订署名为 commit 并能打开对应的 GitHub commit 页面，用户自己的修订署名为“你”且不带外部链接；独立维护的团队沿用同一套时间线结构与入口。
61. 本页不提供“立即检查更新”按钮；用户唯一能主动触发的上游访问是失联状态下的「重新检查」。

## 非目标

本页面明确不提供：

- 可视化工作流、流程节点、成员连线、组织架构或 DAG 编辑器。
- 脱离团队存在的全局 Agent 库。
- Agent 在团队之间移动、链接或共享同一份可变配置。
- 普通成员手动排序；只有主 Agent 固定排在第一位。
- `AGENT.md` 之外的软件内文件编辑器、文件树，以及任何形式的逐行增删对比视图。上游内容与用户内容的自动合并不再是本页非目标，它由[Agent 进化流程](../flows/agent-evolution.md)定义，本页承载其结果的呈现与撤销。
- 对自然语言职责和交棒关系做语义正确性验证，或在删除成员后自动改写其他 Agent 的规则。
- 团队的搜索、预览与安装界面；它们属于[找现成团队](./github-team-discovery.md)与[安装前预览](./github-team-preview.md)。本页只提供入口，并承载安装完成后的结果。
- 自建的团队市场、注册中心、评分、审核或推荐榜；GitHub 本身就是目录，产品不做中转站。
- 向上游仓库推送或提交用户的本地修改；同步只有一个方向，从上游到本地。用户想把自己的改动发出去，走 GitHub 自己的路。
- 可由用户设置的应用级默认团队。
- 会话内团队切换和异常恢复的完整交互。
- Codex、Claude Code、Kimi 的独立运行环境诊断、安装和登录；Pi Provider 的新增、Key 输入、真实能力验证、停用、删除与引用清单由设置页定义。
- Agent 运行配置如何进入会话快照，以及 Codex、Claude Code、Kimi、Pi API 的启动、恢复、中止、过程展示和老会话兼容；这些由主对话与单 Agent 会话页定义。
- 批量迁移某个 Provider 或模型的全部团队、草稿、任务和会话引用；本页只允许逐名修改当前团队成员，批量生命周期操作属于设置页。
- onboarding 如何展示统一执行环境准备、Provider 新增和 API-only 门槛。
- 上游仓库的拉取机制、缓存、鉴权、文件层事务与崩溃恢复等实现细节。
- 软件内永久删除或独立的已删除团队管理页。
