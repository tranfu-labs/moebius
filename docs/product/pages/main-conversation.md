## 页面目标

会话页是用户和一支 Agent 团队的唯一工作面。用户在这里描述目标、看着团队推进、在需要时插话或改变方向、确认结果，直到主 Agent 结合团队完整时间线明确收束本轮。这个收束是一条可持续保存的会话事实，不由成员交棒之间某一刻恰好无人运行来代替。

「新建对话」不是一个动作，而是这个页面还没有任何消息时的样子。产品不设独立的新建对话窗口：新对话页和有历史的会话页是同一个页面的两种状态，区别只在于有没有消息，以及进入时是否已经带上了项目。

会话页只回答六个问题：

1. 这段对话在哪个项目、用哪支团队、以什么方式动我的文件？
2. 团队现在做到哪了，说了什么？
3. 我想改变方向时，话该说给谁？
4. 在一段很长的对话里，我如何纵览真实接力并快速回到某条原消息？
5. 这段对话直接创建过哪些下一层分析对话，我从哪里再次打开它们？
6. Agent 为这段对话启动了哪些仍在运行的本地服务或任务，我如何继续使用和停止它们？

会话页不是运行日志、任务看板或固定阶段的工作流图。用户不需要理解内部编排结构，就能读懂团队在做什么；目录轨只投影已经发生的用户消息与 Agent 可见回复，不把真实协作解释成单向进度。

## 用户场景

- 用户点击侧边栏「新建对话」，还没想好放在哪个项目，先在页面上选。
- 用户从某个项目行进入，项目已经选好，直接描述目标。
- 用户还没有任何项目，需要在这个页面里添加第一个。
- 用户在团队推进途中想补一句话或改变方向。
- 用户想让某个正在工作的成员停下来换个做法。
- 用户想看看团队拆出来的某个子任务进行到哪了，看完回到主线。
- 用户遇到一步没跑起来，想重试或换个人做。
- 用户在运行中发现额度或服务异常，想保留已有内容、停下当前引擎并从同一终局记录临时换模型重跑。
- 用户只配置了 API Provider，希望所选团队直接以 Pi API 启动，不因没有本机 CLI 被挡在新对话之外。
- 用户的 Pi Key 失效、档案被停用或模型下架，希望保留时间线与文件结果，修复后继续，或明确迁移这段会话而不是被静默换引擎。
- 用户想中途换一支团队。
- 用户在团队页保存了成员职责或运行配置，希望不用重启应用；正在使用该团队的已有对话分别提示 `AGENT.md` 与运行配置变化，并允许用户把最新完整团队版本应用到后续工作。
- 用户看到一条 Agent 回复，想确认这次发言实际使用了哪支团队、哪份成员定义和哪组 CLI、model、effort，而不是查看团队现在已经变成什么样。
- 用户在选择团队前，想先看清团队用途、主 Agent 和成员构成，不靠团队名称猜测。
- 用户在长对话底部工作时，想预览早先的提问或成员回复，并直接跳回原消息。
- 用户想纵览一条消息触发的多人接力，或采访阶段多轮用户与主 Agent 往返，不被套进固定阶段。
- 用户看到某次 Agent 运行不符合预期或耗时过长，想从当前记录直接在右侧栏开始一段分析对话，并在以后从直接来源对话再次打开它。
- Agent 启动了 Storybook、Python HTTP 服务或 watcher；用户希望 Agent 回合结束后链接仍可用，并能在当前会话随时查看状态、日志或停止它。
- 用户把任务交出去后切到另一段对话或离开 Moebius，希望只有在这轮真正进入新状态时被叫回来，不因团队内部短暂交棒反复收到“结束—继续”的假信号。

## 入口与去向

### 入口

- 从[主页面侧边栏](./main-left-sidebar.md)顶部「新建对话」首次进入，或上一段新对话草稿已经随首条消息成功发出后再次进入，**不预选项目**。
- 从侧边栏项目行的新建入口进入，带上该项目。
- 点击侧边栏中任意一段已有对话进入。
- 从[全局搜索](./search.md)的结果跳转进入。

从顶部进入一个全新的草稿时不替用户预选项目：项目在发出第一条消息后就永久锁定，替用户猜一个会让一次没看清的点击变成一段归属错误且无法纠正的对话。团队可以预选，因为它随时能改。

如果用户此前已经在新对话中形成尚未发送的草稿，只是切到已有会话或其他页面查看内容，那么再次从顶部进入「新建对话」回到的是同一份草稿，不把它重置为新的未选项目状态。

进入新对话页时，侧边栏顶部「新建对话」呈现选中态，项目列表中不新增任何行。

### 去向

- 发出第一条消息后，这段对话才被创建，侧边栏才出现对应的行。
- 点击时间线中的子会话卡片，在[主页面右侧栏](./main-right-sidebar.md)打开该子任务。
- 从 Agent 运行记录或历史回复的更多菜单选择「在右侧栏分析这条消息」，在[主页面右侧栏](./main-right-sidebar.md)打开或聚焦一段尚未发送的分析新会话，并加入该消息对应的来源胶囊；首次发送成功后它成为直接归属于入口所在对话的分析对话，不进入左侧栏，后续创建、确认和修改顺序见[对话分析与优化流程](../flows/session-analysis.md)。
- 根对话中，点击主会话标题栏里位于右侧栏开关旁的分析面板开关，在主会话区域右上角显示或隐藏入口面板；右侧栏分析对话中，点击该标签自身标题区末端的分析面板开关，在该对话区域右上角显示或隐藏它自己的面板。点击任一面板入口都在既有右侧栏打开或聚焦对应分析对话的唯一标签页。
- 当前会话存在托管运行项时，点击主会话标题栏右侧的「运行项」入口，在原窗口打开该会话的运行项面板；带可用地址的条目可以交给系统浏览器打开。
- 团队按钮通往[Agent 团队](./agent-teams.md)的修复或管理入口。
- 切换到其他对话或页面时，未发送的新对话草稿只被隐藏，不创建侧边栏会话；重新进入「新建对话」时恢复原草稿。

### 新对话（从项目行进入，项目已带上）

```text
│   ┌──────────────────────────────────────────────┐   │
│   │ [▱ 项目 A ▾] [默认工作空间 ⇄] [main]         │   │
│   │ [◇ 开发团队 ▾]                               │   │
│   │ 描述你的目标…                         ＋  ↑ │   │
│   └──────────────────────────────────────────────┘   │
│                                                      │
```

上下文控件与 composer 容器之后直接留白结束，不追加 readiness、成员准备人数、CLI / Provider 兼容性或去 Agent 团队页调整的提示区。checking、ready、missing、needs-login、needs-attention、disabled、unavailable、IPC 延迟或失败都使用同一结构；真实执行引擎启动或配置校验失败只在消息提交后的会话时间线中呈现。新对话不因为没有 ready CLI 而拒绝 API-only 用户发送，也不把团队中至少一个成员可运行夸大为整支团队都可运行。

### 新对话草稿的生命周期

同一份尚未发送的普通新对话草稿包含用户已经选择或填写的**项目、工作空间、团队、正文和附件**。右侧栏中的分析新会话在这五项之外还包含已经收集的**文本胶囊**。在已有会话与其他页面之间导航不会开启另一份新对话，也不会丢弃或改写对应草稿内容：

```text
新对话
┌──────────────────────────────────────────────────────┐
│ [▱ 项目 A ▾] [独立工作空间 ⇄] [moebius/…]           │
│ [◇ 开发团队 ▾]                                      │
│ [▧ 页面截图.png ×]                                  │
│ 保留这段目标…                                ＋  ↑ │
└──────────────────────────────────────────────────────┘
          │
          ├─ 切到已有会话或其他页面 → 草稿暂时隐藏
          │
          └─ 再次进入「新建对话」   → 草稿内容原样恢复
```

导航期间侧边栏仍没有这段新对话的行。只有 session 与首条消息成功创建后，这份草稿才被消费；下一次从侧边栏顶部进入时重新回到项目未选定的新草稿。创建或提交首条消息失败时保留整份草稿和可理解的失败反馈，用户可以直接重试。首条消息已经落库、但随后 Agent 没跑起来，不属于草稿提交失败：对话已经创建，草稿已经消费，运行失败按已有会话的恢复规则处理。

### 带附件的输入框与时间线

输入框右下角的「＋」与发送按钮相邻。点击后使用系统文件选择器添加一个或多个文件；文件也可以直接拖进输入框，剪贴板中的图片可以直接粘贴。输入框上方先显示附件草稿：能够安全解码的 PNG、JPEG、GIF、WebP、SVG、ICO、BMP 与 AVIF 用缩略图，其他文件用文件名、类型和大小组成的普通附件卡片。GIF 首期显示静态预览；SVG 只按不可执行、不可交互、不得加载外部资源的图片方式解码，无法安全预览时降级为仍可发送的普通文件卡片。ICO、BMP 与 AVIF 与 SVG 同语义：作为普通文件提交并进入附件清单，有派生预览时以图片卡呈现，无法安全解码时降级为普通文件卡片，不进入 provider 图片输入。

```text
│   ┌──────────────────────────────────────────────────────┐  │
│   │ [▧ 页面截图.png  ×] [▤ 需求说明.pdf · PDF · 2.4 MB ×]│  │
│   │ 请对照截图和说明检查这个页面                         │  │
│   │                                                ＋  ↑ │  │
│   └──────────────────────────────────────────────────────┘  │
```

图片上传中保留缩略图占位和进度状态；普通文件使用同一位置的卡片状态。任一附件仍在准备或准备失败时不发送整条消息，失败卡片给出重试和移除。已经准备好的文字与其他附件都保留。

发送后，附件与正文共同成为一条用户消息。图片继续显示缩略图，普通文件继续显示附件卡片，不把应用托管路径写进 Markdown 正文或暴露给用户：

```text
│ 你                                                          │
│ 请对照截图和说明检查这个页面                                │
│ [▧ 页面截图.png]  [▤ 需求说明.pdf · PDF · 2.4 MB]           │
```

#### 会话图片预览与大图查看

图片预览的第一优先是让用户不离开时间线就能判断内容，第二优先才是放大检查细节；两者冲突时，时间线的稳定、清晰显示优先。除用户发送的图片附件外，Agent 最终回复中按既有本地文件引用语义识别出的 PNG、JPEG、GIF、WebP、SVG、ICO、BMP 与 AVIF 也在对应回复正文后显示内联预览。远程 Markdown 图片沿用原有渲染，不再生成第二份预览；非图片文件继续使用现有文件卡片。

```text
┌ 主会话页 ────────────────────────────────┐
│ ┌────────── 会话上下文区 ──────────────┐ │
│ └─────────────────────────────────────┘ │
│ ┌────────── 消息时间线区 ──────────────┐ │
│ │ ┌──────── 消息图片预览区 ──────────┐ │ │
│ │ │ ┌────── 图片识别区 ────────────┐ │ │ │
│ │ │ └─────────────────────────────┘ │ │ │
│ │ └─────────────────────────────────┘ │ │
│ │ ┌──────── 图片异常区 ─────────────┐ │ │
│ │ └─────────────────────────────────┘ │ │
│ └─────────────────────────────────────┘ │
│ ┌────────── 待发送图片区 ─────────────┐ │
│ └─────────────────────────────────────┘ │
│ ┌────────── 消息行动区 ───────────────┐ │
│ └─────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

正常图片预览只展示图片本身，不在视觉界面重复显示文件名、格式或来源；这些信息仍保留在图片的替代文字和辅助名称中。多张用户附件按附件顺序排列，Agent 图片按回复中首次出现的顺序排列。图片卡统一 160px 高，宽度按原图比例完整显示并限制最大宽度（320px），不裁剪图片内容；图片状态卡（加载、失败、缺失、变化、不安全）与图片卡同高 160px。单条消息图片超过 6 张时直接显示前 6 张，其余折叠为一个「查看全部图片（共 N 张）」入口，激活后进入大图查看层从本条消息第一张开始按序查看。预览可点击，也可在键盘聚焦后用 Enter 或 Space 打开大图查看层。

预览入口的可访问名称是 `查看大图：{文件名}`；图片替代文字按来源使用 `{文件名}，来自你` 或 `{文件名}，来自 {成员名}`。附件操作使用 `添加附件`、`发送消息`、`移除附件：{文件名}` 和 `重试添加：{文件名}`，不让图标成为唯一说明。

```text
│              居中图片／可拖拽             │

└──────────────────────────────────────────┘
```

大图查看使用现有 Dialog 的遮罩、焦点约束和关闭语义，但内容层按 Lightbox 呈现：不显示文件上下文卡片，图片在接近全屏的深色画布中居中，保持比例并适应可用区域。当前对话中的全部可用图片按消息顺序组成一个查看集合，左右按钮与键盘方向键切换图片；到达首尾时按钮禁用，不循环跳转。查看层支持放大、缩小、恢复适应窗口和拖拽；图片处于适应窗口状态时不拖拽，放大后才允许平移。关闭按钮与 Escape 都能关闭查看层，关闭后恢复触发预览的原消息位置、滚动位置和键盘焦点；查看图片不得停止 Agent 运行或改变文件状态。

图片预览只缓存当前会话仍被时间线或查看层引用的派生预览。关闭查看层释放查看引用；切换到其他对话、消息被移除或组件卸载后，没有其他引用的临时 URL 必须释放，不能把原始路径写入缓存或 DOM。

大图替代文字是 `{文件名}的大图预览`，加载时显示 `正在打开「{文件名}」…`，关闭按钮的可访问名称是 `关闭大图`。

图片状态与动作使用以下文案（状态卡只显示一句主文案与图标，操作按钮承载恢复动作；文件名保留在卡内，类型与来源进入替代文字）：

- 时间线加载中：`正在加载图片…`
- 时间线或大图通用失败：`这张图片暂时显示不了`
- 文件不存在：`找不到这张图片`
- 文件已变化：`图片已变化，重新加载`
- SVG 无法安全显示：`SVG 无法安全显示`
- 操作：`重新加载`、`打开文件`、`关闭大图`。

待发送图片区使用以下文案：

- 准备中：`正在准备「{文件名}」，完成后就能发送。`
- 已准备：`「{文件名}」已准备好，可以发送。`
- 通用失败：`没能添加「{文件名}」。你可以重试，或移除后继续发送其他内容。`
- 文件过大：`「{文件名}」太大，暂时无法添加。移除后可以继续发送其他内容。`
- 不是有效图片：`「{文件名}」不是可读取的图片。你可以重新选择文件，或将它移除。`
- SVG 降级：`无法预览这张 SVG，它会作为普通文件发送。`
- 发送禁用原因：`图片准备好后才能发送`、`请重试或移除无法添加的图片`。

图片加载、读取失败、文件不存在或安全检查失败都占用原预览位置，不让消息宽度突然变化。真正无法添加的文件会阻止发送；无法安全预览的 SVG 不阻止发送，只降级为普通文件。重新加载只读取当前预览，不重新发送消息或运行 Agent。打开原文件继续遵守现有工作空间、文件引用和托管附件边界；目标不可访问时原位说明原因。任何图片异常都不影响同一消息中的正文和其他附件。

可以发送只有附件、没有文字的消息，也可以一次发送多个附件。纯附件首条消息没有正文可用于标题时，使用第一个附件的文件名作为对话标题。首版不额外设置固定附件数量上限；超出系统可安全处理的单文件规模、可用磁盘空间或当前绑定执行引擎实际可处理能力时，必须在发送前给出明确失败原因。

### Claude 运行记录表面

Claude-bound active run 继续复用既有运行块，显示结构化的最新活动、状态、停止入口和最终回复；不再渲染实时 PTY、原始终端字节或 Claude 原生交互提示。composer 仍是唯一的人类输入入口。

Claude 的完整过程通过「完整输出」入口进入主页面右侧栏，读取该次 Claude session 的原生 JSONL 历史，按实际发生顺序展示 Agent 正文、thinking、工具调用与结果、错误和 usage；最终回复不是完整过程的替代品。历史读取失败时只在该次尝试显示过程记录不可用，最终回复与其他尝试仍可读。

SDK 运行不打开登录、工作区信任或 MCP 确认页面。认证缺失、权限无法自动决定、MCP 配置失败等情况进入结构化的安全失败，不让不可见的交互进程等待用户输入；已配置的 Claude 原生认证和普通配置仍由 Claude Code 自身读取。

### 右侧栏中的分析新会话

「在右侧栏分析这条消息」打开的不是分析专用面板，而是本页既有的新对话布局在右侧栏标签中的窄宽呈现。项目与工作空间来自入口所在对话，「通用助手」是初始团队；三项都是正常新对话上下文，发送前仍可改选。

```text
┌ 右侧栏 ─────────────────────────────────────┐
│ 新对话 ×                                  ＋ │
│──────────────────────────────────────────────│
│                    新对话                    │
│                                              │
│           Agent 运行不符合预期？             │
│           Agent 运行太长了？                 │
│                                              │
│ ┌──────────────────────────────────────────┐ │
│ │ [项目] [工作空间] [分支] [通用助手]      │ │
│ │ [文本片段 1 ×] [文本片段 2 ×] …          │ │
│ │ 描述你的目标…                      ＋  ↑ │ │
│ └──────────────────────────────────────────┘ │
└──────────────────────────────────────────────┘
```

文本片段复用附件草稿所在的视觉区域，但不是文件附件。发送前所有片段保持在一行，每个胶囊只显示「文本片段 1」等短标签和删除操作；悬浮、键盘聚焦和辅助技术显示将插入消息的完整 Markdown 文本，这份可读取文本就是发送后最终所选团队获得的全部片段内容。每个删除按钮有包含片段名称的独立可访问名称，可以用键盘聚焦并激活。候选提示词位于正常新会话空态中，可以用鼠标点击或键盘聚焦激活；激活只把对应问题填入正文，不改变文本胶囊。

分析草稿**当前选择的项目**在打开前已经目录不可用，或草稿保留期间变为不可用时，项目上下文标红并原位说明「当前项目文件夹不可用，请先修复，或改选其他项目后发送」。正文、文本片段、普通附件、团队选择和其他草稿内容全部保留并可继续编辑，但即使正文已经填写，发送仍禁用。用户在左侧栏修复当前所选项目后，草稿保持原选择并恢复正常发送条件；用户也可以在首次发送前通过正常项目选择器改选任一可用项目，工作空间选项随新项目重算，文本片段不变并立即按新项目重新判断发送条件。来源项目只决定导航目标，不锁定草稿项目；文本片段可以跨项目、工作空间、团队或 provider 作为可见文本使用，但链接不授权读取目标对话、运行记录、来源项目文件或引用之外的对象。当前所选项目目录不可用本身不得静默丢弃片段、改选项目或创建半成品对话。

首次消息创建成功后，当前标签原地变为本页定义的正常已有会话；标题、时间线、用户右侧气泡、Agent 左侧正文列、运行记录、输入框和响应式行为不产生另一套分析专用布局。发送前的文本胶囊不再作为独立结构留在历史中，而是在首条用户消息正文顶部序列化为固定 Markdown 来源块：

```markdown
> 来源：
> - [消息 · 开发 · “正在修改登录页空状态”](moebius-ref:message/<conversation-id>/<message-id>)
> - [对话 · “登录页运行分析”](moebius-ref:conversation/<conversation-id>)

分析这次运行为什么耗时过长。
```

正常渲染历史时，用户看到的是可读的消息或对话链接，不展开链接地址中的内部标识；进入原始 Markdown 编辑态时则会显示完整公开协议文本和其中的目标 ID。消息引用显示来源成员和原消息开头；对话引用显示来源对话标题。消息引用被激活后打开或聚焦目标对话并精确定位、短暂突出原消息；对话引用只打开或聚焦目标对话，不伪造消息位置。目标已经打开时，消息引用仍定位目标消息；对话引用保持目标对话原阅读位置，只把焦点交给目标对话区域。目标是主内容中的根对话时在主内容完成对应动作，目标是分析对话时在右侧栏打开或聚焦唯一标签。

导航前先沿直接父子关系解析目标所属的根对话。目标与当前工作现场属于同一棵对话树时，复用当前根对话及其右侧栏标签组；属于另一棵树时，一次激活必须原子地切换到目标根对话、恢复该根对话自己的右侧栏标签组，再打开或聚焦目标分析对话，不能把目标挂进当前根对话的标签组。目标根对话本身就是引用目标时，只切换并聚焦主内容。任一步无法完成时保持原工作现场与阅读位置，并把该来源原位降级为不可用。

同一条消息包含多个文本片段时，按用户发送前的胶囊顺序生成多条来源项，来源块之后空一行再接用户正文。历史只保留这一份 Markdown 正文，不再重复渲染文本胶囊。即使在不支持应用内导航的纯 Markdown 阅读器中，来源类型、成员、消息开头或对话标题仍然可读。

应用从文本胶囊生成来源块时必须安全处理原始标题或消息正文：

- 消息摘录先排除消息顶部由本协议生成的完整来源块，再对剩余原始 Markdown 做与正常消息一致的安全解析，按文档顺序取得纯文本投影：标题、段落、列表、引用和表格保留可见文字；链接只取链接标签；图片只取非空 alt；inline code 与代码块取代码文字；mention 使用正常渲染后的可读名称；原始 HTML 只取安全清洗后仍可见的文字。没有正文但有附件时使用第一个附件文件名，正文与附件都没有时降级为「无文字消息」。对话引用取已有可读标题，没有标题时使用「新对话」。
- 换行、制表符和连续空白收敛为单个空格；控制字符、双向文本控制符和不可见分隔符移除。
- Markdown 特殊字符、反斜杠、括号、尖括号、引号和反引号必须正确转义，不得改变链接边界或生成额外 Markdown/HTML。
- 可见摘录按 Unicode grapheme cluster 截取最多 80 个用户可见字符，不能截断 Emoji、组合附加符或代理对；超出后显示省略号，完整原消息仍通过导航查看。
- `moebius-ref:` 是公开的应用内导航文本协议，不证明链接由谁生成。应用、用户或 Agent 写出的同格式链接，只要语法合法且目标对当前用户可访问，都按同一规则导航；复制粘贴后仍然有效。链接地址不得拼接标题、正文、路径或其他外部文本。格式非法、目标缺失或不可访问时不得按外链打开，保留原可读标签并追加「来源不可用」说明；该说明可被键盘聚焦和辅助技术读取，但不能激活。

任意消息中的合法 `moebius-ref:` 都只提供用户导航，不触发 Agent run 的后台来源读取。用户直接输入、粘贴或编辑链接时，它与其他可见 Markdown 一起进入消息；目标消息、目标对话、结构化 run 记录、完整输出和 stdout/stderr 均不会自动附加。链接目标不可用只影响激活后的导航反馈，不阻塞消息提交、排队或 run 创建。

同一 run 中断后恢复、重试、重新建立原执行与恢复失败后的重新执行都使用对应用户消息中已经持久化的可见文本，不刷新链接目标，也不复用历史中可能存在的隐藏来源上下文。消息与对话提交成功后再启动 Agent；此后执行引擎启动失败保留已经创建的消息、分析对话和父面板入口。

### 分析对话入口面板概念

分析新会话首次发送成功后成为直接归属于入口所在对话的分析对话。根对话既可以从左侧栏的整段对话入口发起分析，也可以从其中一条消息发起；分析对话不提供“分析整段对话”的入口，只允许用户从其中某条具体消息继续创建下一段分析对话。新对话只进入当前分析对话自己的面板；每一层都遵守相同的直接父子归属，不向更早祖先面板重复汇总。所有分析对话都不作为普通根对话进入左侧栏。

根对话的面板关闭时，主会话标题栏中的面板开关与右侧栏开关相邻、彼此独立：

```text
┌ 侧边栏 ─────┬ 主会话 ─────────────────────────────────────┬ 右侧栏 ┐
│ 主对话 A  ← │ 主对话 A                 [分析] [右侧栏]   │         │
│ 主对话 B    │ 目录轨   主对话时间线                      │         │
│             │          主对话输入框                      │         │
└─────────────┴──────────────────────────────────────────────┴─────────┘
```

主会话区域宽度充足时，打开的面板在该区域右上角顶格布局。面板中的每一项只是一段分析对话的触发入口，不在面板内承载该分析对话的时间线、输入框、摘要、状态、详情或二级导航：

```text
┌ 侧边栏 ─────┬ 主会话区域 ─────────────────────────────────┬ 右侧栏 ┐
│ 主对话 A  ← │ 主对话 A                 [分析] [右侧栏]   │         │
│ 主对话 B    │                                              │         │
│             │ 目录轨   主对话时间线       ┌ 分析 ───────┐ │         │
│             │                             │ 运行耗时分析│ │         │
│             │                             │ 角色设计检查│ │         │
│             │          主对话输入框       └─────────────┘ │         │
└─────────────┴──────────────────────────────────────────────┴─────────┘
```

点击其中一项后，应用在既有右侧栏中打开对应分析对话的标签页；同一分析对话已经打开时聚焦既有标签，不创建重复标签。面板本身不切换成分析对话详情：

```text
┌ 侧边栏 ─────┬ 主会话区域 ─────────────────────────┬ 右侧栏 ──────────┐
│ 主对话 A  ← │ 主对话 A         [分析] [右侧栏]   │ 运行耗时分析 ×  │
│             │ 目录轨   主对话时间线              │                  │
│             │                 ┌ 分析 ───────┐     │ 分析对话时间线  │
│             │                 │运行耗时分析 │     │                  │
│             │                 │角色设计检查 │     │ 分析对话输入框  │
│             │ 主对话输入框    └─────────────┘     │                  │
└─────────────┴──────────────────────────────────────┴──────────────────┘
```

面板只负责找回与触发打开当前对话直接创建的分析对话，不新增 Subagents、运行时子代理、摘要列表、状态聚合或面板内会话切换能力。更深层分析对话由其直接父对话自己的面板承载，本面板不缩进、不画树，也不重复列出孙辈。

每个正在工作的成员各占一条活动记录；记录内部的最新活动、运行耗时、终态与完整输出遵循[单 Agent 会话](./agent-conversation.md)。主理人和多个专业成员可以同时工作，彼此的活动记录、停止入口和最终结果不得相互覆盖。

输入框始终是用户对当前团队的控制面。系统按这段会话冻结的成员名单解释代码区域外的 mention：正文只指向一个有效成员时直接送达该成员；没有有效 mention、mention 全部无效，或同时指向多个不同有效成员时交给主理人统一调度。目标车道空闲时立即启动；目标成员正在工作时进入该成员自己的 FIFO 待发射队列，不并行、不打断当前 run。待发射区逐条显示目标成员，让用户能区分正在等主理人还是某个专业成员；切换对话或重启应用后，队列与目标仍然保留。

用户发送新消息永远不会隐式停止任何正在运行的成员。主理人忙时，给主理人的消息沿用主理人 FIFO；专业成员忙时，只把明确直达该成员的消息排到该成员车道。不同成员的空闲车道仍可并行启动。主理人或目标成员进入终态后，各自只领取自己队列中最早的一条。

输入框右下角的方形按钮只表示「停下主理人」。它在主理人运行期间保持可见，不因用户开始输入而变成发送按钮；有可发送草稿时，同时提供发送动作，把草稿送入待发射区。专业成员的停止入口只属于各自活动记录，用户可以精确停下其中一人而不影响主理人或其他成员。

用户与 Agent 正文在同一条无卡片时间线中渲染 Markdown；宽表格、代码和图只在自身容器中滚动或缩放。用户消息按真实聊天软件的惯例走右泳道：who 行右对齐，正文收在右侧气泡内；Agent 与系统消息保持左侧正文列。运行中的进度仍是同一个 `runId` 对应的一行：

主时间线中的会话标题、Agent 历史消息与运行中临时记录复用同一条正文列：运行中记录的角色名与最新一行活动摘要左边界必须和标题、Agent 历史消息正文一致，「完整输出」等运行操作贴住同一正文列的右边界。运行态不得因为使用独立组件而向时间线容器外沿偏移或缩窄。用户消息是唯一例外，不占用这条左正文列。

主会话输入框是这条正文列在页面底部的操作延续：已有会话的输入框、其上方按目标标注的待发射区，以及新对话状态的输入框，左右边界都与正文列一致。这样阅读消息和继续输入共用一条稳定的视觉轴，不因从阅读切换到操作而向内跳动；窗口变窄时它们随同一可用宽度一起收缩。右侧栏中的子任务输入框仍服从右侧栏自己的可用宽度，不被主会话列强行拉宽。

### 会话目录轨

目录轨只属于当前打开的主会话，固定在主会话正文列左侧的留白区域。项目与会话侧边栏仍然只负责切换对话，不为每条会话重复绘制轨迹。

```text
┌ 项目 / 会话侧栏 ┬────────────── 当前主会话 ──────────────┬ 右侧栏 ┐
│ 对话 A          │ ┌目录轨┐  会话标题                      │        │
│ 对话 B          │ │ ━    │  你：第一条用户消息            │        │
│ 对话 C          │ │ ━━   │  产品交付负责人回复            │        │
│                 │ │ ━    │  你：继续补充                  │        │
│                 │ │ ⋮    │  远端连续消息暂时收起          │        │
│                 │ │ ━    │  界面原型师回复                │        │
│                 │ │ ━━   │  当前阅读位置                  │        │
│                 │ └──────┘  输入框                         │        │
└─────────────────┴─────────────────────────────────────────┴────────┘
```

目录轨把同一组真实时间线事件投影成收起和展开两种形态。它不是完成百分比，也不假定“产品 → 原型 → 实施 → 验收”只会单向经过一次；`A → B → C → B → C` 必须按真实顺序往返。

```text
收起：固定单列目录             展开：主干 + 成员分支覆盖层

 ━  用户前景色                 ● 用户主干
 ━━ 主 Agent 身份色            ╰────● 主 Agent
 ━  用户前景色                 ●    │
 ⋮  远端连续节点收起           ⋮    │
 ━  专业成员身份色             ╰────┼────● 专业成员
 ━━ 当前阅读焦点                         ◉
```

- 每条用户消息和每条 Agent 可见回复各形成一个目录事件，并各占一个节点行；系统记录、工具活动、隐藏过程、运行状态变化和仍在原地更新的过程片段不另建目录事件。
- 收起态是默认的单列目录，不画圆点，只以共同左端对齐的短横线表示事件。当前阅读焦点比普通横线更长、更实；用户横线使用正文前景色，Agent 横线使用对应成员的稳定头像身份色。颜色只表达作者，不承担运行、异常或未读语义。
- 目录轨与当前主会话左缘保持克制的内间距，上缘避开窗口标题行；主时间线滚动、项目与会话侧栏开合都不改变它在主会话内的锚点。
- 用户悬停或键盘聚焦目录轨时，同一批事件替换为无文字轨迹图：用户消息固定在最左主干，Agent 按首次出现顺序向右分配成员泳道，所有事件都显示为小圆点，当前阅读焦点显示为空心描边环。展开态不常驻显示泳道名称、头像表头或文字标签。
- 用户主干在每个连续可见区间内从首个事件贯穿至末个事件；每个成员分支从该成员第一条可见回复之前的事件节点平滑分叉，纵向穿过该成员的可见回复，并在该成员最后一条可见回复之后平滑并回下一事件节点。分支使用成员身份色，主干使用弱化中性色，当前检查事件关联的轨迹稍加粗；折叠省略区两侧各自收束，不伪造跨区连线。
- 展开层从目录轨向右覆盖，不改变正文宽度、标题位置、输入框位置或主时间线消息排布。展开后轨迹行距适度增加，让分支图获得纵向呼吸空间；目录以展开后的实际行距约束可见容量，保证面板始终留在可用视口内。离开目录轨及其预览后恢复单列目录。
- 所有真实事件在收起态和展开态都具有可命中的悬停、键盘聚焦和点击区域。展开态每一行只有一个真实节点，因此整条事件行都是该节点的命中区，而不是只让圆点本身可悬停；连接线、轨迹行间空白和折叠占位不伪装成某一条原消息。折叠占位虽不选择事件，但仍属于展开轨道的连续 hover 表面：指针从事件行移入时保持展开并保留当前预览，只有真正离开整个轨道或预览卡才进入关闭宽限。
- 展开面板宽度由实际成员泳道数量决定；成员过多时只压缩泳道间距，面板不得随主会话容器空泛拉伸或越过可用宽度。面板使用无阴影的抬升中性底和细描边；focused 外观使用比画布仅轻微分层的 side surface，事件行悬停使用更强的 interaction surface，二者不得塌成同一灰阶。事件行仍保持完整命中区，但悬停底色须在行内四周留出间隙，并位于轨迹线下方，不得贴住面板边界或遮住连线。
- Hover Card 只预览当前事件，不展开整条轨迹。用户事件显示“你”和用户原消息开头；Agent 事件只显示成员可读名称、时间和该 Agent 原回复开头，不再把关联用户消息重复放在标题行。不得显示 `@slug`，也不得生成可能失真的摘要。
- Hover Card 使用紧凑宽度，正文只显示有限行数；横向锚点相对于整个展开轨迹面板保持固定间距。悬停最左或最右泳道的节点都不能改变卡片与面板的间距。窗口空间不足时可以整卡翻转到面板另一侧或约束宽度，但不得按节点横向位置逐点漂移。目录轨必须在取得首个有效视口尺寸后才呈现可定位内容，预览锚点使用独立于展开面板动画的稳定坐标层，首次出现直接落在最终展开坐标，不得从未测量的临时位置或收起面板的位置滑入；后续事件切换与真实尺寸变化仍保持连续跟随。
- 点击任一真实事件后，主时间线精确定位到对应原消息并短暂突出；键盘激活具有相同行为。定位失败时保持原阅读位置并给出可理解反馈，不得静默跳到近似消息。
- 目录轨响应当前主会话的实际可用高度与宽度，而不是侧边栏宽度或窗口媒体查询。长会话的展开面板使用会话区高度约 70% 的显示预算，上下保留呼吸空间，并在高窗口中最多显示 15 行（480px），不得因为空间充足就铺满整个会话区。变窄时优先压缩泳道间距和展开宽度，变矮时减少可见事件并增加省略区，Hover Card 根据窗口边缘翻转或约束位置；目录轨不得溢出会话区，也不得因为左侧栏开合而迁移到侧栏内部。
- 交互骨架可以借鉴 [beUI Preview Rail](https://beui.dev/components/motion/preview-rail) 的事件行命中区、受控当前项、键盘焦点和浮动预览，但不得照搬其相邻项金字塔。Moebius 使用自己的轨迹动效：收起态所有短横线的左端固定对齐；展开面板从同一左侧锚点向右打开，短横线从左端收束，节点横向进入对应泳道，用户主干与成员分支随之绘入；切换检查事件时预览卡沿纵向连续跟随，内容做短促淡换。展开轨面板本身不加阴影；右侧预览卡在亮色用阴影抬升，暗色取消阴影并改用与画布不同的实色卡面。动效不得让目录居中膨胀、左右同时生长或改变正文布局；`prefers-reduced-motion` 下以即时静态切换保留等价信息。

#### 长会话与阅读焦点

目录轨的可见高度取自主会话时间线视口，而不是固定为侧栏原型的 `18px × 9 行`。事件未超过当前容量时全部显示；超过容量时使用跟随阅读焦点的滑动窗口，不永久删除远端事件，也不在目录轨中增加一根常驻内嵌滚动条。

```text
13 个事件，阅读焦点在末尾       阅读焦点靠近开头

━  1                           ━  1
⋮  2–6                         ━━ 2
━  7                           ━  3
━  8                           ━  4
━  9                           ━  5
━ 10                           ━  6
━ 11                           ━  7
━ 12                           ⋮  8–12
━━13                           ━ 13
```

- 当前焦点取主时间线视口中最接近阅读中心的那条可见消息；刚点击目录事件时，以被定位的消息为焦点。它不是“最新回复”或“当前执行成员”的替代状态。
- 当前焦点始终可见，并尽量保留它前后的连续上下文；第一条和最后一条事件作为会话边界尽量保留，远端连续区间才合并为省略占位。焦点位于中段时允许上下两端各出现一个省略占位。
- 省略只代表当前视窗折叠，底层事件及定位能力不得丢失。用户在目录轨内滚动或用方向键移动焦点时，隐藏区进入窗口；该操作不得意外滚动项目列表、切换会话或改变主时间线位置，直到用户明确激活某个事件。
- 切换到其他会话再返回时，恢复该会话上次阅读消息；期间到达的新消息不得强制把阅读焦点跳到末尾。从未打开过或保存位置已经不存在的会话才以最新稳定事件作为初始焦点。
- 可见容量按展开态实际行距与显示高度预算计算：正常窗口取会话区高度约 70%，至少容纳 7 个标准行，高窗口最多容纳 15 个标准行；矮到无法满足最低预算时退回真实可用高度，并把行高在 32–20px 内压缩。焦点前后保留数和成员泳道间距随实际可用空间安全收缩，但主干锚点、首尾边界与当前焦点不得丢失。

```text
   │   tranfu-labs/moebius-team-development          │
   │   负责软件方案、实现、测试与复核                │
   │   主 Agent：开发经理 · 4 名成员                 │
   │   [开发经理] [开发] [测试] [安全审查]           │
   │ ─────────────── 切换到其他团队 ─────────────── │
   │   通用助手                                      │
   │   tranfu-labs/moebius-team-general-assistant    │
   │   处理一般对话与任务                            │
   │   主 Agent：通用助手 · 1 名成员                 │
   │   [通用助手]                                   │
   │ ────────────────────────────────────────────── │
   │ 这段对话沿用当前已载入的团队状态                │
   │ 当前团队的修改不会在这里原地更新                │
   └────────────────────────────────────────────────┘
```

团队选择器中的每个选项都显示完整团队名称、来源、一句话用途、主 Agent、成员数量和当前可读成员。成员使用与 Agent 团队页一致的中性首字头像与显示名称，主 Agent 排在第一位并有文字标识；空间不足时保留主 Agent，并把其余成员收敛为前几名与可激活的 `＋N`。点击或键盘激活 `＋N` 只在当前团队选项内展开完整成员名单，再次激活收起；展开不会选中团队或关闭选择器。成员很多时只滚动该选项的成员区，不能截断最后几名、撑出页面级横向滚动或要求用户先进入团队管理页。选择器不展开每名成员的 CLI、model、effort，这些运行事实属于具体发言的信息卡和团队详情，不能让团队选择退化成配置表。

新对话、分析新会话和已有会话改选团队复用同一个团队选项组件与信息层级，但已有会话必须把「当前实际使用的快照」与「可切换的当前团队目录」分开表达：

- 新对话与分析新会话发送前，所有选项都读取当前已保存的团队状态，不显示尚未保存的团队页草稿。团队页成功保存后，选择器无需重启应用即可在下一次打开或刷新时读取新状态；首次发送以发送时最终选中团队的当前已保存版本建立快照。
- 已有会话的收起按钮始终读取这段对话当前有效快照，显示快照中的历史团队名称、来源及必要的同名辨认信息，不能用当前团队目录里的新名称、新成员或其他后来保存的事实替换。
- 已有会话展开菜单时，顶部带勾选且不可再次选择的「当前对话」选项同样读取有效快照；分隔线下的「切换到其他团队」才读取当前已保存的团队目录。当前快照所对应团队不在下方重复列出，不能把团队菜单变成对当前团队执行原地更新的入口。
- 用户明确选择另一支团队并到达生效边界时，载入目标团队此刻的最新保存版本。之后再从 B 切回 A 时，A 已经是另一支目标团队，因此可以载入 A 届时的最新保存版本；这是一次明确团队切换，不是后台把 A 的修改追溯进原快照。
- 运行中存在待生效切换时，收起按钮显示用户所选目标团队的当前保存身份并保留待生效说明；真正生效后，它改为读取新建立的有效快照。

持续接收更新的团队显示它的上游仓库 `owner/repo`；独立维护的团队不显示仓库名。来源信息不能只在团队管理页出现——用户在这里选的是「哪段提示词来接我这次的活」，谁写的那段提示词是他判断的依据。

仓库名同时是最好的辨认信息：它全局唯一，比任何产品自造的来源文案都准确，因此不再需要「内置来源名称」这种额外文案。

名称相同的合法团队使用稳定、用户可读的辨认信息继续区分：

- 持续接收更新的团队显示 `owner/repo`。它不随用户改名变化，且天然彼此不同。
- 独立维护的团队显示其稳定的**本地创建时间**，使用用户时区的完整日期与时间，例如「创建于 2026-07-29 14:32:05」。创建时间在团队登记后不随改名、复制来源变化或内容编辑而改变，并显示到足以在同名团队之间保持唯一的精度。
- 复制出来的团队使用它自己的创建时间；「复制自」等说明可以额外显示，但不能替代唯一辨认信息。
- 界面不得使用稳定 slug、数据库 ID、文件路径或列表临时序号兜底。排序变化、关闭重开和应用重启后，同一团队的辨认信息保持不变。

同名团队必须在展开列表和收起后的当前团队按钮中都可辨认；已有会话的当前项以有效快照中的身份参与辨认，不能被当前目录状态重新命名：

- 展开列表同时显示名称与来源；两支同名团队都独立维护时再显示创建时间，不能只靠排列顺序、头像或内部标识区分。
- 当前选择的名称与其他可用团队重名时，收起按钮显示足以唯一辨认的仓库名或创建时间；没有重名时可以只显示名称以保持紧凑。
- 每个选项的可访问名称始终包含完整团队名称和来源；同名且同为独立维护时继续包含创建时间。当前按钮的辅助名称还要说明它是当前所选团队，并使用相同辨认信息。
- 新对话首次选择、分析新会话发送前改选、已有会话切换团队和团队异常后的改选都复用同一套辨认规则，不得在某个入口退化成只有名称的列表。
- 选择器不显示 `general-assistant` 等内部稳定标识。来源仓库名不是内部标识——它是用户在 GitHub 上能直接打开的地址，也是他当初据以决定安装的那个名字。

已有会话的当前团队与会话有效快照相比，只要存在已保存变化，就在输入框上方按变化类别显示中性提示：

- 任一成员 `AGENT.md` 变化显示「Agent 定义已更新」提示。
- 任一成员 CLI、model 或 effort 变化显示「运行配置已更新」提示。
- 团队名称、一句话用途、主 Agent、成员增删或稳定身份变化显示「团队信息已更新」提示。

同一类别无论涉及一名还是多名成员都只显示一条，允许用成员数量帮助辨认；不同类别同时变化时分别显示，避免把角色内容与模型配置混成一句模糊说明。

每条提示提供「查看」「应用」和关闭三个动作：

- 「查看」打开弹窗，按成员列出这次变化了什么，使用与团队页编辑器一致的段落标记与来历署名。弹窗右下角是「取消」与「应用」；**「取消」只关闭弹窗，提示保留**。
- 「应用」把点击时这支团队**最新、完整且有效的已保存版本**作为一个整体应用。弹窗里的「应用」与提示上的「应用」是同一个动作，含义完全相同——弹窗展示了哪几名成员、哪几处变化都不改变这一点。用户不能只应用弹窗里看到的某一项，也不能选择应用到哪个历史版本；界面必须把这一点讲清楚，因为把变化摊开来看之后，用户很容易以为自己获得了逐项挑选的能力。
- 关闭只是收起提示：本次会话内不再提示这一批变化，之后若产生新的已保存变化则重新出现。它不改变会话当前使用的快照。

成功应用后，所有已被该版本覆盖的变化提示一并消失，避免形成 `AGENT.md` 新、运行配置旧的混合快照。

通过团队页保存、Finder 或其他外部编辑形成的有效磁盘变化采用相同规则；外部修改尚未被读取、仍处于冲突裁决、文件无效或团队需要修复时不伪装成一份有效更新，而是沿用既有刷新、冲突或修复反馈。

```text
│  ℹ Agent 定义已更新 · 2 名成员        [查看] [应用]  [×]   │
│  ℹ 运行配置已更新 · 1 名成员          [查看] [应用]  [×]   │
│    本对话仍使用当前已载入的版本。任一「应用」都会载入      │
│    整支团队最新保存的完整版本。                            │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ ▱ 项目 A  默认工作空间  main  [◇ 开发团队 ▾]         │  │
│  │ 继续说点什么，或 @ 一个成员…                    ＋  ↑ │  │
│  └──────────────────────────────────────────────────────┘  │
```

点击「应用」时先冻结按钮按下瞬间读取到的完整有效团队版本，后续保存不能让待应用目标漂移。没有已启动或已排队 run 时立即生效；存在这类旧工作时，按钮区合并为「当前工作结束后应用团队更新」，旧 run 与点击前已经排队的消息继续使用原快照，点击后的新消息等待更新生效后再按新成员名单与运行配置解析。应用不会中止或重放工作，不改写历史回复；生效后，用户新发送的消息、由新工作产生的成员接力和其他新发起工作使用新快照，并按新快照建立新的本地 Agent 身份。针对应用前历史步骤执行「重试」「重新运行」或恢复仍是例外：即使它们创建新 run，也继续使用该历史步骤自己的团队与 run 快照，不能因当前会话已经应用新版而改写复现条件。

等待期间关闭再打开应用仍保留同一个冻结目标。应用落盘失败、目标读取失败或目标在点击前已无效时，当前快照保持不变，提示明确说明未应用，并把点击后消息继续保留在可编辑、可移除的「等待团队更新」队列中；这些消息不得自动按旧快照发射，也不得永久隐藏。

失败反馈提供两个明确动作：「重试应用」继续使用第一次点击时冻结的同一完整版本，不重新读取团队页当前最新版；「取消应用并继续使用当前版本」放弃该冻结目标，让等待消息按原有 FIFO 使用当前旧快照继续发射，并根据旧快照与此刻团队最新有效保存状态重新显示分类变化提示。更晚保存不能暗中改变一次重试的目标；用户若要应用更晚版本，先取消本次应用，再从重新出现的提示点击「应用」。应用成功后，如果团队页又产生更晚的已保存变化，只为新增变化重新显示对应类别提示。

「查看」弹窗结构：

```text
┌ 开发团队的变化 ─────────────────────────────────────┐
│ 开发经理                                             │
│▎交付汇总以真机行为证据开头……          官方 v1.3     │
│ └ 原来是「交付汇总列出改动文件」                     │
│                                                      │
│ 测试                                                 │
│▎…                                        你 · 3 天前 │
│                                                      │
│                              [取消]      [应用]      │
└──────────────────────────────────────────────────────┘
```

提示与弹窗不提供单项应用或版本选择，不显示内容指纹、文件修改时间或逐行增删对比。弹窗按段落展示变化与来历，但整支团队仍然只能整体应用。用户也可以不点击，旧对话继续使用当前已载入的快照，关闭重开应用后仍保持；新建对话并选择这支团队时直接使用当前已保存团队状态。说明使用普通信息语义，不使用红色、错误或需要处理的状态，也不触发侧边栏红点。


按钮显示用户刚选择的目标值；仍有切换前已启动或仍具备发射能力的排队 run 时，下方一行说明该值会在这些 run 全部结束后生效。因 Agent 已结束继续能力而从 FIFO 脱离的“未发送 · 原目标不可继续”项目不是排队 run，不阻塞切换。四项上下文里只有团队可以这样改选——项目与工作空间在发出第一条消息后已经锁定。

### 运行异常与中断事实

```text
一步没跑起来
│ (开) 开发                                                   │
│ 正在补空状态验收语句…                                       │
│                                                             │
│ ⚠ 这一步没跑起来（退出码 1）                     [重试]     │
│ ─────────────────────────────────────────────────────────── │

一步卡住了
│ ⚠ 这一步卡住了                                   [重试]     │
│ ─────────────────────────────────────────────────────────── │

你按了停（中性，不触发红点）
│ ⏹ 你让这一步停下了                                          │
│                                   [重试] [改一改重发]        │
│ ─────────────────────────────────────────────────────────── │

无法继续原执行（触发红点，不自动重跑）
│ ⚠ 原执行已经无法继续                                        │
│   你可以重新建立原执行，或直接说话、换一个成员接手。        │
│                                      [重新建立原执行]        │
│ ─────────────────────────────────────────────────────────── │

额度或服务异常（触发红点，不自动切引擎）
│ (开) 开发                                                   │
│ 已经完成的半截正文…                                        │
│ 内容不完整                                                  │
│ ⚠ 当前执行引擎没有产出完整结果                              │
│   已确认额度不可用时说准原因；否则保守说明可能是额度或服务问题 │
│                            [重试] [换执行配置重跑…]          │
│ ─────────────────────────────────────────────────────────── │
```

这些事实彼此可区分，且都由落库的事件类型驱动，因此刷新或重启后仍在。用户中止、额度耗尽、可重试服务繁忙、认证失败、空转、崩溃和恢复不可用不能依靠错误字符串前缀互相猜测，也不能把没有结果的 provider turn 写成成功完成。

首版不自动重试，也没有“重试耗尽”状态或重试次数上限。「重试」全部由用户显式触发；「无法继续」只表示原外部执行会话不能被精确恢复，只有用户点击「重新建立原执行」并确认上下文会重建后才创建新 run 与新执行代。

文案说「这一步没跑起来」或更准确的引擎原因，不说「开发失败了」；这些事实来自机器故障、用户动作或恢复校验，不代表团队协作失败。准确额度原因只有在运行时取得可靠机器信号时才显示；只有空结果、截断输出或通用失败证据时，界面必须保守说明“没有产出完整结果”及可能原因，不得假装知道额度已经耗尽。

### Pi 配置异常与会话迁移

Pi 的配置异常属于受影响 Agent 的运行事实，不把整段团队会话伪装成损坏，也不静默改用其他成员。历史、其他成员和已经产生的文件结果继续可用；只有准备启动、重试或恢复该 Agent 的动作被阻止。

“前往设置修复”“重新启用”“迁移当前会话”和“结束并保留历史”都打开[设置 → AI 服务商](./settings.md)的既有管理面，并预先定位当前冻结引用或历史标识、当前会话和受影响 Agent；本页不复制 Key 表单、Provider 生命周期、迁移事务或危险确认。设置关闭后，本页继续显示该对象的进行中或最终状态；迁移完成时由本页呈现新 Pi 上下文和后续运行结果。

```text
Key 或凭据需要修复
│ ⚠ DeepSeek · 工作档案需要处理                              │
│   这一步没有再次请求服务商。修复后可从这里重试。            │
│                                              [前往设置修复] │

冻结模型已不可用
│ ⚠ deepseek-reasoner 已不可用，原生 Pi 会话不能继续         │
│   迁移会保留 Moebius 时间线，并重新建立原生上下文。         │
│                   [迁移当前会话…] [结束并保留历史]         │

服务商已不受支持
│ ⚠ 原服务商已从支持目录移除，不能再发起新请求               │
│   先选择另一份已就绪档案，或结束这名 Agent 的继续能力。     │
│                   [迁移当前会话…] [结束并保留历史]         │

历史 Provider 档案不可用
│ ⚠ 找不到“DeepSeek · 工作档案”，原冻结配置不能重新建立      │
│   历史标识会保留；请选择另一份已就绪档案，或结束继续能力。   │
│                   [迁移当前会话…] [结束并保留历史]         │
```

- Key 失效、凭据文件不可读或档案被停用时，页面进入匹配的设置入口。修复或重新启用成功不会自动产生下一次 API 请求；用户回到原终局记录显式“重试”，才继续当前 canonical Pi 执行代。保存失败或仍未就绪时保留原记录和操作。
- 冻结模型下架时，“迁移当前会话”只列同一档案中当前可用且已经验证的模型；用户选择后，这段会话中该 Agent 的后续运行永久使用新模型。Provider 档案、服务商、团队默认配置和更早尝试不变。
- 服务商从支持目录移除时，“迁移当前会话”只列另一服务商下当前已就绪的 Provider 档案及其可用已验证模型，并明确显示服务商将发生变化。没有可选档案时提供“前往设置添加服务商”，不会把未验证档案当成迁移目标。
- 导入或数据损坏造成冻结 Provider 档案身份已无法解析时，页面保留快照中已有的服务商、档案名称或历史标识、模型和思考程度，显示“历史 Provider 档案不可用”。原档案无法修复，也不能执行“重试”或“重新建立原执行”；唯一去向是迁移到任一当前已就绪档案及其已验证模型，或结束并保留历史。迁移目标为空时先前往设置添加档案，历史标识在此期间不丢失。
- 迁移保存成功后封存旧 Pi 外部会话，以 Moebius 已保存的可见共享时间线和附件引用建立新 canonical 执行代，并在时间线留下“已迁移到〈服务商 / 档案 / 模型〉；原生上下文已重新建立”。旧过程、失败尝试和文件结果不改写。迁移保存或新会话建立失败时，旧冻结配置与引用保持，页面说明迁移尚未完成并允许重试；不能出现页面显示新配置、设置引用仍指向旧配置的半迁移。
- “结束并保留历史”需要确认它会让该 Agent 在这段会话中永久失去继续、重试和恢复能力。成功后封存其外部会话并解除这段会话对原 Provider / 模型的可恢复引用；时间线、附件、过程记录和文件结果仍可读，团队成员默认配置及其他会话引用不受影响。该 Agent 的全部待发射项同时从原成员 FIFO 脱离，转为输入框上方持久的“未发送 · 原目标不可继续”项目；它们不再算排队 run 或待收束控制工作，因此不阻塞团队切换。每项保留原正文、附件和原目标标签，可单独“编辑后重新提交”或“移除”，但绝不自动交给新团队或其他成员。切换团队后这些未发送项仍原位保留，用户编辑时由自己选择是否加入新成员 mention，再按新快照提交。
- 档案在运行中被停用、Key 被确认失效、凭据变为不可读或目录状态变化时，已经发出的请求按真实结果结束，不在中途换配置。该 Agent 尚未发射的队首进入“执行配置需要处理”，后续项目继续留在原 FIFO；修复后也不自动产生用量，用户显式选择“运行这条”或编辑、移除该项。服务商或模型迁移成功后，旧队列项仍显示原目标与未运行事实，用户决定是否以新配置重新运行。仅仅正在验证轮换 Key 不触发这条规则：验证期间旧有效版本继续服务运行与队列，全部已验证模型通过并原子保存后，后续请求才使用新 Key。
- Pi Provider 异常和迁移失败属于红点事实；用户确认后可清除提醒，但运行阻止与历史状态保持到真正修复或迁移完成。用户亲自确认“结束并保留历史”与按下“停下”一样是中性事实，不再为同一动作产生红点。API Key、完整凭据和服务商原始错误正文不得出现在时间线、迁移弹层或可复制信息中。

### 侧边栏状态点的来源

```text
│ ▾ 项目 A       │
│    落地页验收 ● │  ← 红：有未确认的运行异常、完整结果缺失或项目 / 团队不可继续

│    需求梳理     │  ← 无点：控制工作已结束，且没有需要继续显示的提醒
```

用户按下「停下」之后本身不产生红点。正常完成若带来尚未查看的结果则是蓝点，已经查看且没有手动未读提醒时才是无点。

## 区域与信息

### 页面标题

- 显示这段对话的标题；还没有消息时显示「新对话」。
- 默认标题在发出第一条消息时确定：有正文时取正文开头文字，纯附件消息没有正文时取第一个附件的文件名；之后不随对话内容自动变化。
- 新会话发送首条消息后，应用异步调用当前会话的执行引擎为对话生成标题（不超过 20 字），成功后自动重命名；生成失败时静默保留默认标题，不重试、不阻塞对话。自动生成不覆盖用户已手动重命名的标题。
- 用户可以从[主页面侧边栏](./main-left-sidebar.md#重命名对话)重命名；成功后本页标题立即使用新名称并跨应用重启保留。重命名不改变对话身份、项目、工作空间、历史或运行。
- 长标题单行截断，悬停显示完整标题。

### 托管运行项入口与面板

- 入口只在当前会话存在本次应用运行期间登记的托管运行项时出现；没有运行项时不留空占位，也不把普通 Agent run、测试或构建误算进去。
- 面板按创建时间列出名称、类型、状态和可选地址。状态至少能区分启动中、运行中、已就绪、健康异常、停止中和已退出；“进程已启动”和“服务已就绪”不能显示成同一事实。
- 有地址的条目提供「打开」；所有条目提供「查看日志」。只有仍存活的条目提供「停止」，停止中防止重复提交。没有地址的 watcher 或长任务仍可查看状态、日志和停止。
- 日志只展示 Moebius 已托管的有限 stdout/stderr，不把用户消息、Provider 原始诊断、环境变量或全局配置内容混入。日志持续增长时保留最近内容并明确说明前文已截断。
- 条目由真实进程存活与 readiness 结果驱动，不能从 Agent 正文中的链接或“已经启动”措辞推断。Agent 回合失败或结束不自动停止已经成功托管的运行项。
- 最后一个活动运行项退出后，顶栏不瞬间消失，而明确显示该项已退出或已有若干项结束；用户仍能打开面板查看退出事实与有限日志。面板提供「清除已退出」，确认成功且没有其他条目时入口立即消失；清除失败保留现场并允许重试。确认只删除本次应用运行中的瞬时退出记录，不改变会话历史。

### 上下文

输入框上方按固定顺序显示这段对话的四项上下文：

1. **项目**：这段对话在哪个本地文件夹工作。对话必须归属一个可用项目。
2. **工作空间**：这段对话以什么方式改动文件。「默认工作空间」直接改项目文件夹里的文件；「独立工作空间」把改动隔离在一份副本里，不弄脏原文件夹。
3. **分支**：只显示不可点击，显示**真实的分支名称**，不使用「当前分支」这类字面词。用户要凭它在自己的编辑器或命令行里找到团队正在改的地方。
4. **团队**：负责这段对话的 Agent 团队。

工作空间是**这段对话**的设置，不是项目的设置。同一个项目下，一段对话可以直接改文件，另一段对话可以隔离改动，互不影响。

项目文件夹不是 git 仓库时无法隔离改动，「独立工作空间」不可选并说明原因。

按[Agent 团队](./agent-teams.md)的规则，新建对话使用创建时载入的那一份团队内容与每名 Agent 的执行引擎、Provider 档案身份及不可变服务商、模型和思考程度；CLI 成员没有 Provider 字段，Pi API 成员不把 Key 复制进快照。升级前没有运行配置字段的旧会话沿用 Codex 兼容行为。用户之后在团队页修改成员的 `AGENT.md`、运行配置或 Provider 默认模型，不会改变已经开始的对话；同一 Provider 档案内验证成功的 Key 轮换继续服务引用它的旧会话。团队按钮只需让用户看出“这段对话沿用载入时状态”，不对旧会话错误宣称已经保存了并不存在的运行配置。

### 时间线

时间线是一条按时间顺序的聊天记录，混合用户、团队成员和必要的系统记录。

当前会话的可见用户消息与 Agent 最终回复同时投影到固定在正文左侧的[会话目录轨](#会话目录轨)。目录轨是这条时间线的导航，不是第二份消息记录；消息正文、运行状态和系统事实仍只在时间线中呈现。

每条记录只显示发言者和内容。普通消息的发送或完成时间只在悬停时显示；运行记录的活动、计时、终态与完整输出入口统一遵循[单 Agent 会话](./agent-conversation.md)，不在本页另定义一套。

**能被对话内容本身表达的，不给状态标记。** 成员在回复、在 @ 别人，本身就说明了交棒；成员正在吐字，本身就说明了运行中。产品不额外渲染「已交棒」「已完成」「运行中」这类过程标记，也不让它们在对话结束后留在历史里。

运行记录里的「已进行」与活动行不是额外的「运行中」状态标签：前者解释时长，后者说明机器当前可观察到的动作。只有对话内容表达不了的运行异常与中断事实才升格为可见状态：**一步没跑起来、一步卡住了、用户按了停、额度或服务异常、没有产出完整结果、无法继续原执行**。它们全部来自机器故障、用户动作或恢复校验事实，不是团队协作的失败，文案上说发生了什么，不说「开发失败了」。这些记录的活动来源、优先级、脱敏与时间格式见[单 Agent 会话](./agent-conversation.md)。

用户与 Agent 的对话正文都按 Markdown 呈现。基础语法与 GitHub Flavored Markdown 全部可用，包括标题、强调、引用、列表、链接、图片、行内代码、代码块、表格、任务列表、删除线、自动链接和脚注；中文、日文、韩文标点旁的强调与链接边界必须正常。代码块提供语法高亮，数学公式使用 KaTeX，`mermaid` 代码块在闭合后可渲染为图，并保留 Streamdown 提供的复制、下载或全屏等适用控件。

对话正文中写出的已知团队成员 mention 使用这段会话冻结的成员名单解释：例如 `@implementer` 显示为 `@实现者`，让用户直接看懂在叫谁。点击后只打开这段会话所属团队的现有 Agent 团队详情，不在 Markdown 内增加派工、编辑或执行能力；未知 mention 保持原文，代码块、行内代码和已有链接中的 `@` 不作解释。

已经完成的用户与 Agent 消息按完整 Markdown 静态渲染。正在工作的成员仍然只占一条临时记录：结构化工具、命令、文件事件或 Agent 可见进度到来时，界面只更新同一条记录的活动行；这些事件不各自生成消息。成功结束时，临时记录由最终落库的单条 Agent 消息接管，不同时保留两份；异常或中断时，最后已经可见的 Agent Markdown 由结构化终局记录接管并标注内容不完整，不生成成功消息。若当前执行传输只提供完整的进度段而没有 token delta，界面按进度段更新，不伪造逐字打字效果。

Pi 长会话触发上下文压缩时，时间线在对应 Agent 记录附近显示一次中性的系统事实“已整理较早上下文”，不要求用户确认、不触发红点，也不把压缩伪装成新的 Agent 回复或目录事件。压缩成功后继续当前 Pi 执行代和同一外部会话；下一轮仍必须能引用压缩前已经公开的明确用户要求。压缩失败时保留时间线与原执行现场，按真实失败提供重试，不能只凭内部 token 变化宣称成功。

Markdown 能力不得削弱桌面安全边界。原始 HTML 必须经过清洗，脚本、iframe、事件属性与危险 URL 不得执行；外链只允许 `http`、`https`、`mailto`，在确认后交给系统浏览器；图片只允许 `http`、`https`，不允许 `data:`、`file:`、`javascript:` 或自定义协议。`moebius-ref:` 是唯一新增的受控应用内引用协议：它不进入外链确认或系统浏览器，在用户与 Agent 消息中都只导航；按[对话分析与优化流程](../flows/session-analysis.md)，run 只接收消息中可见的片段文本，不读取引用目标或形成额外授权。格式不合法或目标不可访问时只把导航降级为不可用来源，不阻塞消息与 run。其他未知自定义协议继续阻止。显式写成 Markdown 链接或直接出现在普通正文中的本地 POSIX 绝对文件路径都属于应用内文件引用：保留 Agent 给出的原始路径文本，点击后由[主页面右侧栏](./main-right-sidebar.md)按该会话的实际工作空间分流。真实目标位于工作空间内时打开完整只读文件；路径带行号时直接进入源码并定位目标行，没有行号的 Markdown 文件默认进入 Preview。真实目标位于工作空间外时只打开明确标为「预览」的目标行附近有界文本，不把外部文件升级为完整项目文件。每个文件引用在根 `/` 之后必须至少包含一个非空的实际路径段，单独 `/` 以及 `A / B` 中作为分隔符的 `/` 都只按普通文本显示。裸文本、inline code 与显式 Markdown 文件目标使用同一条路径边界；包括 `/tmp` 与符号链接真实目标在内的任意本机普通文本文件都可按上述内外规则读取，它不经过外链确认，也不离开应用。路径、`cwd`、`runDir`、数据库路径和内部标识作为对话内容按原文显示，不再替换成「路径已隐藏」等占位文案。这个决定明确取代此前的统一隐藏与位置白名单规则：用户需要知道团队改了哪个文件、产物输出到哪里，且工作空间外产物必须能从对话直接预览；占位文案既破坏句意，也切断了文件查看闭环。完整 API Key、凭据和环境变量秘密不属于可见运行事实，仍不得进入正文、过程记录、错误、附件清单或可复制 UI。`file:` URL 仍不能借此导航或读取，Mermaid 使用严格安全模式。系统故障、停下、卡住和无法继续仍由结构化系统组件呈现，不把系统事实重新解释成 Markdown。

**完整输出不进时间线**。当前绑定执行引擎能提供稳定过程记录时，正在工作的记录上提供一个查看完整输出的入口，点击后在[主页面右侧栏](./main-right-sidebar.md)开出该步骤唯一的过程标签，包含安全处理后的原始错误在内的全部输出都在那里，可以一直留着对照。这一步结束后入口仍然保留，历史记录随时可以重新展开。同一步的任一次尝试都聚焦这个标签并定位到对应尝试；当前执行引擎不支持稳定过程记录时，记录明确显示「完整输出不可用」，不提供一个点开后才发现无去向的通用入口。Pi 完整输出同样不得出现 API Key、完整凭据或可复用授权头。

主时间线中已经成功结束、且过程记录可用的 Agent 历史消息把这个入口作为正文下方的消息级轻操作：入口保持与正文左对齐，不移动到 who 行右侧；默认不显示，用户悬停整条消息或用键盘把焦点移入该消息时，才在原位显示一个文件图标按钮。按钮不常驻文字，也不使用占据正文宽度的 `ghost` 文字按钮；图标仍提供「完整输出」的可访问名称与悬停说明。运行中的记录和四种异常事实承担实时监督或恢复，不套用这条隐藏规则：可用入口或明确的不可用说明继续常驻。

### Agent 头像与当时信息

时间线中每条正在运行、成功结束或由结构化异常终局接管的 Agent 记录都把成员头像作为可点击、可键盘聚焦的信息入口。头像的首字、尺寸和身份表达继续复用 Agent 团队页与生产消息组件的既有模式；不能为了可点击而新增一套头像元数据、身份色或独立角色图标。会话冻结成员或本次 run 已知执行配置时，头像默认显示对应 LLM Provider 的小标识，不得等用户打开信息卡后才补上；执行配置没有可靠记录时不猜测 Provider。

激活头像后，在原消息附近打开紧凑信息卡，只回答“这条记录当时绑定或尝试了什么配置”：

```text
┌ 开发工程师 ─────────────────────────────┐
│ @dev · 开发团队                         │
│ tranfu-labs/moebius-team-development    │
│                                         │
│ CLI        Codex                        │
│ Model      gpt-5.6-sol                  │
│ 思考程度  high                          │
│                                         │
│ 团队版本载入于 2026-08-04 14:32         │
│                         [打开 Agent 详情] │
└─────────────────────────────────────────┘
```

- Agent 名称、稳定 `@slug`、团队名称、来源及同名辨认信息都来自这条 run 所属的会话团队快照，不读取当前团队页覆盖历史身份。持续接收更新的团队显示快照中的来源仓库名；同名且同为独立维护时，继续使用这份历史快照中的团队创建时间，不能只靠名称、位置或头像辨认。
- 有可信外部执行开始证据时，CLI、model、effort 标为「实际执行配置」；使用一次性执行配置重跑时，显示该次重跑实际采用的临时配置，而不是团队基础配置。
- 进程未启动、配置在外部执行开始前被拒绝或其他启动前失败时，同三项字段标为「本次计划尝试 · 未开始执行」，不得声称模型已经运行。旧历史只能证明绑定配置、不能证明是否开始执行时，标为「本次绑定配置 · 是否开始未记录」。
- 「团队版本载入于」显示这份快照实际建立并成为会话有效版本的本地时间。它是用户可理解的审计时间，不显示内容指纹、数据库标识、文件路径或源文件 `mtime`。
- 「打开 Agent 详情」使用这条 run 的历史团队稳定身份与成员 slug，打开既有 Agent 团队详情并预选对应成员；它不创建独立 Agent 页面，也不把当前团队或当前磁盘内容当作历史目标。历史事实缺少可解析的团队稳定身份时不提供错误的当前团队跳转。
- 信息卡只呈现当时事实，不展示当前团队的新值，不提供前后差异，也不把“团队现在已变化”塞进每条历史消息。当前团队与旧对话快照的差异只由输入框上方的中性说明解释。
- 升级前无法证明 model 或 effort 的旧历史只显示能够从持久事实确认的字段，并用「此项未记录」解释缺失；不得读取当前团队配置补写，也不得猜测默认值。

点击卡外、按 Escape 或再次激活头像关闭信息卡；关闭后焦点返回原头像。头像和「打开 Agent 详情」分别具有包含成员名称与动作的可访问名称。信息卡不得遮断消息更多菜单、完整输出或分析入口；窄窗口下可以改为使用同一信息层级的受控浮层，但不能产生页面级横向滚动。

这样切分的理由：产品尚未稳定，用户需要监督的是交棒流程本身走没走对，而这件事看最新一行活动摘要就够了；真要逐行读输出的时刻是少数，且往往需要跟改动对照着看——那正是右侧栏的场景。把全量输出留在时间线里，会让用户每次翻阅历史都要滚过大段机器输出，也让右侧栏的过程标签变成同一份内容的第二份拷贝。

本版不服务「离开一段时间后回来快速读懂全部经过」这个场景，也不在界面上暗示自己能做到。

### 分析对话入口面板规则

- 每段打开的对话都拥有自己的分析面板。根对话的面板列出从该根对话整段或其中消息创建的下一层分析对话；分析对话的面板只列出从其中具体消息创建的下一层分析对话。孙辈只进入其直接父对话的面板，不在更早祖先面板重复出现；因此单个面板不缩进、不画树、不显示层级。
- 根对话的分析面板开关位于主会话标题栏、紧邻右侧栏开关；面板锚定主会话内容区域右上角。分析对话显示在右侧栏标签中时，它自己的分析面板开关位于该标签内的对话标题区末端，不与外层右侧栏开关并列；面板锚定该分析对话的内容区域右上角。点击其中入口仍在同一外层右侧栏打开或聚焦兄弟标签，不嵌套第二层右侧栏。
- 每个入口使用对应分析对话已有的可读标题。面板不生成摘要，不展示运行状态、最近活动、团队、模型、路径或内部标识。
- 入口按分析对话创建时间从新到旧排列；创建时间完全相同时用不可变会话标识作稳定内部次序，刷新和重启不得换位。标题单行截断，悬停或键盘聚焦显示完整标题；标题相同时只为重名项补充精确到秒的可读创建日期和时间。重名项连显示时间也相同时，再按稳定内部次序分配不表示时间先后的可读后缀「同名项 A／B／…」；后缀在刷新和重启后保持不变，不展示内部标识。条目超过面板可用高度时只滚动面板列表，不带动所在对话的时间线。
- 点击入口只负责在右侧栏打开对应分析对话的唯一标签；已经打开时聚焦既有标签，不创建重复标签。分析对话的时间线、输入和运行行为继续由右侧栏中的正常会话视图承载。
- 只有根对话的分析面板开关与右侧栏开关相邻但不合并；分析对话标签内的开关只控制该分析对话自己的面板。所有面板都属于其所在对话的内容区域，外层右侧栏仍是独立标签工作区。
- 面板开合状态只在当前应用进程内按当前对话的 session 分别记忆。切换对话再返回时恢复该对话本次运行中的状态；软件重启后全部丢弃并默认关闭。点击入口打开右侧栏标签后来源对话的面板状态保持打开，直到用户主动关闭。
- 面板开关的可访问名称明确使用“分析面板”，通过展开状态说明面板当前是否打开，并支持键盘激活。入口是可聚焦按钮，可访问名称包含完整标题；发生重名时同时包含创建日期和时间。
- 关闭面板后焦点回到分析面板开关。激活入口并成功打开或聚焦右侧栏标签后，焦点进入目标标签；打开失败时焦点保留在原入口并显示可理解原因。

### 运行中的操作条

- 挂在每一条当前正在工作的成员记录末尾；当前执行引擎支持稳定过程记录时常驻提供「完整输出」，不支持时显示局部不可用说明。专业成员的记录还提供只作用于该成员当前 run 的「停下」。
- 主理人的记录不重复提供「停下」；主理人的停止入口固定在输入框右下角的方形按钮。
- 角色行右侧的「已进行 / 耗时 / 完成于」遵循[单 Agent 会话](./agent-conversation.md)，包括排队与暂停不计时、长耗时格式、完成日期格式和重试独立计时。
- 可用的「完整输出」在这一步结束后保留在历史记录上；成功历史消息只在整条消息悬停或键盘聚焦时于正文下方原位显示图标入口，用户之后仍然可以调出这一步的全部输出。

> **「停下」的位置在 2026-07-23 再次裁决。** 2026-07-22 的单 Agent 假设把停止收敛到 composer，并让方形按钮在“停当前成员”和“发送”之间切换；真实团队会让主理人与多个专业成员并行，这会使一个全局按钮既不知道停谁，也在用户打字时消失。新决策按控制权拆分：composer 方形按钮只停主理人，专业成员在各自活动记录上单独停止。两类入口目标不同，不是同一动作的重复入口。

### 结果卡片

- 一轮工作结束、没有成员在继续接力时，时间线末尾出现一张结果卡片，说明**这段对话期间有几个文件发生了改动**，并提供查看入口。
- 卡片只给数量与入口，不在时间线里铺开文件清单。铺开就又变成了噪音，而看清单本身是[主页面右侧栏](./main-right-sidebar.md)的职责。
- 点击查看入口打开右侧栏并落在改动标签。
- 措辞不声称这些改动由团队成员造成。产品无法区分改动来自成员还是用户自己动手，理由与右侧栏一致。
- 没有任何文件发生改动时，卡片如实说明这一点，不省略——「跑完了但什么都没改」也是用户需要知道的结果。
- 项目文件夹不是 git 仓库时不出现结果卡片，因为这类项目没有改动视图。

### 子会话卡片

- 团队把目标拆成多个子任务时，时间线中出现一张卡片，逐行列出子任务、负责成员和**该子任务当前的状态**。
- 子任务的状态必须出现在卡片上。「能被对话内容本身表达的不给状态标记」这条规则不适用于子会话：子会话的内容不在主时间线上，主时间线表达不了它。卡片是唯一的聚合入口，不给状态用户就只能挨个点开才知道跑完几个、有没有一个挂了。
- 子会话不出现在侧边栏。子任务是团队的内部产物，不是用户主动管理的对象；让它们进入侧边栏会使侧栏长度随团队的拆分行为膨胀。
- 点击卡片行在[主页面右侧栏](./main-right-sidebar.md)开出该子任务的标签，父会话留在视野中。标签内的内容、状态表现、输入与操作由右侧栏定义，本页只负责卡片何时出现、显示什么、点击后打开什么。

### 在右侧栏分析这条消息

- 每条正在工作的 Agent 记录、已经形成历史的 Agent 回复，以及承接某个 run 的「一步没跑起来」「一步卡住了」「已停下」「无法继续」异常终态事实，都提供消息级更多菜单。普通用户消息、与 run 无关的系统记录、结果卡片和子会话卡片不重复提供这项入口。
- 运行中的记录把更多菜单放在现有操作条内并保持可达；成功历史回复与「完整输出」一致，只在整条消息悬停或键盘焦点进入时显示消息操作。用户在消息上右键、激活悬停或聚焦后出现的菜单按钮，或使用键盘上下文菜单操作时，必须打开同一份消息菜单并绑定同一条消息；菜单按钮和「在右侧栏分析这条消息」菜单项都必须有独立可访问名称，关闭后焦点回到对应消息或其菜单按钮。
- 入口不改变被点击记录，也不停止、重试或复制 run。它只打开或聚焦右侧栏中的普通新会话，并加入一项指向该消息的来源引用。
- 该消息级文本片段在草稿中持有应用生成的消息引用。首次发送时，应用把胶囊可读取的完整文本序列化为首条用户消息顶部的 Markdown 来源块；所选团队主 Agent 只获得这份可见文本，不自动获得目标消息、结构化 run 记录或完整输出。胶囊的悬浮、键盘聚焦和辅助说明必须逐字公开将要插入的内容。
- 消息入口与根对话左侧栏中的整段对话入口复用同一分析草稿、标签、发送和后续对话行为；入口对象只改变插入的文本片段。分析对话没有左侧栏行，其标题区菜单和分析面板也不补充“分析整段对话”动作。点击消息位置不预先限制用户随后提出的问题。

入口触发后，页面打开或聚焦[对话分析与优化流程](../flows/session-analysis.md)选定的分析新会话草稿，并追加下一个文本胶囊；本页不重复维护草稿归并键。已有分析对话已经发送时，不向其历史静默追加。

### 输入框

- 用户输入自然语言，可以用 `@` 提及当前团队的成员。
- 提示文案在新对话时为描述目标，在已有历史时为继续说话或提及成员。
- 按 Enter 发送，Shift+Enter 换行。**正在用输入法组合文字时按 Enter 只确认候选词，不发送消息**——中文、日文、韩文用户确认拼音候选是高频动作，误发送会把半句话变成一次团队推进。
- 右下角常驻「＋」用于添加本地文件。主理人空闲时提供发送按钮；主理人运行时方形按钮始终只停主理人，有可发送草稿时另行提供发送动作，不能再让停止与发送抢占同一个按钮状态。
- **任意成员正在工作时输入框都保持可用。** 唯一有效成员 mention 直接选择该成员车道；未点名、只有无效 mention 或同时点名多个不同有效成员时选择主理人车道。目标车道空闲时立即发送，忙时进入输入框上方的待发射区；用户发送本身不停止任何 run。
- 待发射区按提交顺序展示目标成员、正文摘要与附件；这些内容尚未进入主时间线。同一目标按 FIFO 领取，不同目标可以独立推进。主理人 pending 沿用既有队列；明确直达专业成员的 pending 在该成员终态后发射，并在应用重启后继续保持目标与顺序。
- 存在 pending 团队切换时，切换请求之前已经进入专业成员队列的消息属于旧团队已排队工作，必须执行到终态后才允许切换；切换请求之后发送的消息等待新团队快照生效，再按新团队成员名单解析 mention 和选择目标，不启动旧团队的新 run。
- 待发射内容中的合法 `moebius-ref:` 只作为已输入的可见 Markdown 保存，不在入队或到达队首时读取目标。链接目标缺失或不可访问不改变 FIFO 顺序，也不阻塞该项写入主时间线和创建 run；用户仍可在发射前按普通待发射规则编辑或移除整项。
- 已有会话中，未发送的正文与附件共同构成该会话的草稿，在切换对话、切换页面、窗口缩放和**重新启动应用**后都保留。新对话草稿还包含项目、工作空间和团队，其导航与消费边界见[新对话草稿的生命周期](#新对话草稿的生命周期)。新对话页虽然不创建对话，草稿本身仍然必须留住——描述目标和准备上下文是用户在这个产品里花时间最多的动作。
- 分析新会话的文本胶囊不等于可发送正文或文件附件；只有胶囊、正文为空时发送保持禁用。用户选择候选提示词或自行输入正文后，发送和标题生成继续使用正常新会话规则。
- 文本胶囊只存在于未发送草稿。发送成功后，应用按固定格式把全部胶囊转换为首条用户消息顶部的 Markdown 来源块，历史中不再保留或重复显示胶囊。
- 任意已有对话的用户输入中出现合法 `moebius-ref:` 时，输入区不把它解释成动态来源；它只作为可见 Markdown 进入下一次 run，并在历史中提供用户导航。

## 操作与反馈

### 创建一段对话

- 进入新对话页不创建任何东西。用户点开又退出，不留下空白对话。
- 普通根对话发出第一条消息时才真正创建，侧边栏随即出现对应的行并选中。
- 分析新会话首次发送成功后创建为归属于直接来源对话的分析对话，不在侧边栏新增普通根对话行；直接来源对话的入口面板新增一个可再次打开它的触发入口。
- 创建过程中防止重复提交。首条消息先把全部可见文本片段按顺序各序列化一次，再原子提交 session、首条消息及对应左侧栏行或父面板入口；链接目标状态不参与创建校验。提交成功后消费新对话草稿，随后 Agent 进程启动失败不会把已经落库的消息、对话和入口退回草稿状态。

### 分析对话归属、归档与移除

- 每段分析对话只归属于直接创建它的来源对话；项目选择决定它在哪里工作，不改变它出现在哪一段来源对话的面板。分析对话不产生独立左侧栏入口。
- 本版本不为分析对话提供独立归档入口。用户从既有入口归档根对话时，该根对话以及通过逐层直接归属连接的全部后代一起隐藏；恢复根对话时整棵树和各直接父面板入口一起恢复，但不自动重开归档前的分析标签，用户按需要从直接父面板逐层打开。未归档工作现场的软件重启恢复继续由右侧栏规则定义。
- 待归档根对话的任意后代仍有运行中或待接回的控制工作时，归档不可执行，并明确说明仍有分析对话正在工作；用户停止或等待全部后代结束后再操作。
- 项目选择和项目移除都不得改变直接父子归属、把分析对话改挂到其他面板，或让它变成左侧栏根对话。项目移除把每段因此归档的根对话或分析对话作为子树根：该子树中的全部分析后代及其父面板入口递归隐藏，即使后代使用其他项目；子树之外的未归档父对话及兄弟入口保持。只有侧边栏定义的停止运行、放弃待接回与原子移除全部成功后才提交入口清理，任一步失败都保留原面板内容。已移除项目及归档子树的查看和恢复能力仍由项目移除流程、左侧栏及未来恢复入口统一定义。
- 关闭分析对话的右侧栏标签只关闭视图，不归档、不删除，也不改变它在直接父对话入口面板中的归属。

### 从消息开始分析对话

- 用户打开 Agent 记录或 run 异常终态事实的更多菜单并选择「在右侧栏分析这条消息」后，右侧栏立即打开或聚焦流程选定的分析新对话。
- 每次操作只追加一个文本胶囊。胶囊右侧的删除只移除这项尚未发送的来源引用，不改变来源消息或其他草稿内容；删除按钮可以用键盘聚焦、拥有包含片段名称的可访问名称，并可由键盘激活。
- 胶囊按加入顺序显示短标签；编号是否因删除重排不在本页决定。可读来源和将向所选团队提供的内容范围只通过悬浮、键盘聚焦和等价辅助说明出现，不在窄侧栏中常驻展开。
- 分析新会话提供两个首版候选问题：
  - 「Agent 运行不符合预期？」填入「分析这段对话是否符合这个 Agent 团队设计的预期」；
  - 「Agent 运行太长了？」填入「分析这段对话为什么占用的时间那么长，主要耗时在哪一块，是否符合团队设计的预期，是否有优化空间」。
- 候选问题可以用鼠标点击或键盘聚焦激活，只填入可编辑正文；用户可以改写、删除或完全自行输入。文本胶囊不随候选变化。
- 分析草稿首次发送成功后，当前右侧栏标签原地进入正常已有会话视图；这段会话持久化为直接归属于入口所在来源对话的分析对话，后续从该来源对话自己的入口面板再次打开。草稿中的文本胶囊同时转换为首条用户消息正文顶部的 Markdown 来源块，历史不再显示胶囊。

### 选择项目与添加项目

- 项目按钮列出全部可用项目，末尾是「添加项目…」。
- 没有待恢复的新对话草稿时，从侧边栏顶部进入的项目为未选定状态，用户必须显式选择或添加；存在待恢复草稿时回到该草稿已选的项目。
- 「添加项目…」通过系统文件夹选择器添加本地项目，成功后直接成为这段对话的项目。
- 添加被取消或失败时不创建项目，也不改变当前选择，页面其他输入保留。
- 所选文件夹已经绑定一个活动项目时不重复添加，提示用户该文件夹已被使用。
- 项目在发出第一条消息后锁定，显示为不可点击的文本。归属一旦形成就不再改变。

### 选择工作空间与团队

- **工作空间只能在发出第一条消息之前选择，之后与项目一同锁定**，显示为不可点击的文本。
- 锁定的理由：[主页面右侧栏](./main-right-sidebar.md)以「这段对话开始时的状态」为基线回答「这段对话改了什么」，而这个问题只有在一段对话从头到尾都在同一个地方工作时才有答案。中途换地方，改动会分散在两处，用户唯一想问的问题就变成没法回答的问题。
- 选择独立工作空间时，隔离副本基于项目当前所在的提交，**不包含用户尚未提交的改动**。界面必须说清楚这一点。
- **团队仍然可以在对话进行中切换。** 换人不改变工作现场，与工作空间不是一回事。
- 切换团队时如果会话有一个或多个已启动或仍具备发射能力的排队 run，**这些 run 全部进入终态后再生效**；没有这类 run 时立即生效。切换不中止任何已启动的 run，也不留下半截改动。因目标 Agent 已结束继续能力而脱离 FIFO 的未发送项目只保留为用户草稿，不属于这里的排队 run，也不阻塞切换。这延续现有 effective / pending 团队切换语义，并与[主页面侧边栏](./main-left-sidebar.md)对项目文件夹失效的处理保持一致。
- 生效后不重放已经完成的步骤。
- 团队预选上一次成功创建对话时使用的团队；没有历史选择或上次团队已不可用时，回退到软件自带的第一支团队。
- 发出第一条消息创建对话时，系统把所选团队的成员内容及每名 Agent 当时生效的执行引擎、Provider 档案身份与不可变服务商、模型和思考程度一起载入为这段对话的团队快照。Key 始终只从本机凭据文件按档案身份使用，不进入快照、消息或过程记录。
- 团队页成功保存团队名称、用途、成员内容、主 Agent、成员构成或运行配置后，新建对话并选择这支团队时可在不重启应用的情况下使用当前已保存版本；正在使用该团队的已有会话显示分类变化提示，并允许用户显式应用完整最新版本。尚未保存的草稿不进入选择器、变化提示或快照。
- 新对话页不读取或展示 onboarding readiness，不显示成员“仍需准备”的人数、CLI / Provider 名称、兼容性提示或去团队页调整的引导。项目、工作空间、团队、正文和附件是这里唯一需要用户理解与完成的发送上下文；当前成员的冻结配置是否能执行由随后真实启动该成员时的运行时硬门决定。
- 对话中明确改选另一支团队并到达上述生效边界时，系统从当前已保存目录重新载入目标团队的完整快照；此前已完成的历史不改写，由新团队接管之后的推进。切换请求之后进入待发射区、尚未解析目标的消息必须先等新快照生效，再按新团队名单决定直达成员或交给新主 Agent。A → B → A 中第二次选择 A 也按此规则载入 A 届时的最新保存版本。
- 切换前已经启动的 run，以及切换请求之前已经明确排入专业成员车道的消息，都保留其来源团队内容与运行配置，不会在半途换执行引擎、Provider、模型或思考程度。团队切换等待这些工作全部结束后再生效；随后需要接回的专业结果与切换后消息由新团队继续处理。
- 团队快照生效后保持稳定，团队页后来发生的已保存修改不会自动改变正在使用该团队的会话快照。旧对话在输入框上方按 `AGENT.md`、运行配置和其他团队信息分别提示；用户点击任一「应用」后，整支团队最新完整版本按旧工作结束边界生效。新建对话并选择这支团队时直接载入最新保存版本；已有会话主动改选另一支团队时也按正常切换规则载入目标团队的最新保存版本。

### Agent 执行与恢复

- 每次 Agent 执行在启动时从当前会话团队快照冻结该 run 自己的成员内容与完整运行配置。执行引擎是硬绑定：Codex、Claude Code、Kimi 或 Pi API 只启动各自引擎；Pi 还硬绑定 Provider 档案身份、不可变服务商、模型和思考程度。绑定引擎没有启动、配置无法执行或执行失败时，如实记录这一步没跑起来，不自动换用另一 CLI、Provider、档案默认模型或其他模型。
- 每个新 run、同一 run 的正常恢复、重试、重新运行和恢复失败后的重新执行都只使用关联用户消息中已持久化的可见文本。runtime 不解析其中的 `moebius-ref:` 目标，也不追加历史 execution context 中遗留的隐藏来源正文。
- 新会话第一条消息与后续新 run 使用同一条直接启动路径：系统不先跑一轮独立来源或能力预检，真实的进程启动、Provider 有效状态、认证和运行配置应用结果就是动态校验。Agent 启动失败时保留已经创建的会话、用户消息与冻结团队快照，显示安全且可理解的“这一步没跑起来”原因，并允许按对应恢复路径处理。
- Pi 在真正发出请求前读取档案最近保存的有效版本。“正在验证”是叠加活动，旧有效版本仍为已就绪时继续运行；有效状态为“需要处理”或“已停用”、服务商不再受支持、冻结模型不可用或本机凭据文件无法读取时，本 run 不向服务商发请求，也不产生 API 用量。页面保留目标消息和排队位置，准确区分“去设置修复 / 重新启用”“迁移当前会话”“结束并保留历史”，不把它们折叠成通用重试。
- Key 明确失效时，当前 run 安全结束并保留已经产生的正文、文件改动和过程；用户从设置轮换并验证同一档案后，可回到原记录显式重试并继续使用该档案关联的 Pi 外部会话。短暂限流、额度不足或服务繁忙只影响当前 run，不永久撤销档案就绪状态；用户决定何时再次产生用量，产品不自动连发。
- Codex、Claude、Kimi 与 Pi 都必须把执行终局归一化为穷尽的结构化事实，至少区分成功、用户或系统中断、idle、工具执行或 provider max timeout、额度耗尽、可重试服务繁忙、认证或凭据失败、冻结配置不可用和崩溃。provider 原始 error code / message / data 只进入受信任诊断，正常时间线只消费安全分类；没有可靠分类时显示保守原因，不能降级成成功。
- 本地监督只由真实进展刷新：新增 Agent 正文、非空 reasoning、工具开始或结束、明确文件改动算进展；重试回显、配置更新和心跳不算。工具从开始到匹配结束或结果之间属于已知在途工作，暂停通用空转计时并切换到独立、可配置且更宽的工具执行闸；结束后重新计时。合法长命令不能被普通 idle 误杀，卡在凭据、网络或子进程里的工具也不能无限运行。总墙钟只在可调报告阈值到达时提醒，不杀掉仍有真实进展的 run；可识别的服务繁忙使用独立等待闸，默认五分钟，期间在活动行显示重试状态。
- Claude-bound run 在创建或恢复 Claude session 前，必须对本次实际解析到的同一绝对路径重新执行 `--version`；低于 `2.1.170` 时直接进入稳定的“Claude Code 需要升级”失败，不执行 Agent SDK query、不创建或改写 external session link、不启动 Codex/Kimi，并提供受信任的「更新 Claude Code」入口。更新动作固定执行该解析路径的 `update` 子命令、保持 `shell:false`，成功后允许按原 run 快照显式重试；原始 stderr、路径和内部异常不得进入 renderer。
- 普通 Claude Agent 通过 Agent SDK query 按原生 Claude 配置边界启动：Moebius 不使用 `--safe-mode`、`--strict-mcp-config`、`--disable-slash-commands` 或 `--tools` 等隔离选项，也不查找、读取、解析、复制、转换或改写用户与项目的 Claude 配置；只传递本次快照的 model、effort、权限、禁止内部 Agent/team 的 disallowed tools 和当前会话的托管 MCP。Claude 最终加载哪些 CLAUDE.md、用户 settings、hooks、MCP、skills、plugins 或其他扩展仍属于 Claude 自身行为，不是 Moebius 的实现或验收责任。Moebius 只保留会话、冻结 model/effort、权限与禁止内部 Agent/team 等产品运行边界。AI 建队的隔离 profile 仍由 onboarding 定义，不适用这条普通运行规则。
- Claude Code 通过统一的 Agent SDK query 执行：普通 Claude 会话和 AI 建队都使用同一个 SDK adapter；首次执行创建 canonical Claude session，后续轮次使用同一 ID 的 `resume`，每次 query 都是一个有明确终局的 provider turn。SDK 不把 PTY 暴露给页面，也不等待不可见的登录、工作区信任或权限确认；安全策略无法自动决定时以结构化失败结束。SDK 持久化的原生 JSONL 是完整输出和 usage 的唯一来源，过程标签按该记录恢复 Agent 正文、thinking、工具调用与结果、错误和 cache read / creation 等 usage；Moebius 不复制第二份 provider 原生过程内容。两条入口共享 session / resume / usage / MCP 注入与错误映射，但 AI 建队仍使用隔离工作空间、受限工具、`dontAsk` 和 JSON Schema 输出，普通 Claude 仍按本项目既有配置归属加载用户与项目设置。此机制只适用于 Claude，Codex、Kimi 与 Pi 的运行、恢复和过程展示保持各自既有语义。
- Pi API 正常任务默认全部放行，不出现 sandbox 或逐次工具审批。计划、Web、MCP、Skills、并行子 Agent、文件与图片输入、长上下文压缩和托管运行项都进入同一条 Agent 记录与团队调度；某项外部能力没有配置或本次不可用时，活动记录准确说明该项不可用，基础文件与命令工作可以继续，但页面不得宣称该能力已执行。
- 本地持久 Agent 身份由「这段对话 + 生效团队快照 + 角色」共同确定；身份之下按**执行代**保存当前 canonical 外部会话与冻结运行配置。一个身份的首个执行代第一次真正执行时允许创建一个 Codex thread、Claude Code session、Kimi session 或 Pi session；一旦取得 external ID，普通新消息、成员接力、下一步骤、重试、改一改重发和重启恢复都必须 resume 当前执行代的同一个 ID。只有用户明确执行“重新建立原执行”“迁移当前会话”，或使用一次性的“换执行配置重跑”，才允许建立另一执行代；不得因启动失败、配置变化或最近会话猜测而偷偷创建第二个外部会话。
- “重新建立原执行”与“迁移当前会话”会封存旧执行代，保留旧过程和尝试记录，并以 Moebius 已保存的可见共享时间线与附件引用建立新的 canonical 执行代。重新建立沿用原冻结配置；迁移使用用户明确选择的新模型或新 Provider，并永久改变这段会话中该 Agent 后续运行的冻结配置，但不改团队默认值。时间线显示“原生上下文已重新建立”及配置是否变化，旧外部会话此后不再 resume。一次性换配置只服务该次 run，终局后普通新消息仍回到 canonical 执行代。
- 明确改选团队并使新快照生效后，即使角色同名也属于新 Agent 身份，允许自己的首个执行代；旧快照 ID 不得交给新快照。
- 首次创建尚未取得当前执行引擎的 `thread.started`、`session/new` 或等价 external ID 成功证据就失败，表示外部会话没有建立，用户重试时仍可再次走该执行代的首次创建。一旦观察到 external ID，系统必须立即把它绑定到 Agent 身份和执行代；即使随后 prompt、输出校验、落库或发布失败，该执行代下一次也只能 resume。若已有执行证据却缺失 ID，必须显示「原执行已经无法继续」，不得把它伪装成首次执行。
- 每个 Agent 执行代保存自己已看过的公开时间线游标。首个执行代首次创建接收当时完整共享时间线；后续 resume 只接收该成员尚未看到的公开消息增量与本轮对应附件。用户明确重新建立或迁移后，新 canonical 执行代重新接收 Moebius 已保存的完整可见共享时间线，并从该边界建立新游标。这样 A → B → A 接力时，A 能收到离开期间 B 的公开回复，又不会在同一原生会话内重复注入已有历史。只有 Agent 回复成功形成公开事实后才推进游标；失败轮保留原游标供显式重试。
- resume 前必须证明 external ID 与当前会话、团队快照、角色、执行代、工作空间、冻结 persona、执行引擎及完整冻结运行配置属于同一身份；Pi 还必须匹配 Provider 档案身份、服务商和模型。各执行引擎返回的 ID 必须与请求 resume 的 ID 一致。冻结 Pi Provider 档案身份已经无法解析时，不进入通用“原执行已经无法继续”，而进入“历史 Provider 档案不可用”，只提供迁移或结束继续能力。除此之外的关联缺失、冲突、不唯一、不兼容，或 provider 明确报告会话不存在时，只执行这一次 resume 并进入「原执行已经无法继续」；不得猜测最近会话、跨引擎恢复、清空 ID 或自动发起第二次 full / `session/new`。只有原冻结配置仍完整可用时，用户才可明确“重新建立原执行”；配置已失效时只显示与原因匹配的修复、迁移或结束路径。
- 升级前旧会话只在同一 Agent 身份下能归一出唯一兼容 external ID 时建立 canonical 关联；没有候选或出现两个不同 ID 都明确失败，不按时间或成功状态猜测。团队快照缺少运行配置字段的旧会话继续把 legacy Codex 配置作为不可变身份，不读取当前团队页配置补写，也不自动切到 Claude Code、Kimi 或 Pi API。
- 团队页不产生“无法验证”或“需要调整”状态；静态格式有效的运行配置不阻止创建对话或切换团队。动态不可执行只在真正启动对应成员时成为该 run 的失败事实。

### 托管运行项

- 需要跨当前 Provider invocation 或 Agent 回合继续运行，或者明确需要用户持续监督的本地进程必须作为托管运行项启动；普通一次性命令继续使用 Provider 原生前台终端能力。Agent 不应自行使用后台 shell、`nohup`、double-fork 或约定正文 JSON 让进程逃逸。
- Codex、Claude、Kimi 与 Pi 在每次创建或恢复执行时都能看到同一组托管运行项能力。能力只作用于当前会话与其工作空间，Agent 不能选择其他会话、越出当前工作空间作为工作目录，或把一段 shell 字符串交给 Moebius 执行。
- 启动请求可以说明可读名称、服务／任务／watcher 类型、可执行文件、参数、相对工作目录、可选 readiness 与可选本地地址。服务与 watcher 没有预期自然终点；托管 task 有自然终点，但用户明确要求它跨当前 Provider invocation 继续或在面板持续监督。预期在当前原生工具调用内结束、结果立刻由 Agent 消费的 Python、测试和构建仍是普通前台命令，即使运行数分钟；耗时长本身不把它变成托管 task。地址和 readiness 都不是必填，满足上述边界的 Python 长任务没有 URL 也可以被托管。
- Moebius 返回的运行项标识、真实状态与地址才是可依赖结果。Agent 正文中的链接只用于向用户说明，不创建、认领或恢复进程。
- 托管工具已经成功返回只证明该进程动作完成，不证明 Provider 本轮已经正常结束。特别是 Kimi 在工具返回后仍未结束 ACP 回合时，系统必须在独立的有限窗口内停止等待并形成可重试终局；已经托管的进程保持可见和可控，不因 Provider 回合超时被偷偷停止或重复启动。
- 每次 Provider 执行使用临时的会话级能力注入，不修改 Codex、Claude、Kimi 的用户全局配置或 Pi Provider 档案。恢复同一 Provider session 时仍重新注入当前能力，不依赖上一轮提示残留。
- 临时能力的注入、初始化或工具发现失败时，本轮必须明确说明能力不可用，不产生成功 Agent 回复、不启动或登记目标进程，也不得改用 `nohup`、后台符号、double-fork 或正文 JSON 伪装成功。

### 说话与提及

- 用户从 composer 发出的消息若在代码区域外只包含一个不同的有效成员 mention，系统直接启动该成员，不先运行主 Agent。正文中同一有效成员重复出现仍视为一个目标；无效 mention 与唯一有效成员并存时不遮蔽该有效目标。无有效 mention、mention 全部无效，或包含两个及以上不同有效成员时，消息交给当前团队主 Agent。
- 主 Agent 仍是未明确单点直达时的默认接收者，也是专业成员无显式交棒回复后的最终控制权回交目标。直接点名只改变这一条用户消息的第一位执行者，不取消主 Agent 的接回与收尾职责。
- 成员回复中有合法 `@` 时按显式交棒继续；成员回复没有合法 `@` 且该成员不是主 Agent 时，系统只按团队结构把下一棒交回主 Agent，不根据正文内容猜测结论。主 Agent 不再仅凭“回复里没有合法 `@`”让本轮自然结束，而是在不继续交棒时明确留下本轮收束事实。
- 主 Agent 可以在接回控制权后继续派工、询问用户或自由形成收尾文案，产品不规定固定成员顺序、固定验收阶段或固定收尾模板。它结束本轮时只需把结论归入“有新结果”“需要用户处理”或“确认没有新增内容”；这些是会话状态，不从正文关键词、角色措辞或测试结论猜测。
- 主 Agent 在回复中提及成员就是一次派工。同一成员在旧派工尚未收尾时被主 Agent 再次提及，第二次派工取代第一次：尚未开始的旧派工不再执行；已经开始的旧派工可以留下历史输出，但其晚到结论不再继续推动接力，后续推进以最新一次派工为准。不同成员的派工互不影响；用户直接点名仍只是排队，不产生派工覆盖。
- 从专业成员完成回复到主 Agent 接回并完成收尾之间，整段接力仍属于进行中；侧边栏不得提前显示蓝点，子会话不得提前显示“已结束”，结果卡片也不得提前出现。
- 如果当前成员被停下、没跑起来、卡住，或项目 / 团队已经不可用，系统保留真实异常与恢复入口，不伪造一条主 Agent 成功收尾；“最终回主 Agent”约束正常完成的成员接力，不覆盖失败和用户主动停止。
- 用户直接点名一个**正在工作**的专业成员时，消息进入该成员的持久 FIFO，等待当前 run 进入终态后再启动；不并行，也不中断。主 Agent 在回复中提及一个正在工作的专业成员，仍表示主理人重定向：先让该成员停下当前这一步，再带着主理人的新指令重新开始。提及其他成员则可以在已有成员继续工作的同时启动新的专业成员。
- 这是用户已有的中断权的代行，不改变团队成员之间的扁平关系。
- **补一句话与打断由此分开**：用户说话永远不会直接打断专业成员；直接 `@成员` 忙时只是排队。用户要立即停止某个专业成员，使用该成员活动记录上的「停下」。用户也可以不点名或点名多个成员，把意见交给主理人，由主理人判断是否需要中断并重派。

### 添加与发送附件

- 点击「＋」打开系统文件选择器；把一个或多个文件拖进输入框得到同样结果；从剪贴板粘贴图片时把图片作为附件，不把 `file://` 或原始本地路径插入正文。粘贴普通文字仍然只编辑正文。
- 图片附件支持 PNG、JPEG、GIF ��� WebP��剪贴��图片按 PNG 托管。运行时按该 run 绑定执行引擎的真实图片输入能力交付，不因某套 CLI 或 Pi 模型不支持而改用另一执行引擎。SVG 与其他格式按普通文件显示和交付，不伪装成原生图片输入。
- 文件进入草稿后就复制到应用数据目录的托管区，界面与持久化只使用不透明附件标识。原文件随后移动、改名或删除，不影响草稿恢复；消息发送后，也不影响历史预览、失败重试或重新运行。
- 发送把正文、附件顺序和消息归属作为一个提交处理：全部成功才新增用户消息并开始运行；失败时不留下只有正文或只有部分附件的消息。
- 图片在运行前由应用准备为只属于本轮的安全副本，并按绑定执行引擎的真实协议作为图片输入；普通文件也使用本轮安全副本，通过包含文件名、类型和大小的附件清单告诉 Agent。普通文件不被宣称为任一执行引擎的原生文件附件，也不冒充图片输入。Pi 请求只获得本条消息及其运行需要的附件内容，不因为 Provider 档案存在而读取其他附件或项目外对象。
- 重新运行使用消息已经托管的副本，不重新读取原路径。时间线中的附件预览由结构化附件组件和受控本地资源端点提供，继续禁止 Markdown 直接加载 `file:`、`data:` 或自定义协议。
- 用户移除尚未发送的附件时，从该草稿中删除它；已经发送的附件属于历史消息，本页不提供单独删除入口。

### 专业判断与程序状态

- 测试、复核、“通过”“不通过”和“验收”等词都可以出现在普通 Agent 对话中，不因角色或关键词自动生成程序状态、系统提示、返工子任务或父任务汇合。
- 专业成员仍应按各自 `AGENT.md` 提供判断、证据和下一步建议；主 Agent 读取这些内容并对会话下一步负责。
- 当前版本不提供机器可判定的子任务语义完成或自动汇合。复杂并行任务是否全部满足目标仍由主 Agent 判断；本轮收束只保存主 Agent 已经作出的对用户结论，不替系统证明任务成功或自动验收子任务。
- 创建子会话属于明确的程序副作用，可以继续使用受控结构化事件；其中任务检查点是可选上下文，不要求 formal acceptance statements。旧输出中的验收语句只兼容显示为任务检查，不触发验收入账或自动汇合。

### 停下

- 「停下」中止被明确指向的当前 run，是中性事实，不是失败。输入框右下角方形按钮只指向主理人；每个专业成员活动记录上的「停下」只指向该成员。停止一条 run 不得连带停止同会话中的其他 run。
- 主理人被停下或自然进入其他终态后，存在待发射内容时通常自动发射最早一条；如果团队切换仍在等待其他 run 结束，则继续等待，等新团队快照生效后再发射。专业成员被停下不单独触发主理人待发射内容。
- 停下之后可以继续说话，开启新的一轮。
- **停下后同时提供两个不同动作**：「重试」使用原输入创建新 run；「改一改重发」把**本轮起点——用户最近发出的那条消息**回填到输入框（附件保持为该消息的托管副本引用），用户修改并发送后新增一条用户消息和一个新 run。两者都从零计时，均不继续或修改原 run。
- 回填的消息已经包含 Markdown 来源块时，来源块作为普通正文的一部分原样进入编辑框，不重新恢复为文本胶囊；编辑框会显示完整 `moebius-ref:` 地址和目标 ID，因为它们属于公开文本协议。用户可以删除、改写或新增来源链接，合法目标与其他同格式 Markdown 一样导航，不区分作者。再次发送时不追加第二份来源块，也不重新序列化已经不存在的历史胶囊；新消息与「重试」都只使用各自消息中可见的完整正文，不读取链接目标。
- 停下或异常终态前已经显示的 Agent 正文必须留在该终局记录中并标注内容不完整，不能随活动 run 消失，也不能作为成功 Agent 消息落库。
- 回填不撤销已经产生的文件改动，也不修改或删除时间线里的原消息；重发是一条新消息，开启新的一轮。产品不提供历史消息的原地编辑或从某条历史消息分叉重跑——那会暗示文件改动能跟着一起撤销，而这不成立（见待讨论「用户拿不回 Agent 动过的东西」）。

### 重试

- 一步没跑起来、卡住或被停下时，系统记录旁提供「重试」。
- 已停下、卡住、认证或凭据失败、额度不可用、服务持续繁忙或没有产出完整结果时，还提供「换执行配置重跑」。用户在原位选择 Codex、Claude Code、Kimi 或 Pi API；CLI 继续选择 model / effort，Pi 只列当前已就绪 Provider、可用已验证模型和实际支持的思考程度，不显示或要求输入 Key。首版选择只作用于这一次新 run，不写团队配置，也不改变会话 canonical 冻结快照。每次确认生成独立提交身份；重复选择同一配置仍是新的用户意图，同一次提交的重复请求则保持幂等。
- 当前冻结 Pi 档案仅因 Key、凭据或停用而不可用时，页面优先提供匹配的设置修复入口；用户仍可明确选择另一份已就绪配置进行一次性重跑。冻结模型或服务商已经下架时，页面同时区分一次性重跑与永久“迁移当前会话”，不得用一次成功的临时 run 冒充后续普通消息已经可继续。
- 用户也可以不重试，直接说话或换一个成员接手。
- 首版不自动重试，不设置次数上限，也不产生“重试耗尽”状态；按钮不会因为尝试次数增加而自动消失。
- 每次「重试」创建新的 run，沿用原步骤绑定的角色、团队快照、工作空间和完整运行配置；若当前 canonical 执行代已经取得 external ID，新 run 必须 resume 该 ID，不借用最近一次其他身份或执行代的运行，也不创建 replacement session。
- 原用户消息含合法 `moebius-ref:` 时，重试仍按普通 Markdown 原样复用该消息；链接目标状态不影响重试 run 创建。
- 「换执行配置重跑」是上一条的显式例外：它创建同一步的新 run 和一次性执行代，以当前公开时间线 full 启动用户所选引擎；正常退出恢复仍 resume 该一次性会话。终局后原 canonical 配置和外部会话继续供后续普通 run 使用，临时执行代不得覆盖它们；一次性 Pi run 在可继续期间仍作为 Provider 引用，终局且不再可恢复后解除该临时引用。
- 每个重试 run 独立显示本次运行耗时与完成时刻，不显示跨重试累计耗时；同一步的完整输出按第几次尝试聚合保留。
- 重试与恢复都不会回滚已有文件改动，因此 Agent 仍需先检查工作空间现状，避免重复执行已经完成的副作用。

### 退出应用与恢复执行

- 用户正常退出桌面应用时，系统先为已经建立外部执行会话的活动执行持久化「可恢复暂停」，再终止对应 CLI 或 Pi 请求等待；下次启动时自动继续这一次执行。正常退出不留下假运行状态，也不要求用户重复发送原消息。
- 崩溃、强制结束进程或断电无法可靠写入可恢复暂停。此类遗留运行在下次启动时显示为「一步卡住了」，只有用户显式点击「重试」后才以原输入创建新 run，不自动重跑，也不冒充对原 run 的恢复。
- 自动恢复仍精确继续同一未完成 run 并累计原耗时；它与普通后续 run 共用同一个 Agent external session，不另建恢复专用 thread。
- 自动恢复沿用原 run 对应的已持久化可见消息，不读取引用目标；来源目标后续变化不会进入恢复或下一次新 run。
- 恢复前必须校验 session、原 `runId`、角色及其 run 级团队快照、工作空间身份、执行代、完整运行配置和 Agent external session 关联；Pi 还要校验 Provider 档案身份、服务商和冻结模型。全部匹配且配置仍允许请求时才继续；校验失败或外部会话丢失时，原 run 只记录一次恢复失败，不自动重新执行或 full 重建。Pi Key / 凭据异常、档案停用、模型或服务商下架、历史 Provider 档案缺失分别进入各自状态，不用通用 resume 失败掩盖。
- 只有原冻结配置完整且仍可执行、但原生 external session 本身丢失或关联失败时，「无法继续」才提供「重新建立原执行」。用户确认后以原用户消息的可见文本、原 run 团队快照、原冻结配置和当前工作空间现状创建新 canonical 执行代，从零计时；页面明确提示原生上下文会从 Moebius 已保存的可见时间线重新建立。原 run、旧 external ID、已有耗时与文件副作用全部封存保留，链接目标不可用不阻塞重新建立。历史 Provider 档案缺失时不显示该操作，只显示迁移或结束继续能力。
- 系统可以在内部诊断中记录本次执行的 cached input token，但不在正常对话界面展示 token cache 指标，也不把 cache 命中当作恢复成功的判据。
- 正常退出时，托管运行项与可恢复的 Agent run 使用不同规则：Agent run 仍按本节写入可恢复暂停，托管运行项则全部停止且下次启动不恢复。任一运行项无法在有限时间内回收时，应用不得声称已经安全退出。
- 崩溃、强制结束进程或断电后，下次启动只清理由 Moebius 能够确认归属的残留进程并把旧登记视为结束；不重新执行旧命令，不恢复旧地址，也不把残留误显示为继续运行。

### 侧边栏状态点的触发

会话页保存每一轮从开始、推进到收束的唯一状态事实；它与用户在[主页面侧边栏](./main-left-sidebar.md#标记为已读与未读)保存的提醒确认共同决定这段对话显示哪种点。本节是红点事实来源和本轮收束语义的唯一定义处；侧边栏负责用户确认、手动未读、菜单和清除生命周期。

主 Agent 明确收束一轮时，必须留下“有新结果”“需要用户处理”或“确认没有新增内容”之一。成员交棒、某名成员结束、当前没有活动成员、队列在调度缝隙里暂时为空，都不能单独产生收束。这样一轮内可以有很多次内部开始和结束，但对用户只形成一次由主理人负责的结论。

一轮以一次需要团队推进的用户动作开始：新对话首次发送，以及上一轮已经收束或终止后的首次发送、重试或重新运行都会开始新一轮。主 Agent 已收束为“需要用户处理”时，这一轮已经结束；用户回答问题、完成指定动作后继续，属于新一轮。进行中追加的消息都归入当前轮，无论它交给主 Agent 还是直接点名专业成员；这些消息和对应待发射工作处理完之前，主 Agent 不能收束当前轮。直接点名成员不另造轮次边界，只按发送时这段对话是否仍在推进判断。打开对话、标记已读、切换页面或只查看结果都不开始新一轮。每一轮只保留一个最终收束结论，后一轮不会覆盖前一轮已经留在时间线中的结论。

主 Agent 没有留下收束事实，而会话已经没有活动工作、待发射内容或等待主理人接回的专业结果时，应用开始 **30 秒**静默确认。计时期间继续显示闪烁点，不显示倒计时，也不提前发送“结束”状态。出现新的用户消息、Agent 可见活动、待发射项新增／移除／发射，或专业成员结果进入／离开等待主理人接回状态时，本次计时立即取消；再次满足全部静默条件后从 30 秒重新开始。切换页面、刷新、休眠唤醒或重启应用不得把已经经过的静默时间清零；恢复后按最后一次可见活动和当前真实工作状态继续判断。连续静默满 30 秒时必须形成“本轮没有明确收尾”，不得无限保持闪烁。

“本轮没有明确收尾”只说明应用没有拿到主理人的结论，不得冒充主理人说任务完成或没有新增内容；会话页留下可读系统记录，并把它作为需要用户处理的事实。已有失败、卡住或不可继续事实按其真实原因呈现；用户亲自按下“停下”或确认“结束并保留历史”属于中性终止，不再被静默兜底改写成红点。

主 Agent 把一轮收束为“需要用户处理”时，它的可见回复必须同时说清为什么现在需要用户、用户需要回答的问题或完成的动作，以及完成后如何继续。能在输入框回答的内容直接给出明确问题；必须去设置或其他页面处理时给出准确入口，并说明返回后应使用“继续”还是“重试”。侧边栏“标记为已读”只确认提醒，不代表用户已经完成这项任务，也不会自动开始下一轮或产生外部调用。

| 侧边栏的点 | 会话页的事实 |
| --- | --- |
| 红点（需要你处理） | 主 Agent 已把本轮收束为需要用户处理，或至少存在一个用户尚未确认的当前待处理事实：一步没跑起来、一步卡住、额度或服务异常、没有产出完整结果、无法继续原执行、Pi Provider / 模型不可用、会话迁移失败、本轮没有明确收尾，或者三种不可继续状态（项目文件夹不可用、团队已删除、团队需要修复） |
| 蓝点（未读） | 没有未确认红点事实、当前没有正在推进的一轮，并且主 Agent 的最新结果尚未查看；用户也可以在无点状态主动把对话标记为未读 |
| 闪烁点（正在推进） | 没有未确认红点事实，本轮已经开始但尚未形成主 Agent 收束或静默兜底结论 |
| 无点 | 没有未确认红点事实；本轮尚未开始、主 Agent 已确认没有新增内容，或已有新结果已经查看 |

最后一条消息是否提及成员不独立创建或清除任何点；会话当前是否仍在推进，只读取本页统一的一轮状态事实，不从正文文字或某一瞬间是否存在活动成员反推。专业成员已经回复但主 Agent 尚未接回、存在待发射内容或存在其他待收束工作时，都仍显示闪烁点，不得提前显示蓝点或无点。

三种不可继续状态同时产生待处理事实和会话页的只读表现，两者不互斥：用户尚未确认该事实时，红点把他叫回来；用户从侧边栏标记为已读后，红点可以停止显示，但本页只读表现、系统记录和恢复入口继续保留，直到问题真正恢复。

红点事实出现后，侧边栏的「标记为已读」一次确认提交时已经共同形成当前红点的全部已知事实；刷新、轮询和重启不得让同一事实重新点亮，确认之后新增的待处理事实仍会再次点亮。状态点始终只有一个：红点优先；没有红点但本轮尚未收束时显示闪烁点；没有红点、没有正在推进的一轮且最新结果未查看时才显示蓝点。开始新一轮时，上一轮结果未读或用户手动建立的返回提醒结束，不保留隐藏蓝点。

蓝点的手动设置、清除和跨重启规则由[主页面侧边栏](./main-left-sidebar.md#标记为已读与未读)定义。Agent 新结果形成的蓝点在用户明确打开并成功展示最新结果后清除；用户手动未读不会因为当前内容已经可见或应用自动恢复而立即消失，但该对话开始新一轮时会由闪烁点接管并结束这条返回提醒。

用户按下「停下」不触发红点：那是用户自己刚做的动作，不需要产品回头提醒他。

用户被红点带回这段对话时，页面上一定有主 Agent 的待处理结论或一条说明发生了什么的系统记录，不会出现「被叫回来却看不出要我干什么」的情况。只有主 Agent 能把正常协作收束为需要用户处理；专业成员的普通回复不能越过主理人直接改变这段对话的最终状态。

| Pi 会话迁移完成 | 系统事实显示新配置与“原生上下文已重新建立”，旧过程不改写 | 以新配置显式重新运行、继续说话 |
| Pi Agent 已结束继续能力 | 该 Agent 的历史与结果可读，但不能继续、重试或恢复；不影响其他成员 | 改选团队，让新快照接手后续工作 |
| 未发送 · 原目标不可继续 | 从已结束 Agent 的 FIFO 脱离，保留原目标、正文和附件；不计为排队 run 或控制工作，不阻塞团队切换 | 编辑后明确重新提交、移除；不自动改派 |
| Pi 已整理较早上下文 | 对应 Agent 记录旁显示一次中性系统事实，不形成回复、目录事件或红点 | 继续工作 |
| 正常退出后有可恢复执行 | 下次启动自动恢复同一次执行，不新增用户消息 | 等待、说话、停下 |
| 无法继续原执行 | 恢复校验失败，不自动重跑，侧边栏红点 | 重新建立原执行、说话、提及成员 |
| 项目文件夹不可用 | 历史只读，项目按钮标红并提供修复；未确认时侧栏显示红点 | 修复项目文件夹；输入与发送禁用 |
| 团队已删除 | 历史只读，团队按钮标红；未确认时侧栏显示红点 | 改选团队；输入与发送禁用 |
| 团队需要修复 | 历史只读，团队按钮标红；未确认时侧栏显示红点 | 去修复或改选团队；输入与发送禁用 |
| 附件准备中 | 输入框内显示附件缩略图或卡片及准备状态 | 继续编辑、添加或移除；发送禁用 |
| 附件准备失败 | 失败附件就地说明原因，其他草稿内容保留 | 重试、移除；发送禁用 |
| 加载中 | 保持时间线结构的加载占位 | 等待结果 |
| 加载失败 | 保留页面框架，显示原因与重试 | 重试、切换对话 |

### 三种不可继续状态的共同规则

项目文件夹不可用、团队已删除、团队需要修复使用同一种表现：历史只读、输入与发送禁用、对应上下文按钮标红。区别只在说明文案和恢复路径。

**恢复条件必须明确**：

- 项目文件夹修复成功后，这段对话恢复输入、发送和团队推进能力，历史与选择不变。
- 团队被删除后改选另一支可用团队，这段对话恢复推进能力；已有历史保留，新团队从当前上下文接手。
- 团队修复完成后，这段对话自动恢复推进能力，不需要用户再操作一次。

**这三种情况在有成员正在工作时发生**：已经拥有有效隔离副本、能够安全完成的执行跑完当前这一步再停止；依赖已经不可用的项目文件夹或团队内容、无法安全继续的执行立即停止并留下可读的系统记录。产品不得在执行已经无法继续时仍显示成员正在工作。

## 弹层与危险操作

- 添加项目使用系统文件夹选择器，不删除、移动或修改用户文件。
- 添加附件使用系统文件选择器、拖拽或图片粘贴，并把内容复制到应用托管区；不会移动、改名或修改原文件，也不会把原路径作为消息内容保存。
- 「默认工作空间」直接改动项目文件夹里的文件。
- 「独立工作空间」把改动隔离在副本中，副本基于项目当前所在的提交，不包含用户尚未提交的改动。
- 从独立切回默认前必须说明之后的改动会直接落在项目文件夹里。
- 「停下」中止当前这一步，已经产生的文件改动不会被回滚，界面不得暗示可以撤销。
- 「迁移当前会话」会永久替换这段会话中受影响 Agent 的后续 Pi 配置，并建立新的原生上下文；确认前必须显示旧配置、新配置、不会修改团队默认值以及旧过程仍保留。迁移不回滚文件改动。
- 「结束并保留历史」会永久关闭这段会话中受影响 Agent 的继续、重试与恢复能力并解除该会话的运行引用，必须二次确认；它不删除时间线、附件、过程记录、文件结果、团队配置或其他会话引用。
- 「停止运行项」只终止所选托管进程组，不停止当前 Agent run、其他运行项或同会话成员；已产生的文件与外部副作用不会回滚。
- 本页不提供删除对话、删除消息或删除文件的能力。

## 响应式与窗口行为

- 时间线是页面唯一的主要滚动区域；页面标题和输入框保持可达。
- 有新内容且用户停留在底部时自动跟随；用户已经向上翻阅时不打断，提供回到底部的方式。
- 窗口变窄时上下文按钮逐项收敛，项目和团队最后收敛。
- 根对话的分析面板锚定主会话区域右上角；右侧栏分析对话的面板锚定该标签内对话内容区域右上角。两者可用宽度充足时都顶格参与所在对话布局，宽度不足时都复用会话目录轨展开层的覆盖原则，在所在对话内容右上方展开，不改变该对话正文宽度、输入框位置或阅读焦点，也不改变外层主会话布局。长列表只在当前面板内部滚动。
- 右侧栏在窄窗口下的覆盖行为由[主页面右侧栏](./main-right-sidebar.md)定义；从覆盖状态关闭后，会话区回到原滚动位置。
- 分析新会话位于右侧栏窄宽容器时仍使用本页响应式规则：候选问题可以纵向排列，上下文按既有优先级收敛，文本胶囊保持单行横向查看，删除、Tooltip 等价键盘说明、正文和发送始终可达。
- 侧边栏关闭时，页面左上角提供「打开侧边栏」按钮。
- macOS 集成标题栏下正确避让系统交通灯并保留可拖拽区域。
- 运行项入口与分析面板、右侧栏开关共享 46px 顶栏控件密度；窗口变窄时先收敛运行项名称为数量或图标，但入口、状态辅助名称和停止操作仍可达。
- 长文本换行不撑破布局；代码与命令输出横向滚动，不撑宽页面。
- 附件草稿在窄窗口内换行；图片缩略图和普通文件卡片不得撑宽输入框，拖拽反馈不得成为唯一可发现的添加入口。

## 待讨论

以下问题已经在评审中被提出，本版**明确不作答**，不得由实现自行决定：

### 用户拿不回 Agent 动过的东西

「看不见」这一半已经解决：一轮结束的结果卡片说明有几个文件发生改动，[主页面右侧栏](./main-right-sidebar.md)承载文件清单与行级对比。产品不设独立的交付结果陈列区仍然是有效结论——右侧栏是按需打开的证据区，不是常驻陈列区。

「拿不回来」这一半仍然悬空：「停下」之后已经产生的半截改动怎么办；用户看到不该有的改动时能否在产品内还原；选择独立工作空间的用户如何把成果带回项目；首次使用时默认值恰好是最不可逆的那个，是否需要提醒。

这四件事共同决定用户敢不敢让团队动他的真实项目，跨越会话页、右侧栏和项目设置，需要一次完整裁决，可能由一份流程 PRD 承接。

### 出问题时给用户的信息不够

- 是否要在 run 总耗时之外持续显示“多久没有真实进展”。本次只解决真实进展与卡住的机器判据，不新增常驻计时字段。
- 重试前是否需要提示上一次已经产生的文件改动。首版已确认不自动重试，不在这里重新开放该决定。

### 其他

- **结构化子任务裁决协议**：本轮收束事实只记录主 Agent 对用户作出的结论，不自动判断子任务是否通过或多个子任务是否可以汇合。未来若引入机器处理，必须使用显式、版本化、绑定任务标识和裁决权限的结构化事件，并定义证据、幂等、重试与错误可见性；不得重新回到自然语言关键词推断。

## 关联流程

本文档只记录会话页在各流程中的职责：

- 添加第一个项目并开始第一段对话。
- 团队接力推进一个目标直到结束。
- 从没跑起来、卡住或停下的状态恢复。
- 团队拆出子任务并各自推进。
- 会话进行中切换团队或改变工作空间。
- [会话分析与优化](../flows/session-analysis.md)：本页提供 Agent 消息入口、发送前文本胶囊、发送后 Markdown 来源导航、候选问题和完整复用的新会话 / 已有会话布局。
- [BYOK Agent 运行](../flows/byok-agent-runtime.md)：本页冻结 Pi Provider 配置，承接 API-only 启动、配置异常、一次性重跑、会话迁移、原生上下文重建与结束继续能力；单次 Agent 的具体过程与终局展示由单 Agent 会话页定义。

## 指标与验收

### 产品指标

- 用户从进入新对话页到发出第一条消息所需的操作次数。
- 因为界面没说清而重复发送同一指令的次数，目标为零。
- 点开又退出新对话页产生的空白对话数量，目标为零。
- 用户提及成员纠正方向后，团队真正改变行为的比例。
- 红点对话中存在明确待处理结论或可见异常记录的比例，目标为全部；正常完成的对话被误标为红点的次数，目标为零。
- 团队内部交棒缝隙被误判为本轮结束的次数目标为零；每一轮最终都能追溯到主 Agent 收束、真实异常、用户主动终止或“本轮没有明确收尾”之一。
- 用户从长会话当前位置预览并定位到任意一条历史消息所需的时间与误定位次数。
- 用户从一条 Agent 记录进入分析新会话并提交首个问题时，手工查找或复制会话路径、外部会话标识和日志的次数，目标为零。
- 用户从任一 Agent 记录确认该次团队、成员定义及“实际执行／计划尝试／仅绑定”的 CLI、model、effort 事实所需操作不超过两次：打开头像信息卡、按需查看只读 `AGENT.md`；因为看到当前团队值而误判历史执行配置的次数目标为零。
- 用户在团队选择器中不离开新对话页即可辨认主 Agent 与成员构成；因只看到团队名称而选错团队、随后立即切换团队的次数目标为零。
- 用户从任意来源对话打开它直接创建的正确分析对话所需的操作不超过两次：打开当前对话的分析面板、激活目标入口；误开其他来源对话或孙辈分析对话的次数目标为零。
- 每个被激活的来源项单独计量：消息级来源一次激活后到达对应对话和消息，对话级来源一次激活后到达对应对话；误定位次数、特殊字符导致链接失效或串改正文的次数均为零。
- 托管运行项成功率的分母是 Agent 通过受控能力发起并被 Moebius 接受的每次启动；只有进程状态可见、readiness 与真实探测一致、跨 Agent 回合仍可操作且停止后进程与端口都关闭才计成功，目标为 100%。
- **冻结配置一致性：**每个 Pi run 在页面可见的服务商、档案和模型都与该会话当前执行代一致；未经用户明确一次性重跑或迁移而使用其他配置的次数必须为零。
- **Pi 恢复可解释性：**以配置异常或原生会话不可恢复为分母，用户一次进入原终局记录就能看到唯一匹配的修复、迁移、重新建立或结束路径；把一次性重跑误认为永久迁移、或修复后自动产生 API 用量的次数必须为零。
- **秘密泄露：**完整 API Key 或可复用凭据出现在本页消息、过程、普通错误、迁移弹层、附件清单或可复制 UI 中的次数必须为零。

### 长会话操作台可用性

长会话中的历史信息必须保持完整、可读、可定位，同时不因历史长度让用户无法继续工作。该要求是用户体验预算，不规定服务端、客户端或渲染层的具体实现方式。

- 冷启动后的首次双向进入中，普通会话 → 长会话和长会话 → 普通会话两个方向都进行独立观察；每个方向的单次 click-to-settled 结果不超过 1.50 秒。
- 热切换在两个方向各重复 15 次；click-to-settled p50 目标不超过 1.05 秒，p95 目标不超过 1.15 秒。
- 会话保持打开且没有事实变化时，状态刷新不得造成时间线可见内容的无效跳动、重排或交互阻塞；运行中的耗时、实时正文、活动摘要、失败和终态变化仍须按既有频率可见。
- 用户在长会话中可以到达首条、末条和中段消息，能够从目录轨精确回到任意可见消息；切换会话再返回时保留原阅读位置，位于末尾时继续跟随新消息。
- 加载或切换失败时，用户已经看到的主内容、选中态、右侧栏、草稿和阅读位置保持不变，不留下只切换一半的界面。
- 该预算以脱敏大样本和真实 Electron 页面验收；不得为了达到时间目标丢弃历史、运行状态、草稿或失败现场。

### 验收标准

1. 没有待恢复的新对话草稿时，从侧边栏顶部进入新对话页不创建任何对话，且**项目为未选定状态**；退出后侧边栏不新增行，也不留下空白对话。
2. 从项目行进入时该项目已被选中，且与顶部进入是同一个页面。
3. 发出第一条消息后对话才被创建，侧边栏出现对应行并选中；默认标题在有正文时取该消息的开头文字，纯附件消息取第一个附件文件名。新会话首条消息后应用异步生成并重命名标题（不超过 20 字），生成失败或用户已手动改名时保留既有标题。用户之后从侧边栏重命名时，本页标题立即同步并在重启后保持，且不改变对话身份或现场。创建成功会消费该新对话草稿，下一次从顶部进入重新从项目未选定开始。
4. 项目未选定或一个项目都没有时，草稿可以输入、团队可以改选，但发送被禁用；从项目按钮可以添加项目并直接用于本次对话。
5. 项目与工作空间在发出第一条消息后一同锁定为不可点击文本；团队在对话进行中仍可切换。
6. 切换团队时，所有已经启动或仍可发射的排队 run 进入终态后再生效；同一边界先载入新团队状态，再把待接回结果和切换后提交的消息交给新团队主 Agent，不产生半截改动。因原目标已结束继续能力而脱离队列的未发送项目不阻塞切换，切换后仍保留原目标标签、正文和附件，只有用户编辑并明确提交后才按新团队处理。
7. 同一个项目下的两段对话可以分别使用默认工作空间和独立工作空间，互不影响。
8. 项目文件夹不是 git 仓库时，「独立工作空间」不可选并说明原因。
9. 分支显示真实分支名称，用户可以据此在自己的编辑器或命令行中定位。
10. 时间线中不出现「已交棒」「已完成」「运行中」这类过程状态标记；普通消息时间只在悬停时显示，运行记录显示带语义的运行耗时。
11. 主理人与每个专业成员各自复用[单 Agent 会话](./agent-conversation.md)的最新活动、计时、终态、完整输出、停止与重试规则；全局会话只负责把这些记录并行聚合，并保证彼此不会覆盖。
12. 没跑起来、卡住、已停下、额度或服务异常、没有产出完整结果和无法继续原执行等事实可见且彼此可区分；异常或中断前已经可见的正文标注内容不完整，刷新页面或重启应用后仍然可见。
13. 普通会话中的用户正文、Agent 正文、运行步骤、实时摘要和系统记录按原文显示路径、`cwd`、`runDir`、数据库路径与内部标识，不出现「路径已隐藏」「机器信息已隐藏」等替代文案；包含 `direct`、`worktree` 或 `handoff` 的正常句子也保持原文。分析新会话发送后的 Markdown 来源链接可以在不可见链接地址中携带经过严格校验的对话与消息标识，但可见正文只显示来源类型、成员、消息摘录或对话标题；内部引用不得扩散为外链或授予额外读取权限。
14. 用户从 composer 发出的消息只有一个不同的有效成员 mention 时直接启动该成员；未点名、只有无效 mention 或同时点名多个不同有效成员时交给主 Agent。直接目标忙时消息进入该成员持久 FIFO，不并行、不打断；主 Agent 提及正在工作的专业成员仍按重定向语义让它停下并带新指令重启。
15. 团队拆出子任务时时间线出现卡片，**每行显示子任务、负责成员和当前状态**；子会话不出现在侧边栏；点击卡片行在右侧栏开出该子任务的标签，父会话仍可见，关闭后回到原滚动位置。
16. 侧边栏红点完整覆盖主 Agent 明确要求用户处理、本轮没有明确收尾、没跑起来、卡住、额度或服务异常、没有产出完整结果、无法继续原执行、Pi Provider / 模型不可用、Pi 会话迁移失败、项目文件夹不可用、团队已删除和团队需要修复；正文措辞和专业成员普通回复不参与点的推断。红点与尚未收束的一轮重叠时先显示红点，用户标记为已读后同一事实跨刷新和重启保持已确认，若该轮仍在推进则转为闪烁，之后新增待处理事实仍能重新点亮。没有红点且当前没有正在推进的一轮时，未查看的新结果或用户在无点状态建立的手动未读显示蓝点并使用“未读”辅助名称；开始新一轮后只显示闪烁点，不并列或隐藏保留蓝点。专业成员已回复但主 Agent 尚未接回、存在待发射内容或其他待收束工作时仍显示闪烁。主 Agent 确认没有新增内容时回到无点；用户按下「停下」或明确“结束并保留历史”本身不触发红点。

18. 上述三种情况在有成员正在工作时发生，能安全完成的执行跑完当前一步再停止，无法继续的立即停止并留下可读记录；界面不再显示成员正在工作。
19. 新对话已经选择或填写的项目、工作空间、团队、正文和附件在切换到已有会话或其他页面后仍然保留；分析新会话已经收集的文本胶囊也随对应分析草稿保留。重新进入对应入口恢复同一份草稿，导航期间不创建侧边栏会话。

22. 主 Agent 把一轮收束为有新结果后，时间线末尾出现结果卡片，说明有几个文件发生改动并能一步打开右侧栏的改动标签；没有文件改动时如实说明；措辞不声称改动由团队成员造成。确认没有新增内容或本轮没有明确收尾时不伪造结果卡片。
23. 非主 Agent 有合法 `@` 时按显式接力继续，无合法 `@` 时下一棒确定性回到主 Agent；主 Agent 不继续交棒时必须留下有新结果、需要用户处理或确认没有新增内容之一，不能只靠回复中没有 mention 推断结束，也不产生自我循环。
24. 任意 Agent 正文出现“验收”“通过”或“不通过”都不会触发本地程序化验收、吞掉同消息交棒或生成缺少验收语句的系统提示。
25. 一个主 Agent run 与多个专业 Agent run 可以在同一主会话中并行；每条活动记录按自己的 runId 原地更新和停止，不得以 session 级单一 active run 覆盖其他成员。非主 Agent 无 mention 回复已经落库但主 Agent 尚未收尾时，会话和子会话仍显示进行中；活动成员或待发射内容在调度缝隙里暂时归零也不得产生结束状态。只有主 Agent 明确收束，或全部工作与待接回结果连续静默满 30 秒后形成“本轮没有明确收尾”，这一轮才结束。
26. 会话、侧边栏、子会话卡片和结果卡片使用同一份可持续保存的一轮状态事实；活动 run、待发射内容和待接回结果只说明仍在推进，不能反向证明任务结束、成功或验收通过。运行中切换团队后由新团队主 Agent 接管后续收尾；失败、卡住、停下或不可用状态不被伪装成成功收尾。
27. 本地结构化 child descriptor 没有 formal acceptance statements 时仍能创建子会话；可选检查点只显示为“任务检查参考”，不产生验收事实或自动汇合。
28. 用户与 Agent 正文使用同一套安全 Markdown 呈现，覆盖基础 Markdown、GFM、CJK、代码高亮、KaTeX 与 Mermaid；系统事实继续使用结构化组件。
29. 一个运行中的 Agent run 无论产生多少 JSONL、工具或可见进度事件，主时间线都只保留一条原地更新的临时记录；结束后只留下最终落库的一条 Agent 消息，不因流式输出增加消息数量。
30. Markdown 中的危险 HTML、协议和 `file:` URL 不可执行；外链经确认后由系统浏览器打开，Mermaid 使用严格安全模式。
31. 输入框右下角的「＋」可以选择一个或多个本地文件；文件拖入输入框和剪贴板图片粘贴可以到达同一附件草稿状态，键盘用户可独立完成选择、移除、重试和发送。
32. 图片附件显示缩略图，其他文件显示含文件名、类型和大小的普通附件卡片；发送后两者继续作为同一条用户消息的结构化内容显示，不借助 Markdown `file:` URL。
33. 支持纯附件消息和多附件消息；纯附件首条消息使用第一个附件文件名生成标题，不因正文为空拒绝创建对话。
34. 未发送附件与正文草稿一起跨对话切换和桌面重启恢复；新对话的附件还随同该草稿的项目、工作空间和团队一起恢复。原文件在添加后移动或删除，草稿、历史预览、失败重试和重新运行仍可使用应用托管副本。
35. 正文、附件顺序、分析新会话文本胶囊向 Markdown 来源块的转换和消息归属原子提交；有附件仍在准备或准备失败时发送禁用，上传失败或 session 与首条消息提交失败后不出现半条消息，项目、工作空间、团队、正文、附件和文本胶囊均不丢失；原子创建成功后对应草稿被消费，历史只保留来源块与正文，即使随后 Agent 启动失败也不恢复成新对话草稿。
36. PNG、JPEG、GIF、WebP 图片在运行前进入本轮安全副本，并按 run 所绑定执行引擎的真实图片协议交付；SVG 和其他普通文件通过本轮安全副本与附件清单交给 Agent，不宣称为任一执行引擎的原生文件附件，也不因附件能力差异改用另一套 CLI、Provider 或模型。
37. 附件界面不显示原始路径或应用内部路径；任何附件标识都不能被用来读取这条消息之外的附件或其他本地文件，预览内容不得执行脚本。
38. 首版不人为设置固定附件数量上限；超过系统可安全处理的单文件规模、磁盘空间不足、格式无效或托管副本写入失败时，在消息提交前明确说明并允许重试或移除。
39. 用输入法组合中文、日文、韩文文字时按 Enter 只确认候选词，不发送消息；组合结束后按 Enter 正常发送，Shift+Enter 始终换行。
40. 主理人运行时 composer 方形按钮始终只停止主理人，不因输入内容变化而消失；发送按 mention 解析结果立即进入目标车道或对应待发射队列。主理人与每个专业成员各自按 FIFO 领取，专业成员终态只触发自己的直达队列；若团队切换仍在等待旧团队 run 或切换前仍可发射的专业成员队列，则切换后提交的消息必须等新团队状态生效后再解析目标。已转成“未发送 · 原目标不可继续”的项目不参与等待或自动发射。
41. 用户按停后，「你让这一步停下了」的系统记录旁同时提供「重试」与「改一改重发」：前者以原输入创建新 run，后者回填该步用户消息正文与附件引用，修改并发送后产生新消息和新 run；两者均从零计时，原消息和已有文件改动不被修改或回滚。
42. local Agent 身份按 `session + teamSnapshotFingerprint + role` 区分；每个身份只有第一次允许创建外部执行会话，取得 ID 后普通新消息、成员接力、下一步骤、重试、改一改重发、重新运行与重启恢复都只 resume 同一 ID。切换到新团队快照后，同名 role 是新身份。用户与同一 Agent 连续对话、执行重试或经历 A → B → A 接力时，Agent 能继续引用这段会话中自己先前看到的要求和其他成员公开回复；页面不会无故显示“原生上下文已重新建立”，只有用户明确重新建立、迁移或一次性换配置时，页面才说明上下文边界发生变化。
43. 用户正常退出有活动执行的应用并重新打开后，页面自动继续同一步，不新增用户消息、不从零重放，也不自动产生新的运行或服务商用量；应用崩溃或被强制结束后，没有可恢复暂停标记的遗留执行落成“一步卡住了”并等待用户操作，不自动重跑。
44. resume 校验 Agent 身份、工作空间、冻结 persona、执行引擎、运行配置与 external ID；缺失、不唯一、不兼容、ID 冲突或 provider 会话不存在时只失败这一次 resume，不猜测其他会话、不跨执行引擎、不执行 full / `session/new` fallback。原记录只出现一个与原因匹配的可执行去向：原配置仍可用但原生上下文丢失时提供“重新建立原执行”；Pi Key、停用、模型或服务商问题提供修复或迁移；历史 Provider 档案缺失时只提供迁移或结束继续能力。页面不静默改用另一引擎、档案或模型，也不让用户点击必然失败的操作。
45. 首版不自动重试且不设重试上限，所有重试和重新建立都由用户显式触发；重试和重新运行创建新 run、独立计时，并与此前尝试在同一步完整输出中依次保留，但不创建 replacement provider session。每次尝试在页面上独立显示耗时、结果与完整输出入口，更早尝试和已经产生的文件改动保持可见；尝试次数增加不会自动隐藏按钮，也不会让页面声称文件已回滚。恢复机制不修改历史或执行 Git reset、checkout、merge、rebase。
46. 创建对话、明确改选另一支团队或显式应用当前团队更新生效时，快照包含每名 Agent 的 `AGENT.md`、执行引擎、Provider 档案、模型、思考程度和完整团队身份。团队页后续修改不会自动改变旧对话，也不会让下一条普通消息静默换配置；新建对话选择该团队、旧对话明确切换至该团队，或旧对话点击分类提示中的任一「应用」时，才载入对应边界冻结的完整保存版本。应用后的新消息与新工作使用新版；应用前历史步骤的重试、重新运行和恢复继续使用历史步骤自己的快照。同档案 Key 成功轮换后旧 Pi 会话仍可继续。
47. Agent 执行按快照执行引擎硬绑定；绑定的 CLI、Pi 档案、服务商、模型或凭据不可用时留下明确失败事实，其他 CLI、Provider 或模型的启动次数为零，也不出现来自它们的成功回复。Pi 在配置修复前保持用户消息、附件、已有正文和文件结果，页面不伪装成任务已经运行。
48. 升级前旧会话只在同一 Agent 身份能证明唯一兼容 external ID 时建立 canonical 关联；没有候选或存在冲突都 fail closed。缺少运行配置字段的旧会话继续使用不可变 legacy Codex 身份，不读取当前团队页配置补写快照，也不自动切换到 Claude Code、Kimi 或 Pi API。
49. 团队切换前已启动的每条 run 冻结原团队内容与运行配置，继续按原团队和原运行配置显示到真实终态；切换后针对旧步骤发起的重试或重新运行仍使用原 run 快照，当前团队接手必须开启新的执行动作。用户从旧步骤点重试时页面仍明确归属于旧团队尝试，不把历史改写成新团队成果；迁移 Pi 只改变受影响 Agent 此后的普通运行，不改更早尝试或团队默认配置。
50. 每个 Agent 身份首次创建接收完整共享时间线；后续 resume 只接收其公开时间线游标之后的消息增量与对应附件。A → B → A 时 A 必须收到 B 的公开回复，失败轮不得提前推进 A 的游标。用户明确重新建立或迁移后，页面显示“原生上下文已重新建立”，新一轮仍能引用此前可见历史。
51. 无论 onboarding readiness 是检测中、可用、缺失、未登录、需要处理、已停用、不可验证、读取延迟还是读取失败，新对话页都不显示成员准备人数、CLI / Provider 准备信息、兼容性提示或调整去向，也不把这些状态加入发送条件。普通操作台挂载、shell 就绪、进入团队页和第一条消息都不执行独立能力探测。第一条消息在原子创建会话、消息和团队快照后进入所选执行引擎的运行时硬门，并按 mention 规则直接启动唯一目标成员或主 Agent；CLI 缺失、版本过旧、未登录、拒绝 model/effort，或 Pi 档案、凭据、服务商、模型不可用时，页面保留已经创建的会话、消息、草稿清理结果与快照，并显示准确的“这一步没跑起来”或配置恢复入口。
52. 只有当前打开的主会话在正文列左侧常驻一条单列短横线目录；项目与会话侧栏的每个会话行仍保持普通导航密度，不出现目录轨。主时间线滚动时目录轨固定可见，左侧栏开合不得改变它所属的主会话区域。
53. 悬停或键盘聚焦目录轨后，同一批事件向右覆盖展开为无文字多泳道；用户消息、主 Agent 和专业成员的每条可见最终回复都能通过整条事件行预览并定位，真实 `A → B → C → B → C` 顺序不丢失。用户主干与按成员首次出现顺序排列的分支使用平滑曲线表达接力，并在省略边界分别收束；展开前后正文宽度、标题、输入框、事件纵向位置和阅读焦点不发生重排。
54. 长会话超过目录轨按当前时间线视口计算的容量时，窗口围绕阅读中心折叠远端连续事件，并尽量保留首尾边界；滚到开头、中段和末尾时焦点与省略区相应移动。切换会话再返回恢复上次阅读消息，新消息不强制跳底，从未打开或位置失效才聚焦最新稳定事件。
55. 悬停用户事件显示“你”和原消息开头；悬停 Agent 事件只显示成员可读名称、时间和回复原文开头，不重复显示用户消息标题。预览卡始终相对展开轨迹面板保持固定横向间距，不因节点位于最左或最右泳道而漂移；不显示 `@slug`、不生成摘要。点击或键盘激活精确定位并短暂突出原消息；定位失败时保持原阅读位置。
56. 用户或 Agent 正文中的显式 Markdown 本地文件链接与普通裸绝对路径只有在根 `/` 后至少包含一个非空的实际路径段时才保持原文并可点击；单独 `/`、`A / B` 中的分隔符、inline code `` `/` `` 与显式 Markdown 根目标都不产生文件引用。`/tmp`、无扩展名路径和不存在的目标仍按绝对路径识别，目录、不存在或不可读由文件面板反馈而不由 renderer 预判。点击后按 canonical 目标是否位于当前会话工作空间内分流：工作区内打开完整只读文件，带行号时直接进入源码并定位；工作区外只打开明确标识的目标行附近有界预览。无行号的工作区 Markdown 默认进入 Preview，带行号时默认进入源码。`file:` URL 和本地图片仍不导航、不读取。
57. 正文中的已知团队成员 mention 按会话冻结成员名单显示可读名称，点击只打开所属 Agent 团队的现有详情入口；未知 mention 保持原文，代码块、行内代码和已有链接中的 `@` 不被改写或触发。
58. 正在工作的 Agent 记录、已完成 Agent 回复和承接 run 的四种异常终态事实都能通过右键消息、可聚焦的菜单按钮和键盘上下文操作打开同一份消息菜单并选择「在右侧栏分析这条消息」；三种入口绑定同一条消息、生成同一个消息级文本片段，关闭菜单后焦点返回对应消息或菜单按钮。该操作不停止、重试或改写来源 run。
59. 分析入口打开或聚焦流程选定的分析新会话草稿并追加一个文本胶囊；页面 PRD 不另行判断归并键，已经发送的分析对话不接收静默追加。
60. 文本胶囊只在未发送草稿的附件区域保持单行短标签，每项删除按钮均有包含片段名称的可访问名称，可由键盘聚焦和激活；将生成的可读来源及交付范围可通过悬浮、键盘聚焦和辅助技术读取。来源后续变化不改写胶囊标签，但新 run 启动时读取目标最新内容；发送成功后历史不再渲染胶囊。
61. 分析新会话显示两项候选问题，每项均可由鼠标或键盘激活；激活只填入可编辑正文，不改变文本胶囊，用户也可以完全自行输入。
62. 分析新会话初始预选来源项目、来源工作空间和「通用助手」，发送前仍可按正常新会话规则改选；创建结果使用发送瞬间的最终选择。
63. 只有文本胶囊、正文为空，或分析草稿当前选中的项目目录不可用时不能发送；首次发送成功后当前标签原地使用本页正常已有会话布局，标题、时间线、运行记录、输入框和响应式行为没有分析专用分叉；文本胶囊按原顺序转换为首条用户消息正文顶部的 Markdown 来源块，来源块后空一行再接用户正文。
64. 分析新会话在右侧栏窄宽和覆盖式窗口中仍能用鼠标与键盘查看并激活候选问题、横向浏览文本胶囊、删除胶囊、读取完整文本、编辑正文并发送。
65. 团队选择器存在任意合法重名时，展开列表和重名项的收起按钮都可唯一辨认：持续接收更新的团队用 `owner/repo`，同名且同为独立维护时用稳定且足以唯一的本地创建时间。辅助名称包含同一组信息；新对话、分析新会话、已有会话切换和异常改选入口表现一致，排序或重启不改变辨认信息，界面不显示内部稳定标识、路径或临时序号。
66. 分析草稿当前选择的项目目录不可用时，项目上下文标红并说明修复或改选路径，正文、附件、团队与文本片段全部保留且可编辑，发送保持禁用；修复当前项目后保留原选择并恢复正常发送条件，改选其他可用项目后重算工作空间选项、保留文本片段并立即按新项目恢复正常发送条件。来源项目只决定引用目标，不锁定草稿项目；来源目标后来不可用时该项按「来源不可用」处理，不得把草稿项目改回来源项目。该状态不得静默丢草稿、改项目或创建半成品对话。
67. 分析新会话首次发送成功后成为归属于直接来源对话的分析对话，不作为普通根对话进入左侧栏；根对话标题栏中存在与右侧栏开关相邻、彼此独立且可读为“分析面板”的开关，右侧栏分析对话则在自身标题区末端显示只控制自身面板的同名开关。
68. 分析对话入口面板只列可读标题和触发入口，不承载摘要、状态、最近活动、详情、输入或面板内切换；首次激活某项在既有右侧栏中打开该分析对话的标签，再次激活同一项只聚焦既有标签，不创建重复标签。
69. 根对话和右侧栏分析对话的面板都锚定各自内容区域右上角：所在对话宽度充足时顶格布局，宽度不足时覆盖展开；不得改变所在对话的正文宽度、输入框位置或阅读焦点，也不得让分析对话嵌套第二层右侧栏。该能力不新增 Subagents 或运行时子代理功能。
70. 当前对话没有直接子分析对话时面板显示「暂无分析对话」；加载中显示面板内占位，读取失败显示不同于空态的原因与重试。切换根对话或右侧栏分析标签时，不得短暂显示上一段对话的分析入口。
71. 分析入口按创建时间从新到旧排列，时间完全相同时用不可变会话标识稳定排序；长标题单行截断但完整标题可由悬停、键盘聚焦和辅助技术读取，同名入口补充精确到秒的创建时间，连显示时间也相同的重名项再使用稳定且不表示时间先后的「同名项 A／B／…」；长列表只滚动当前面板，不滚动所在对话的时间线。
72. 分析面板开关支持键盘激活并暴露展开状态；关闭面板后焦点回到开关。每个入口均可独立聚焦和键盘激活；打开成功后焦点进入目标右侧栏标签，失败时保留在原入口并显示原因。
73. 两段主对话各自存在分析对话时，任何一段主对话的入口面板只显示自己的分析对话；用户可以在两次操作内打开目标分析对话，且不会打开另一段主对话的同名分析。
74. 根对话可以通过左侧栏整段入口或消息入口创建下一层分析对话；分析对话不在标题区菜单、分析面板或其他位置提供“分析整段对话”，只能从其中某条具体消息创建下一层。两类下一层都只显示在直接来源对话自己的面板，不在更早祖先面板重复出现；分析对话中的面板打开孙辈时复用同一外层右侧栏的兄弟标签，不嵌套侧栏。
75. 分析面板开合状态在当前应用进程中按具体对话 session 隔离记忆，切换对话再返回时恢复；软件重启后全部默认关闭。激活分析入口打开或聚焦右侧栏标签时，来源对话的面板不自动关闭。
76. 本版本没有分析对话独立归档入口；归档根对话会递归隐藏它的全部后代，恢复根对话时恢复整棵树及各直接父面板入口但不自动重开归档前的分析标签。任一后代仍有运行中或待接回控制工作时归档不可执行。项目移除把每段因此归档的根对话或分析对话作为子树根，递归隐藏全部分析后代及相应父面板入口，即使后代使用其他项目；子树之外的未归档父对话与兄弟入口保持。停止运行、放弃待接回和移除提交全部成功前，入口不得提前消失；任一步失败或回滚后原面板内容保持。上述操作不得改变任何分析对话的直接父子归属、面板位置或左侧栏身份。
77. 消息级来源链接一次激活即可打开或聚焦目标对话、精确定位并短暂突出原消息；对话级来源链接只打开或聚焦目标对话。目标已经打开时，消息级仍执行定位，对话级保持原阅读位置。目标属于当前对话树时复用当前根对话及其唯一右侧栏标签；目标属于另一棵树时，一次激活原子地切换到目标根对话、恢复它自己的右侧栏标签组并打开或聚焦目标，不能把目标挂入当前标签组；失败时保持原工作现场和阅读位置。
78. 应用从胶囊生成消息摘录时先排除既有来源块，再从安全 Markdown 纯文本投影取值：链接取标签、图片取 alt、代码取代码文字、mention 取可读名称、HTML 只取清洗后可见文字、附件消息取首个文件名；随后空白归一、移除控制与双向控制字符、转义 Markdown/HTML 特殊字符，并按 Unicode grapheme cluster 截取最多 80 个用户可见字符。
79. `moebius-ref:` 是公开的受控应用内引用语法，不证明作者身份；应用、用户、Agent 或复制文本产生的合法引用导航表现相同。语法非法、目标缺失或不可访问时保留原标签并显示可聚焦的「来源不可用」，不得进入外链流程；除该协议外的未知自定义协议继续阻止。
80. 含来源块的消息执行「改一改重发」时，完整 Markdown 正文原样回填，不恢复胶囊；编辑框明确显示公开 `moebius-ref:` 地址及目标 ID，用户删除、改写或新增后按普通 Markdown 接受，不区分作者。再次发送不追加第二份来源块；执行「重试」时完整复用原正文，来源引用不丢失、不改写、不重复，两者都不读取链接目标。
81. 任意用户或 Agent 消息中的合法 `moebius-ref:` 都只导航，不向当前或后续 run 自动交付目标内容。
82. 输入框中的每个来源胶囊通过悬浮、键盘聚焦和辅助技术公开将插入消息的完整文本；最终 Agent 即使使用不同项目、工作空间、团队或 provider，也只获得这份可见文本，不获得目标对话、运行记录、来源项目文件或其他对象。
83. 新用户消息含文本片段时，严格按“按顺序各序列化一次可见片段 → 提交消息；若为首条消息则同时创建对话及对应入口 → 创建 run 并启动 Agent”执行。链接目标状态不参与提交；Agent 进程启动失败保留已经创建的消息、对话和入口。
84. 同一 run 中断后的正常恢复、重试、重新运行、恢复失败后的重新执行及其他新 run 都使用关联用户消息中已持久化的可见文本，不刷新链接目标，也不拼入旧 execution context 中的隐藏来源正文。
85. 胶囊可读取文本无论长短都逐字作为自身唯一载荷；应用不得用更长的目标消息、对话或输出替换短片段，也不得在时间线不可见处追加这些内容。
86. 带合法来源引用的待发射项按普通 FIFO 规则发射；链接目标缺失或不可访问不阻塞队首，也不改变其他目标车道。用户仍可在发射前编辑正文或移除该项。
87. 在主对话分别发送唯一 `@qa`、无 mention、无效 mention 和 `@qa @dev` 时，实际第一位启动成员依次为 qa、主 Agent、主 Agent、主 Agent；未被选择的成员不得产生 run，代码块和行内代码中的 mention 不参与选择。
88. 当 qa 正在运行时再次唯一 `@qa`，页面显示目标为 qa 的待发射项，当前 qa 不被中断且不会出现第二个 qa run；切换对话或重启应用后该项仍在，旧 run 进入终态后它按 FIFO 启动并继续使用这段会话中 qa 的既有持久 Agent 身份。
89. Claude-bound run 每次 full/resume 前都以本次实际 executable 的 `--version` 检查 `2.1.170` 全局最低版本；旧版不执行 Agent SDK query、不创建或修改 external session、不崩溃、不调用其他 CLI，并显示脱敏升级原因与受信任更新入口。普通 Claude run 不传配置抑制 flags、不创建 replacement settings，也不查找、读取、解析、复制或管理用户 Claude 配置；不要求 Moebius 证明 Claude 最终加载了哪些原生扩展。普通 Claude 与 AI 建队共享 Agent SDK adapter；AI 建队仍使用独立隔离 profile、受限工具和结构化 JSON 输出。
90. 在真实 Electron 主页面分别使用 Codex、Claude、Kimi 与 Pi API 启动一个受控本地 HTTP 服务后，所属会话顶栏出现运行项入口；Agent 本轮结束或进入下一轮后同一运行项标识、进程和地址仍存在，HTTP 请求可获得预期响应。
91. 当前会话只有一个运行项时入口显示名称与状态，多个时显示数量；展开后每项分别显示启动中、运行中／已就绪、健康异常、停止中或已退出，并且无 URL 的 watcher 仍可查看日志与停止。
92. 从运行项面板点击「打开」只把经过校验的 loopback 地址交给系统浏览器；点击「停止」只停止所选进程组。停止完成后状态进入已退出，原 HTTP 端口不可连接，其他运行项和 Agent run 不受影响。
93. 托管运行项的工作目录只能是所属会话工作空间内的相对位置，启动始终使用可执行文件与参数数组且不经过 shell；正文 JSON、Markdown 链接、`nohup` 或后台命令不能创建受 Moebius 认领的运行项。
94. 正常退出真实 Electron 时，全部托管运行项在应用进程结束前被回收且端口关闭；重新启动后不自动重启。模拟上次崩溃留下的、具有可验证 Moebius 归属的残留时，启动阶段先清理再开放新会话，旧命令不会再次执行。
95. Kimi 的托管工具返回成功但 ACP `session/prompt` 不返回终局时，运行项继续可见且可操作，Agent run 在配置的有限��口后��成可重��超时，��会无限保持忙碌，也不会把工具调用成功当作 Agent 成功回复。
96. Codex、Claude、Kimi 与 Pi API 在首次运行和继续同一原生上下文时都能从真实页面使用相同的托管运行项入口；创建成功后用户能看到同一运行项跨 Agent 回合保持可打开、可看日志和可停止，不需要修改对应 CLI 或 Provider 档案设置。
97. 任一执行引擎本轮无法使用托管运行项能力时，目标 Agent 记录明确显示该能力不可用，不形成成功回复、运行项卡片或可打开地址，也不声称已经在后台启动；用户修复后可以显式重试，其他既有运行项保持可见。
98. 当前会话最后一个活动运行项退出后，顶栏保留可见的已结束事实和日志入口；用户明确清除成功后入口不留空位，清除失败时退出事实、日志和操作现场保持。
99. 新对话、分析新会话和已有会话团队菜单复用同一团队选项信息层级，每项显示名称、来源、一句话用途、主 Agent、成员数量与成员列表；空间不足时保留主 Agent 并用可激活的 `＋N` 收敛，鼠标和键盘都能在不选中团队、不关闭菜单的情况下展开完整成员名单并再次收起。已有会话的收起按钮和顶部带勾选的「当前对话」项读取有效快照，分隔线后的其他可选团队读取当前已保存目录；团队改名后，当前按钮与勾选项仍显示快照中的历史名称、来源及同名辨认信息。选择器不显示每名成员的执行引擎/model/effort，也不显示内部稳定标识。
100. 团队页保存团队名称、用途、主 Agent、成员构成、`AGENT.md` 或运行配置后，无需重启应用；新建对话并选择这支团队时由首次发送载入最新保存版本。已有会话不会自动应用当前团队修改，但可点击变化提示中的任一「应用」载入完整最新版本；用户明确切换到另一支团队时同样载入目标团队最新保存版本，A → B → A 的第二次选择 A 亦按此规则执行。
101. `AGENT.md`、运行配置和其他团队信息分别变化时，输入框上方分别显示「Agent 定义已更新」「运行配置已更新」「团队信息已更新」中性提示；同类多项合并、不同类别分开，每条都有「查看」「应用」和关闭。「查看」弹窗按成员列出变化与来历，其中的「取消」只关闭弹窗、提示保留，其中的「应用」与提示上的「应用」结果完全相同。任一「应用」都冻结点击时整支团队最新、完整且有效的保存版本，不提供单类别应用或版本选择，也不显示技术指纹、保存时间或逐行增删对比。没有旧工作时立即生效；存在旧 run 或排队消息时等待它们终结，点击后消息等新快照生效再解析，关闭重开仍保持同一冻结目标。成功后覆盖到的提示全部消失；应用后的新消息与新工作用新版，历史步骤重试、重新运行和恢复仍用各自旧快照。失败时原快照不变，点击后消息留在可编辑、可移除的等待队列且不按旧版发射；「重试应用」只重试原冻结版本，「取消应用并继续使用当前版本」才按旧快照释放等待消息并重算变化提示。Finder 等外部有效修改使用同一规则；提示不用错误语义且不触发红点。
102. 每条运行中、成功或异常终局 Agent 记录的头像都可由鼠标和键盘打开当时信息卡，并在已知执行配置时默认显示对应 Provider 标识；信息卡显示该 run 的 Agent、团队名称、来源及必要的同名辨认信息、执行引擎/model/effort（Pi 另显示 Provider 档案与思考程度）、快照载入时间，并提供跳转到历史所属 Agent 团队详情且预选该成员的入口，不再提供历史 `AGENT.md` 查看 Dialog。存在可信外部执行开始证据时三项配置标为「实际执行配置」；启动前失败标为「本次计划尝试 · 未开始执行」；旧历史无法证明开始事实时标为「本次绑定配置 · 是否开始未记录」。信息卡不显示技术指纹、文件路径、源文件修改时间、当前团队值或前后差异；其他旧历史缺失字段显示「此项未记录」，不得用当前团队配置补写；缺少历史团队稳定身份时不得错误跳转当前团队。
103. 没有任何 ready CLI、但所选团队主 Agent 已绑定已就绪 Pi Provider 时，用户可以正常发送首条消息；页面创建会话并显示所选服务商与模型对应的 Pi Agent 正文或活动，不出现 Codex 启动、CLI 安装提示或静默回落。主对话、运行记录和完整输出入口均不显示或要求重新输入 Key。
104. Pi Key 明确失效、凭据文件不可读或档案已停用时，目标 Agent 的新 run 与队首不请求服务商；页面保留用户消息、附件、已有正文、文件结果和原冻结配置，并显示匹配的修复或重新启用入口。设置修复成功后页面不会自动产生下一次用量，用户显式重试才继续这段会话原有的 Pi 原生上下文。
105. Pi 遇到短暂限流、额度不足或服务繁忙时，当前档案不会被页面永久标成不可用；用户能按原配置重试，也能选择另一已就绪配置进行一次性重跑。临时 run 结束后，下一条普通消息仍使用这段会话原来保存的配置，页面不会把一次性成功冒充成会话已经迁移。
106. 冻结 Pi 模型下架时，页面不再恢复旧原生会话，也不预选档案默认模型。用户可以把当前会话中该 Agent 迁移到同档案另一已验证模型；成功后系统事实显示新模型和“原生上下文已重新建立”，旧过程、时间线、附件和文件结果保持，后续普通消息使用新模型，团队默认配置不变。
107. Pi 服务商从支持目录移除时，迁移只接受另一服务商下已就绪的 Provider 档案与已验证模型，并在确认前显示服务商变化。没有目标档案时用户能前往设置添加；成功后显示新档案和上下文重建，失败时旧配置、引用、历史与迁移入口全部保持，不留下半迁移。
108. 对于冻结模型、服务商或历史 Provider 档案不可用，用户也可以确认“结束并保留历史”。成功后受影响 Agent 不能继续、重试或恢复，这段会话对原 Provider / 模型的可恢复引用解除；时间线、附件、过程和文件结果仍可读，其他成员、团队配置及其他会话不受影响。原成员全部待发射项转为不阻塞团队切换的“未发送 · 原目标不可继续”，逐项保留正文、附件和原目标，允许编辑后明确重提或移除，但不自动改派。该用户动作不产生红点。
109. Pi 配置在队首等待期间失效时，该条和后续同成员 FIFO 保持顺序、目标与可编辑内容，不自动跳过、不自动改配、不自动产生用量；修复后用户显式“运行这条”，或把原文改配重发。运行中才发生停用、Key 明确失效或目录变化时，已经发出的请求按真实结果收敛，不在中途偷换配置。
110. 任一执行引擎的原生会话丢失或无法安全对应时，页面只记录一次“原执行已经无法继续”，不会自动重建。用户明确“重新建立原执行”后，页面封存旧原生上下文，以原冻结配置和 Moebius 可见时间线开始新的原生上下文，并显示“原生上下文已重新建立”；旧耗时、尝试和文件副作用不被改写。
111. 在已配置对应能力的真实 Pi 会话中，计划更新、Web、MCP、Skill、并行子 Agent、文件与图片输入及托管运行项都进入同一主时间线和成员记录，不另开 API 专属页面，也不出现 sandbox 或逐次工具审批。任一外部能力缺失时页面说准该项不可用，基础文件与命令工作仍可继续，不能显示该项已完成。
112. Pi 长会话发生上下文压缩时，真实页面只显示一次中性系统事实“已整理较早上下文”，不中断当前工作、不新增 Agent 回复或目录事件；压缩后的下一轮仍能引用压缩前的明确要求并继续同一 Pi 外部会话。仅检查内部 token 计数不能满足本条。
113. Pi 的完整 API Key、凭据和服务商原始错误正文在团队快照、消息、运行过程、完整输出、迁移弹层、附件清单、普通错误和可复制 UI 中均不可见；路径与非秘密运行事实继续按既有规则可读，不能用统一隐藏掩盖用户需要的证据。
114. 已就绪 Pi 档案正在验证或保存新 Key / 模型版本时，主对话继续使用操作前的有效版本并可正常运行、恢复和发射队列；失败草稿不覆盖旧版本。原本已停用或需要处理的档案在验证期间仍不发请求，只有全部验证与保存成功后，后续显式运行才读取新的有效版本。
115. 导入或损坏数据导致冻结 Pi Provider 档案已不存在时，页面仍显示保存下来的服务商、档案历史标识、模型和思考程度，并明确标记“历史 Provider 档案不可用”。页面不显示必然失败的“重试”或“重新建立原执行”，用户只能迁移到当前已就绪档案，或结束继续能力并保留历史；没有目标档案时可以先前往设置添加。
116. 在真实页面依次完成新对话首次发送、进行中追加消息、进行中直接点名专业成员、主 Agent 收束、收束后继续、终止后重试和重新运行：首次发送开始第一轮；进行中追加与直达成员都留在当前轮且阻止提前收束；收束或终止后的继续、重试和重新运行分别开始新一轮。每一轮只形成一份最终结论，后续轮次不覆盖历史结论；打开对话、标记已读和切换页面均不产生空轮次。
117. 让一轮在没有活动工作、待发射内容或待接回结果、且主 Agent 没有收束事实的状态下静默：前 30 秒侧边栏持续闪烁且不显示结束；连续满 30 秒后形成“本轮没有明确收尾”系统记录并显示红点。第 30 秒前新增消息、出现 Agent 可见活动、改变待发射项或改变待接回结果会取消本次计时，下一次全部静默时重新计算完整 30 秒；切换页面、刷新、休眠唤醒和重启不能延后应有结论。用户主动停下或结束继续能力不进入此兜底。
118. 主 Agent 把一轮收束为需要用户处理后，用户从侧边栏红点进入该对话，无需查看过程记录即可在最终回复中看见待处理原因、明确问题或动作及继续方式；在输入框回答，或从指定入口完成动作并按提示继续／重试后，页面开始新一轮并重新显示进行状态。只执行“标记为已读”不会完成任务、自动继续或产生外部调用。

## 现状参考与产品缺口

现有本地对话操作台已实现单条时间线、实时进度、停下、失败与卡住记录、项目选择、工作空间切换和成员提及。这些是现状参考，不是本文的需求上限。

相较本文定义，当前实现的主要缺口：

- **工作空间是项目级设置**：现在切换一次会波及该项目下的所有对话；本文要求它是每段对话各自的设置。
- **本地对话仍会回退读取共享的 Agent 素材目录**：本文与[Agent 团队](./agent-teams.md)一致，Agent 只来自团队，没有脱离团队的全局来源。
- 输入框上方没有团队按钮，团队无法在对话中改选。
- 分支显示的是「当前分支 / 会话分支」字面词，不是真实分支名。
- 从项目行新建会立即创建并落盘一段空白对话，而不是进入不落盘的新对话页；从顶部进入没有对应形态。
- 添加项目不在项目按钮中。
- 时间线渲染「已完成」「已显示」等过程状态标记，未按本文收敛。
- 子会话在侧边栏平铺，没有卡片入口、卡片状态，也没有承接它的右侧栏。
- 对话标题、侧边栏状态点的触发与联动尚未建立。
- 三种不可继续状态的恢复条件与运行期行为尚未实现。
- 用户与 Agent 正文仍按纯文本渲染；运行中只展示从 stdout/stderr tail 提取的一行摘要，没有安全 Markdown、Streamdown 插件或 Agent 可见进度段的原地渲染。
- Enter 发送未区分输入法组合状态，中文候选词确认会直接把半句话发送出去。
- 没有「改一改重发」：停下后用户只能手动重新打一遍原话。
- 输入框只有正文和发送按钮，没有本地文件选择、拖拽或剪贴板图片入口；对话存储、时间线和本地 Agent 运行链路也没有附件事实。
- 会话快照、运行硬门、恢复和临时换配置仍只表达三套 CLI，尚未承接 Pi Provider 身份、配置异常、执行代、永久迁移、结束继续能力和上下文压缩事实。

`docs/wireframes/pages/console.md` 中与主内容区有关的内容由本文接管，该文件不再新增会话页事实。历史上的独立新建对话窗口定义已被本文取代：新建对话与会话页是同一个页面，添加项目和团队选择改由页面内的上下文按钮承接。

## 非目标

本页面不定义：

- 子任务标签的内部结构、输入方式和操作，由[主页面右侧栏](./main-right-sidebar.md)定义。
- 侧边栏的项目与对话组织方式，由[主页面侧边栏](./main-left-sidebar.md)定义。
- Agent 团队的管理、编辑和修复界面，由[Agent 团队](./agent-teams.md)定义。
- onboarding 如何检查和呈现 Codex、Claude Code、Kimi 或 Pi API 环境准备，不由本页定义。
- 独立“运行环境”诊断页的入口、检查范围和反馈形态，留待后续页面设计。
- Codex、Claude Code、Kimi 与 Pi API 的完整过程内容和降级细节由[单 Agent 会话](./agent-conversation.md)与[主页面右侧栏](./main-right-sidebar.md)定义；本页只聚合成员记录、显示入口和会话级恢复动作。
- 交付结果的独立陈列区。产品不设这样的区域，结果就是这条对话的最后部分；用户要看这段对话改了哪些文件，从结果卡片进[主页面右侧栏](./main-right-sidebar.md)。
- 根对话归档与恢复的操作入口由侧边栏和[全局搜索](./search.md)定义；本页只定义每段对话与其直接子分析对话的归属，以及根对话递归归档时的运行中拦截和后代可见结果。分析对话不提供独立归档入口。
- 高保真颜色、字体数值、精确像素和动效参数。
- 云端文件库、文件夹附件、远程 URL 抓取或把普通文件冒充为任一执行引擎的原生附件；本 change 只定义本机文件的托管副本、结构化呈现与运行期受控路径。
