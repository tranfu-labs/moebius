# Moebius 产品需求文档

> 状态：核心产品命题与 BYOK / Pi 执行方向已确认
>
> 当前范围：只记录已经确认的产品级结论；页面结构、状态矩阵与异常细节由 `docs/product/pages/` 和 `docs/product/flows/` 承接。
>
> 产品形态：仅面向 Apple Silicon Mac 正式提供的本地桌面端 App

## 产品命名

产品的统一品牌名为 `Moebius`，面向用户的产品名称、仓库内技术标识、应用配置与本地运行目录都必须围绕这一名称保持一致，避免同一产品同时存在多套名称。

这次命名切换是一次明确的破坏式变更：产品不继续识别旧名称对应的应用目录、环境覆盖或运行协议。当前 worktree 的磁盘路径与 GitHub remote 属于外部仓库状态，不由应用命名规则修改。

## 产品定位

Moebius 是一款面向 Codex、Claude Code 同类用户的本地多 Agent 协作产品。用户既可以沿用已经登录的 Codex、Claude Code 或 Kimi CLI，也可以直接配置 DeepSeek 等受支持服务商的 API Key，通过 Pi 获得对标当前本地 Codex 的编码 Agent 工作方式。

用户用自然语言定义 Agent 及其团队，让多个专业角色围绕同一任务自动推理、执行、审查、交棒和验收。产品的目标不是同时调用更多 Agent，而是让 Agent 形成可以持续推进和自我校正的团队，尽可能减少人类充当消息中转站、流程监督者和重复验收者。

## 目标用户

核心用户是已经使用或愿意使用编码 Agent，并希望任务执行进一步自动化的人。他们可能已经安装 Codex、Claude Code 或 Kimi，也可能只有受支持服务商的 API Key；没有现成 CLI 不应阻止其完成首次引导和开始任务。

这类用户通常：

- 能够使用自然语言描述任务、角色职责和项目规则。
- 已经接受 Agent 读取本地项目、运行命令和产出修改。
- 不满足于单轮问答或一个 Agent 独立完成全部工作。
- 希望方案、专业审查、实现和验收能够由不同 Agent 自动接力。
- 希望减少重复补充上下文、手动复制结果、指定下一角色和催促下一步。
- 仍然要求过程可见、失败可恢复、结果可验收。
- 希望常见 API 服务商只需选择名称、填写 Key 和模型，不必理解 Base URL 或底层兼容协议。

当前不对用户职业、团队规模或商业属性做进一步细分。

## 核心问题

单个编码 Agent 可以完成复杂工作，但一项任务从提出到可靠交付，通常仍需要用户持续参与：

1. 把需求交给执行 Agent。
2. 检查方案是否完整，是否遗漏模块影响。
3. 找其他角色提供架构、测试或用户视角的审查。
4. 把审查意见重新转述给执行 Agent。
5. 等待实现后再次安排测试和验收。
6. 发现问题时恢复上下文并组织返工。
7. 持续判断当前该由谁接手、为什么卡住、是否真的完成。

用户因此承担了团队调度、上下文传递和质量监督三种额外职责。角色和任务越多，人工干预越频繁，Agent 的自动化价值越容易被协调成本抵消。

## 价值主张

Moebius 让用户配置的是“Agent 团队”，而不是需要手工绘制的固定工作流。

团队中的 Agent 根据自然语言职责和协作规则自行判断、交棒、检查和修正。每支团队的主 Agent 对一轮会话拥有编排与收尾责任：它可以把工作交给任意成员，成员之间可以继续自然接力，但控制权最终回到主 Agent，由主 Agent 结合完整时间线决定继续派工、询问用户或给出可见收尾。用户主要参与目标表达、关键裁决和最终结果确认，不再负责在每个步骤之间复制信息和指定下一步。

产品提供五项核心价值：

1. **自然语言定义角色**：Agent 的职责、判断方式、协作边界和交棒条件以自然语言表达。
2. **团队自动接力**：一个 Agent 完成当前职责后，可以把任务继续交给合适的团队成员。
3. **专业分工保证质量**：不同 Agent 承担方案、架构、执行、测试和复核等不同职责，而不是重复回答同一个问题；专业结论作为主 Agent 判断下一步的输入，不由正文关键词直接驱动程序状态。
4. **过程可见且可恢复**：用户能看见当前角色、任务阶段、等待对象、失败原因和交付结果，并能从中断处继续。
5. **执行环境可选择且体验一致**：团队成员可以使用 Codex、Claude Code、Kimi 或 Pi API；无论底层执行引擎为何，用户都获得同一套团队接力、过程记录、停止、重试、恢复和托管运行项体验。

## 核心产品概念

### Agent

Agent 是一个职责明确的专业角色，例如开发、开发经理、测试、产品经理、用户画像或设计师。

Agent 由自然语言文件定义，内容可以包括：

- 角色职责与能力边界。
- 应当读取和遵守的事实。
- 判断结果质量的方法。
- 与其他角色的协作方式。
- 何时交棒、交给谁，以及何时等待用户。

Agent 属于 Moebius 的应用级配置，不从属于某一个具体项目。同一个 Agent 可以加入多个团队。

每个团队成员都保存独立运行配置：执行引擎、模型和实际支持的思考程度；选择 Pi API 时还保存应用级 Provider 档案。团队配置只决定新会话的默认运行方式，既有会话使用创建或明确迁移时冻结的配置，不因团队日后编辑而静默变化。

### Agent 团队

Agent 团队是一组围绕同类任务协作的 Agent，是产品中由用户选择和管理的一等对象。

例如，开发团队可以包含：

```text
开发团队
├─ 开发
├─ 开发经理
└─ 测试
```

产品团队可以包含：

```text
产品团队
├─ 产品经理
├─ 用户画像
└─ 设计师
```

团队定义“有哪些专业角色共同负责这类任务”。团队成员的自然语言职责和交棒规则在实际任务中形成协作过程。

“工作流”不是当前需要用户单独创建、绘制或维护的一等对象。工作流是 Agent 团队处理具体任务时自然形成的运行过程。主 Agent 是会话主理人而不是其他成员的组织层级；它固定的是控制权归属与最终收尾，不固定成员执行顺序或专业判断方法。

### AI 服务商档案

AI 服务商档案是可被多支团队和多个 Agent 复用的应用级 Pi API 配置。用户从 Moebius 维护的服务商目录中选择 DeepSeek 等明确支持的服务商，输入 API Key 并选择已列出的 Agent 模型；首版不要求或允许填写 Base URL 与任意模型 ID。

档案只有在固定的真实能力测试验证了模型回复和无项目副作用的工具调用，并完成本地安全保存后才成为“已就绪”。Key 不进入团队文件、会话、过程记录、普通错误或可复制界面。服务商身份创建后不可原位更换；改用另一服务商需要新建档案并由用户明确迁移引用。

首次验证只发送 Moebius 自带测试内容，不读取用户项目。真正运行 Pi Agent 时，用户消息、完成任务所需的项目内容、附件和工具结果会发送给用户所选第三方服务商；产品在首次建档时集中说明该数据边界，不引入逐次工具审批。

### 项目

项目是用户允许 Moebius 工作的本地目录，也是会话、项目上下文和交付结果的工作现场。

项目提供：

- 本地工作目录。
- 代码、文档和其他项目事实。
- 会话与交付结果的归属。
- Agent 执行任务时需要的项目上下文。

项目不拥有 Agent 或 Agent 团队。同一套应用级团队可以服务多个项目。

### 会话

会话是用户在某个项目中围绕一个目标展开的持续任务空间。

每个会话：

- 属于一个项目。
- 创建时默认选择一个 Agent 团队。
- 保留用户、Agent 和系统共同形成的上下文。
- 记录 Agent 执行、交棒、等待、失败、返工和验收结果。
- 允许用户在需要时手动切换团队。
- 冻结每名持久 Agent 的执行引擎、Provider 档案、服务商、模型和思考程度，使团队设置变化不会改写历史。

当前产品心智中，“发起任务”等同于“创建或进入一个会话并描述目标”，不另外向用户暴露一套与会话并列的顶层任务概念。复杂目标内部可以产生子任务或子会话；主时间线、右侧栏标签和单 Agent 过程共同承接这些内容，不把它们升级成另一套顶层任务系统。

切换团队时保留当前会话及已有上下文，由新团队接管切换后的任务推进；系统不新建会话，也不重新执行已经完成的历史步骤。

当冻结的 Pi 模型或服务商已经不可用时，用户可以明确迁移当前会话到另一有效模型或 Provider，并从 Moebius 保存的可见时间线建立新的原生上下文；也可以结束继续能力并保留只读历史。一次性换执行配置重跑只影响该次尝试，不冒充永久迁移，也不修改团队默认值。

## 产品运行形态

Moebius 只提供本地对话操作台：用户可以通过桌面应用使用，也可以在开发或高级使用场景中通过
`pnpm start` 启动同一套本地服务。两种入口共享 local console 的会话、团队、provider 与恢复语义，
不形成第二套远程任务运行时。

产品不再提供后台 GitHub issue runner、GitHub issue mention 扫描或独立 GitHub 状态 observer；桌面
应用也不再启动、监管或展示这些后台进程。删除运行形态不等于删除 GitHub 作为外部协作与发行平台：
版本检查、Release 下载、源码仓库链接等用户主动打开的外链能力继续保留。

本地开发过程中，Agent 可以请求 Moebius 托管一项需要跨 Agent 回合继续运行的本地进程，例如
Storybook、Vite、Python HTTP 服务、watcher 或长任务。它们是当前会话工作现场的一部分，不是新的
远程任务运行时，也不恢复已经退役的 GitHub runner。一次性测试、构建和普通 Python 命令仍由 Agent
在自己的前台执行过程中完成，即使它们可能运行数分钟；只有明确需要跨当前 Provider 执行继续存活，
或需要用户在会话中持续查看和停止的进程进入托管运行项。有限任务只有满足这条边界才称为托管 task，
耗时长本身不是托管理由。

托管运行项可以跨 Agent 回合存活，但不跨 Moebius 应用生命周期自动恢复。用户正常退出时，应用停止
全部托管运行项后再退出；应用崩溃后再次启动时只清理能够确认属于 Moebius 的残留进程，不自动重启
旧命令。用户始终从所属会话查看状态、打开可用链接、阅读有限日志并主动停止。

已有数据目录中的历史 GitHub runner 状态不是本次产品能力的一部分。应用不得为了移除运行形态而
主动删除用户磁盘上的历史状态；它只停止读取、迁移和写入这些状态。

### Desktop 持久 Agent 的执行会话连续性

Desktop 当前实际使用的持久 Agent 只有两类：主操作台中的 local 对话 Agent，以及首次引导
或 Agent 团队页中的 AI 建队草稿。两类身份分别由 local 的「会话 + 团队快照 + 角色」和
AI 建队的 draft 隔离。

每个持久 Agent 身份第一次执行时允许创建一个 Codex thread、Claude Code session、Kimi session
或 Pi session；取得 external ID 后，普通后续消息、接力、重试和恢复都必须继续同一个原生会话。关联缺失、冲突、上下文不兼容、原生会话不存在或恢复失败时必须明确失败，不能静默清空身份、切换执行引擎、Provider 或模型。

只有三种用户明确动作可以建立新的原生上下文：原冻结配置仍可用时“重新建立原执行”、配置失效时“迁移当前会话”，以及只服务一次尝试的“换执行配置重跑”。前两者保留旧过程并明确显示上下文已经从 Moebius 可见时间线重新建立；迁移永久改变当前会话中受影响 Agent 的后续冻结配置，重建不改配置，一次性重跑结束后普通消息仍回到原冻结配置。历史 Provider 档案已经缺失时不提供必然失败的原配置重建，只允许迁移或结束继续能力并保留历史。

local Agent 首次接收完整共享时间线，后续接收自己尚未看到的公开时间线增量；这让成员
保留 provider 内的工作记忆，同时仍能看到其他成员离开期间形成的公开结论。明确切换
团队快照后，同名角色也属于新 Agent 身份。AI 建队跨 draft 不共享 provider session。

Pi 长会话触发上下文压缩时，时间线显示唯一一次“已整理较早上下文”，并继续同一 Pi 原生会话；压缩后的下一轮仍应能引用压缩前已经公开的明确要求。计划、Web、MCP、Skills、并行子 Agent、文件输入和托管运行项都归入同一 Agent 的可见过程；图片按目录模型真实能力处理，首版 DeepSeek V4 明确为文本输入。某项外部能力未配置时准确说明不可用，不能宣称已经执行。

local 无 mention 路由与 CEO guardrail 是一次性辅助推理，没有持久 Agent 身份，不纳入上述
连续性契约。readiness、版本检查与安装不产生 Agent 推理会话。

## 视觉语言原则

产品界面采用近黑底暗色优先的 dashboard 视觉语言，令牌级细节以 `packages/console-ui/DESIGN.md` 为包内事实源，本节只定义全局原则：

- 画布近纯黑、卡面微亮、描边可见，层级靠亮度与描边表达；圆角基线 14px。
- 运行状态一律渲染为状态 pill（状态图标 + tinted 底 + 同色描边），不使用圆点 + 裸文字。
- 状态色相：running 琥珀、pending 蓝、waiting 紫、completed/displayed 中性灰；等待类状态允许使用专属色相。
- 交互 accent 唯一靛蓝 `#5E6AD2`，亮暗双主题一致。
- 绿 / 红只用于验收裁决与危险事实；唯一例外是未读计数允许使用红色圆角标。
- 所有状态色令牌亮暗双主题成对定义，不允许单主题取值。

## 品牌与发行平台

Moebius 使用同一枚黑色莫比乌斯环与白色方形底组成的产品图标。系统应用图标、应用内品牌位置、首次启动引导、辅助诊断界面和官网都应从这一品牌母版派生，避免在不同入口使用彼此近似但不一致的无限符号。

正式发行只面向 Apple Silicon Mac。官网、安装包和公开发布记录都应明确这一适用范围，不向用户提供或暗示 Windows、Linux、Intel Mac 或 universal 版本。选择单一平台是为了把当前有限的交付与验证资源集中到核心用户真实使用的本地桌面体验；其他平台不属于当前产品支持承诺。

对外发布同时提供用户安装和应用更新所需的同版本文件，两者必须使用同一产品图标。

## Agent 与团队配置

Agent 和团队保存在 Moebius 的应用数据目录中，作为可跨项目复用的应用级配置。

产品应允许用户：

- 在首次启动时先获得至少一个已就绪执行环境：可用的 Codex、Claude Code 或 Kimi CLI，或真实能力验证通过的 Pi Provider 档案。
- 在首次引导和设置中维护同一批应用级 Provider 档案；没有 ready CLI 时仍可只用 Pi API 完成 AI 建队。
- 配置或选择 Agent 团队，并在创建前看见每名成员实际保存的执行引擎、Provider、模型和思考程度。
- 使用一套可以立即开始工作的默认团队。
- 查看一个团队包含哪些 Agent。
- 修改已有 Agent 和团队。
- 新建适合其他任务领域的 Agent 和团队。
- 在具体会话中选择默认团队，并在后续手动切换。

Provider 生命周期由[设置](./pages/settings.md)定义，团队成员运行配置由[Agent 团队](./pages/agent-teams.md)定义，具体存储与运行协议留给 OpenSpec，不在总 PRD 重复。

## 运行环境与数据目录

产品层统一使用“Moebius 应用数据目录”描述 Agent、团队、配置和本地运行数据的归属。

- 打包后的生产环境默认使用 `~/.moebius`。
- 当前桌面开发环境默认使用项目仓库根目录作为数据目录。
- 开发、测试或高级使用场景可以通过 `MOEBIUS_DATA_ROOT` 显式覆盖数据目录。

产品界面不应把开发环境路径当作普通用户的默认心智。开发环境与生产环境必须保持数据目录边界清晰，避免测试配置、开发数据和真实用户数据相互污染。

Provider 元数据属于 Moebius 应用数据，完整 API Key 使用系统凭据能力安全保存，不能作为普通文件或界面字段取回。产品保持本地会话事实源，但 Pi 请求会按用户已知的数据边界把完成任务所需内容发送给所选第三方服务商；“本地产品”不得被表述为“所有任务数据始终不离开本机”。

## 核心用户旅程

当前确认的主旅程为：

```text
首次启动
  → 检查本地执行环境
  → 已有可用 Codex / Claude Code / Kimi，或添加并验证 Pi API Provider
  → 配置或选择 Agent 团队
  → 团队存在不可用成员时，明确选择替换为当前已就绪 API，或暂不替换并继续
  → 确认团队包含的 Agent
  → 添加本地项目
  → 在项目中创建会话
  → 默认选择一个 Agent 团队
  → 用户描述目标
  → 主 Agent 组织团队成员自动协作和交棒
  → 必要时等待用户裁决或允许用户切换团队
  → 专业成员把检查结果与执行证据交回主 Agent
  → 主 Agent 向用户收尾或继续推进
```

没有任何 ready CLI 的用户可以只凭已就绪 Pi Provider 完成上述旅程，包括“跟 AI 聊出团队”和首条真实编码任务。首次引导细节见[首次引导](./pages/onboarding.md)，端到端 Provider 与运行恢复见[自带 API 的编码 Agent](./flows/byok-agent-runtime.md)。

## 开发域 MVP

开发域是验证 Agent 团队价值的第一条样板场景。

默认开发团队至少包含：

- **开发 Agent**：理解需求、形成方案、实施修改并提供实现证据。
- **开发经理 Agent**：检查架构选择、模块边界、依赖影响和长期维护风险。
- **测试 Agent**：检查方案是否可验证，并在实现后执行独立测试或复核，把发现和证据交回主 Agent。

目标协作过程为：

```text
用户提出开发任务
  → 开发经理作为主 Agent 判断如何推进
  → 开发、测试和其他成员按各自 AGENT.md 自然接力
  → 专业成员给出方案、实现、测试、复核或返工意见
  → 接力链最终回到开发经理
  → 开发经理结合完整时间线继续派工、询问用户或收尾
```

开发域首先验证以下产品假设：

- 用户发起任务后，多数协作节点可以自动推进。
- 每个 Agent 承担明确且不重复的职责。
- 上游审查意见能够进入后续执行，而不是停留在对话中。
- 方案、实现、测试和复核结论保留可追溯的对话与执行证据。
- 专业成员发现问题时能够携带依据交棒返工，且最终回到主 Agent 裁决。
- 中断或失败不会迫使用户从头描述任务。
- 用户不需要持续充当团队调度器。

这些是需要通过下文“非预期人工干预率、自动闭环率、首次交付有效率、返工率、无效协作率与任务成功率”共同检验的产品假设，不是单次交付的模糊验收条目。具体任务样本、分母和观察窗口由对应指标与验收计划定义，不能用评审者主观判断“多数”“明确”或“持续”来宣称通过。

本次 BYOK / Pi MVP 的用户可观察交付判据为：

- 在没有 ready CLI、只有受支持 API Key 的干净环境中，用户能完成首次引导、创建至少一名明确绑定 Pi Provider 与模型的可运行团队成员，并发出首条真实编码任务；该成员在页面产生可见正文或工具活动。
- 在受控项目中，Pi API Agent 能从真实页面完成指定文件读取、可核对修改和确定性命令或测试；磁盘 diff、命令结果和最终说明一致。计划、Web、MCP、Skills、并行子 Agent和文件输入只有在验收环境已配置相应能力时才要求产生用户可观察结果；未配置时页面必须准确显示缺失。首版 DeepSeek V4 收到图片时必须显示文本模型限制，不能宣称已经理解图片。
- 分别使用 Codex、Claude Code、Kimi 与 Pi API 发起、停止、重试和恢复受控任务时，四者都进入同一套团队接力、运行记录与托管运行项页面；Pi API 全程不出现 sandbox 或逐次工具审批。具体跨页面步骤与判据以[自带 API 的编码 Agent](./flows/byok-agent-runtime.md#端到端验收)为准。

当前版本不把 Agent 正文中的“验收”“通过”“不通过”等自然语言解释为机器控制事件，也不维护由这类文本自动生成的结构化验收事实。子任务是否满足目标、多个子任务是否可以汇合，暂由主 Agent 根据共享时间线与专业证据判断。未来如需可靠自动汇合，应另行设计由 Agent 显式输出、带版本、任务标识、裁决权限与证据字段的结构化事件协议；在该协议建立前，不用关键词推断补洞。

## 长期愿景

长期目标是让用户只参与真正需要产品判断和个人裁决的部分。

以产品设计为例：用户先通过对话确认产品目标和用户画像，后续由产品经理、用户画像、设计、开发和测试等 Agent 自动讨论并补全需求、交互、视觉、技术和验收细节；发现矛盾时自动回到对应角色修正，最终形成达到约定质量标准的可用应用。

开发域是第一条样板团队，不是产品能力的最终边界。后续可以通过新的 Agent 团队扩展到产品设计等其他领域。

## 成功指标

### 非预期人工干预率

一次任务中，因为重复补上下文、手动催办、纠正错误交棒或恢复卡住流程而需要真人介入的节点数，占全部协作节点的比例。

产品主要降低非预期人工干预。产品取舍、危险操作和用户明确保留的审批属于预期干预，不应被当作自动化失败。

### 自动闭环率

从用户描述目标到主 Agent 给出可见收尾，无需非预期人工干预的任务占比。

### 首次交付有效率

主 Agent 首次向用户收尾后，无需因遗漏、错误或未满足目标而重新打开返工的任务占比。

### 返工率与返工轮次

至少经历一次专业成员指出问题或主 Agent 判断未达目标并退回执行角色的任务占比，以及每项任务从首次方案到最终收尾的平均返工次数。

### 无效协作率

Agent 重复提问、重复审查、没有新增信息的交棒或错误路由，占全部 Agent 协作行为的比例。

### 任务成功率

在约定条件内完成用户目标、提供必要证据并由主 Agent 向用户收尾的任务占比。

### BYOK 配置与首任务成功

分别跟踪 API 配置完成率、API-only 首次引导完成率、首个 Pi Agent 可见活动时延、同一档案复用率、零 Base URL 负担和秘密泄露次数。指标必须区分产品失败与服务商限流、额度或网络失败；具体分母、时间窗口和目标值以[自带 API 的编码 Agent](./flows/byok-agent-runtime.md#产品指标)为唯一事实源，不在总 PRD 复制另一套数字。

自动化指标必须与任务成功率共同观察。减少人工干预不能以降低结果质量、隐瞒失败或省略任务所需的测试与复核为代价。

## 当前非目标

当前阶段不包含：

- 商业化、付费方案和收入模型。
- 按职业或团队规模建立精细用户分层。
- 建设复杂的可视化工作流编辑器。
- 要求用户学习平台专用工作流 DSL。
- 一开始覆盖所有知识工作领域。
- 以 Agent 数量或对话轮次作为产品价值指标。
- 为追求完全无人监督而牺牲过程可见性、恢复能力和结果质量。
- 用户自定义 Base URL、任意 OpenAI-compatible 服务商或任意模型 ID；只有进入 Moebius 服务商与模型目录并通过真实能力测试的组合属于支持范围。
- 公开插件市场、插件安装器或用户可编辑的 Pi 扩展目录。首版使用 Pi 及选定扩展承接 Codex 对标能力，但不把插件治理变成用户产品面。
- Pi sandbox、权限系统或逐次工具审批。首版编码 Agent 默认允许读取和修改已选项目、运行命令并调用已配置工具。
- Moebius 代管服务商账号、购买或共享额度、合并账单，或在 API 失败时自动切到另一 Provider 或 CLI。
- 为 Pi 单独建设 LSP、云端 Agent、定时任务、Computer Use 或浏览器自动化产品面。

## 待讨论

以下内容仍未形成产品裁决，不阻断当前 BYOK / Pi 首版方向：

1. DeepSeek 之外首发哪些明确服务商，以及服务商目录的更新与恢复上架节奏。
2. 持续任务的 API 用量、费用明细和预算控制如何展示。
3. Web、MCP、Skills 等外部能力未配置时的完整设置入口；首版只要求如实显示可用或缺失。
4. 重试前是否提示上一次已经产生的文件差异，以及一次性执行历史是否提供独立清理入口。
5. 项目添加、失效、重新绑定、移除和数据保留规则中尚未被现有页面 PRD覆盖的边界。
6. 当前实现与已确认产品要求之间的实施顺序、模块拆分和迁移策略；这些由本次 OpenSpec 方案收束，不回写成新的产品决定。

已确认的首次引导、设置、Agent 团队、主对话和单 Agent 会话要求分别以 `docs/product/pages/` 中对应页面为事实源；跨页面 BYOK 旅程以 `docs/product/flows/byok-agent-runtime.md` 为事实源。总 PRD只持有产品定位、核心概念、能力承诺和全局边界。
