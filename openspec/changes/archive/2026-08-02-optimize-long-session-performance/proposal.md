# 提案：optimize-long-session-performance

> 记录性质：事后补录的决策记录。性能实现、定向验证、独立复核和完整门禁均已在本 change 文档落盘前完成；本目录用于保存原因、方案权衡和稳定契约，不伪造“先写方案后实现”的时间顺序，也不重新授权或扩大运行时代码范围。

## 需求基线

| 文件 | 小节 | 变更 | 状态 |
| --- | --- | --- | --- |
| `docs/product/pages/main-conversation.md` | `指标与验收`、`会话目录轨` | 补充长会话的可交互性、阅读完整性和 click-to-settled 性能预算，并作为时间线与阅读恢复锚点 | 已写入 |
| `docs/product/pages/main-left-sidebar.md` | `选择对话`、`指标与验收` | 作为选择失败保留完整界面的现有产品锚点 | 已有 |

产品要求写在 `docs/product/`，因为它回答用户应得到什么；本 change 只保存本次诊断如何落到实现、为什么选择这些机制，以及怎样证明没有牺牲既有行为。

## 背景

用户反馈长会话加载和切换明显变慢。使用脱敏大样本复现后，问题不是单一的 JSONL 解析：样本约 30 MB、26,605 个事件，store 最终投影为 211 条记录，其中 143 条是公开消息、68 条是内部运行占位；API 对外只返回 143 条，内部占位不能进入时间线 DOM。

旧路径的两个累计成本更显著：

- 空闲轮询每秒重复返回约 513 KB 的完整状态，并在内容未变化时仍提交新的状态对象。
- 长时间线一次挂载约 10,635 个 DOM 节点，使 Markdown、代码块、目录轨和布局计算共同参与每次历史切换。

store 热读约 1 ms，远小于上述传输、提交和浏览器布局成本。因此不能把“事件很多”直接等同于“投影必须重写”。

## 提案

在不改变消息事实、状态语义和用户现场的前提下，收敛为两项最小优化：

1. 服务端对完整状态快照生成 ETag，客户端按当前选择发送条件请求；快照不变时返回 304 且不提交 React 状态，快照变化时继续返回 200 并更新活动、失败和终态事实。
2. 时间线保留完整的公开消息逻辑列表，只窗口化当前视口附近的 DOM，按真实 Markdown 高度测量，并补齐首尾滚动、未挂载消息 Relay 定位、中段阅读恢复和末尾新消息跟随。

导航失败的完整现场恢复作为同一交付中的行为护栏：选择、主内容路由、右栏开合与可见性、host、tabs 文档与 active tab、草稿和阅读位置一起捕获；目标加载失败或过期时整体恢复。

## 影响

- **数据通道**：未改变 store 的 211 条记录、API 的 143 条公开消息或 68 条内部占位的可见边界；未压缩、改写或删除原始会话事实。
- **渲染层**：减少空闲无效提交和历史 DOM 规模，但不减少可定位的公开消息。
- **导航与恢复**：普通、搜索和 hosted 分析入口共享失败回滚现场，避免旧主内容与新右栏形成双事实。
- **诊断面**：Profiler 仅在显式验收 query 下挂载；正常运行不创建正式的全局性能接口。
- **不在本轮**：增量 store 投影缓存、JSONL 格式改写、消息压缩、持久化迁移和新的产品交互契约。

## 为什么要保留这个 Spec Change

现行 `openspec/specs/` 只应描述已经实现并验证的行为，不能承担“当时观察到什么、比较过哪些方案、为何没有改 store”的诊断历史；产品 PRD 也不应写入 ETag、React commit 或 DOM 节点等实现细节。把这次记录放在 change 中，可以同时保留：

- 用户性能预算的产品来源；
- 方案选择与被否决方案的依据；
- 代码、测试和真实 Electron 证据之间的追溯关系；
- 实现早于文档补录这一事实。

归档时，只有 `spec-delta/` 中仍然成立的判据回流到行为规格；原因、测量样本和取舍继续留在本 change 的历史记录中。
