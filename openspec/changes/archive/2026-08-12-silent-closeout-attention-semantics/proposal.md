## 背景

v0.5.0 发布后，用户报告「所有对话都显示红点」。根因调查（2026-08-11）确认：

1. 升级前会话事实日志没有 `primary_closeout` 一等收束信号，升级后首次轮次评估经静默兜底（静置 ≥30s）被追溯落盘 `silent-closeout`，UI 对 terminal `silent-closeout` 点亮红点 → 静止历史会话整片变红。
2. `primary_closeout` 与 `round_terminal` 同毫秒成对落盘，重评时严格 `>` 比较把一等信号误判为旧轮 → 已收束会话重评走静默兜底 → 红点复现且与事实日志不一致。
3. 读状态操作（标记已读/未读、查看）推进会话 `updated_at`，击穿轮次剪枝，把「读」误当成内容活动触发重评。

修复方向（F1–F4）由实现者完成并经独立技术复核通过；但复核同时发现：**把「silent-closeout 不单独点红」按「产品意图未变 → spec 内联」档处理属于分档错误**。修复前的 PRD 明确写着「整轮最终停在……『本轮没有明确收尾』时转为红点」，本次变更实质修改了这条产品规则，且「没有明确收尾的成员交棒轮不再红」与用户目标（当前会话不红）存在取舍——按 `openspec/changes/AGENTS.md` 的边界，产品意图变更 MUST 经用户确认并走完整 change，不能以 spec 内联单方面定下。

本 change 是**流程补正**：先有实现与真机证据（已通过独立复核），后由独立技术复核发现分档错误，再由用户于 2026-08-12 明确确认产品规则，最后补齐 change 并归档。本文如实记录该顺序，不伪造「先设计后实现」的先后关系。

## 提案

将轮次状态点的红点语义从「静默兜底结论本身点亮」改为「由独立异常/待处理事实点亮」：

- `silent-closeout`（静默兜底收束）不单独点亮红点；它仍是收束事实，会话投影为 terminal，按未读派生蓝点或无点。
- 红点来源收窄为：`awaiting-user` 一等收束（需要用户处理）与未确认异常事实（attention / `run-not-started` / `run-stuck` / `retry-exhausted` / 不可继续状态）。
- 同时修复重评一致性：同毫秒一等信号归属当前轮（`isNotBefore`）；persist-skip 时返回既有事实的权威投影（`planRoundExistingState`）；读状态操作不再推进 `updated_at`。

用户确认的产品规则（2026-08-12）：

> 某轮没有主 Agent 明确收尾，但系统也没有卡死、启动失败、重试耗尽、等待用户等异常事实时，不显示红点。真正异常仍显示红点，运行中仍闪烁，普通未读仍显示蓝点。

## 影响

- **业务域**：local-console（轮次收束判定与持久化一致性）、console-ui（状态点派生）、Dock 计数（与状态点同源）。
- **对外行为**：升级前被追溯落盘的 `silent-closeout` 不再点亮历史会话；`sessions/*.jsonl` 不被改写（投影兼容）；真实异常会话的红点保留（由独立异常事实承担）。
- **既有边界**：`awaiting-user` 红点经发新消息自然消除；其「标记为已读」菜单在服务端 STALE 守卫不认识 roundState 时返回 409 属既有边界，本变更后触发面收窄，不扩 scope。
