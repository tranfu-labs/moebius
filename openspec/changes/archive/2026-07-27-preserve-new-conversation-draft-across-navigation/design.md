# 设计：preserve-new-conversation-draft-across-navigation

## 方案

桌面 renderer 为新对话保留一份独立于当前页面展示状态的未发送草稿。草稿统一持有项目、会话级工作空间、团队与正文，附件继续使用新对话自己的托管草稿归属：

1. 首次从侧边栏顶部进入且没有待恢复草稿时，建立项目未选定的新草稿；从项目行进入时沿用该入口明确给出的项目。
2. 用户切到已有会话或其他页面时，把新对话切成隐藏状态；已有会话继续使用自己的正文与附件草稿键，不覆盖隐藏的新对话草稿。
3. 用户再次进入「新建对话」时，若尚有未消费草稿则恢复原项目、工作空间、团队、正文和附件；若其项目已经不可用，则沿用既有不可用项目处理，不伪造可发送状态。
4. 用户在新对话里明确改选项目时，工作空间随目标项目的当前缺省模式重新选择，之后仍作为该草稿的会话级选择保存。
5. session 与首条消息原子创建成功后清理正文与附件草稿并结束这份新对话生命周期；创建失败保持全部选择和内容，解除提交中状态以便重试。
6. 原子创建完成后的 Agent 启动属于新建会话的后续运行；其失败不恢复已经消费的新对话草稿。

## 权衡

选择“同一草稿跨导航隐藏/恢复”，而不是每次点「新建对话」都重新初始化，是因为导航不应具有清空用户上下文的副作用，也不需要为了保存草稿提前创建空白 session。

草稿不提升为项目级或全局工作空间偏好。它只代表这一段尚未创建的对话，因此恢复不会影响正在浏览的已有会话，也不会改变下一段新对话的默认值。

不增加新的持久化 schema 或服务端草稿对象：正文和附件已有各自的草稿持久化边界，本次只收敛桌面 renderer 中选择项与页面展示的生命周期。

## 风险

- 页面展示状态与附件草稿键切换不一致，会把已有会话附件误投影到新对话；通过状态机与附件草稿切换测试覆盖。
- 成功创建后若只清正文未清选择或附件，下一次进入会错误恢复旧上下文；消费动作必须同时结束整份新对话草稿。
- 隐藏期间项目被移除或失效时不能继续原样发送；重新展示时必须服从既有项目可用性边界。
- 回滚时可恢复为每次进入都重新初始化，但会重新引入用户已经确认的导航丢失问题，因此只作为实现故障的临时退路。
