# 设计：team-selection-user-review-gate

## 方案
`AgentTeamOption` 继续作为三类入口共享的摘要组件。默认态显示名称/来源、单行用途、主 Agent/成员数和「查看成员」；展开态把成员头像与名称放进选项内的有限高度滚动区。披露按钮拦截菜单项选择事件并支持键盘。

共享菜单壳使用 Radix 可用高度变量、`100dvh` 和固定产品上限共同约束，外壳 `overflow-hidden`。头部、目录、底部为 flex 三段，只有目录 `min-height: 0; overflow-y: auto`。新对话没有当前项和快照说明，但复用同一滚动目录。

产品研发团队新增 `user-reviewer`，并把原 `product-reviewer` 改名为「产品规格评审」。主 Agent 在 Page Story/原型准备后先交用户任务评审；实现和功能/视觉验收完成后，再交同一角色从真实入口复核。失败统一回主 Agent 分类，避免用户评审直接规定实现。

## 权衡
不把所有信息压缩成更小字号，也不只给整个浮层加滚动；前者仍然信息过载，后者会让当前选择和快照说明滚走。保留成员详情，但改为用户主动披露，以兼顾快速判断与深度辨认。

不让产品规格评审兼任用户任务评审：前者已经知道产品理由和验收答案，无法提供可靠的首次使用证据。新增角色会增加两次接力成本，但只在有用户界面的产品改动启用，换取开发前拦截错误方向和交付后拦截“技术正确、用户不会用”。

## 风险
- 嵌套披露按钮必须保持键盘可达且不能触发团队选择；用组件测试和真实菜单操作复核。
- 很多团队或很多成员仍需要滚动，但滚动被限制在目录或成员区，不再扩大整个页面。
- 直接同步本机官方团队会使其相对已记录的 v2 基线显示已自定义；不修改官方状态账本，未来通过产品内官方更新能力显式归一。
- 既有会话保存的是团队快照，不会自动获得新评审角色；新会话或明确应用团队更新后生效。
- 回滚代码与种子提交即可恢复应用行为；本机团队若需回滚，应通过保留副本/官方更新流程而非改写状态账本。
