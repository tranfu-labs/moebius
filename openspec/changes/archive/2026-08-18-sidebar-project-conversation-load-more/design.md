# 设计：sidebar-project-conversation-load-more

## 本项目适用方案

### 模块划分与数据流

1. **分页视图决策**：在现有 `conversation-sidebar.tsx` 中增加纯函数和常量，复用既有 `orderSessionsByCreatedAt`；输入为已排除置顶项的完整有序会话，输出当前可见批次、是否还有更多以及下一批上限。
2. **项目行集成**：在 `ConversationSidebar` 内维护项目 id 到可见上限的临时状态，默认 5；点击 `Show More` 后每次增加 10。项目折叠时清除该项目的上限和加载态，并取消尚未提交的本地加载任务。
3. **显示与本地化**：用现有 `Button` 的 `ghost` 变体放置在项目会话列表底部；加载时禁用按钮、设置 `aria-busy` 并使用现有 `LoaderCircle` 与 reduced-motion 约定。新增英文 `Show More` 和中文“显示更多”及加载辅助文案。
4. **验证**：扩展侧栏组件测试；必要时补充长列表 Story，最后由真实 Electron 侧栏验收确认点击、加载、折叠和重新展开行为。

数据流保持：

```text
local-console state（完整项目会话）
  → toSidebarProject（根会话 / 非分析会话）
  → 排除置顶并按 createdAt DESC 排序
  → 当前项目可见上限（5，之后每次 +10）
  → 会话行 + 底部 Show More
```

### 关键选型与结构决策

| 约束 | 采纳结论 |
| --- | --- |
| 用户只要求侧栏按批次呈现；当前 state props 已包含完整会话列表，且没有分页 API 或总数契约 | 采用 `console-ui` 内的视图级渐进加载，不新增 HTTP、SQLite 或持久化格式；无需改变桌面运行时数据流 |
| 现有侧栏已在置顶 section 与项目 section 之间分流，项目列表已排除 pinned | 分页只作用于项目内未置顶会话，置顶区保持现状且不重复 |
| 既有 PRD/spec 要求项目内按 `createdAt` 倒序且状态变化不重排 | 先排序再截取，加载更多只扩大窗口，不按运行、未读或选中状态重新排序 |
| 现有项目折叠状态是组件内临时状态；用户明确要求折叠后重置 | 可见上限和加载态均为项目级临时状态，不写 localStorage；折叠时重置为默认 5 |
| 设计系统已有 Button ghost 变体、LoaderCircle、`aria-busy` 与 reduced-motion 模式 | 复用现有组件和 token，不新增按钮样式或动效模式 |
| 点击必须产生可观察加载态，但数据已在内存中 | 使用一次可取消的本地异步提交边界，让 loading 先提交、下一帧再追加 10 条；折叠、卸载或项目移除时取消，避免迟到结果恢复隐藏项目 |

### 测试策略

- 纯逻辑：验证 0/5/6/15/16 条边界、首次 5 条、后续每次最多 10 条、最后一批不足 10 条时隐藏按钮，以及排序不被改变。
- 组件：验证按钮仅在有更多时出现；点击后立即 disabled/`aria-busy`，随后追加 10 条；重复点击继续追加；折叠清除 loading 与批次，重新展开回到 5 条；置顶区不受影响；中英文文案存在。
- 回归：运行受影响的 console-ui 测试、类型检查和 console-ui build；步骤 4 再执行完整 `pnpm test`。
- 真机：在真实 Electron 侧栏从项目展开入口验证 5 条初始列表、Show More、加载态、批次追加、无更多隐藏、折叠取消和重新展开重置。

## 权衡

- 不改后端分页接口：实现范围小、回退简单，且当前 state 已一次提供完整列表；代价是网络响应和 SQLite 读取量不变，本 change 只优化侧栏可视长度。
- 不持久化已加载批次：符合用户要求的折叠重置，也避免把短期浏览状态变成应用偏好。
- 不把加载按钮提升为项目菜单动作：它属于当前项目会话列表的连续浏览操作，放在列表底部可直接表达“加载下面的对话”。

## 风险

- 项目数据刷新期间会话总数可能减少；可见上限保留但由当前数组裁剪，按钮按当前数据重新判断，不显示空行。
- 折叠时若本地加载任务已排队，必须取消其提交；测试会覆盖迟到回调不恢复已折叠项目。

## 方向性风险判定

无方向性风险。所有方向选择均有本项目依据：用户明确规定了批次与重置语义，现有组件已承载完整列表和折叠临时状态，现有设计系统已有 ghost/loading 模式；没有仅凭惯例选择的数据格式、对外 API 或持久化契约。本步无需 spike 或用户方向确认。

本方案经评审交接后自主定稿，按纪律第 3 条分级作为基准。
