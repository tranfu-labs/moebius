# UI 打磨判断

这份文档只收**默认判断会错的地方**。通用设计知识（对齐、一致性、留白要够）到处都有，不在这里。每条都来自 2026-08 Agent 团队详情页的打磨实录：先按直觉做、被实测或用户当场打脸之后才写下来，附当时的数字和原话。

## 一、横线是偷懒的分组方式

默认直觉：内容分组 → 画分割线、加边框。

事实：一个只有三组内容的页面画了 7 处线，用户点名「是不是 AI 有一个通病，就是很喜欢画横线来分割」。删到 2 处后页面反而更清楚——剩下的 2 处是下拉自身的边框，不是分割线。

关键是把两种边框分开看：

- **面的抬升**——卡片、浮层的描边（本仓库 DESIGN.md：零阴影，只靠 1px 描边分层）。该留。
- **段落分隔**——本该由留白和字号层级（邻近性）承担的工作。全删。

**推论：阅读内容不装盒子。** 右栏正文原本也是一张卡，去掉后正文直接落在页面底色上，与左边的控制面形成「一个是面板、一个是文档」的对比——这个对比本身就是分组，比任何一条线都清楚。

判据：每条线问一句——它在抬升一个面，还是在偷懒分段？后者删，用留白补。

## 二、关键信息不能挂在 hover 上

默认直觉：看不清 → hover 放大；要提示能力 → hover 时出现。

事实：画像候选实测只有 28px（generate-avatar-set 自己写着「28–32px 很多风格直接失效」），问题是真的，但 hover 放大是错的解法——**hover 对键盘和触摸都不存在，最需要看清的人反而拿不到**。正解是恒定放大到 40px（popover 268 → 328px），并加测试断言禁止 `hover:scale`/`hover:h-`/`hover:w-` 回潮。

判据：这个信息/能力用户拿不到 hover 时还能获得吗？不能 → 别挂在 hover 上。

## 三、提示元素找不到干净落点时，先怀疑它语义就是错的

默认直觉：占位难看是布局问题，换个定位方式就好。

事实：拖拽抓手图标改了三版全失败——`opacity-0` 隐藏但**位置照占**（每个胶囊左边常年空一块）；改绝对定位落进 8px 间隙，又变成「悬浮时突出去一块」；两头都不对。最后发现根因不在布局：**整个胶囊都能拖，抓手却暗示「只能从这里拖」，语义本身是错的**。删掉它，问题就不存在了——常驻文字提示「拖动排序，第一位是主 Agent」+ `cursor: grab` + 主 Agent 的 accent 描边已经够。删后实测：胶囊左内缩回到正常 13px（`px-3`），间距均匀 8px。

判据：一个元素在哪儿摆都不对时，别再换第四种定位——问它该不该存在。

## 四、实现细节会不停往 UI 里漏，同一轮删了三次

默认直觉：区域标题写清来源（文件名），文案把系统规则解释给用户。

事实：同一类毛病连删三次——

1. 「AGENT.md」区域标题：用户关心「这个 Agent 负责什么」，不是文件叫什么名。原话：「用户又不关心 AGENT.md，对吗？」
2. 「独立属于 "我的开发团队 / @dev-manager"」：想教「同 slug 在不同团队互不影响」，但这只在可能引起意外时才需要说，常态下每次都念是噪音。
3. 保存 banner 第二行「新对话会使用最新设置；旧对话可从变化提示中应用完整团队版本」：整句是系统规则，每存一次念一遍。「无需重启」更糟——**在安抚一个产品自己不该制造的恐惧**。

判据：写任何一句界面文字前问——用户此刻的任务需要它吗？还是它在向用户解释系统的内部模型？后者删。

## 五、预期之内的成功只配最小确认

默认直觉：保存成功 → 弹一条横幅总结一下。

事实：「已保存 1 项」这个计数在**保存前**有用（提醒有东西没存），保存后再报一遍是噪音；而且确认早已存在——「未保存 N 项」消失 + 保存按钮变灰就是反馈。最终形态：按钮旁一句短促的「✓ 已保存」，再次改动自动撤掉。同时「放弃修改」按钮空闲时不渲染（实测：空闲时不存在，有改动才出现）——没有可放弃的东西时它是恒亮的灰噪音。

例外要认得：列表页「保存全部并离开」之后的横幅保留——用户已离开现场，那时确实需要一次总结。

判据：反馈的体量与意外程度成正比。意料之中的结果，用状态消失做确认；离场后的结果，才值得一条横幅。

## 六、同一页两种保存模型，靠视觉提示补不回来

默认直觉：标题失焦即存很顺手，表单区手动保存也合理，各用各的。

事实：团队名/描述做成了和成员名/描述**一模一样的视觉**，行为却相反——按 Enter 一个存了一个没存，「视觉在骗人」。而「全部改成即时保存」也走不通：运行配置保存前要校验、失败要保留草稿（即时保存表达不了失败态）；成员名和正文在同一个文件里，单独即时写盘会写出「名字新、正文旧」的文件。

真正一致的界线只有一条：**没有中间态的动作即时生效（拖拽任命——要么放下要么没放下），有中间态的编辑走草稿（打字）。** 按这条线，团队信息进草稿、保存升为页面级，全页只剩一个保存（实测 `保存按钮数: 1`），放进吸顶页头（滚动后实测仍可见）。

判据：同视觉必须同行为；即时还是草稿，按「有无中间态」划，不按控件类型划。

## 七、别想当然认定页面主线

默认直觉：这页有个 markdown 编辑器，编辑器就是主体，给它更多空间。

事实：用户原话「正常人不会想要去写 md，主线一般只是想要去修改配置，md 更多的是看」。方向整个反过来：AGENT.md 改为**读优先**（默认渲染态 + 浮出的「编辑」入口），运行配置成为常驻主体。连带页面高度 1182 → 931 → 900，进了一屏。

判据：先答「用户来这页最高频的动作是什么」，把空间和常驻位给它。「有编辑能力」不等于「编辑是主线」。

## 八、重复信息按职责判断，不按像素判断

默认直觉：同一信息出现两次 = 重复，删掉一处。

事实：成员条和身份横带里画像、名字各出现两次，用户问「会不会有点重复」。删谁不是看像素：那条身份横带除「可编辑」外没提供成员条没给的信息——**它是选中态的复读**，删；而合并后画像仍出现两次，但性质不同了：成员条里是**导航图标**（选谁），卡片里是**头像选择控件**（点它换脸），各有职责，留。

判据：给每处出现指派一个职责（导航/编辑/展示），说不出独立职责的那处才是重复。

## 九、承载真实操作的交互控件，别手搓低成本版本

默认直觉：拖拽用原生 HTML5 DnD 糊一个，省依赖。

事实：用户点名「非常简陋，只是用了一些最基础、低成本的方式」。手搓版没有键盘路径、没有读屏播报——而这是**任命主 Agent 的控件，不是装饰**。换 @dnd-kit（core 6KB）后白拿：空格拿起 → 方向键移动 → 空格放下 → Esc 取消，全程 live region 播报；加 4px 启动距离防止点击被误判成拖拽。

坑：dnd-kit 的 `attributes` 带 `role="button"`，直接展开会盖掉 `role="tab"`——只取排序相关的那几项。

判据（与 apple-motion 条二同构）：先问「库不可替代的部分是什么」。popover 动效里那是速度保持（通常不需要，可以不装）；拖拽里那是键盘/读屏这套可访问性机器（自己造不出来，必须装）。

## 十、需求会被后来的能力覆盖——PRD 条款有出生时间

默认直觉：PRD 写了「持续显示并允许复制 `@<slug>`」，照做。

事实：编辑器里输入 `@` 已有成员自动补全，手动复制 slug 是**不存在的需求**——那条 PRD 是自动补全出现之前定的，留着只是占地方。删掉整行后右栏顶部与左卡完全对齐（实测两者 top 都是 300），连带消掉了 4px 错位。

判据：为一个控件辩护前，查它依据的条款是什么时候、在什么能力背景下写的；被后来的路径覆盖 → 删控件、改 PRD。

## 十一、框架监听的事件不是你以为的那个

默认直觉：测失焦保存就 dispatch `new Event('blur')`。

事实：React 的 `onBlur` 走的是 **`focusout`**（`blur` 不冒泡所以委托不到），dispatch `blur` 看到标题变了却没有保存反馈，差点误判成「反馈没接上」——变的其实只是本地草稿。`.focus()` 转移焦点也没触发，最后发 `focusout` 才跑通。这与 apple-motion 条十一的 `pointerdown` 教训同族：**用合成事件测框架行为，先确认框架委托的是哪个原生事件。**

判据：合成事件测不出预期行为时，第一嫌疑不是功能坏了，是事件名不对。
